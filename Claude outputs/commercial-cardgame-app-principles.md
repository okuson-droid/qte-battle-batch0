# 商業水準のカードゲーム対戦アプリに必要なこと

作成日: 2026-09-20
出どころ: QTE Battle の商業水準ギャップレビュー(2026-08-11)と、その後の演出・音・決着・段階的解決の各バッチ(32〜37、84)で得た教訓を、言語とゲームルールに依存しない形へ一般化したものである。
想定する読み手: これから別のカードゲーム対戦アプリを商業水準へ引き上げようとする開発者。オンライン対戦が未実装の段階から読める順に並べてある。

---

## 0. 最初に押さえる一文

QTE のレビューの総評は「欠陥は作りの粗さではなく、面の欠落に集中している」であった。実装済みの部分の出来がいくら良くても、タッチで操作できない・音が無い・決着の体験が無い、といった「面」が丸ごと欠けていれば商業製品としては成立しない。したがって、個々の作り込みより先に、必要な面の一覧を持つことが最も効く。本書はその一覧である。

---

## 1. 土台の設計(オンライン化の前に決めること)

ここで決めたことは後から変えるのが最も高くつく。オンライン対戦が未実装である今が、最も安く正しい形にできる時期である。

### 1-1. ルールエンジンとUIを完全に分ける

エンジンは「現在の状態と1つの操作を受け取り、新しい状態と、起きた出来事の列を返す」純粋な状態機械にする。画面・通信・時間の概念をエンジンに持ち込まない。こうしておくと、同じエンジンが対人戦・AI戦・自動テスト・リプレイ・観戦のすべてで使い回せる。

### 1-2. サーバを唯一の正にする

クライアントは表示と入力だけを担当し、ルールの判定を行わない。クライアントが送るのは「この操作をしたい」という意図であり、結果を決めるのは常にサーバである。クライアント側に判定を置くと、不正対策と同期ずれの両方で破綻する。

### 1-3. 隠匿情報はサーバ側で視点ごとに切る

相手の手札や山札の中身は、席ごとのビューをサーバで作る段階で落とし、そもそも送らない。クライアント側で「隠して表示する」方式は、通信を覗けば見えるので構造的に漏れる。QTE では演出の検出を「自分に届いたビューの差分」に限ったことで、見えないカードが演出から漏れる事故が原理的に起きない形になった。

### 1-4. 決定性を確保する

乱数はシードで管理し、操作の列をログとして残す。初期状態とシードと操作列があれば対局を完全に再現できる状態にしておく。再接続時の復元、リプレイ、観戦、バグの再現、AI の学習データは、すべてこの性質から派生して手に入る。

### 1-5. 合法手の列挙をエンジンが提供する

「いま何ができるか」をエンジンが答えられるようにする。UI はそれを受けて、出せるカードや選べる対象を光らせるだけでよい。UI 側でルールを再実装して合法性を推測すると、エンジンと必ず食い違う。

### 1-6. 出来事を「順序のある構造化データ」として出す

これが QTE で最も高くついた教訓である。QTE は当初、前後2つのスナップショットの差分から演出を作った。サーバ変更が不要で、視点フィルタも自動的に効く優れた方式だったが、差分には順序も段階も間も無い。1操作の解決が1回の配信に畳まれるため、カードをプレイした後の処理が一瞬で終わり、何が起きたのかが分からない。しかも大きく動く派手なカードほど、差分が多すぎて演出が丸ごと抑制された。結局 Batch 84 でサーバを変更し、解決の各段のスナップショットを順序付きで送る方式へ作り直すことになった。

最初からエンジンが「ドローした」「ダメージを与えた」「破壊された」といった出来事を、順序付きの構造化データとして返す設計にしておけば、この作り直しは不要である。

あわせて、演出の材料にしてよいのは書式ではなく構造である、という原則を守ること。表示用のログ文字列を正規表現で読んで出来事を検出する方式は、文言を直した瞬間に黙って壊れる。構造が足りないなら、読み取り側で復元せず、書く側に構造を足す。

## 2. 通信と接続の堅牢性

対戦アプリで最悪の事故は「相手には届いていないのに、双方がそれに気づかない」状態である。通信は切れるものとして設計する。

必要なものは次のとおりである。切断を検知して画面に明示し、切断中は入力を止めること。再接続時は差分ではなく状態の全量を送り直して復帰させること。操作に連番を振り、二重送信と順序の入れ替わりをサーバ側で弾くこと。サーバの再起動で対戦部屋が消えないよう、状態を永続化すること。特に無料枠のホスティングでは再起動が日常的に起きるため、永続化の有無は対戦時間が長いほど効いてくる。

対戦相手と出会う経路もここに含まれる。部屋のリンクを共有する方式であれば、リンクをワンクリックでコピーできること、貼った先でアプリ名が分かるプレビュー(OGP)が出ることが、主動線の品質そのものになる。不特定の相手とマッチングする方式であれば、持ち時間・放置対策・途中離脱の扱いが必須になる。

## 3. 「何が起きたか分かる」演出

商業タイトルと個人制作の最も大きな差はここに出る。演出の目的は派手さではなく、状態変化を人間が認識できる速さと順序に翻訳することである。

### 3-1. 順序・段階・間

処理は一つずつ、順番に、間を置いて見せる。1操作で複数の効果が連鎖するなら、連鎖の各段が目で追えなければならない。再生中は入力を止め、盤面をわずかに沈めるなどして「いまは再生中である」ことを伝える。相手の操作も自分の操作と同じように再生する。

### 3-2. 待ち時間の上限を設計で保証する

演出は待ち時間でもある。1操作あたりの総再生時間に上限を設け、超える場合は畳む。畳んだことは画面に示す。スキップ機能を付けるなら上限は緩くてよいが、付けないなら上限の保証は必須になる。

### 3-3. 演出の層を盤面から分離する

動く要素は盤面の上に重ねた独立の層(オーバーレイ)に置く。こうすれば盤面側を単純な全消し再描画のまま保てる。飛ぶ演出は、旧位置に使い捨ての複製を置いて新位置へ動かし、本物の盤面は即座に最終状態にしておく方式で足りる。演出の時間定数は一箇所に集め、画面ごとにばらばらの秒数を書かない。

### 3-4. 観測できないことは演出にしない

山札の一番上しか配信されない、といった「窓」のあるゾーンでは、届く情報の出入りが実際の出入りと一致しない。ドローで次のカードが見えるようになっただけなのに「出現した」と演出してしまう類の誤りが起きる。見えている範囲の変化と、実際の出来事を区別すること。

### 3-5. 山場を抜かさない

QTE では移動やタップといった日常の所作から先に演出を入れた結果、ゲーム開始・攻撃・決着という山場が無演出のまま残った。決着に至っては、宣言を送信するだけで画面に何も起きず、ゲームは「終わる」のではなく「止まる」状態だった。感情曲線の頂点である決着は、費用対効果が最も高い演出対象である。リザルト表示と再戦への動線を含めて設計する。

### 3-6. 動きを減らす設定を尊重する

OS の「視差効果を減らす」設定に従い、演出を止められるようにする。

## 4. 操作感

### 4-1. 入力は最初から一つの経路で受ける

マウス・タッチ・ペンを単一の入力経路で受ける作りにする。QTE はマウスのドラッグ&ドロップと右クリックだけで操作を組んだため、スマートフォンではカードを1枚も動かせなかった。後からタッチ対応を足すのは、操作体系の作り直しに等しい。

### 4-2. 画面サイズに追随する

盤面の寸法を固定値で書かず、基準となる変数から導く。タッチで押す対象は 44px 四方以上を確保する。すべての端末で完全に遊べる必要はないが、どこまでを対象とするかは決めて明示する。対象外の端末で「非対応であることの表明すら無い」のは二重の欠落である。

### 4-3. カードの内容をすぐ読める

ホバーまたは長押しでカードが拡大されること。テキストを確認するたびにクリックを要求しない。

### 4-4. 操作の前後で必ず何かが返る

できる操作の対象は光らせる。できない操作には、できない理由を示す。破壊的な操作(投了・退室・リセット)には確認を挟む。どの操作にも、押した瞬間に視覚か音の反応を返す。誤操作を戻せる余地(対象選択のキャンセルなど)を用意する。

### 4-5. 細かい事故を塞ぐ

盤面上でテキスト選択が走らないようにする。右クリックや長押しで OS のメニューが開かないようにする。こうした小さな事故は、対戦中の没入を確実に削る。

## 5. 音

効果音は 8〜12 種あれば最低線に届く。ドロー・配置・攻撃・被ダメージ・ターン開始・勝敗が中心である。ミュートと音量の設定は必須で、初期音量は控えめにする。ブラウザで動かす場合は自動再生の制限があるため、最初のユーザー操作で音を有効化する処理が要る。

音は動きではない。視覚演出を切っている利用者にこそ、音は状態変化を伝える数少ない手段になる。したがって、演出のオン・オフと音のオン・オフは別の設定にする。1回の状態更新で鳴らす音は1つに絞り、優先順位を一箇所で定める。BGM は後回しでよい。

---

## 6. 見た目の一貫性

色・フォント・余白・角丸といった値は一箇所で定義し、全画面がそこを参照する形にする。QTE では文明色の定義が3箇所に重複し、ロビーは明るい背景、対戦は暗い背景、デッキ編集はまた別の配色という状態で、画面を移るたびに白黒が反転していた。

製品名の表記を一つに揃える。ページタイトル、favicon、共有時のプレビュー、スクロールバーの色、読み込み中の表示といった細部を埋める。一つ一つは小さいが、総和が「未完成感」を作る。

外部の CDN に依存する場合は、障害時に全体が壊れないよう手当てをする。静的ファイルのキャッシュ更新は手作業で版数を書き換える方式にしない。手作業の管理は必ず漏れる。

---

## 7. 対戦以外の面

対戦画面だけでは製品にならない。必要な面は次のとおりである。

デッキ編集には、検索、絞り込み、並べ替え、枚数制限の即時表示に加えて、コスト分布の可視化、不正なデッキを保存・使用させない検証と「何が足りないか」の一覧、作業中の自動保存、複数デッキの保存枠が要る。

初めての利用者には、初回のヘルプと、各操作要素の名称が分かる説明(ツールチップ)を用意する。設定画面には、音量、演出、表示に関する項目をまとめる。対戦後にはリザルトと再戦の動線を置く。余力があれば、観戦とリプレイは1章の決定性から比較的安く作れる。

公開 URL から到達できる画面は、すべて品質の下限として見られる。未完成の画面を残すなら、到達できないようにするか、未完成であることを明示する。

## 8. 進め方

### 8-1. 先に前提を決める

「誰が、どういう状況で遊ぶのか」を早い段階で決める。QTE は「Discord で通話しながら遊ぶ」という前提を置いたことで、チャット、エモート、ターンタイマー、BGM がまるごと不要になり、逆に切断時の挙動と部屋リンクの共有体験の重要度が上がった。前提は、作るものを削るための最も強い道具である。

### 8-2. ギャップレビューから始める

実物を触り、欠落を重大度で分類して優先順位を付ける。分類の目安は、商業製品として成立しない欠落、競合と並べた瞬間に見劣りする点、体験の質を確実に下げている点、細部、の4段である。良い点も同時に記録し、維持すべき資産を明確にする。

### 8-3. 入口の無い機能を作らない

QTE ではターン開始の演出を作ったあとで、ターンを進める入口が画面に無いことに気づいた。演出や機能を作る前に、それが実際の遊びの中で発火する経路があるかを確かめる。

### 8-4. 検証の体制を持つ

エンジンには自動テストを持つ。画面は、実際のブラウザで実際のポインタ操作を行う自動テストまで用意する。合成したイベントでは再現しない不具合が実在する。見た目の確認も、スクリーンショットの比較など機械的に回せる形にしておくと、変更のたびに壊れていないことを確かめられる。検証環境と実環境の差(背景色、実サーバの応答、端末の違い)で痛い目を見ることがあるため、最終確認は必ず実環境で行う。

### 8-5. 判断を記録する

設計判断と裁定を番号付きの台帳に残す。なぜその形にしたかが残っていないと、後の変更で同じ議論をやり直すか、捨てた案を知らずに拾い直すことになる。

## 9. Python で作る場合の構成

最大の分岐は、クライアント(画面)を何で作るかである。

滑らかな演出、タッチ対応、配布の容易さを狙うなら、Python はサーバ側(エンジンと WebSocket による通信)に専念させ、画面は Web(HTML / CSS / JavaScript)で作る構成が近道である。FastAPI などの非同期フレームワークが WebSocket を扱える。この構成であれば、本書の内容はほぼそのまま適用できる。

画面も Python のデスクトップ用ライブラリで作り、実行ファイルとして配る構成も成立はする。ただし、アニメーション、タッチ、画面サイズへの追随、更新の配布を自前で抱えることになり、商業水準の UI へ到達する費用は Web より高くなる。

どちらの構成でも、1章の設計(エンジンの純粋性、視点ごとのビュー、決定性、合法手の列挙、順序付きの出来事)は共通であり、先に固めてよい。既に Python のルールエンジンがある場合は、そのエンジンが「順序付きの出来事の列」と「席ごとのビュー」を返せるかを最初に点検するとよい。

## 10. 着手順の目安

オンライン対戦が未実装の段階から始める場合、次の順が手戻りが少ない。

まず、遊ぶ前提を決める(8-1)。次に、エンジンが1章の5つの性質を満たすかを点検し、足りなければ足す。続いて、通信の層を作り、切断と再接続を最初から組み込む(2章)。そのうえで、入力を単一経路で受ける盤面を作り(4章)、順序付きの出来事から演出を再生する層を載せる(3章)。音(5章)、見た目の統一(6章)、対戦以外の面(7章)はその後でよいが、決着の体験だけは早めに入れる。最後に、実物を触ってギャップレビューを行い(8-2)、残りの優先順位を決める。
