## 1. 設計根拠★

### 1-1. 席選択を独立ページにせず、盤面ページ内のゲートにした

設計書 2-1 は「盤面の前に**必ず**通る」「部屋コード直リンクで来ても通る」と定める。
独立ページ(`/manual/seat/{id}`)にすると、この「必ず」を守るのは
**盤面ページ側の分岐**になる。すなわち「occupantId が無ければ席選択へ飛ばす」という
リダイレクトを1本書き、それが将来も消えないことに賭けることになる。

盤面ページの中にゲートを置けば、`resolveOccupant()` が解決するまで
STOMP に接続せず盤面も描かないため、**通らない経路が存在しない**。
「必ず通る」を分岐ではなく構造で表現するほうが強い。

副次的に、新しいコントローラもテンプレートも増えない。
b系バッチでサーバに触る量を最小にできたのはこの選択のためである。

同じゲートを「入室前」と「入室後の昇格」の2場面で使い回している。
違いは**部屋情報の出所だけ**(一覧API か ビューか)であり、
席ボタンの状態を決めるロジック `applyGateSeats` は1つで済む。

### 1-2. ★入室前に部屋を1件引く API を足した(唯一の Java 変更)

一覧 API は鍵つき部屋の `roomId` を **null** で返す(1-3・F1)。これは正しい。
IDが鍵を兼ねている以上、一覧に出した瞬間に鍵の意味が消えるからである。

しかしその結果、**一覧から自分の部屋を特定できない経路が構造的に存在する**。

- 鍵つき部屋にIDを打って入る人
- `/manual/battle/{id}` の直リンクで来た人

この2つは設計書 2-1 が明示的に想定している経路であり、そこで
「部屋名・種類・席の埋まり・在席者名を入室前に表示する」ことが要求されている。
材料を取る手段が無いのは 21a の設計漏れであり、マスターの承認を得て
`GET /manual/api/rooms/{roomId}` を1メソッド追加した。

**★鍵の意味は損なわれない。** この API は部屋IDを**知っている人**にしか答えない。
IDを知っていること自体が入室の権利である(1-2)以上、
その人に部屋名と席の埋まりを見せても新しく漏れる情報は無い。
盤面状態を返さないのは一覧と同じである。

一覧と単体で組み立てを共有する `toSummary` に切り出したのは、
**出す項目が2箇所に分かれると片方だけに項目が足されて食い違う**ためである
(21a が `ManualLogRenderer` で配信とダウンロードを共有させたのと同じ形)。

### 1-3. ★「A=下」を外すとき、入れ替えるのは表示位置だけである(設計書10章)

20c までの `manual-battle.js` は `view.seatA` を下段、`view.seatB` を上段と
決め打ちし、席IDも `'A'` / `'B'` のリテラルで書いていた。
21b でこれを外すにあたり、**踏んではならない罠が1つある**。

> 表示の上下と、サーバへ送る席IDを一緒に反転させてしまうこと。

反転させると、サーバが受け取った `"A"` が「席A」なのか「その人の自席」なのか
決まらなくなる。送信データは**閲覧者の視点から独立**していなければならない。
これは 21a が矢印で画素座標を送らないと決めたのと同じ理由である
(座標系が閲覧者ごとに違うなら、座標を送ってはいけない)。

そこで本バッチでは、視点の責務を4つの小さな関数に閉じ込めた。

```js
bottomSeatId(view)  // 下段に描く席のID(= view.viewerSeat。観戦者は A)
topSeatId(view)     // 上段に描く席のID
seatOf(view, id)    // 席IDから席ビューを引く
bottomSeat/topSeat  // 上の合成
```

**この4つは「どの席ビューをどちらの入れ物へ描くか」しか答えない。**
描画関数は席そのものを `seatView.id`(= サーバが入れた実席)から取り、
`cardLocation` / `registerDropTarget` / 送信ペイロードには常にそれを渡す。
結果として、描画関数の中に `'A'` / `'B'` のリテラルは1つも残っていない
(残っているのは上の4関数と、席を列挙するループの `['A','B']` だけである)。

検証では実マウスで確かめてある。席Bで入った状態で自分の手札を自分の場へ
ドラッグすると、画面上は「下から下へ」だが `toSeat` は `"B"` になる。
相手側(画面の上)へ落とすと `"A"` になる。

### 1-4. 枚数の出所を `counts` に変えた(21c の前倒しではない)

対戦部屋では、非公開ゾーンが `zones` に**キーごと現れない**(21a 1-2)。
20c までのコードは中身の配列を数えていたため、そのままだと
「山0 禁0 確0」と表示される。実際には36枚あるのに0と出るのは、
隠しているのではなく**嘘をついている**。

そこでゾーンの枚数を引く経路を `zoneCount(seatView, zoneName)` に一本化し、
サーバが全ゾーンぶん送っている `counts` を優先するようにした
(「何枚あるか」は公開情報である — 3-3)。

★**これは 21c の「相手上段の再構成」の前倒しではない。**
並び・大きさ・要素の種類には一切触れていない。表示している数の出所だけを
正しくしている。マナの裏向き枚数(`manaFaceDownCount`)と手札の枚数ラベルも同じ扱いである。

### 1-5. 判定を「押せない」で表す — サーバのエラーに頼らない

席選択で埋まっている席のボタンは**無効化**し、在席者名を出す。
「押せるが失敗する」でも情報量としては同じだが、人間にとっては違う。

同じ方針を対戦部屋のヘッダにも適用した。

| 対象 | 21b での扱い | 根拠 |
|---|---|---|
| Redo ボタン | 対戦部屋では**隠す** | D6。永久に押せないボタンを置かない |
| デッキ読込 | 対戦部屋では**自席のぶんだけ出す** | E3 |
| 宣言 | 席が無ければ送らずに案内 | D4 |
| ドラッグ | 対戦部屋の観戦者は `dragstart` で `preventDefault` | 6-1 |

★いずれも**操作補助にすぎず、検証はサーバが行う**(設計判断27)。
21a が権限判定を「理由を返す関数」にしてビューへ `canUndo` を載せたのと同じで、
表示と検証が同じ事実を見ている状態を保つ。

観戦者のドラッグを止めたのは、サーバが黙って棄却する(6-4)ぶん
**掴めてしまうと赤いエラーが出るだけの操作**になるからである。
掴ませない側で止めれば、その1往復ごと消える。

### 1-6. ログ書出リンクに `occupantId` を付けた(21a の積み残しを前倒し)

21a のハンドオフはこれを 21c に振っていた。理由は
「対戦部屋は 21b までUIから作れないため実害が無い」であった。

**21b が対戦部屋をUIから作れるようにした時点で、この前提が消える。**
積み残しの期限は「いつやるか」ではなく「いつ壊れるか」で決まるため、
このバッチで直した。1行である。

### 1-7. 在室者リストはヘッダ1行を維持したまま情報量を増やす

設計書 2-3 の要求は「ヘッダ1行を維持」と「観戦者の視点まで表示」の両立である。
20c のヘッダは既に密度が高く、人数ぶんチップを並べると簡単に折り返す。

チップは3人ぶんまで直接出し、超えたぶんは `+n` に畳む。
全員ぶんの詳細(役割・観戦の視点・切断中の残り時間)はポップオーバーへ送る。
**★観戦者の視点を見せるのは飾りではない。**「全見え」の人が居ることを
知らないと、プレイヤーは自分が何を隠せているのか判断できない。

### 1-8. 部屋作成をロビーに残し、入室はゲートに寄せた

ロビーは原則として**入室しない**画面にした。部屋を選んで盤面ページへ送るところまでが
仕事であり、名前と席の決定はゲートが行う。入口が1本なら、
一覧から来ても直リンクで来ても同じ検証・同じ表示を通る。

唯一の例外が「部屋を作る」である。21a の `createRoom` が作成と同時に
作成者を席へ着かせる仕様であり、そこで `occupantId` が発行される。
ロビーはそれを `localStorage` へ保存してから遷移するため、
**作成者はゲートを素通りする**(復帰と同じ扱い)。

## 2. 実装時に踏んだ / 避けた罠

- **★`page.evaluate` に Promise を返す関数を渡さない。** `openJoinGate` は
  席が選ばれるまで解決しない Promise を返す。検証で
  `page.evaluate((s) => openJoinGate(s), summary)` と書いたところ、
  Playwright が戻り値の Promise を待って**永久に返らなくなった**。
  `{ openJoinGate(s); }` と波括弧で包んで戻り値を捨てる。
- **★スクリプト直下の `let` は `window` のプロパティにならない。**
  検証ハーネスの `render()` は `window.latestView = v` としていたが、
  `manual-battle.js` 内部の `latestView` は別物であり null のままだった。
  20c までは `renderAll(v)` に直接渡していたので露見しなかったが、
  21b の「席に着く」はビューを内部変数から読むため、押しても何も起きなかった。
  グローバルの字句環境にある束縛へ直接代入する形に直した。
  **★検証ハーネスが本物とズレていると、動いていないものが PASS する。**
- **`battle.css` の共有クラスに触らない**(ハンドオフ3章)。追加した3クラスは
  すべて `manual-` 接頭辞の新規クラスであり、ファイル末尾への追記で済ませてある。
- **席選択ゲートの `z-index` は帯(1040)・全面表示(1050)より上**に置く。
  入室が済むまで盤面に触らせない画面が、何かの下に潜ってはならない。
- **`setGateBusy` が席の無効化を上書きしない**ようにした。通信中の一時的な無効化と
  「席が埋まっているから無効」は別の理由であり、`dataset.occupied` で区別している。
  区別しないと、通信が終わった瞬間に埋まっている席のボタンが有効に戻る。
- **`createHandCard` の既定席 `'A'` を null に変えた。** 席を省略した呼び出しは
  現状無いが、既定値として `'A'` が残っていると視点固定の名残が生き続ける。

### 3-4. 手元での動作確認

**A. 一人回しの回帰(20c までと同じであること)**

1. `http://localhost:8080/manual` を開く → 部屋一覧が出る(最初は空)
2. 部屋名を空のまま「全公開」で作成 → 盤面へ入る(席選択は出ない)
3. デッキを読み込む → 手札4枚、山札36枚
4. ドラッグで場・マナ・墓地へ移す / Undo・Redo が効く
5. ログ書出でファイルが落ちる(URL に `occupantId` が付いている)

**B. 対戦部屋(21b の本番)**

1. ロビーで種類=**対戦**、部屋名「テスト」、名前「あかり」、席A、観戦=許可、鍵=なし
   → 作成して入室
2. 一覧を更新すると「テスト / 対戦 / A:あかり / B:空き」が出る。**部屋IDは出ない**
3. 別ブラウザ(またはシークレット)で `http://localhost:8080/manual` → 一覧の「入る」
   → **席選択画面が出る**。席Aは「席A: あかり」で押せない
4. 名前を空のまま席Bを押す → 「対戦部屋では名前が必要です」で止まる
5. 名前「ばんり」で席Bへ着席 → 盤面が出る。**自分(B)が下、あかり(A)が上**
6. 相手の山札チップが「山36」等になっていること(0ではない)
7. ヘッダのデッキボタンが**デッキBだけ**であること
8. 名前チップをクリック → 在室者ポップオーバーに2人と役割が出る
9. 「席を立つ」→ 観戦になる。ヘッダが「席に着く」に変わる。**ドラッグしても動かない**
10. 「席に着く」→ 席選択が開き、空いた席Bに座り直せる

**C. 鍵つき部屋**

1. 鍵=ありで対戦部屋を作る
2. 別ブラウザの一覧では「IDが必要」と出て「入る」ボタンが無いこと
3. 「部屋IDで入る」に作成側のヘッダに出ている部屋IDを打つ → 席選択画面へ進めること

**D. 切断復帰**

1. 対戦部屋に2人で入る
2. 片方のタブを閉じる → もう片方の在室者ポップオーバーに「切断中 あとn秒」が出ること
3. その席に第三者が座れないこと(席選択で無効になっている)
4. 閉じたタブと同じブラウザで開き直すと、席選択を経ずに同じ席へ戻ること

## 4. 理解確認 Q&A

**Q1. 席選択を独立ページにしなかったのはなぜか。URLが分かれるほうが分かりやすいのに。**

A. 「盤面の前に必ず通る」を守る主体が変わるからである。独立ページにすると、
盤面ページに「occupantId が無ければ席選択へ飛ばす」というリダイレクトを書くことになる。
その1行が消えたり、条件がずれたりすれば、席を選ばずに盤面へ入れてしまう。
盤面ページの中にゲートを置き、**入室が済むまで接続も描画もしない**形にすれば、
「通らない経路」がそもそも作れない。守りたい性質は分岐ではなく構造で表す。

**Q2. 一覧APIがあるのに、なぜ1件だけ引くAPIを足したのか。一覧から探せばよいのでは。**

A. 鍵つき部屋は一覧に `roomId` が載っていないからである(そこが鍵だからである)。
つまり「一覧の何番目が自分の打ったIDの部屋か」を照合する手段が原理的に無い。
直リンクで来た人も同じである。設計書 2-1 がその経路を明示的に想定している以上、
IDから1件を引く入口が必要だった。**IDを知っている人にしか答えない**ので、
鍵としての意味は損なわれない。

**Q3. 自席を下にするとき、なぜサーバへ送る席まで入れ替えてはいけないのか。**

A. サーバが受け取った `"A"` の意味が閲覧者によって変わってしまうからである。
席Bの人が「自分の場」に置いたとき、視点込みで送ると `"A"` が飛ぶ。
サーバはそれを席Aと解釈するので、相手の場にカードが出る。
**視点は見る側の都合であり、盤面の事実ではない。**
21a が矢印で画素座標を送らないと決めたのと同じ判断で、
座標系(ここでは席の呼び方)が閲覧者ごとに違うなら、それを送ってはいけない。

**Q4. 相手の山札の枚数を出すのは情報漏れではないのか。**

A. 漏れではない。3-3 が「枚数のみ」を公開と定めている。
隠すべきなのは**何のカードか**であって、**何枚あるか**ではない。
実際、現実のカードゲームでも相手の山札の厚みは見えている。
サーバも `counts` を全ゾーンぶん無条件に送っており、
21b はその値を使うようにしただけである。0 と表示するほうがむしろ嘘になる。

**Q5. 観戦者のドラッグをクライアントで止めたのは、「クライアントで判定しない」方針に反しないか。**

A. 反しない。サーバの棄却は**そのまま残っている**(6-1。`ManualPermissions` が拒否する)。
クライアント側で止めたのは検証ではなく**操作補助**である。
これを入れないと、観戦者が何かを掴むたびに赤いエラーが1回出るだけになる。
検証がサーバにあることと、無駄な操作を画面で減らすことは両立する
(設計判断27 の「クライアント側のチェックは操作補助にすぎない」がまさにこの関係である)。

**Q6. ログ書出リンクの修正は 21c の担当だったのに、なぜ前倒ししたのか。**

A. 21c まで待ってよい理由が、21b の成果によって消えたからである。
21a が「対戦部屋は 21b までUIから作れないため実害は無い」と判断したのは正しかったが、
21b は**まさにその対戦部屋をUIから作れるようにするバッチ**である。
積み残しの期限は「予定のバッチ」ではなく「前提が壊れる時点」で決まる。

**Q7. 検証ハーネスの `window.latestView` の件は、なぜ気づきにくいのか。**

A. **壊れていても PASS するからである。** `window.latestView = v; renderAll(v)` は
20c までのすべての検証で正しく動いていた。描画関数は引数の `v` を使うためである。
内部変数を読む機能(21b の「席に着く」)を足して初めて食い違いが表面化した。
ハーネスは本物に似ているほど役に立つが、似ているだけでは足りない。
**「ハーネスでだけ通る」は「ハーネスでだけ壊れる」(20c)と同じ根を持つ。**
