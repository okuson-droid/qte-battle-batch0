## 1. 台帳の修正について

前チャットで指摘した `qte-cards.json` の QTE-0113・0134・0136 の notes の矛盾(裁定1と
逆の記述になっていた件)は、発注者から裁定1に沿った修正版を受け取り解消済みである。
リポジトリ側の台帳(`src/main/resources/cards/qte-cards.json`)は元々この修正版と一致して
いたため、リポジトリへの追加修正は不要だった。

## 2. カードの分類と実装方針

`qte-handoff-v3.md` 2-2 の3分類に沿って実装した。

### ★既存機構のみ・登録不要(3枚)

ウィンド・ペティ(0010)・疾風の先陣(0016)・スカイ・スワロー(0129)は印刷キーワード
(知識・守護・突進・速攻)のみで完結する。`CardMaster.hasKeyword` が全ての判定箇所で
汎用的に参照されるため、`CardEffectRegistry` への登録が一切不要である。

### ★StatCalculatorの動的評価のみ(4枚)

結集する風の精(0124: 場のミニオン合計コスト分軽減)・疾風のレイピア(0130: リーダー
2回攻撃)・サイクロン・フェンサー(0133: ミニオン2回攻撃)・詠唱の風詠士(L010: 3枚目の
コスト軽減)は、`StatCalculator` の該当メソッドにカードIDで分岐を足すだけで完結する。
`maxAttacks`・`maxLeaderAttacks` は12aの時点で「Batch 12bでここに追加する」という
コメント付きの空実装が既に用意されていたため、実装箇所を探す手間はなかった。

### a1のカウンタのみ(6枚)

神風の大号令(0113)・ガイル・フォックス(0117)・ストーム・カイザー(0120)・
嵐の呼び手(0128)・疾風の導き手(L009)・詠唱の風詠士(L010、上記に分類済み)は
`cardsUsedThisTurn` を読むだけで完結する。0113は解決時にスナップショットとして
攻撃力+Nを配り、以降カードを使っても増えない(裁定2)。

嵐の呼び手(0128)は「相手のミニオン1体を戻す」対象選択が要るが、`ResumePoint` に
専用の器を用意していないため(用意されていた5件はいずれも別カード用)、a9には乗せず
`AutoChoice.highestPrintedAttack` による自動選択とした。対象は印刷攻撃力が最も高い
ミニオン(除去対象として価値が高いと推定できるため)。

### 新機構を使う(15枚)

残りのカードは a2(攻撃回数)・a3(体力修正)・a5(強化使用+行き先置換)・
a6(ミニオン起動能力)・a9(割り込み選択)のいずれかを新規に組み合わせて実装した。

## 3. ★突風のまとめ役・暴風の双剣の既知の限界

この2枚のカードテキストは「自分が"他の"カードを使用するたび」(0134)
「自分がカードを使用するたび」(0136)であり、qte-cards.json の裁定1注記は
「自分自身の使用(召喚・装備)ではバフが乗らない」と明記している。

しかし a1 の `afterCardUsed → CardEffectRegistry.fireCardUsed` は、**カードの使用が
解決し終わった後の「現在の場」を走査してON_CARD_USEDを発火する**。ミニオンの召喚
(`summonToField`)はこの走査より前に完了しているため、0134自身が召喚された直後に
発火するON_CARD_USEDイベントには、召喚されたばかりの0134自身も含まれてしまう。
同様に0136の装備も、装備完了後にイベントが発火する。

結果として、**0134・0136は自分自身の召喚・装備の瞬間にも、他のカードと同じように
1回だけバフを受けてしまう**(以降の挙動、および他のミニオンへの影響は文言どおり正しい)。

厳密に文言どおりにするには、`fireCardUsed` が走査する場のスナップショットを
「このカードの使用が始まる前」の時点で確定させ、それを `afterCardUsed` の呼び出し元
(playCard・playTabooCard・specialSummon・summonFromGrave・useLeaderAbility・
useMinionAbility の6箇所)から渡すよう a1 のシグネチャを変更する必要がある。
これは a 系(基盤設計)の変更範囲であり、b 系バッチの範囲を超えると判断し、
本バッチでは着手していない。影響は「1ターンに1回だけ、自分自身に+1が余分に乗る」
という軽微なものであるため、独立バッチとして着手するかどうかの判断を発注者に委ねる。

## 4. a9の新規割り込み(ResumePoint 5件)の実装

いずれも12aで用意された `ResumePoint` の器に実装を乗せた。

- **TAILWIND_DISCARD(選択の追い風 0126)**: 「してもよい」の任意選択。守護持ちの
  手札が0枚なら問い合わせ自体を出さない。
- **MANA_CONVERT_PUT(風のマナ変換 0127)**: 表向きマナを1枚手札に戻した後、
  手札全体から1枚を選ばせる必須選択。この操作のために `GameActions.returnFaceUpManaToHand`
  を新設した(既存の `returnFaceDownManaToHand` は裏向き専用だったため)。
- **WINDHOLE_SECOND(回帰の風穴 0116の強化使用)**: 1体目のバウンス解決後、盤面の
  残り数で自動/選択を分岐(降臨の伝道師と同じ0/1/2+の流儀)。対象は自分・相手
  両方の場(記法規約2-9どおり、限定の無い「ミニオン」は両者を参照する)。
- **GUARD_STAFF_TARGET(風護の杖 0123)**: 攻撃時効果。`GameService.leaderAttack` の
  switch には足さず、switch実行後に別枝として `resolveGuardStaffAttack` を呼ぶ形にした
  (発注者の指示どおり)。0/1体は自動決定、2体以上はa9。選択結果側の処理本体は
  `GameService` と `CardEffectRegistry.resolveChoice` の両方に同一の3行を持たせている
  (両クラスは相互依存できないため。重複はごく小さい)。
- **GALE_KNIGHT_RECOVER(詠唱の疾風騎士 0114)**: ターンエンド時トリガー。墓地の
  スペルが2枚以下なら選ぶ余地がないため自動で全回収、3枚以上ならa9で2枚まで選ばせる。

### ★クライアント側: MINION種別の割り込みは今回が初出

`GUARD_STAFF_TARGET` と `WINDHOLE_SECOND` は候補が場のミニオン(instanceId)であり、
これまでのa9カード(降臨の伝道師)は候補が手札・墓地・公開領域のみだったため、
場のミニオンをクリックして選択する経路が未実装のままだった(`pickChoiceCandidateByMinion`
は空関数)。今回の実装で以下を追加した。

1. `PlayerView.ChoiceCandidateView` に `minionInstanceId` フィールドを追加
   (kindがMINIONのときだけ値が入る)。
2. `GameViewBuilder.buildPendingChoice` のMINION分岐を、自分の場だけでなく
   相手の場も検索するよう拡張した(回帰の風穴の2回目は相手ミニオンも対象になりうるため)。
3. `battle.js` の `pickChoiceCandidateByMinion` を実装し、クリックされたinstanceIdと
   一致する候補を探して送信する。
4. `onOpponentMinionClick` にも割り込み選択のチェックを追加した(従来は自分のミニオンの
   クリックしか割り込み選択を拾っていなかった)。

## ✅ 動作確認手順

1. 風文明リーダー(疾風の導き手 or 詠唱の風詠士)でルームを作成し、風スターターデッキで
   対戦を開始できることを確認する(`DeckValidator`が弾かないこと)。
2. 神風の大号令: 2枚使用した後に唱え、自分のミニオン全体の攻撃力が+2されることを確認する。
3. 風のマナ変換: 表向きマナが0枚のときに使用し、「何も起こりませんでした」のログが出て
   落ちないことを確認する。表向きマナがあるときは、手札から置くカードを選べることを確認する。
4. 回帰の風穴を強化使用(コスト+1)し、1体目バウンス後に2体目の選択肢(自分・相手双方の
   ミニオン)が場のミニオンクリックで選べることを確認する。
5. 風護の杖を装備してミニオンが2体以上いる状態で攻撃し、割り込み選択が出て、選んだ
   ミニオンの体力+1・守護付与が反映されることを確認する。
6. 詠唱の疾風騎士でスペルを5回撃った後にターンエンドし、墓地のスペルが3枚以上あれば
   選択UIが、2枚以下なら自動回収でログが出ることを確認する。
7. `python3 tools/check_structure.py src/main/java` → 異常なし。
8. `python3 tools/check_all.py .` → 項目1・3・5・6すべてパス、WIND_STARTERが40枚。
9. `python3 tools/check_records.py src/main/java` → 不一致は3件のみ(いずれも既知の誤検出、
   本バッチ以前から存在する箇所であることを目視確認済み)。
10. `node --check` と `check_undeclared.py` → 異常なし。

## ✅ 理解確認

<details>
<summary>Q1. 突風のまとめ役(0134)と暴風の双剣(0136)は、なぜ「自分自身の使用では
バフが乗らない」という裁定どおりに実装されなかったのか?</summary>

`afterCardUsed`は、カードの使用(召喚・装備を含む)が完了した**後**に呼ばれ、
その時点の「現在の場」を走査してON_CARD_USEDを発火する。ミニオンの召喚・ウェポンの
装備は、この走査が始まる前にすでに完了しているため、召喚・装備されたばかりの
0134・0136自身も走査対象に含まれてしまう。これを裁定どおりに直すには、
「使用が始まる前」の盤面スナップショットを`afterCardUsed`の6箇所の呼び出し元から
渡すようa1のシグネチャ自体を変更する必要があり、a系の変更範囲になるため今回は
見送った。
</details>

<details>
<summary>Q2. 嵐の呼び手(0128)の「相手のミニオン1体を戻す」対象は、なぜプレイヤーに
選ばせず自動選択にしたのか?</summary>

`ResumePoint`(a9の器)は12aの時点で5件しか用意されておらず、いずれも別カード
(選択の追い風・風のマナ変換・回帰の風穴・風護の杖・詠唱の疾風騎士)専用である。
0128のために新しい`ResumePoint`を追加することもできたが、この効果は「a1のカウンタ
のみで完結する」に分類されたカードであり、a9という別の新機構を持ち込むと分類の
一貫性が崩れる。そのため、既存の`AutoChoice`(闇文明で確立した「解決の途中で自動
決定する」方針)に印刷攻撃力最大という基準を1件追加する形で解決した。
</details>

<details>
<summary>Q3. 回帰の風穴(0116)の2回目のバウンス対象に、なぜ相手のミニオンも
選べるようにしたのか?</summary>

qte-project-reference.mdの記法規約(2-9)により、「相手の」等の限定が無い
「ミニオン」は自分と相手の両方を参照する。回帰の風穴の基本効果もこの規約どおり
`Side.ANY`で実装しており、強化使用の2回目も同じカードの同じ効果の繰り返しである
以上、対象範囲を変える理由がない。
</details>
