## 1. ★★★着手時に伺った3件(裁定359〜361)

### ★★★裁定359 —— 一時公開ゾーンは「公開」と「非公開」の別を持つ。非公開は本人にしか配らない

**問**: 相手の一時公開ゾーンを見せるか。

**答**: **器に「公開か」の旗を1つ持たせる。**非公開の束は、
相手にも観戦者にも**空の列**として配る。

★★<b>これは新しい規則ではなく、本文がずっと言っていたことである</b>:

| カード | 本文 | 相手に見せてよいか |
|---|---|---|
| 《降臨の伝道師》(QTE-M-LIGHT-22) | 山札の上から4枚を**公開** | ★**見せてよい** |
| 《愚乱怒土地》(QTE-M-EARTH-30) | 山札の上から2枚**見て**…**相手に見せず**加える | ★★★**見せてはいけない** |

★★★**80 まで、配信は絞っていなかった。**
`GameViewBuilder` の `buildRevealedCards(player)` は `isSelf` を1度も通しておらず、
<b>《愚乱怒土地》の見た2枚が、相手にも観戦者にも名前つきで届いていた</b>。

★<b>実害が出ていなかったのは、`battle.js` がこの欄を1度も読んでいなかったからにすぎない</b> ——
**81 が描くようになった時点で漏れる穴だった**。

★★<b>絞るのは配信の1箇所である</b>(設計判断9)——
クライアントで絞ると、フィルタの正が2箇所になる。
★<b>`battle.js` が読む `revealedPublic` は、見出しの言葉を選ぶためだけに使う</b>。

### ★★★裁定360 —— 「公開」は中身の配信とログの両方で伝える。配信を跨げない場面はログが埋める

**問**: 《降臨の伝道師》の「公開」を、【守護】の枚数によらず相手に見せられるか。

**答**: **ログにカード名を並べる。**中身の配信は「配信を跨いだとき」にしか届かないので、
それだけでは片肺になる。

★★★<b>この答えは、実寸を測ったことで変わった</b>(80 の教訓の実演)。

**マスターが最初に選んだ道**は「公開領域に必ず通してから確定する」だった。
★**着手せず、先に測った**(73・80 の教訓)——

`GameWsController` 355〜359行:

```java
synchronized (room.getLock()) { action.apply(room); }   // 効果の解決はぜんぶこの中
broadcaster.broadcast(room);                            // 配信は終わってから1回だけ
```

★★★**効果の解決中に配信は1度も起きない**(通常モードで `broadcast` を呼ぶ口は**この1箇所だけ**)。

| 場面 | 公開領域が配信に載るか |
|---|---|
| 《降臨の伝道師》【守護】2枚以上 | ★**載る**(問い合わせで解決が止まる) |
| 《降臨の伝道師》【守護】0枚・1枚 | ★★**載らない** —— <b>同じ配信の中で入れて消えるので、誰にも観測できない</b> |
| 《愚乱怒土地》 | ★載る(問い合わせで止まる)。ただし**非公開**なので本人だけ |

★★<b>「常に公開領域を通す」だけでは片肺は治らなかった</b> —— 入れて消えるあいだに誰も見ていない。

★実寸と、そこから出た3つの道(c1: 確認を挟む / c2: 途中で配信する口を作る / c3: ログに名前を並べる)を
出したうえで、マスターが **c3 + 器の別** を選んだ。

★★★<b>ログなら 0枚・1枚・2枚以上のどれでも同じように届く</b> —— <b>片肺がそもそも生まれない</b>。

★★**書き分けは入口3つぶん**である(`revealFromTopOfDeck` の呼び出し):

| 入口 | 本文 | ログ |
|---|---|---|
| 《降臨の伝道師》 | 4枚を**公開** | 「公開しました: 【A】【B】【C】【D】」 |
| 《光霊・ネフラ》 | 3枚を**表向きにする** | 「公開しました: 【A】【B】【C】」 |
| 《愚乱怒土地》 | 2枚を**見て** | 「**見ました**」(★名前は書かない) |

★<b>80 まで、この3つは同じ1行を出していた</b>(「公開しました」・名前なし)——
<b>器が1つだったので、ログも1つになっていた</b>。

### ★★★裁定361 —— 描く場所は `#auto-playing` の真下の `fixed` の層

**問**: どこに描くか。

**答**: **プレイ中のカードの真下**(`right: 300px` / `top: 412px` / `z-index: 1010`)。

★★<b>実測で決めた</b>(65・69〜72 の教訓)。1280×800 の満杯の盤面で:

| 置き場所 | 実測 | 判定 |
|---|---|---|
| 右列中段 `.auto-side-mid` | 294px 固定。最悪ケースで **264px 使用済み → 余り 30px** | ★**溢れる**(面の列は 65px 要る) |
| 中央列 `.auto-main` | 満杯の盤面で **752 / 750** —— <b>すでに 2px 溢れている</b> | ★**帯を足す余地が無い** |
| `fixed` の層 | 場所を奪わない | ★★**ここしか無い** |

★<b>`#auto-playing` はまさにこの問い合わせの間に出ている</b>ので、
「このカードが、この束を公開した」と**縦に読める**。

★★★**z-index は `#auto-playing`(1390)と揃えていない。**
<b>ここは演出の着地点だからである</b> —— fx層(1020)より上に置くと、
飛んできたゴーストの最後の数フレームが帯の裏へ隠れる。
★<b>揃えないことにも理由が要る</b>(裁定358 と同じ形の判断)。

★**`pointer-events: none`。**読むための面であって操作の道具ではない ——
<b>覆いは守りではない</b>(71 の判断)。

## 3. ★次のバッチへの申し送り

### 3-1. ★★★「絞っている」と書いたコメントは、絞っていることの証拠ではない

`CardEffectRegistry` の 5747行は「GameViewBuilder が isSelf で絞る」と書いていたが、
**絞っていなかった**。

> ★★<b>77 の教訓(用意した側は「使われている」と思い込む)の、ちょうど逆の顔である</b> ——
> <b>使う側が「絞られている」と思い込んでいた。</b>
> ★<b>どちらも、書いた人が確かめずに書いた文である。</b>

★<b>次に「あちらが◯◯してくれる」と書くときは、その場で1件でいいから測ること。</b>

### 3-2. ★★★描いていない欄は、漏れていても誰も気づかない

`revealedCards` は 44 からビューに載っており、**穴もそのときから在った**。
★<b>実害が出ていなかったのは、読む側が1度も読んでいなかったからにすぎない</b>。

> ★<b>「描いていないから安全」は、安全ではなく<b>先送り</b>である。</b>

★★<b>次に「ビューに在るのに画面に無い欄」を見つけたら、
塞ぐ前に<b>公開範囲</b>を確かめること</b> —— そこが今のところ<b>誰にも測られていない</b>。

### 3-3. ★★儀式を描きたくなったら、まだ 38 と同じ工事が要る(80 の 3-3 は生きている)

★81 は<b>その壁に別の顔で当たった</b> ——
「効果の解決中に配信が1度も起きない」ことが、**儀式が描けない理由そのもの**である。
★★<b>80 は「サーバに材料が無い」と書いたが、より正確には
「材料はあっても、それを見せる<b>配信の機会</b>が無い」である</b>。

★<b>作るなら c2(解決の途中で配信する口)であり、
それは配信の口を2つにする工事である</b>(設計判断48 の兄弟)。
★★<b>しかも止めないなら結局見えない</b> —— 38 と同じ「間」の仕組みまで要る。

### 3-4. ★★★時間で待っている番人は、まだ他にもある

★81 は 62-8(通常モードは配信で音が鳴る)を直した ——
**unlock のあと 200ms 固定でバッファの decode を待っていた**(余裕は実測 73〜114ms)。

★★<b>直し方は 79 とまったく同じである</b>(設計判断61)——
<b>事実で待ち、わざとの遅れを同じバッチで入れる</b>。

★★★<b>遅らせを入れる場所で1つ踏んだ</b>: `sfxPreload` は
**ページを開いた時点で全部取りに行く**(裁定283 の (c))ので、
<b>遅らせるのは `goto` の前でなければ効かない</b>。
★<b>しかも開いてからクリックまでの待ちより長くしないと、
クリックの時点でもう届いており、待ちが1ミリ秒も働かない</b>。

> ★<b>次に「たまに落ちる」に出会ったら、頻度ではなく<b>余裕</b>を測ること</b> ——
> そして<b>遅らせが本当に効いているかも測ること</b>(裁定186)。

★★**手動モードの側(`snd` のページ)は、まだ 200ms / 400ms の固定待ちのままである。**
★<b>同じ形なので、同じ日に同じ症状が出うる</b>。81 は触っていない。

### 3-5. ★★教訓を知っていることと、当てられることは別である

壊し検証の軸9(《光霊・ネフラ》)は、**77・79・80 が3度書いた教訓そのもの**だった ——
「規則が n 入口ぶんあるなら、番人も n 入口ぶん要る」。
★<b>知っていたのに、番人を書いた時点では2入口ぶんしか置いていなかった</b>。

> ★★★<b>壊し検証は番人を試す道具だが、<b>番人の数を決めさせる</b>道具でもある。</b>
> ★<b>軸を立てて当てる先が無かったら、それは足りない番人である。</b>

### 3-6. ★別の性質を1つの番人にまとめない

軸12/17(描く・印)と軸18/19(操作を吸う・層が下)は、最初<b>1つの `check` にまとまっていた</b>。
★<b>壊し検証で「2つの軸が同じ番人に当たる」形が見えたので、番人の側を分けた</b>。

> ★<b>別の理由から来ている性質は、別の番人にすること</b>
> (72 の教訓「理由の幅と結論の幅を揃える」の、番人の側の顔)。
