## 1. 何を作ったか

### 1-1. 縦の収支

設計書0章の見積りに対する実測(1280×950・カード画像あり・センターライン展開中)は
**888px** であった。従来は約993pxで、900px前後の実表示域では手札か相手の情報が
画面外に溢れていた。溢れは解消している。

| 行 | 実測 |
|---|---|
| ヘッダ(1行) | 40 |
| 相手上段 | 148 |
| 相手ミニオン | 140 |
| センターライン(展開時) | 130 |
| 自分ミニオン | 140 |
| マナ+リーダー | 135 |
| 手札 | 150 |
| **合計** | **888** |

### 1-2. 画面の変更点

1. **ヘッダを1行にした。** 部屋コード・接続状態・在室者・デッキ読み込みステータス・
   ボタン群を1行に収めた。ターン数とフェイズの表示・操作は削除した。
2. **リーダー行(185px)を廃止した。** パイル群は右列へ移り、リーダーはマナ行の右端へ移った。
3. **リーダーとウェポンを1タイルに合体した。** リーダータイル自体が WEAPON のドロップ先で
   あり、装備中のウェポンは右下に重なる44×60のミニタイルとして出る。
4. **センターラインを新設した。** 両ミニオン行の間に [プレイ中 | 公開] の帯を常設した。
   空のときは24px、カードが入ると130pxへ自動展開し、0枚に戻ると自動で畳む。
5. **右列を224→288pxへ広げ、パイルをカード画像にした。** 上段[禁忌][山札][確認] /
   下段[消滅][墓地]。非公開パイルは裏面画像、公開パイルは最上段の表画像を敷く。
6. **ログを折りたたみにした。** 既定は直近2行ぶん、クリックで右列内をその場拡張する。

## 2. 設計根拠★

### 2-1. ★共有ゾーンを席の下に置かなかった理由

`PLAY` と `REVEAL` を「常にA席の `zones` へ入れておき、画面だけ中央に描く」という
慣習方式は、実装量が最も小さい。それでも採らなかった。

**モデルとして嘘になるからである。** 将来 `seatA.zones.REVEAL` を読んだ人間は、
それを「A席の公開ゾーン」と解釈する。実際には両者の共有物であり、B席が置いたカードも
そこに入っている。この食い違いは、読んだ人が間違った前提でコードを書くまで表面化しない。
18cの「帯から盤面へドラッグできる」と同じ種類の、記述と実態のズレである。

移行の心配が要らないことも後押しした。部屋はメモリ上にのみ存在し永続化が無いため、
デプロイで再起動すれば部屋ごと消える。データを読み替える必要がそもそも発生しない。

### 2-2. ★共有かどうかの判定を1箇所に閉じた

共有ゾーンを足すと、「席の下か、ゲームの下か」という分岐が
**移動先の解決・移動元の探索・取り外し・クリア** の4箇所に現れる。
4箇所に同じ `if (zone.isShared())` を書けば、必ずどれかが漏れる。

そこで `ManualGameState.cards(seatId, zone)` を1本立て、分岐をその中だけに閉じた。
`ManualOperationService.move` は移動先を `state.cards(toSeatId, request.toZone())` で引き、
`ManualBoardIndex.detach` は取り外しを `state.cards(ref.seatId(), ref.zone())` で行う。
どちらも共有かどうかを知らない。

`ManualSeat.zone()` が共有ゾーンで**例外を投げる**のも同じ狙いである。
空リストを返して黙って通すと、「席の公開ゾーンへ入れたつもりのカードが消える」という
形で後から発覚する。呼び出し側の誤りは、その場で止めるほうが安い。

### 2-3. ★`seatId == null` を許す判断

共有ゾーンのカードは席に属さない。`ManualCardRef` の `seatId` を null にすることで
それを表した。影響したのは3箇所である。

- `BOARD_ORDER`: `ref.seatId().ordinal()` が NPE になるため、null を -1(席より前)に倒した。
- `detach`: 上記の `cards()` 経由に変えた。
- `describeOrigin`(ログ): `席null` という文字列が出るため、共有判定を先に置いた。

「専用の型を作る」「`ManualSeatId.SHARED` を足す」も検討したが、前者は所在を表す型が
2つになって `requireAll` の戻り値が扱いにくくなり、後者は `state.seat(SHARED)` という
呼べない組み合わせを enum が許してしまう。null は明示的に javadoc に書いてある限り、
この規模では最も素直である。

### 2-4. ★ウェポンの付け替えは「判断を実装しない」原則の明示的な例外である

設計書16 5-1 は「アプリが担うのは同じ盤面を見ていることの保証だけ」と定め、
コスト支払い・戦闘解決・勝敗判定を実装しないとしている。
本バッチの**ウェポン付け替え(古いウェポンを自動で墓地へ送る)は、この原則から外れる**。
アプリが人間の代わりに行き先を決める、手動モードで唯一の処理である。

採用した経緯は次のとおりである。

1. リーダータイル自体をドロップ先にした結果、「装備済みかどうか」でドロップの
   当たり判定を変えると人間に説明できなくなった(旧・拒否規約は撤回した)。
2. 「いつでも落とせる」を選ぶと、2枚目を置いたときの後始末が要る。
3. クロエは自動化に反対したが、マスターの判断で採用した。

**そのうえで、行き先の正しさはアプリの責任になる。** 総合ルール 2-3 により禁忌デッキ由来の
カードは場を離れると墓地ではなく消滅へ行く。自動で墓地へ送ると、禁忌由来のウェポンで
必ず誤る。そこで `ManualCardInstance.fromTaboo` を新設し、デッキ読み込み時に一度だけ
刻むことにした。

**★由来は「現在地」からは復元できない。** 禁忌ゾーンから場へ出た時点で現在地は WEAPON に
なっており、そこから「元は禁忌だった」は分からない。だから個体の属性として持つ。

なお、この処理は**ただの移動**である。Undo でも、墓地から消滅への手動移動でも取り消せる。
ログに `(付け替え: 《武器名》→墓地)` と必ず残すのはそのためである。

### 2-5. ★ミニタイルに操作を詰め込まなかった

現行のウェポンタイルは ATK・使用済/未使用バッジ・札チップ・+ボタンを持つ。
44×60 にこれを全部載せると、どれも押しにくい当たり判定になる。
ミニタイルは**画像と枚数バッジだけ**にし、数値・使用済・札はウェポン操作モーダル
(`#weapon-modal`)へ集約した。ウェポンに進化は無いため進化バッジは持たない。

モーダルは LP モーダルと同じく**押しても閉じない**。そのため、再配信のたびに中身を
組み直す `refreshWeaponModal` を置いた。押した結果がその場で反映されないと、
押せたのかどうかが分からなくなるためである。

### 2-6. ★空のセンターラインは「片側だけ24px」にはしない

設計書2-3は「空のときは高さ24pxの細いドロップバー」と定める。実装では、
**片側にカードが入って130pxへ開いたとき、空のもう片側は相方に合わせて縦に伸びる。**

センターラインは1本の帯であり、片側だけ24pxで浮くと帯として読めなくなる。
また空の側の伸びはドロップ対象の面積が増えるだけで、縦の収支に影響しない
(帯全体の高さは開いた側の130pxで決まる)。展開状態を表すクラス
`manual-center-open` は空の側には付かないため、状態としては正しく区別されている。

### 2-7. ★リセット時に共有ゾーンを全消去する

`applyImport` は `seat.clearAll()` で席のゾーンだけを空にする。共有ゾーンは席の外に
あるためこれが届かない。放置すると、山札へ戻らない個体が中央に残り続ける。

`ManualCardInstance` は持ち主を持たないため「A席由来だけ消す」は原理的に書けない。
仕切り直しの操作である以上、中央も一緒に片付くほうが盤面の一貫性を保てる、という
マスターの判断で `loadDeck` / `resetRoom` の両方で `clearSharedZones()` を呼ぶことにした。

### 2-8. ★ターン/フェイズはUIだけ消し、サーバは残した

`turn` / `phase` の `@MessageMapping` とサービスメソッドは削除していない。
UIから到達できない休眠コードとして残っている。フェイズ2の対戦モードでターン管理が
必要になったとき、サーバ側を作り直さずUIだけ再設計できるようにするためである。
`tools/` の機械チェックは呼び出し元の有無を見ないため、誤検出にはならない
(実際にパスすることを確認済み)。

### 2-9. REVEAL の表示名を「一時公開」から「公開」に変えた

設計書1-2・2-3が「公開」と書いているため、`ManualZone.REVEAL` の `displayName` と
JS の `ZONE_LABELS` を揃えた。ログ文言と山札全面表示のボタン名にも波及する。
あわせて、全面表示のボタンに「確認へ」を1つ足した(計11個)。設計書2-4の用途例
「山札の上から3枚を見て1枚を手札に加える」が最も短い手順になるためである。

## 4. 理解確認 Q&A

**Q1. なぜ `ManualSeat.zone(ManualZone.PLAY)` は空リストではなく例外を返すのか。**

A. 席に属さないゾーンを席から引こうとするのは、呼び出し側の誤りだからである。
空リストを返すと、そこへ入れたカードがどこにも現れないという形で後から発覚する。
誤りはその場で止めるほうが、追跡のコストが圧倒的に小さい。
状態モデルの一様性(`zones` の EnumMap 1本)は、ゾーンが席に属する限りでの一様性であり、
共有ゾーンはその前提の外にある。

**Q2. 表裏の正規化(20a)は、共有ゾーンへの移動にも効いているか。**

A. 効いている。`FACE_UP_ON_ARRIVAL` に `PLAY` と `PRIVATE` を足したためである
(`REVEAL` は20aの時点で入っていた)。正規化は `move` の1箇所に閉じてあり、
盤面ドラッグ・帯・全面表示のボタン・複数選択の一括移動という4経路すべてがそこを通る。
共有ゾーンへのルーティングを `move` の中で行ったのは、この関門の内側に留めるためでもある。

**Q3. Undo で共有ゾーンが戻るのはどこで保証されているか。**

A. `ManualGameState.copy()` に `sharedZones` の深いコピーを足した1箇所である。
スナップショット方式(設計書5-6)は「状態をまるごと複製して積む」であり、
複製の対象から漏れたものは巻き戻らない。設計書3-2が「実装時に必ず確認すること」と
名指ししていた要注意ポイントであり、テストでも直接確認している。

**Q4. 禁忌由来かどうかを、なぜ「今どのゾーンに居るか」で判定しないのか。**

A. 判定に必要なのは由来であって現在地ではないからである。禁忌ゾーンから場へ出た時点で
現在地は FIELD / WEAPON になっており、そこから「元は禁忌だった」は復元できない。
`fromTaboo` はデッキ読み込み時に一度だけ立て、以後変えない。

**Q5. ウェポンの自動墓地送りは、手動モードの原則に反しないのか。**

A. 反する。本解説2-4に「明示的な例外」として記録した。原則を曲げた代償として、
行き先の正しさ(禁忌由来なら消滅)までアプリが面倒を見る責任が生じている。
自動化は、それ単体では終わらず、必ず付随する正しさの責任を連れてくる。
