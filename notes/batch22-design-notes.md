## 1. 設計根拠★

### 1-1. ★クリック規約の入れ替えは「回数の多い操作を主ボタンへ」である

設計書 1-1 はマスター指示として書かれているが、原則としても筋が通る。
カードゲームで最も回数が多い操作は **「見る」** である。効果テキストを読み直す、
相手が何を出したか確かめる、自分の裏向きマナが何だったか思い出す — これらはターン中に
何度も起きる。20c までの規約は、最も回数の多い操作を副ボタン(右クリック)に置いていた。

実装上は、この入れ替えが**分岐を1つ消している**点が重要である。

```js
// 20c まで: 左クリックがゾーンを見て分岐していた
if (zone === 'HAND' || SHARED_ZONES.has(zone)) { setZoom(card); return; }
send('tap', ...);

// 22: 左は常に拡大。ゾーンを見る必要が無い
setZoom(card);
```

ゾーンを見る責務は新設した `onCardContextMenu` へ移った。
**判断を持つ関数が1つ減ったわけではないが、「主たる操作が単純なほうがよい」**という
配置になっている。左クリックは全カード共通で1行、例外の説明は右クリック側だけを読めばよい。

### 1-2. ★★相手の裏マナの内訳は「サーバを触らないほうが正しい」(2-7)

一見サーバに `manaFaceDownUntappedCount` を足したくなるが、**足さないほうが正しい**。
理由は3つあり、どれもこのプロジェクトで既に決めた原則である。

**(a) 引ける値である。** `ManualSeat.availableMp()` の javadoc は「裏向きのマナも数に入れる」と
明記している。したがって次が恒等的に成り立つ。

```
裏アンタップ = mp − (表向きカードのうち tapped でない枚数)
裏タップ     = manaFaceDownCount − 裏アンタップ
```

**(b) 同じ情報を2箇所に置かない(設計判断28)。** サーバに専用フィールドを足すと、
`mp` と重複する情報が2つ届く。片方の計算だけを変えたときにずれる余地が生まれ、
しかも**そのずれは画面上で矛盾として見える**(MP は5なのに内訳の合計が4になる)。

**(c) 新しく漏れる情報が無い。** タップ状態は実物のカードが寝ているかどうかであり、
盤面を見れば分かる公開情報である。MP を数値で公開している(21 設計書 3-3)時点で、
アンタップ枚数は既に相手へ渡っている。つまりこれは
**「既に渡してある情報を読みやすく並べ直しただけ」**であり、公開範囲の変更ではない。

★実装には依存関係のコメントを残した。`availableMp()` を「表向きだけ」に変えると
この式は静かに壊れる — 例外も出ず、数字が少しずれるだけである。
**壊れ方が静かな依存ほど、依存する側に書いておく必要がある。**

★防御的な丸めも入れてある(0 と `manaFaceDownCount` でクランプ)。
サーバとクライアントの一時的なズレで負や超過が出たとき、
**嘘の数字を出すより丸めるほうがよい**(21b 1-4「0 と表示するほうが嘘になる」と同じ軸)。
検証項目として `mp=99` の異常なビューを流し、総枚数を超えないことを確かめている。

### 1-3. ★★ウェポン枠の新設は「呼び出し側がフラグを渡す」で解いた(3-4)

自席はウェポン枠、相手は合体タイル。**席によってドロップ先が違う**構造になる。
ここで `createLeaderTile` の中に「自席かどうか」を書くと、21b が確立した規約
(描画関数の中に `'A'` / `'B'` を書かない)を破ることになる。

```js
createLeaderTile(seat, { withWeapon: true });   // 相手上段の呼び出し
createLeaderTile(seat, { withWeapon: false });  // 右列の呼び出し
```

★**呼び出し側は既に知っている。** `renderOpponentTop` は「上段を描く関数」であり、
`renderPiles` は「自席の右列を描く関数」である。知っている側が渡し、
知らない側は受け取るだけ — これは 21b で `bottomSeat` / `topSeat` に集約したのと同じ形である。
判定を描画関数の中へ入れると、その関数を別の場所から呼んだ瞬間に間違える。

★この変更で**アンカーも移った**(3-5)。`registerZoneAnchor(el, seatId, 'WEAPON')` を
ウェポン枠へ移し忘れると、矢印のウェポン宛の端点が相手上段の合体タイルを指したままになる
(21c 7-1)。移動を伴う変更で最も落としやすい種類の1行なので、
**アンカーの引き先そのものを検証項目にした**(`anchorElement({seatId:'A', zone:'WEAPON'})`
が返す要素のクラス名を見る)。座標や見た目ではなく**対応表を直接確かめる**ほうが、
壊れたときに原因が1つに絞れる。

★リーダー(ゾーン null)のアンカーは両席とも合体タイル/リーダータイルに残っている。
「全ゾーンが全閲覧者のレイアウトにアンカーを持つ」という 21c の性質は維持されている。

### 1-4. ★裏向きマナを絵にしても、ルール上の確認手段は失われない(2-4)

総合ルール 2-9 は「裏向きマナの内容は、持ち主はいつでも確認できる」と定めている。
裏面画像にすると一覧では中身が読めなくなるが、**1章の入れ替えと噛み合って
確認はむしろ速くなっている**。

| | 20c まで | 22 |
|---|---|---|
| 裏マナの中身を見る | 右クリック | **左クリック** |

拡大表示は常に表面画像を出す(20a 2-4)ため、1クリックで中身が読める。
2つの変更を別々に評価すると「裏マナが読めなくなった」に見えるが、
**同じバッチで入る変更どうしの相互作用まで見ると逆になる**。

★`faceDown` は**絵の出し分けにだけ**使っている。公開範囲を決めるのはゾーンであり
(21 設計書 3-4)、対戦部屋で相手の裏マナが漏れないのは
**サーバがカードオブジェクトを載せないから**である(21a 3-3)。
`faceDown` に「相手へ公開しない」の意味を持たせると、クライアントの描き方が
公開範囲の一部になってしまう。

### 1-5. ★「揃える」対象を絵の種類に限定した(2-2)

マナの表示を統一するとき、素直に考えると「相手の裏向きも枚数分並べる」ことになる。
そうしなかったのはマスター確認済みの判断だが、理由は明確である。

**相手の裏向きマナは中身が届かないため、枚数分並べても情報量が1ビットも増えない。**
1枚+バッジのほうが幅を食わず、枚数も直接読める。
**揃えるのは「絵の種類」であって「枚数の数え方」ではない。**

同じ理由でタップの表現も揃えていない(2-5)。自席=回転 / 相手=減光である。
これは同じ状態を違う記法で描いているのではなく、**制約が違う**。相手上段には 148px の
高さ制約があり、回転させると外接矩形が伸びる(21c 1-3)。
★「統一」を目的にすると、制約の違いを無視して両方を悪くしがちである。
統一するのは**読み手が混乱する部分**だけでよい。

### 1-6. ★数値のボタン化に「常時 ±」を選ばなかった理由(4-2)

「押せば変えられる」を直感的にする方法は2つあった。

| 案 | 問題 |
|---|---|
| 常時 `−` `+` ボタン | 場のタイルは幅110pxしかない。`−` と `+` を押し込むと当たり判定が小さくなりすぎる |
| **枠+鉛筆(採用)** | 当たり判定はチップ全体。まとまった値を動かす手段はモーダル側に既にある |

★**小さい的を作らない**が判断軸である。鉛筆(✎)は装飾であり、当たり判定はチップ全体に
してある。ホバーで枠と背景が強まるのは「押せることの最終確認」であり、
`title="クリックで編集"` は読み上げ環境と迷ったときの保険である。

★**修正値チップ(`.manual-stat-chip`)はボタン化していない**(4-3)。
印刷値との差(`+2` / `-1`)は**状態の表示であって操作ではない**。
ボタン化すると「押せるもの」と「読むもの」が混ざり、
ボタン化の目的そのもの(押せるものを見分けられるようにする)が達成できなくなる。
検証項目に「`.manual-stat-chip.manual-stat-button` が0件であること」を入れてある。

### 1-7. ★数値モーダルの ± はクライアントで完結させた(4-4)

サーバの `stat` 操作は差分ではなく**絶対値**を受ける。`-1` / `+1` を足すにあたって
選択肢は2つあった。

| 案 | 判断 |
|---|---|
| サーバに差分の経路を足す | ★退けた。このバッチは Java に触らない(X1)。加えて、同じ操作に絶対値と差分の2経路が できると「どちらが正か」が曖昧になる |
| **入力欄の現在値を ±1 して確定(採用)** | 押した結果が入力欄にもその場で出るため、「押せたのかどうか」が分かる |

★LPモーダルの ± は従来どおり**サーバの差分**(`delta`)のままである。
LP は複数の閲覧者が同時に触りうる値であり、差分のほうが競合に強い。
一方 ATK/HP は特定のカード1枚の値であり、絶対値で十分である。
**同じ見た目のボタンでも、値の性質が違えば送るものが違ってよい。**

### 1-8. ★山札を例外に残したことは、規約と矛盾していない(1-3)

新しい規約に対して山札の左クリックだけが例外(1枚ドロー)になる。
これを「規約の穴」と読むのは正しくない。

- **左を拡大にしても意味が無い。** 山札の一番上は非公開である。拡大しても裏面か、
  自分のものなら「次に引く1枚が見える」というルール上おかしい表示になる
- **右は既に新規約と一致している。** 全面表示は「一覧を開く」であり、
  他のパイルの右クリック(帯を開く)と同じ役割である

つまり矛盾しているのは左だけで、**そこには拡大に相当する意味が存在しない**。
「例外があるから規約が弱い」のではなく、
**規約を当てはめる対象が無い場所に、別の意味を割り当てている**だけである。
操作説明にも「ここだけ例外」と明記した(5-2)。隠すと、
規約を信じて左クリックした人が予想外にドローすることになる。

### 1-9. ★「押しても何も起きない」を作らない(1-5)を右クリックにも適用した

手札・センターライン・帯の中のカードはタップできない。ここで右クリックを無反応にすると、
規約は一貫するが**故障と区別が付かない**。21 設計書 3-5 が非公開チップに
フィードバックを入れたのと同じ判断で、拡大を返すようにした。

★同じ考え方を、**非公開ゾーンの左クリック**にも広げた。1章は
「相手の墓地・消滅の一番上を左クリックで拡大」と定めているが、対戦部屋の非公開ゾーンでは
拡大するカードが届いていない。ここで何も起きないと 21c で直したはずの問題が
**左クリック側に再発する**。`zoomTopOrDeny` を通し、21c と同じ明滅+トーストを返す。

```js
function zoomTopOrDeny(el, seatView, zoneName, fromHead) {
    if (!isZoneVisible(seatView, zoneName)) { flashDenied(el); showToast(...); return; }
    ...
}
```

判定材料は 21c と同じく **`zones` にキーがあるかだけ**である。
「対戦部屋か」「相手席か」を組み立て直さないので、公開範囲の定義がクライアントへ写らない。

## 2. 実装時に踏んだ / 避けた罠

- **★★検証で「タイルの中央」を押すと数値チップに当たる。**
  `page.locator('.manual-tile').click()` は要素の中央を押す。`.manual-tile` は
  `justify-content: space-between` で名前・数値・札を縦に並べており、
  **中央にあるのは数値チップ**である(1-6 の専用ボタン)。
  そのため「左クリックで拡大される」検証が `zoom=null` で落ち、続く操作が
  開きっぱなしのモーダルに阻まれて TimeoutError になった。
  → カード本体を押す検証は `.manual-tile-name` を狙うようにした。
  ★**「タイルを押す」と書いたつもりが「タイルの上のボタンを押していた」**という取り違えは、
  ボタンを増やすバッチでは起きやすい。
- **★拡大の検証は「tap が送られない」だけでは足りない。**
  それだけだと**何も起きなかった**ときと区別が付かない。
  `#zoom-panel img` の `src` まで見て、**何が拡大されたか**を確かめている
  (`zoomedImage()` を新設)。上の罠が見つかったのはこの検証があったからである。
- **★21c の既存項目のうち「クリックで帯が開く」は右クリックへ書き換えが要る。**
  相手の公開ゾーン(墓地)と全公開部屋の手札チップの2件。
  一方「非公開チップをクリックしても帯が開かない」は**そのまま通る**
  (`zoomTopOrDeny` も同じ明滅+トーストを返すため)。
  ★落ちた項目を直すのではなく、**新しい仕様に合わせて書き換える**(設計書 7-2)。
- **★オーバーレイの id は `manual-overlay-root` であり `overlay-root` ではない。**
  トーストも `#manual-toast` が**出しっぱなしで `d-none` を付け外しする**実装なので、
  「出ている」を数えるには `:not(.d-none)` が要る。
  存在の有無で数えると、1度出た後は常に真になる。
- **★ハーネスの Bootstrap 代替に `.table-bordered` / `thead` / `fw-bold` / `ps-4` が無かった。**
  操作説明を表へ書き直したときに使ったユーティリティである。寸法の検証には影響しないが、
  21c 2章の教訓(代替の漏れは「ハーネスでだけ壊れる」)どおり代替へ足した。
- **★ウェポン枠のドラッグ起点から専用ボタンを除外する。**
  枠全体を `draggable` にすると ATK チップや使用済トグルからもドラッグが始まる。
  20a 3-1 と同じく `dragstart` の中で `document.elementFromPoint()` を見て
  `preventDefault()` している(`e.target` ではダメ。`e.target` は最初から枠自身になる)。
- **★ドロップ先を1つ減らす変更は「送られないこと」を検証しないと確かめられない。**
  自席のリーダータイルが WEAPON を受けなくなったこと(W2)は、
  実マウスで落として **`toZone: 'WEAPON'` の move が送られない**ことを見ている。
  「ウェポン枠へ落とせる」だけでは、リーダーが二重に受けていても通ってしまう。
- **`syncCounts` を忘れると fixture が嘘をつく。** ウェポンや相手のマナを足した fixture では
  必ず `syncCounts` を呼んでいる。`counts` がずれたまま
  「枚数が正しい」検証を書くと、検証自身が誤った前提を固定する。

## 4. 理解確認 Q&A

**Q1. 左右を入れ替えるだけなら、`onCardClick` の中身を入れ替えれば済むのではないか。
なぜ新しい関数(`onCardContextMenu`)を作ったのか。**

A. 入れ替える前は**左クリックだけが分岐を持っていた**(HAND / 共有ゾーンなら拡大、
それ以外はタップ)。入れ替えると、その分岐は右クリック側へ移る。
1つの関数の中で入れ替えると「左クリックのハンドラなのに右クリックの分岐が書いてある」
状態になり、呼び出し側(`addEventListener('click', ...)`)と中身が食い違う。
関数名がイベント名と対応していることは、**読む人が中身を読まずに済むための情報**である。
結果として `onCardClick` は3行になり、ゾーンを見なくなった。

**Q2. 相手の裏マナの内訳をサーバから送れば、引き算のバグを心配しなくて済むのでは。**

A. 心配の対象が移るだけである。サーバから送ると、今度は
**「サーバの内訳と `mp` が一致しているか」**を心配することになる。
値が2つある限り、ずれる可能性は消えない(設計判断28)。
一方、引き算で出す方式では `mp` が唯一の正であり、**定義上ずれようがない**。
残るリスクは「`availableMp()` の意味を変えたときに壊れる」だけで、
それは実装にコメントで書いてある。
★**重複を作って両方を検証するより、重複を作らないほうが検証すべきものが減る。**

**Q3. 自席と相手でウェポンの置き場が違うのは、覚えることが増えていないか。**

A. 増えていない。むしろ減っている。20c までは
**「リーダーに落とすと装備される」という比喩**を覚える必要があった。
22 では自席について「ウェポンはウェポン枠に置く」という**場所と意味が1対1の説明**で足りる。
相手側の合体タイルは「相手が装備しているかどうかが分かる表示」であって、
そこへ落とす操作は日常的には使わない(相手に装備させるのは稀な手動操作である)。
★**頻度の高い操作の説明が短くなるなら、頻度の低い操作が例外になるのは割に合う。**
なお相手上段には 148px の高さ制約があり、枠を1つ足す余地が物理的に無い。

**Q4. 盤面の高さが 804px から 821px に増えている。設計書 2-8 は
「縦を増やさない」「ラベルを削って相殺する」と書いていたはずだが。**

A. **相殺できなかったので、増やしたうえで実測を報告している。**
2-8 は「ラベルは1行に収めることで相殺する」と書いていたが、
20c の時点で**ストリップのラベルは既に1行**であり、削り代が無かった。
削るとすれば `padding` を数px詰めることになるが、上限900pxに対して79pxの余裕がある状況で
行を窮屈にするのは目的と手段が逆である。
★**設計書の前提が実物と違っていたときは、前提のほうを訂正して報告する。**
無理に数字を合わせるために別の場所を悪くするのは、設計書に従っているようで従っていない。
増えたぶんは見出し1行(16.1px)+ margin(1px)ちょうどであり、
ウェポン枠は右列の既存の行に収まったため**縦に1pxも足していない**(実測で確認済み)。

**Q5. 「左クリックで拡大される」の検証で、なぜ `tap` が送られないことだけでは不十分なのか。**

A. **何も起きなかった場合と区別が付かない**からである。実際、この検証を書いたことで
「クリックがタイル中央の数値チップに当たっていて、カード本体が押せていない」という
取り違えが見つかった(2章)。`tap` が送られないことだけを見ていたら、
テストは通り、しかし**規約は検証されていない**状態で納品されていた。
★21c の Q7(厳しい検証項目を書いて初めて「どこが似ていないか」が分かる)と同じ話で、
**「起きてほしいこと」を確かめないと、「起きてほしくないこと」だけでは何も保証されない。**

**Q6. 非公開ゾーンの左クリックまで `zoomTopOrDeny` を通す必要があったのか。
設計書1章は「左=拡大」としか書いていない。**

A. 書いていないが、書いてある内容から導ける。1章の表は
「相手上段の墓地・消滅 → 左クリック = 一番上のカードを拡大」と定めており、
対戦部屋では**そのカードが届いていない**。素直に実装すると `cards[cards.length-1]` が
`undefined` になり、何も起きない。これは 21c 3-5 が
「無反応は故障に見える」として直したのと**同じ問題が左クリック側に生えた**状態である。
21c が右クリック側(当時は左)だけを直していたのは、当時そちらしか一覧を開かなかったからで、
規約を入れ替えれば同じ手当てが反対側にも要る。
★**規約を入れ替える変更は、以前の規約に紐付いていた手当ても一緒に動かす必要がある。**

**Q7. 数値モーダルの ±1 が、サーバへ「絶対値」を送っているのは気持ち悪くないか。
LP は差分を送っているのに。**

A. 値の性質が違うためである。LP は**2人+観戦者が同時に見ている1つの数値**であり、
自分がモーダルを開いている間に相手が変えることがありうる。差分なら両方の操作が生きるが、
絶対値だと後勝ちで片方が消える。一方 ATK/HP は**特定のカード1枚の値**で、
そのカードを同時に2人が編集する場面は事実上無い。
★**「同じ見た目のボタンだから同じ実装であるべき」ではない。**
競合しうる値かどうかが、差分と絶対値の分かれ目である。
