## 1. 外部依存の自前配信(レビュー C-2)

### 1-1. 何が問題だったか

40 までのテンプレートは、Bootstrap と stomp.js を jsdelivr から読んでいた。
**`integrity` 属性は9枚すべてに無く、フォールバックも無かった。**

| ライブラリ | 参照していた画面 | 落ちたときに起きること |
|---|---|---|
| `bootstrap.min.css` | 7枚 | 見た目が崩れる |
| `stomp.umd.min.js` | `battle.html` / `manual-battle.html` | ★**盤面が一生来ない** |

### 1-2. ★stomp のほうは C 級ではない

レビューはこの項目を C(細部)に分類していたが、**stomp.js のぶんは B 級である**。

CDN が落ちる・ブロックされる・企業や学校のネットワークで弾かれると、
WebSocket クライアントが存在しないまま盤面が開く。購読が張れないので配信が届かず、
**画面には「接続中...」以外に何も出ない**。使う人には原因が分からない。
通話しながら遊ぶ前提では、片方だけがこの状態になると「相手の画面が止まっている」
という形で現れ、切り分けに時間を取られる。

完全性の側も実害がある。`integrity` が無い以上、CDN 側が差し替われば
**任意の JavaScript が対戦画面で走る**。その画面はデッキも部屋も見える立場にある。

### 1-3. なぜ SRI ではなく自前配信を選んだか

3案あった。

| | SRI を付ける | SRI + ローカルフォールバック | **自前配信** |
|---|---|---|---|
| 改竄 | 防げる | 防げる | ★起こりえない |
| 可用性 | ★**悪化する**(ハッシュ不一致でも読まなくなる) | 保てる | ★依存が無い |
| 第三者へのリクエスト | 残る | 残る | ★消える |
| 容量 | 0 | +253KB | +253KB |
| 仕組みの数 | 1 | ★2(検知コード + ファイル) | 1 |

**フォールバック案は結局ローカルにもファイルを置く**。容量が同じなら、
検知コードという仕組みを1つ増やす理由が無い。したがって自前配信を選んだ。

★盤面はもともと CDN のキャッシュ共有の恩恵をほとんど受けていない。
25 で画像を捨てて以降、見た目の主は独自 CSS(`battle.css`)であり、
Bootstrap が担っているのはユーティリティクラスだけである。

★デッキメーカーは 39 の時点で「Bootstrap を読み込まない」と決めてある
(`manual-deck-maker.html` の head のコメント)。41 でもその判断は変えていない。

### 1-4. ファイル名にバージョンを入れた

`bootstrap-5.3.3.min.css` / `stomp-7.0.0.umd.min.js` としてある。

CDN をやめた以上、**更新は手動になる**。名前に版が入っていないと、
数か月後にディスクを見ても「今どれを配っているのか」が分からない。
`battle.css(v=41)` のようなクエリ方式にしなかったのは、こちらは
**自分たちが書き換えるファイルではない**からである。中身が変わるときは必ず版が変わる。

**取得手順(更新するとき)**

```
npm pack bootstrap@<version>
npm pack @stomp/stompjs@<version>
tar xzf ... で package/dist/css/bootstrap.min.css と package/bundles/stomp.umd.min.js を取り出す
static/vendor/ へ版つきの名前で置き、テンプレートの参照を書き換える
```

★npm から取ったファイルが CDN のものと同一であることは、SRI ハッシュで確認した
(`sha384-QWTKZyjpPEjISv5WaRU9OFeRpok6YctnYmDr5pNlyT2bRjXh0JMhjY6hW+ALEwIH` が
Bootstrap 5.3.3 の公開値と一致する)。

### 1-5. 検証は「結線」を測る

見た目ではなくファイルの対応を測る(項目3つ)。

1. テンプレートに `cdn.jsdelivr.net` が1つも残っていないこと
2. ★テンプレートが書いている `@{/vendor/...}` が**すべて実ファイルに当たる**こと
3. ★stomp を読んでいるのが `battle.html` と `manual-battle.html` の2枚**ちょうど**であること

2 が本命である。名前を打ち間違えても Thymeleaf は黙って 404 を返すだけで、
Bootstrap なら「なぜか崩れている」、stomp なら「なぜか動かない」にしかならない。
**わざと `stomp-7.0.0.umd.js` と打ち間違えて、項目2が落ちることを確認した。**

### 1-6. ★ハーネスでは今も読み込まない(意図的)

`build_harness.py` は 41 以前と同じく `<link>` / `<script>` を落とす。
自前配信になったので技術的には読めるようになったが、**読ませていない**。

ハーネスの見た目の基準は「Bootstrap 無し + 31 の黒背景スタブ」で確立しており、
488項目がその上で通っている。**配信方法を変えたバッチで基準まで動かすと、
落ちた項目が「配信の失敗」なのか「基準の変化」なのか切り分けられなくなる。**

★ハーネスのファイルサーバ(`verify.js`)は `/css/` と `/js/` しか配っていない。
読ませたくなったらルートを足すこと。**積み残しとして 6章に書いた。**

## 2. 右クリックの受け皿(レビュー C-4)

### 2-1. 何が問題だったか

22 1-7 で右クリックを操作に割り当てて以来、盤面の右クリックは
**アプリの操作**である(拡大・ウェポン・カードメニュー)。個々の要素は
それぞれ `preventDefault()` しているが、**要素と要素の隙間には誰も居ない**。
そこで押すとブラウザのメニューが出て盤面を覆う。手が滑っただけで
「アプリの外」が顔を出す。

### 2-2. ★★「全部止める」にしなかった

`document` 全体で `preventDefault()` すれば1行で済む。**そうしなかった。**

止めてよいのは「右クリックが操作である場所」だけで、次の3つは既定の動作を残す。

| 例外 | 理由 |
|---|---|
| 入力欄(`input` / `textarea` / `select` / `contenteditable`) | 貼り付け・元に戻すはブラウザのメニューの仕事である |
| **ログ**(`#log-box`) | 対戦の記録は読んで**コピーする**ものである(設計書 5-5) |
| 開いているモーダルの中 | 説明文・確認文を選んで写せる必要がある |

★1行で書けるほうが短いが、**そのぶん奪うものが見えなくなる**。
奪う範囲を明示的に書いておけば、後から範囲を直せる。

### 2-3. ★網は「下」に張る

捕捉フェーズ(capture)ではなく、`document` のバブルで受ける。
そして最初に `e.defaultPrevented` を見る。

捕捉フェーズにすると、**既存の10箇所の右クリック操作を全部この1本が横取りする**。
個々のハンドラが先に走り、そこで止まっていればここは何もしない、という順序が正しい。
「発火点を増やさない」(裁定68)とは逆向きに見えるが、こちらは
**発火点ではなく受け皿**であり、既存の経路を1つも変えていない。

### 2-4. 検証は「止まること」と「止まらないこと」を対で測る

```
★★★盤面の隙間で右クリックしてもブラウザのメニューが出ない   → prevented === true
★★★ログの右クリックは奪わない                              → prevented === false
★★入力欄の右クリックは奪わない                              → prevented === false
★★開いているモーダルの中では右クリックを奪わない             → prevented === false
```

**片方だけ測ると、`document` 全体を止める1行に書き換えても検証は通ってしまう。**
実際に「例外の3行を消す」壊し方で、後半3項目が落ちることを確認した。
受け皿そのものを外す壊し方では、先頭の項目が落ちる。

観測は `window` のバブルに置いたリスナで行う(`document` のハンドラより後に走る)。
クリックは実マウス(`page.mouse.click(..., { button: 'right' })`)である。

## 3. ★★★面の質感 — 32c の不具合と、その修正

### 3-1. 何を見つけたか

デッキメーカーのタイルを盤面と同じ質感にする作業の検証を書いていて、
**光沢の強さが場所ごとに変わっていない**ことに気づいた。盤面を測ると、こうだった。

| 要素 | 設定されている `--mc-sheen` | **実際に描かれた光沢** |
|---|---|---|
| `.mcard`(外枠) | 0.14 | 0.14 |
| `.mcard-inner`(胴) | 0.05 | ★**0.14** |
| `.mcard-head`(頭) | 0.12 | ★**0.14** |
| `.mcard-foot`(足) | 0.07 | ★**0.14** |

32c の設計解説 2-1 はこう書いていた。

> `--mc-gloss` の中の `var(--mc-sheen)` は、**`--mc-gloss` が実際のプロパティへ
> 代入される要素**の値で解決される。だから `--mc-gloss` は継承させたまま、
> `--mc-sheen` だけを子で上書きすれば、同じ角度・同じ形の光が強さだけ変わって走る。

**これは誤りである。**

### 3-2. なぜ効かないのか

カスタムプロパティの値に含まれる `var()` は、**そのカスタムプロパティを宣言した要素**の
計算値時点で置き換えられる。子が継承するのは**置換済みのトークン列**であり、
子が `--mc-sheen` を上書きしても、既に埋まった数値はもう変わらない。

32c では `--mc-gloss` を `.mcard, .mcard-backface, .mcard-frame` で宣言していた。
したがって `.mcard` の 0.14 で焼き付き、`.mcard-inner` / `-head` / `-foot` が
自分の値を宣言しても、光沢には届いていなかった。

**32c が「胴は読む面である。光沢は 0.05 まで落とし、文字の下に模様を作らない」と
書いた意図は、一度も実現していない。** 32c 以降の盤面は、読む面に
意図の約3倍の光沢が乗った状態だった。

### 3-3. 直し方 — 宣言する場所を、使う要素すべてにする

形(角度・止まり位置)の記述は 1箇所のままで、**宣言だけを各要素に降ろす**。

```css
.mcard, .mcard-inner, .mcard-head, .mcard-foot, .mcard-backface, .mcard-frame,
.tile, .tile-inner, .t-head, .t-foot,
.bigcard, .bc-inner, .bc-head, .bc-foot {
    --mc-sheen: 0.14;                        /* 既定。自分の規則で上書きしたほうが勝つ */
    --mc-gloss: linear-gradient(115deg, ... var(--mc-sheen) ...);
}
```

こうすると `var(--mc-sheen)` はその要素自身の値で解決される。
**32c の狙い(形は1箇所・強さだけ場所ごと)は、この形で初めて成立する。**

★一覧から漏れた要素は光沢が**出なくなる**(`var` が未定義になる)。
新しく `var(--mc-gloss)` を使うときは必ずここへ足すこと。検証が番人である(3-5)。

### 3-4. ★デッキメーカーのクラス名を battle.css に書いた

上の一覧には `.tile` / `.bigcard` 系も入っている。他画面のクラス名が
`battle.css` に並ぶのは結合に見えるが、次の理由でこちらを選んだ。

- 裁定107「カードの面とクロームは別のパレットである。**面は盤面のフェイスに従う**」。
- 39 は同じ判断を色でやっている。デッキメーカーの独自パレットを捨て、
  色の正を `battle.css` の `:root` に置いた(裁定60)。
- **代わりに形を2箇所へ書けば、「片方だけ直される日」が確実に来る。**
  名前を1箇所に集めるほうが安い。

★`:root` に置く案は採れない。それをやると 3-2 の不具合がそのまま再発する
(継承の時点で強さが焼き付く)。**この点は検証で固定した。**

### 3-5. 検証(6項目)

| 項目 | 何を守るか |
|---|---|
| ★★★光沢の強さは場所ごとに実際に変わる(0.14 / 0.05 / 0.12 / 0.07) | 3-2 の不具合そのもの |
| ★★胴の光沢が面の中でいちばん弱い | 値を調整するときに**関係**を壊さない |
| ★★★光沢の形は battle.css から来ており、`:root` には置かれていない | 3-4 の再発防止 |
| ★★★デッキメーカーのタイルが盤面と同じ光沢を使っている | 裁定107 の結線 |
| ★★★光沢は場所ごとに強さだけが変わる(デッキメーカー側) | 仕組みが両画面で生きている |
| ★★デッキメーカーの質感も transform / filter を使わない | 32c 2-2 のデッキメーカー版 |

**★★★1項目めは `--mc-sheen` の値そのものを測らない。**
それは「上書きしたか」しか見ておらず、**まさに今回の不具合を素通りする**
(上書きはされていた。効いていなかっただけである)。
測るのは**解決後の背景に現れた数値**——結果のほうである。

「光沢の宣言を `:root` に戻す」壊し方で、4項目が落ちることを確認した。

### 3-6. デッキメーカーの面を盤面と同じ組み立てにした

`.tile` / `.tile-inner` / `.t-head` / `.t-type` / `.t-foot` / `.t-cost` と、
詳細ペインの `.bigcard` / `.bc-inner` / `.bc-head` / `.bc-type` / `.bc-foot` / `.bc-cost`
を、盤面の `.mcard-*` と同じ層構成にした。

- 層の順は「斜めの光沢 → 上端の縁ハイライト → 文明色の深み」(盤面と同じ)
- 文明色の止まり位置も盤面の値へ揃えた(78/6・55/30 → 88/16・58/26・70/50)
- コストの宝石は 3層 radial + `text-shadow`(盤面と同じ)
- 型の帯は「上端の明かり + 下向きの陰」の溝(盤面と同じ)

**★`.bigcard` の `inset` の縁は背景の層へ移した。**
32c が「縁のハイライトは background の層で描く」と決めている
(`box-shadow` をアニメーションする明滅と混ざるため)。

**★★質感に `filter` と `transform` は使わない。**
32c の理由(タップの遷移に巻き込まれる)に加え、デッキメーカーには理由がもう1つある。
`.tile` は `hl-dim` で `filter` を、`:hover` / `:active` で `transform` を既に使っている。
質感が同じものを使うと、**40 追補のカーブ強調を押すたびに質感が巻き添えで変わる**。

**★文明色の変数名は `--c` のまま**(盤面は `--mc`)。
裁定111「規約は共有し、コードは複製する」の系列であり、
名前を合わせても共有できるコードは無い。

- **★ハーネスが vendor を読んでいない**(1-6)。読ませるなら `verify.js` の

- **★Bootstrap / stomp の更新は手動になった**(1-4)。取得手順は 1-4 に書いた。
  依存の版を上げるときは、SRI ハッシュで CDN 版との同一性を確認すること。
- **★32c の設計解説 2-1 は誤った説明のまま残っている。** 本書 3-2 が訂正である。
  `notes/batch32c-design-notes.md` を読む人が先に誤解しないよう、
  ハンドオフの「既知の落とし穴」へ入れた。
- **名前付きスロット**(40 Q2 = b で採用決定・41 で再度見送り)は積み残しのまま。
- **部屋の永続化**(レビュー優先順位10)は保留。方式の検討結果は
  `batch41-persistence-design-options.md` にある(★Render 無料枠には
  ファイルの永続化が存在しないため、サーバ側の永続層は本番で何も守らない)。
- レビュー優先順位11(Pointer Events + 盤面スケーリング)は未着手。**これが最後の1つ。**
- C の残り: `user-select` の見直しは 41 では触っていない。
