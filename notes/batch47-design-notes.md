# Batch 47 設計解説 —— 「効果未実装」の印(裁定D2 の本体)

実施: 2026-08-19。`notes/ver11-migration-plan.md` の **P1 後半**である。

46b で通常モードのカードの正が `manual-cards.json`(235枚)になった。だが Ver1.1 の
カードのうち **64枚は効果が実装されていない**。46b までは「使えるのに何も起きない」を
避けるため、そういうカードをデッキ構築の入口で弾いていた。それは裏を返せば
**Ver1.1 の全カードでデッキが組めない**ということでもある。

裁定D2 が選んだ道は「入れられるようにして、印を出す」である。本バッチはその実装であり、
**気づきにくさの原因は「入れられること」ではなく「黙って不発になること」だ**、という
線の引き直しである。

出発点は 46b の **193件全緑 / verify 520項目**、終着点は **206件全緑 / verify 527項目**である。

## 1. ★調査で分かった、計画の前提のずれ

実装に入る前に 235枚と現行コードを突き合わせた。2つ、計画の前提が実物とずれていた。

### 1-1. 「参照あり44枚」は数え方が甘かった

46a が作った `tools/report_effects.py` は、実装の3段(裁定164)をこう数えていた。

```
登録あり  … CardEffectRegistry の9つの表にIDがある
参照あり  … 登録は無いが、どこかの Java にIDが書かれている
未実装    … カードIDがコードのどこにも現れない
```

**「どこかの Java」に `DeckFactory` が含まれていた。** `DeckFactory` はプリセットデッキの
中身であり、151行にわたってカードIDが並ぶ。これらは実装ではなく**デッキの内容**である。

そのせいで **5枚が実装済みに化けていた**。うち4枚はキーワードだけのカードで実害は無いが、
1枚は本物だった ——

> **《百獣の王 ベヒーモス》(QTE-M-EARTH-7)**
> Ver0.4 ではバニラ(効果なし)。**Ver1.1 で【召喚時】他のミニオン全てに7ダメージ。
> 体力の多いリーダーに3ダメージ、が付いた。** 実装は無い。
> そして**土のプリセットデッキに1枚入っている。**

`DeckFactory.java` のコメントは今も `// 百獣の王ベヒーモス 9/10/10 バニラ` と書いてある。
**データ側の変更にコードが追いついていなかった**わけで、46b の裁定175 と同じ形である。
移行バッチは既存の不整合を掘り出す。

★このカードは 47 で実装しない(効果の実装は P2 の仕事)。代わりに**印が付く**。
`EffectImplementationTest.プリセットに入っている未実装カードに印が付く` が
「印が絵に描いた餅ではない」ことの実地確認になっている。

### 1-2. 【常在】は1つの仕組みではない

計画は「【常在】フレーム(`PersistentAura` の拡張)」と書いていた。20箇所を全部読んだところ、
**【常在】は4つの別々の形の総称**だった。

| 形 | 例 | エンジンの現状 |
|---|---|---|
| 評価するたびに場を見る | 光霊・テングスン、アルキンティス、詠唱の風詠士 | **既にこの形で動いている**(設計判断4) |
| 場に居る間ずっと反応する誘発 | ロロイヨ伯爵、英皇アントマルエル、妖ノ長・ストク | トリガーの拡張 |
| ターン開始時の自壊 | ハク霊、コク霊 | `ON_TURN_START` が無い |
| 進化専用 | 6枚 | P3(54〜55) |

**★`PersistentAura` は方向が違う。** あれは「次にスペルを唱えるまで」「次の相手のターン終了時まで」
のように**期限を型として持つ**器である。【常在】に期限は無く、条件は「場に居ること」だから、
状態として保存してはいけない —— 評価のたびに場を見る、という既存のやり方がそのまま答えになる。
**保存した瞬間、そのカードが場を離れたときに消し忘れる。**

そして**足りない `TriggerType` は実質3つだけ**だった(未実装50枚を全部読んで数えた)。
`ON_TURN_START` / 盤面全体のミニオン登場 / 場以外から墓地へ置かれたとき、である。

つまり計画が「エンジン語彙の大工事」と見積もっていた仕事の中身は、
**器を1つ作ることではなく、トリガーを3つ足すこと**だった。6章へ続く。

## 2. 「実装済み」をどう判定するか(裁定164 の本丸)

### 2-1. 問題

効果の実装には置き場所が2つある。

1. **登録あり** —— `CardEffectRegistry` の9つの表のどれかに載っている
2. **宣言あり(旧称: 参照あり)** —— 表ではなく**ルール側の判定点に直接書かれている**

2 が厄介である。たとえば《平和の結界》の「Attack3以上のミニオンは攻撃できない」は
`RuleGuards.minionAttackDenial` の中の `if` 文であり、どの表にも載っていない。
**Java には「どこかの if 文にこのIDが書いてある」ことを知る手段が無い。**

素朴に `CardEffectRegistry` の表だけを見て印を出すと、
**実際には正しく動いている38枚に「効果未実装」と書いてしまう。** 嘘である。

### 2-2. 採った形 —— 判定点を持つクラスが自分で名乗る

マスター裁定により、**ルール側の各クラスが `IMPLEMENTED_CARDS` を公開する**形にした。

```java
// RuleGuards
private static final String PEACE_BARRIER = "QTE-M-LIGHT-23";   // 平和の結界
...
public static final Set<String> IMPLEMENTED_CARDS = Set.of(
        PEACE_BARRIER, GLEAM_SHIELD, GENESIS_IRIS, ABSOLUTE_GAIA, ZODIAC,
        MICHAEL, HOLY_PROTECTOR_AURA, JUSTICE_SHIELD, JUDGEMENT_ANGEL,
        ORDER_ENFORCER, TEMPLE_KNIGHT);
```

宣言しているのは6クラス、合わせて **47枚**である。

| クラス | 何を実装しているか | 枚数 |
|---|---|---|
| `RuleGuards` | できる／できないの判定(攻撃・破壊・ドロー・使用の禁止) | 11 |
| `StatCalculator` | 動的な数値(コスト・攻撃力・攻撃回数) | 21 |
| `GameService` | リーダーの攻撃時に発動するウェポン + リーダー2枚 | 9 |
| `GameActions` | 置換効果(肩代わり)・踏み倒しの禁止・場を離れたとき | 3 |
| `PlayerState` | ゾーン上限(大地の巨頭) | 1 |
| `CardEffectRegistry` | 表に載せず、このクラスのコードに直接書いた4枚 | 4 |

**★中身はコード中の定数そのものである。** 別の場所にIDを書き写していない。

### 2-3. ★そのために定数化した(裁定130)

`StatCalculator` は `if ("QTE-M-WATER-5".equals(cardId))` のように**文字列リテラルを
メソッドの中に直接書いていた**。このまま `IMPLEMENTED_CARDS` を作ると、
同じIDが**判定に使う場所と宣言と2箇所**に書かれることになる。
同じ値が2箇所にあると、必ず片方だけが直される日が来る。

そこで **`StatCalculator` の21枚・`GameService` の7枚・`GameActions` の3枚・
`CardEffectRegistry` の4枚を定数へ引き上げた。** 判定も宣言も同じ定数を指すので、
**IDのリテラルはカード1枚につき1つだけ**になった。

★おまけとして、`StatCalculator` が読みやすくなった。以前は文明ごとのコメントを頼りに
マジックストリングを追う必要があった。

★機械置換をかけたので、**差分は1ファイルずつ目で読んだ**(裁定171)。
`StatCalculator` の `ZOMB_STRIKER`(QTE-M-DARK-16)だけは意味が違うので、
定数にはしたが `IMPLEMENTED_CARDS` には**入れていない** ——
群がる死霊王が「墓地にある《ゾンストライカー》の数」を読むために名前を知っているだけで、
`StatCalculator` がゾンストライカーの挙動を実装しているわけではない。

### 2-4. `CardEffectRegistry.isRegistered()` は実行時の表を見る

```java
public boolean isRegistered(String cardId) {
    return spellEffects.containsKey(cardId) || triggers.containsKey(cardId) || ...;
}
```

**ソースを走査するのではなく、組み上がった表そのものを見る**(裁定170)。
`registerXxx()` が直接 `put` しようが `register(...)` や `watchOwnMinionDestroyed(...)`
のようなヘルパを通そうが、結果は同じ表に入る。

★これは机上の話ではない。`tools/report_effects.py` はソースを走査していたため、
**ヘルパ経由で登録された《不滅のネクロマンサー》(QTE-M-DARK-5)を数え落としていた。**
Java 側が表を直接見る形にしてあれば、この種の数え落としは起こりえない。

### 2-5. `EffectImplementation` —— 答える場所は1つ

```java
public boolean isImplemented(CardMaster card) {
    if (!CardTextKeywords.hasEffectSentence(card.text())) {
        return true;                       // キーワードだけのカードは印を付けない
    }
    return effects.isRegistered(card.id()) || RULE_SIDE.contains(card.id());
}
```

`RULE_SIDE` は6クラスの宣言を集めただけで、**ここに書き写していない**。

### 2-6. ★この判定が答えられないこと(裁定165)

見ているのは**カードID単位**である。したがって
**「効果文が3つあってそのうち1つだけ未実装」は検出できない。**
【召喚時】が登録されていれば、同じカードの【常在】が未実装でも「実装済み」と答える。
部分実装の追跡は P2 の各文明バッチが設計解説で受け持つ。

## 3. 「効果の文があるか」の規則

キーワードしか書かれていないカードは、エンジンにカードIDが1つも現れないが、
**キーワードの仕組みだけで正しく動く。** そこに印を付けたら嘘になる。

規則は `CardTextKeywords.hasEffectSentence(text)` に置いた。テキストの読み方の規則は
1箇所に集める(裁定158 の延長)。中身は「【…】を取り除いて、句読点と空白しか残らないか」だが、
実データを見ると2つ、素朴な規則では足りない点があった。

### 3-1. ★丸括弧は「ふつう注釈、ただし【特殊召喚】だけは条件」

Ver1.1 のテキストには、キーワードの直後に丸括弧が付くものが34箇所ある。

| 直前のトークン | 件数 | 括弧の中身は |
|---|---|---|
| 威圧 / 潜伏 / 還元 | 4 | **注釈**(キーワードの意味の言い換え) |
| 特殊召喚 | 12 | **発動条件そのもの** |
| 進化 | 18 | **素材の指定**(P3) |

```
【突進】【威圧】(相手の攻撃対象にならない)        ← 括弧を落とさないと「効果あり」に見える
【特殊召喚】(手札が7枚以上なら手札を3枚捨てて出せる) ← 落とすと「効果なし」に見える
```

**注釈を落とさないと**《ホーリー・ガーディアン》《ディープシー・シャーク》
《不動の岩石竜》に印が付く —— この3枚は正しく動くのに嘘をつくことになる。
**【特殊召喚】の括弧を落とすと**、未実装の特殊召喚が印なしで黙って不発になる。

そこで規則を「**キーワード表記の直後の丸括弧は落とす。ただし【特殊召喚】は例外**」とした。
【進化】は `Keyword` に載っていないので、そもそも「キーワード表記の直後」に当たらず、
何もしなくても残る。**例外は1つだけで済んでいる。**

`CardTextKeywordsTest.キーワードの注釈の括弧は効果の文として数えない` が両方向を測る。

### 3-2. 「効果なし」

《フレア・ポーン》(QTE-M-FIRE-2)の本文は**そのまま「効果なし」**である。
これを文として数えると印が付く。しかも火のプリセットに3枚入っている。

規則に1行足して空文と同義に扱った。**★カードIDではなく表記を見ている**ので、
同じ書き方のカードが増えても自動的に効く。

### 3-3. ★同じ規則が Python にもある(意図した重複)

`tools/report_effects.py` にも同じ判定がある。裁定163 が戒めた形だが、次の理由で残した。

- **印(=遊びに影響する判定)の正は Java ただ1つ**である。ツールは印を出さない。
- ツールの判定が左右するのは**進捗の数字だけ**である(裁定165)。

スクリプトの冒頭にその旨を明記し、「数字がずれたら正である Java 側に合わせること」と書いた。
今日の時点では両者とも **効果文あり215枚 / 未実装64枚**で一致している。

## 4. デッキ構築 —— スペルの門を開けた

`DeckValidator.requireImplemented` から**スペルの効果登録の検査を撤廃した**。
これで未実装スペル13枚がデッキに入る。

★**進化ミニオン18枚は今も弾く**(裁定166)。線の引き方は 46b と同じである ——
効果が未実装のミニオンは「出せるが何も起きない」で済むが、**進化は場に出す手段そのものが無い**。
印を見てもできることが1つも無いので、印の趣旨から外れる。

★**文明の検査は残した。** 全6文明が実装済みなので現在は誰も弾かないが、
文明なしの《ピュア・エレメント》はデッキに入るカードではないため、ここで止まる。
`DeckValidatorTest.文明なしのカードはデッキに入れられない` が番人である。

★`DeckValidator` から `CardEffectRegistry` への依存が無くなったので、フィールドごと外した。

## 5. 印の出し方

### 5-1. ビュー

`CardView`(手札・禁忌)と `MinionView`(場)に `effectUnimplemented` を足した。
**判定はサーバで済ませて真偽値だけを送る。** クライアントに「実装済みか」の規則を持たせない ——
持った瞬間、同じ規則が Java とブラウザの2箇所に置かれる(裁定163)。

### 5-2. ★面には手を入れない(裁定141)

印は既存の**バッジ**(`.auto-badges` / `.auto-badge`)に載せた。
フェイス(`.mcard-*`)には transform も filter も擬似要素も足していない。
バッジは面の**上に重ねる別要素**である。

バッジの作り方が3箇所(手札・禁忌・場)に散らないよう、
`newBadgeBox()` / `addBadge()` / `attachBadges()` の3つにまとめた。
これで **【★特殊召喚可】と【⚠効果未実装】が同時に出る**(以前は入れ物の作り方が
「特殊召喚可のときだけ」だったので、素直に足すと片方しか出なかった)。

### 5-3. 色

`.auto-badge-unimplemented { color: #ff9b9b; }`

他のバッジ(凍結・タップ・能力・特殊召喚可)はどれも「**今これができる**」を伝える。
印だけは「**書いてあるとおりには動かない**」という否の知らせなので、否の色にした。
**★新しい色を作っていない**(裁定32) —— `#ff9b9b` は `.manual-fx-lp-down`
(体力が減る演出)が既に使っている色である。

★検証もこの事実を使う。**色の値を検証スクリプトに書き写さず**、
`.manual-fx-lp-down` を貼った探り用の要素と印の色を、同じ CSS から読んで突き合わせる(裁定131)。

### 5-4. ★今回出していない場所(マスター裁定)

- **右クリック拡大** … 出さない。テキストの読み口であり、印は面の側で足りる。
- **デッキメーカー** … 出さない。あの画面は手動モードと共用で、手動モードでは効果を
  人が解決するため「未実装」は意味を持たない。出すなら「通常モードでは動かない」という
  限定つきの文言が要り、判定もサーバから配る口を新設することになる。必要になったら別バッチで。
- **リーダー選択画面** … 出さない。未実装リーダーは6人いるが、起動能力のボタンが出ないだけである。

## 6. ★【常在】と TriggerType を 47 から外した(マスター裁定)

1-2 に書いたとおり、「【常在】フレーム」の実体はほぼ「`TriggerType` を3つ足すこと」だった。
そして**その3つを使うカードは1枚も実装されていない**(すべて P2 の担当である)。

**使い手のいない器は設計ではない。** 裁定167(一度も実行されていないテストは検証ではない)の
親戚であり、器だけ先に作ると「そのトリガーが本当にその形でよいか」を確かめる材料が無いまま
形が固まる。P2 の各文明バッチで、実際のカードと一緒に作るほうが確実である。

したがって **47 は「印」1本**とし、`notes/ver11-migration-plan.md` の 2章(フェーズ計画)も
それに合わせて書き換えた。P2 の各バッチが、自分の文明に要るトリガーを自分で足す。

★引き継ぎのために、47 の調査で分かった **P2 で要る3つのトリガー**をここに残す。

| 足すもの | 要るカード |
|---|---|
| `ON_TURN_START`(ターンのはじめ) | ハク霊 / コク霊(風) |
| 盤面全体のミニオン登場(自他を問わない) | ロロイヨ伯爵(水) / 英皇アントマルエル(光)。★裁定156(2) が「自分の」と書いていない誘発は両者を見る、と定めている |
| 場以外から自分の墓地に置かれたとき | カムバックキーパー(闇) |

## 7. 数え方の是正と、新しい番人

### 7-1. ツールが直したこと

| 症状 | 直したこと |
|---|---|
| `DeckFactory` を実装として数えていた(1-1) | 走査から外した。プリセットのIDの実在検査は `check_all.py` 項目3 と `DeckValidatorTest` が担う |
| コメント中のカード名・IDを実装として数えていた | ソースからコメントを取り除いてから走査する |
| ヘルパ経由の登録(`watchOwnMinionDestroyed`)を数え落としていた | ヘルパの一覧を持たせた |
| 「参照あり」という呼び名 | 「宣言あり」に改めた。実態が変わったので名前も変えた |

数字は **登録113 / 宣言38 / 未実装64**(旧: 登録112 / 参照44 / 未実装63)になった。
★増えた「未実装64」は**悪化ではない** —— 数え間違えていたものが正しくなっただけである。

### 7-2. ★宣言の過不足を両方向から見る

`check_declarations()` を足した。これが 47 で追加した番人の本体である。

1. **足し忘れ** … ルール側のファイルにIDが書いてあるのに、登録にも**どのクラスの**宣言にも無い
2. **宣言が腐った** … 宣言にあるのに、**そのファイルの宣言以外の場所**で1度も使われていない
3. **置き場所が想定外** … ルール側でもデッキ内容でもないファイルにカードIDが書かれている

★**1 は全クラスの宣言の和と比べ、2 はファイルごとに見る。**
1枚のカードの実装が2クラスに分かれることが実際にある ——
