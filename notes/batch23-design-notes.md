## 1. 設計根拠★

### 1-1. ★★開始シーケンス中の棄却を「1箇所」に置けた理由(7-1)

設計書 7-1 は止める操作を10個(move / tap / flip / stat / label / draw / shuffle /
evolve / undo / redo)列挙している。素直に読むと10箇所に判定を書くことになるが、
**実際に書いたのは2箇所である。**

盤面を変える操作はすべて `ManualOperationService.apply` を通る。21a が
「1回の操作の型は `apply` が握る」と決めたときの理由(履歴への push を書き忘れると
Undo するまで症状が出ない)がそのまま効いており、**同じ絞り込みが棄却にも使える**。

```java
public void apply(ManualRoom room, ManualActor actor, Function<...> mutation) {
    ManualPermissions.require(ManualPermissions.denyDuringStart(room));   // ← ここ1行
    ...
}
```

Undo / Redo だけは `apply` を通らない(履歴そのものを動かすため)ので、
`undo` / `redo` に個別に置いた。**合計2箇所である。**

★これは偶然ではない。**「1回の操作」という概念に器を与えておくと、後から
「全操作に共通の条件」を足すのが1行で済む。** 逆に、操作ごとに判定を書き足す形だと、
次に操作を1つ足した人が必ず書き忘れる。17b が `push` について学んだことと同じ形である。

★この構造は「止めないもの」(7-2)にもそのまま効いている。
自由メモ・勝敗宣言は `applyDirect` を通り、リセット・退室・席の移動は `execute` を通る。
**どれも `apply` を通らないので、何もしなくても止まらない。**
経路が意味ごとに分かれていたおかげで、「止める/止めない」の線が既に引かれていた。

### 1-2. ★★開始フェーズを `ManualGameState` に入れないという判断の実際の効き方(2-6)

設計書 2-6 は「Undo で巻き戻ってはならないから `ManualRoom` に置く」と書いている。
実装してみると、この判断は**もう1つ別の問題も同時に解いていた。**

`ManualStartService` は盤面を大きく書き換える(clearAll → シャッフル → ドロー)。
もしフェーズが `ManualGameState` にあれば、開始処理も `apply` を通したくなる。
しかし `apply` は今や `denyDuringStart` を呼ぶので、**開始処理が自分自身に弾かれる。**
フェーズを部屋側に置いたことで、開始処理は `applyDirect`(履歴に積まない経路)を素直に
通れる。

★**「巻き戻ってはならないもの」と「巻き戻す仕組みを使わないもの」は同じ集合である。**
ログを `ManualRoom` に置いた 17b 2-5 の判断が、そのまま3つ目の住人を迎えた形になった。

### 1-3. ★★「作成者」を occupantId ではなく席で持つ(2-4)

マスター指示は「部屋の作成者に表示される」である。素直に occupantId で持つと、
**作成者が席を立った / 切断して猶予が切れた部屋は、永久に開始できなくなる。**

```java
@Setter private ManualSeatId creatorSeat;   // ★席で持つ
```

席で持てば、座り直した人が権利を引き継ぐ。これは 21a が共有ゾーンの所有
(`placedBySeat`)を席基準にしたのと**同じ判断**であり、そのときの理由
(「切断して入り直した人が自分の置いたカードを動かせなくなる」)がそのまま当てはまる。

★さらにフォールバックを1つ置いた。**作成者席が空席なら、どちらの席でも押せる。**

```java
if (creator == null || room.occupantOfSeat(creator).isEmpty()) {
    return null;   // 押せる人が居ない画面を作らない
}
```

権限を厳密にするほど「誰も押せない状態」が生まれやすくなる。
7-2 のリセットと同じ発想で、**行き止まりを構造的に作らない**ほうを優先した。

### 1-4. ★初期化処理を2つ作らなかった(6-3)

設計書 6-3 は「新しい初期化処理を書かないこと。既存の reset を呼ぶ」と書いている。
実装では **`resetRoom` を呼ぶのではなく、`resetRoom` が使っている `applyImport` を
手札枚数つきで呼ぶ**形にした。

```java
private void applyImport(ManualSeat seat, ManualDeckImport imported)            // 従来(4枚)
private void applyImport(ManualSeat seat, ManualDeckImport imported, int handSize) // ★追加
public  int  dealForStart(ManualRoom room, ManualSeatId seatId, int handSize)      // ★開始用の入口
```

★理由は 6-3 の**目的**にある。あれが避けたいのは「2種類の初期化が存在すると、
どちらを通ったかで盤面の残り方が変わる」ことであり、**同じ1本を通ることが本質**である。
`resetRoom` を先に呼ぶと、直後の配り直しで同じ席をもう一度 `clearAll` することになり、
ログに「リセットして引き直した」という**起きていない操作**が1行増える。

デッキ読込・リセット・開始シーケンスの3つとも `applyImport` の1本を通っており、
違うのは**引く枚数だけ**である。それは分岐ではなく引数で表した
(22 の `createLeaderTile(seat, { withWeapon })` と同じ形)。

### 1-5. ★ピュア・エレメントは「設定が無くても起動する」ほうを選んだ(5-2)

設定の検証には3つの選び方があった。

| 案 | 判断 |
|---|---|
| 起動時に検証して**落とす** | ★退けた。一人回しでは無くても困らない機能であり、設定漏れで<b>アプリ全体が上がらなくなる</b>ほうが害が大きい |
| 配布のたびに検証する | ★退けた。毎回同じ結論を出す計算であり、しかも失敗が対戦の途中で初めて分かる |
| **起動時に検証し、警告して無効化(採用)** | 問題は起動ログで分かり、ゲームは進む。ログに「配布を省略した」と残る |

```java
} else if (cards.findOptionalById(configured).isEmpty()) {
    log.warn("qte.manual.pure-element-id = {} は手動モードの台帳に存在しない。..." , configured);
    this.pureElementId = null;
}
```

★`ManualCardRepository.findById` は存在しないIDで例外を投げる。
起動を落としたくないので、**Optional を返す入口を1つ足した**(`findOptionalById`)。
「見つからないことを呼び出し側が扱える形」が要るなら、例外を握りつぶすのではなく
そういう入口を用意するのが素直である(`findByImageId` が既に同じ形をしている)。

★**ビューにも `pureElement` を載せてある。** 設定の有無を判断する場所を2つ作らないため、
画面は `ManualStartService.isPureElementAvailable()` の結果を受け取るだけにした。

### 1-5b. ★★ピュア・エレメントは表向きで渡す(マスター裁定 2026-08-06・設計書 5-3 の訂正)

設計書 5-3 と総合ルール 2-5 の4は「後攻プレイヤーに【ピュア・エレメント】を
**裏向きで**渡す」と定めている。初版はそのとおりに実装したが、
**マスターの裁定によりこれを表向きに改めた。**

> 総合ルール 2-5 の4の文言には語弊がある。手札のカードは自分だけ見るのだから、
> ほかのカードと同じ扱いにすること。

★この裁定は正しい。**手札は持ち主しか見ないゾーンである。**
対戦部屋では相手にカードオブジェクトがそもそも届かない(21 設計書 3-3)し、
全公開部屋は元から全部見えている。**裏向きにしても情報が1ビットも変わらない。**

実物のカードゲームで「裏向きで渡す」のは<b>相手に見せないため</b>であって、
受け取った本人が中身を見られない状態にするためではない。総合ルールは物理的な所作を
そのまま書いており、その所作が保証していた性質(相手に見えない)は、
このアプリでは**ゾーンの公開範囲がすでに保証している**。
所作をそのまま写すと、目的が二重に達成される代わりに**副作用だけが残る。**

副作用は実際に現れていた。手札行では裏向きのカードが
**灰色の箱に「(裏向き)」と書かれただけのタイル**として描かれる(`createHandCard`)。
つまり**持ち主にも何のカードか分からない**という、
ルールが意図していない不利益だけが発生していた。

★**設計上はむしろ単純になった。** 5-3 は
「`HAND` の表向き正規化(`FACE_UP_ON_ARRIVAL`)を通さない経路で置くこと」という
注意を要求していたが、表向きでよいならその衝突自体が消える。
`ManualCardInstance.of()` は `faceDown = false` で個体を作るので、
ゾーンへ素直に追加するだけで済む。**避けるべき特別扱いが1つ減った。**

★**教訓**: 総合ルールの記述が「物理的な所作」である場合、
その所作が**何を保証するために存在するのか**を先に取り出すこと。
保証したい性質が別の仕組み(ここではゾーンの公開範囲)で既に成立しているなら、
所作を写すのは害にしかならない。21 設計書 3-4 が
「手札の `faceDown` に『相手へ公開』の意味は無い」と書いていたのは、
まさにこの区別のことだった。**その原則を、配布処理にも適用し切れていなかった。**

### 1-6. ★マリガンをサーバの1操作にした効果(4-4)

設計書 4-4 は3つの理由(順序・ログ・検証)を挙げている。実装して分かったのは、
**3つ目(設計判断27)が最も効いている**ことである。

```java
int drew = gameService.drawCards(seat, back.size());   // ★引く枚数はサーバが決める
```

リクエストに「引く枚数」が無い。載せていないのではなく、**載せる場所が無い**。
クライアントが戻した枚数と引く枚数を食い違わせる経路が構造的に存在しない。
検証項目にも「`mulligan` に `count` / `drawCount` が載っていないこと」を入れてある
(「送られないこと」の検証。22 2章)。

★同じ理由で `/start-order` も席を受け取らない。押せる席はサーバが
`orderChooserSeat` で知っている。**受け取らなければ偽装の余地も生まれない**
(21c の `firstPlayer` が occupantId だけを受けたのと同じ判断)。

### 1-7. ★マリガンUIを専用オーバーレイにしたことで守れたもの(4-3)

22 のクリック規約は **左=見る / 右=動かす** である。マリガンは **左=選択** であり、
盤面の手札行でこれをやると「モードによって左クリックの意味が変わる画面」になる。

専用オーバーレイに閉じ込めると、**そこは別の画面であると見た目で分かる。**
21b が席選択を「盤面ページ内のゲート」にしたのと同じ考え方で、
**守りたい性質を分岐ではなく構造で表す。**

★**新しい選択操作は発明していない。**
- 選択の記法は既存の黄枠(`.manual-tile-selected` と同じ色)
- 拡大は右クリック(このオーバーレイ内のローカル規約。ヘルプと画面上部に明記)
- Ctrl+左の複数選択は**使わない**。この画面では選ぶこと自体が主目的であり、
  修飾キーを要求するほうが操作を増やす

★拡大の出し先には手当てが要った。右列の `#zoom-panel` は
バックドロップ(z-index 1950)の**下**にあり、オーバーレイが開いている間は見えない。
そのままだと「右クリックしても何も起きない」になる(22 1-5 の再発)。
**オーバーレイの中に拡大枠を置き、同時に `#zoom-panel` にも入れた**ので、
閉じた後は通常どおり右列に残る。

### 1-8. ★[ゲームを始める] を全公開部屋限定にしなかった(6-1 からの意図的な逸脱・要確認)

設計書 6-1 は「ボタンは**全公開部屋のみ表示**。対戦部屋では両者のデッキ読込で
自動的に開始モーダルが出る」と書いている。**実装では対戦部屋にもボタンを出した。**

理由は、6-1 のとおりに作るには次のどちらかが要るためである。

| 案 | 問題 |
|---|---|
| クライアントが条件を見て `start-begin` を自動送信する | 描画から状態変更を起こすことになる。resync・再接続・両者同時などで**二重送信の余地**が生まれ、しかも人間が押していない操作がログに載る |
| サーバがデッキ読込の瞬間に `ORDER_METHOD` へ遷移する | 「まだ始めたくない」場面でも盤面がロックされる。デッキを読み直すたびに開始シーケンスが始まってしまう |

設計書 2-2/2-3 は対戦部屋について「両席がデッキ読込済みになった瞬間 →
**開始できる合図をビューに載せる**」と書いている。**ボタンが出ること自体がその合図**である
と読み替え、`view.start.canBegin` が真のときだけ出す形にした。
条件(全公開=1席以上 / 対戦=両席 / 押せる人か)はすべてサーバが判定している。

★**この1点だけマスターの確認を頂きたい**(本書5章の質問1)。

### 1-9. ★「押せるか」をビューに載せたことで、クライアントに条件が写らなかった(9章)

`ManualStartView` が運ぶのは**判定の結果**だけである。

```java
phase == ManualStartPhase.ORDER_METHOD && mayControl,   // canChooseMethod
```

クライアント側の対応するコードは1行になった。

```js
toggleStartModal('start-method-modal', !!start.canChooseMethod);
```

★もしフェーズと部屋の種類と作成者席をクライアントへ送って組み立て直させると、
**「作成者席が空席ならどちらでも可」(1-3)というフォールバックがクライアントにも
写る**ことになる。21a の「公開範囲の判定を2箇所に書かない」と同型の罠であり、
片方だけ直したときに「ボタンは出るのにサーバが弾く」形で表面化する。

★待機表示(7-3)も同じ理由でサーバが文にしている。クライアントごとに組み立てると、
誰が何を待っているのかの解釈が分かれる。

## 2. 実装時に踏んだ / 避けた罠

- **★★「送られないこと」の検証で、そもそも掴めていなかった。**
  開始中のドラッグ抑止を `#pile-grid .manual-pile` へのドロップで検証したところ
  PASS したが、**同じ操作を `PLAYING` で行っても何も送られなかった**。

  → ドロップ先を `.manual-pile[data-zone="TRASH"] .manual-pile-face` に変え、
  **「開始中は送られない」と「開始後は同じ操作が通る」を対で**検証するようにした。
  ★22 2章の教訓(「起きてほしくないことだけを検証すると何も保証されない」)が
  そのまま再発した。**ロックの検証は必ず「解除後に通ること」と対にする。**
- **★`verify/shot.js` が `latestView` の片方にしか代入していなかった。**
  スクリーンショットを撮ったらマリガンオーバーレイが出ず、盤面がそのまま写った。
  `window.latestView` だけに入れても `manual-battle.js` 内部の `latestView` は null の

  21b が `verify.js` で踏んだのと同じ罠が `shot.js` に残っていた。

- **★`tools/check_structure.py` は `List.<String>of()` を「未解決のメソッド呼び出し」と

## 4. 理解確認 Q&A

**Q1. 「手動モードで判断を実装しない」が憲法なのに、先攻後攻もマリガンもアプリがやって
いる。原則を捨てたのではないか。**

A. 捨てていない。**境界を引き直した**。5-1 が禁じているのは
「ゲームの状況を読んで、何が起きるかをアプリが決める」ことであり、
コストの支払い・召喚時効果・戦闘の解決・攻撃可否・勝敗判定がその実体である。

総合ルール 2-5 の手順は**盤面の状態に一切依存しない決まりきった段取り**である。
選択の余地があるのは「先攻をとるか後攻をとるか」と「どの札を戻すか」の2箇所だけで、
**どちらも人間が押す**。アプリが引き受けたのは乱数とシャッフルと枚数を数えることであり、
それらは `shuffleDeck` / `drawCards` / `rollDie` として既に存在していた処理である。

★境界が守られていることは、**やらないことを明示する**ことで担保している
(`ManualStartService` のクラス javadoc)。ターンを進めない。フェイズを進めない。
デッキ切れを判定しない。マリガンの枚数に上限を設けない。
この4つが崩れた瞬間に、このバッチは 2-6 へ踏み込んだことになる。

**Q2. 開始中の棄却を、なぜ操作ごとではなく `apply` に置いたのか。
操作ごとに書いたほうが「どの操作が止まるか」がコードから読めるのではないか。**

A. 読めるのは書いた瞬間だけである。**次に操作を1つ足す人が必ず書き忘れる。**
17b が履歴の `push` を `apply` に集約したときの理由と同じで、
書き忘れの症状が「その操作だけ開始中に通ってしまう」という、
**気づくのが遅い形**で出る。

一方「どの操作が止まるか」は、**経路がすでに意味で分かれている**ため
コードから読める。`apply`(盤面を変える)は止まり、
`applyDirect`(ログだけ)と `execute`(部屋そのもの)は止まらない。
★止める/止めないの線が、判定ではなく**呼び出し経路**に対応している。

**Q3. マリガンで、なぜクライアントに「引く枚数」を送らせないのか。
戻した枚数と同じなのだから、クライアントが計算しても同じ結果になるはずだ。**

A. **「同じ結果になるはず」を前提にしないのが設計判断27である。**
外から来るデータはすべて検証する。クライアントが引く枚数を決められる形にすると、
検証を1つ足す必要が生まれる(戻した枚数と一致しているか)。

★リクエストに載せなければ、その検証は**要らなくなる**。
「検証を足す」より「検証すべきものを減らす」ほうが強い。
22 の Q2(相手の裏マナの内訳を引き算で出す)とまったく同じ形の判断である。

**Q4. 開始シーケンスの途中で Undo できないのは不便ではないか。
ダイスの出目が気に入らないときに戻したくなるはずだ。**

A. その用途は**戻してはならない**。ダイスを振り直せるなら、
乱数を機械に任せた意味(公平さの保証)が消える。

技術的な理由もある。開始処理は「シャッフル → ドロー → 戻す → シャッフル → ドロー」
という複数の状態変更を含み、途中まで戻せると
「シャッフル後の並びだけ戻る」といった**意味のない中間状態**が作れてしまう。
加えて対戦部屋の Undo は深さ1(21)であり、そもそも全体を戻せない。

★代わりに**リセットは開始中でも必ず通る**(7-2)。仕切り直したいなら、
中途半端に戻すのではなく最初からやる。これは「戻せない」ではなく
**「戻し方は1つに決めてある」**である。

**Q5. `ManualStartPhase` を `ManualGameState` に入れると具体的に何が壊れるのか。
Undo で巻き戻っても、フェーズが戻るだけではないか。**

A. 「フェーズだけが戻る」のが問題である。開始が完了した後(`PLAYING`)に Undo すると、
盤面はそのままでフェーズが `MULLIGAN` に戻る。すると
**盤面は開始済みなのに、盤面操作がロックされ、マリガン画面が開き直る。**
そこで確定を押すと、開始済みの手札からもう一度引き直しが始まる。

★しかも `copy()` に含めるかどうかで必ず迷う。含めなければ「巻き戻らないフィールドが
スナップショットの中に1つだけある」という説明の付かない例外になる。
**巻き戻ってはならないものは、巻き戻る器の外に置く。**
ログを `ManualRoom` に置いた 17b 2-5 と同じ判断である(1-2)。

**Q6. `[ゲームを始める]` を対戦部屋にも出したのは設計書 6-1 と違う。
設計書どおりに自動でモーダルを出すことはできなかったのか。**

A. できるが、**描画から状態変更を起こす**ことになる。クライアントが
「両席のデッキが揃った」を見て `start-begin` を自動送信する形は、
resync・再接続・両者が同時に条件を満たした瞬間などで二重送信の余地が生まれ、
しかも**人間が押していない操作がログに載る**。

サーバ側でデッキ読込の瞬間に遷移させる案もあるが、こちらは
「まだ始めたくない」場面でも盤面がロックされ、
デッキを読み直すたびに開始シーケンスが始まる。

★設計書 2-2/2-3 は対戦部屋について「**開始できる合図をビューに載せる**」と
書いている。**ボタンが出ること自体がその合図**である、と読み替えた。
条件はすべてサーバが判定しており(`view.start.canBegin`)、
クライアントは真偽値1つを見て出し分けているだけである。
★ここだけマスターの判断を仰ぎたい(5章の質問1)。

**Q7. マリガン画面の拡大を、なぜ右列の拡大パネルに出さなかったのか。
22 で「左=見る」に統一したはずだ。**

A. **見えないからである。** マリガンのバックドロップ(z-index 1950)が右列を覆う。
そのまま右クリックしても「何も起きない」ように見え、
22 1-5 で潰したはずの問題が別の場所で再発する。

★オーバーレイの中に拡大枠を置き、**同時に右列の `#zoom-panel` にも入れている**。
閉じた後は通常どおり右列に残るため、規約から外れた記憶が残らない。

なお「左=見る」との衝突自体は、専用オーバーレイに閉じ込めることで解いている(1-7)。
盤面の手札行では従来どおり左が拡大であり、この画面だけが違う。
**違う画面であることを見た目で分かるようにしてあるので、規約は破れていない。**
