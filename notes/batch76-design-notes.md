## 2. 実装 —— 4枚をどう「選ばせる」形にしたか

4件とも **割り込み(`PendingChoice` + `ResumePoint`)** に移した。
足した再開先は4つである。

| 再開先 | カード | 候補の種類 | `payload` |
|---|---|---|---|
| `MANA_WRAITH_TRASH_TO_MANA` | マナを貪る怨霊 | `TRASH`(墓地の位置) | 使わない |
| `TABOO_PRICE_MANA_DESTROY` | 禁忌の代償 | `MANA`(マナの位置) | ★**後半で出す墓地のカードID** |
| `MOANIRU_INTERCEPT` | 光霊・モアニール | `MINION`(instanceId) | 使わない |
| `HOLY_SIGNAL_LOWEST_HP` | ホーリー・シグナル | `MINION`(instanceId) | ★**最高攻撃力側の instanceId** |

### 2-1. ★★★候補は「位置」で持つ(カードIDではない)

墓地とマナは**同名のカードが並びうる**。IDで問い合わせると候補が同じ文字列で並んで
区別できないうえ、`PendingChoice.pointsAtZonePositions()` の控え
(Batch 64 が置いた「候補が指す先が動いていないか」の番人)も効かない。

★**動かす直前に、位置をカードIDへ写し切る**こと ——
`putTrashCardIntoManaFaceDown` は**カードIDで墓地から取り除く**ので、
1枚目を動かした時点で2枚目の位置がずれる。
★同名が2枚選ばれたときは同じ文字列が2つ並ぶが、
`List.remove(Object)` は1回に1枚しか外さないので枚数は合う。

### 2-2. ★★★《禁忌の代償》—— 「その後」を守るために `payload` が要る

本文は「裏向きマナ1枚を破壊する。**その後**自分の墓地からコスト4以下のミニオンを
1体選び場に出す。」である。

★**問い合わせは「中断」ではなく「後回し」である**(`PendingChoice` の Javadoc)——
`requestChoice` を呼んでも<b>呼び出し元の続きはそのまま走る</b>。
したがって素直に書くと、

```
requestChoice(...);              // 破壊はまだ起きていない
effectPutSequence(...);          // ← 先に出てしまう
```

となり、**「破壊 → その後出す」の順が逆転する**。
★出す先も `payload` に載せて再開先へ運び、
`resolveTabooPriceDestroy` が「破壊してから出す」を1本で持つ形にした。

> ★★<b>番人でもこれを測っている</b>: `代償は答える前に蘇生しない`。

### 2-3. ★★★《光霊・モアニール》—— 相手のターン中に問う

肩代わりは `GameActions.tryReplaceLeaderDamageWithGuardian` で起きる。
これは**効果ダメージ・ミニオンの攻撃・ウェポンでの攻撃**の3経路から呼ばれ、
多くは<b>相手のターン中</b>である。

★問い合わせを出しても盤面が動かないことは、**既に在るもの**が保証している ——
★**番人を置く場所を選ぶ前に、そこまで届くかを確かめた**(70〜75 の教訓)。

| 何が止めるか | どこに在るか |
|---|---|
| 手番の側が盤面を動かせない | `GameService.requireTurnPlayer`(相手の選択待ちも見る・裁定214 の対) |
| 戦闘の解決が進まない | `GameService` の `pendingAttack`(Batch 51) |
| ターンが渡らない | `endTurn` の `turnHandoffPending`(Batch 58) |

★★★**選んだ個体が既に居なければ、残っている候補を1体壊す。**
1回の解決でリーダーが2度ダメージを受けると問い合わせが2つ積まれ、
**どちらの候補にも同じ個体が並ぶ** ——
そこで「居ないから何もしない」に落とすと<b>肩代わり1回がただになる</b>。

> **失われるのは選択であって、代償ではない。**

★<b>どのカードが肩代わりするかを再開先の側に書き写さない</b>(裁定130)——
`GameActions.destroyChosenGuardian` が `RuleGuards.leaderDamageInterceptors` を
呼び直す形にしたので、カードIDは `RuleGuards` の1箇所にしか無い。

### 2-4. ★★★《ホーリー・シグナル》—— 64 の「構造上の都合」は割り込みには掛からない

64 はここを自動決定のまま残し、理由をこう書いていた ——
「2つ目の `Requirement` にすると `GameService.validateTargets` の `usedMinionIds` に
引っかかり、相手の場が1体しか居ないときに**カードが使用不能になる**」。

★**その都合は今も生きている**(だから呼び出し側にそのまま書き残した)。
★★<b>禁じられていたのは「2つ目の Requirement」であって「選ばせること」ではない</b> ——
割り込みは `validateTargets` を1度も通らない。

> ★★★**64 の判断は誤りではなく、前提が「宣言時に選ばせるなら」だった。**
> 75 の「『旗を立てる人が居ない』は、居るようになった日に結論が変わる」と同じ形である。

★破壊は**両方まとめて再開先で行う** ——
「両方の対象を、まだ何も壊れていない盤面で先に確定してから破壊する」という
56 からの性質を保つためである。最高攻撃力側は `payload` で運ぶ。

## 3. ★★★禁忌デッキ経路の使用条件の抜け(裁定不要のバグ)

### 3-1. 症状

### 3-3. 直した形

`playTabooCard` の **賢魂の分岐(`asSoul`)より後・支払いより前**に1行足した。

★★**賢魂の道には掛けない。**54 の `requireSoul` の Javadoc が
