| 項目 | 前 | 後 |
|---|---|---|
| 音源 | Web Audio による**合成** | **音声ファイル**(mp3・18本) |
| 手動モードの音 | 11種 | **11種**(数は変わらない) |

| JUnit | 637件 | **640件**(+3。`BattlePageTest`) |
| verify | 545件 | **578件**(+33) |

**作らなかったもの**: BGM(裁定16)/ 通常モードの**演出**(fx 層。裁定287 により差分の採取までで止めた)/

## 0. ★★★裁定74 が覆った経緯

Batch 37 は「**音源はコードで合成する。音声ファイルを同梱しない**」を選んだ(裁定74)。
2026-08-21、マスターの裁定によりこれが**失効した**(裁定283)。

★★**旧裁定は誤っていなかった。**37 の設計解説 2-3 はこう書いている。

> 理由は**失敗の広さ**である(裁定27 の一般形)。
> ★静的ファイルの版数は既に3系統あり、36 で「揃っていること」を機械判定にしたばかりである。
> **4系統目を増やす判断は、そのバッチの次に置くものではない。**

この判断は、**37 の時点の前提のもとでは正しい**。当時「音声ファイルを用意する」とは
「誰かが素材を探し、ライセンスを確かめ、リポジトリに置く」という**まだ誰もやっていない作業**を
指していた。そのコストと、増える失敗経路3つを天秤にかければ、合成のほうが軽い。

**変わったのは前提である** —— マスターがフリー素材を用意すると決めた。
素材の調達が済むなら、天秤の片側が軽くなる。**結論が変わったのは前提が変わったからであって、
37 の推論が間違っていたからではない。**

★この区別は書き残しておく価値がある。**「昔の判断が誤っていた」と書くと、
次の人は当時の推論まで疑う**ようになる。疑うべきは推論ではなく、前提が今も生きているかである。

## 1. ★★引き受けた4つの失敗経路

37 の比較表の右列(音声ファイル側)を、今回すべて引き受けた。手当ては次のとおりである。

| | 37 が挙げた失敗 | 62 の手当て |
|---|---|---|
| 読み込み失敗 | ある(404・遅延) | **鳴らない。理由は状態行に出す**(1-1) |
| キャッシュ版数 | **4系統目**が増える | **独立した定数1つ**で持つ(1-2) |
| ライセンス | 要確認 | **CC0 に限る**(1-3) |
| 調整 | 素材を作り直す | 受け入れた(1-4) |

### 1-1. 読み込み失敗 —— 鳴らないが、黙らない(裁定283)

**合成のコードは撤去した。**`sfxTone` / `sfxNoiseSweep` / `sfxEnvelope` / `sfxRattle` は無い。
読み込めなかった音は**鳴らない**。

★保険として合成を残す道もあった。採らなかった理由は裁定70・71 と同じ筋である ——
**「どちらが鳴るか」の分岐を1つ増やすと、音が語るものが1つ減る。**
「この音は、置いたという意味である」が「置いたか、あるいは合成側にフォールバックしたか」になる。
音が情報を持つ、という筋がそこで折れる。

★ただし**黙ってはいない。**鳴らない理由を出す場所は、37 が既に作っていた
(`#sound-modal-status`。裁定76)。読み込み失敗は**その新しい1件**である。

```
音の一部を読み込めなかった(3件)。その音だけが鳴らない
```

★★**並び順に理由がある。**状態行は上から順に「音が**1つも**鳴らない理由」であり、
読み込み失敗だけが「**一部の音だけ**が鳴らない」理由なので最後に来る。
全部鳴らない人に「一部が読み込めなかった」と言っても、その人の困りごとは解けない。

★あわせて `sfxStatusWarn()` を新設した。警告色の判定は `!sfxReady()` ではなくこちらである ——
**読み込み失敗はゲートではない**(他の音は鳴る)**が、言うべき理由ではある**。

### 1-2. ★★取得と復号を分けた(裁定283 の含意)

ファイルを読む処理は**2段になっている**。理由は unlock の決まり(裁定73)である。

| 段 | いつ | なぜそこか |
|---|---|---|
| **取得**(`fetch` → `ArrayBuffer`) | ページを開いた時点 | 早いほうがよい。読み込み失敗を**操作より前に**検出できる |
| **復号**(`decodeAudioData` → `AudioBuffer`) | **最初のユーザー操作**(unlock) | 復号には `AudioContext` が要る。それを操作より前に作ってはいけない |

★この分割は、裁定73(unlock は最初のユーザー操作である)を守りながら
裁定283 の (c)(起動時に先読みして失敗を検出する)を成り立たせる唯一の形である。
片方に寄せると、どちらかの裁定が破れる。

★`decodeAudioData` は渡された `ArrayBuffer` を**切り離す**ので、原本は使い回せない。
復号したものは `sfxRaw` から取り出して捨てている。

### 1-3. ★★版数(裁定284)

```js
const SFX_BASE = '/sounds/';
const SFX_VERSION = 1;
function sfxUrl(file) { return `${SFX_BASE}${file}?v=${SFX_VERSION}`; }
```

★**JS の版数と同じ数字を使い回さない。**「音だけ差し替えたのに `manual-battle.js` の
版数を上げる」ことになり、**1つの数字に意味が2つ載る**。

★**版数を持たない選択は採れなかった。**実測したところ、このプロジェクトは
`Cache-Control` を1つも設定していない(`application.properties` に `spring.web.resources.*` が無い)。
Spring Boot の静的配信は既定でキャッシュ指示を付けないので、
**ブラウザは `Last-Modified` から有効期限を勝手に推定する**。
既存の js / css が `?v=` を付けているのは、まさにこれを避けるためである。

★ファイル名に版数を入れる案(`place-v1.mp3`)も検討した。取りこぼしが構造的に起きない利点があるが、
**音の版数がファイル名に散る** —— 37 の「音の性格を `SFX_SPECS` の表1つに集める」という規律の
裏返しになる。定数1つなら表のすぐ隣に置ける。

★★**版数の系統は4つになった。**裁定74 が避けようとしていたものである。
落とし穴(「性能・接続」節)を訂正した。

### 1-4. ライセンス —— 3章へ

いちばん危ない失敗経路であり、**規則1つで丸ごと潰した**。3章に分けて書く。

### 1-5. 調整 —— 受け入れた

37 は「調整は数値の表を1行直すだけ」を利点に挙げていた。ファイル化でこれは失われる。
**素材を差し替えるしかない。**

★ただし完全には失っていない —— `SFX_SPECS` の `gain` は残してある。
音どうしの相対バランスに加えて、**素材ごとの録音レベルの差もここで吸収する**。
「うるさい・小さい」はこの表の1行で直せる。「音色が違う」だけが素材の差し替えになる。

## 2. ★★★機械検証23件のうち、作り替えになったのは0件だった

着手前の見立てでは、**AudioContext の境界に張り込んでいる11件が作り替えになる**と数えていた。
実際には**1件も作り替えていない。**

### 2-1. なぜそうなったか —— 再生方式の選び方

音声ファイルを鳴らす方法は2つある。

| | `<audio>` 要素 | **AudioContext + AudioBuffer** |
|---|---|---|
| 音量マスター | 要素ごとに設定 | **`sfxMaster.gain` 1箇所のまま** |
| 連打 | 使い回すと前の音が切れる | **何本でも重ねられる** |
| unlock | 別の仕組みが要る | **`sfxUnlock` がそのまま効く** |
| 既存の検証 | ★**11件が全部作り替え** | ★**`createBufferSource` を数える形が残る** |

★★**AudioContext + AudioBuffer を選んだ。**合成時代の `sfxNoiseSweep` も
`createBufferSource` を呼んでいた(ホワイトノイズのバッファを鳴らすため)。
**ファイル再生も同じノードを使う。**したがって
「音源ノードがいくつ作られたか」で鳴ったことを測る形が、そのまま生き続ける。

★これは偶然ではない。**37 が「`sfxPlay` が呼ばれたか」ではなく
「WebAudio の境界で何が作られたか」で測ることにしたから**である ——
呼ばれても鳴っていないことがある、という理由でその測り方を選んだ結果、
**音の作り方が変わっても壊れない検証**になっていた。

★★教訓として一般化するなら: **実装の呼び出しではなく、実装が触る境界を測ると、
実装を入れ替えても検証が生き残る。**

### 2-2. それでも新しく13件足した

既存が生き残ったことと、新しい失敗経路に番人が要ることは別である。手動モード側に13件足した。

| # | 何を測るか | 裁定 |
|---|---|---|
| 62-1 | `static/sounds/` のファイルが全部 `CREDITS.md` に載っている | 285 |
| 62-2 | `SFX_SPECS` が名指すファイルが実在する | —— |
| 62-3 | 両モードに共通する音は同じファイル・同じ gain / 珍しさの順序が同じ | 289 |
| 62-4 | 音の版数が JS の版数と別の数字である | 284 |
| 62-5 | 散らすのは `tap` と `place` だけ / 2連続で同じものを鳴らさない | 286 |
| 62-6 | 読み込み失敗で鳴らない・理由が状態行に出る・合成が撤去されている | 283 |

★★**62-6 は本物の経路で失敗させている。**ハーネスのサーバに `SOUND_RESPONSE` を置き、
`/sounds/` の応答を 404 にできるようにした(`ZONE_RESPONSE` と同じ形)。
`fetch` をスタブすると「404 のとき何が起きるか」ではなく
「スタブが何を返すか」を測ることになる。

## 3. ★★★ライセンス —— 規則1つで丸ごと潰した(裁定285)

### 3-1. 問題の形

`okuson-droid/qte-battle-batch0` は**公開リポジトリ**である。
`src/main/resources/static/` に置いたファイルは、**GitHub 上で誰でも単体でダウンロードできる。**

★★したがって「**アプリに組み込んでよい**」だけでは足りない。「**再配布してよい**」でなければならない。

| サイト | 商用 | クレジット | 再配布 | public リポジトリ |
|---|---|---|---|---|
| 効果音ラボ | 可 | 不要 | **禁止** | ★★**不可** |
| OtoLogic | 可 | **必須**(CC BY) | 可 | 可(ただし画面に表記が要る) |
| **CC0 素材** | 可 | 不要 | 可 | ★★**可。無条件** |

マスターは「リポジトリを素材に合わせる」(非公開化)ではなく
「**素材をリポジトリに合わせる**」(CC0 限定)を選んだ。
★非公開化は**サンドボックスの `git clone`(毎バッチの出発点)が認証情報を持たないため落ちる**
という代償が大きい。

★★**この規則の御利益は、以後この話を二度と考えなくてよくなることである。**
再配布・改変・商用・表記のすべてが無条件になる。CC BY を混ぜないのは、
**1つ混ぜた時点で「画面のどこに表記を置くか」という設計判断が発生する**ためである。

### 3-2. ★記録は義務である(表記ではない)

`static/sounds/CREDITS.md` に、ファイルごとに
「用途 / 原本のファイル名 / パック / パックのURL」を書いた。ライセンスと取得日は全件共通である。

★CC0 は表記を要求しない。**これは表記ではなく記録である** ——
後から「これはどこの音だったか」「本当に CC0 だったか」を確かめられない状態にしないために置く。

★★**機械判定を1つ置いた。**`static/sounds/` にある mp3 が全部 `CREDITS.md` に載っているか。
出所不明の音が1つ紛れ込む経路を塞ぐ(61 までの「取りこぼしの番人」と同じ形である)。

### 3-3. ★★実測で分かったこと —— 調査だけで素材を決めてはいけない

指示書の 3-2 は「Kenney の3パックで11種が全部埋まる」という調査結果を持っていた。
**実物を展開したところ、2点ずれていた。**

| | 調査 | 実物 |
|---|---|---|
| ファイル名 | `cardSlide1.ogg` | **`card-slide-1.ogg`**(ケバブケース) |
| `attack` の素材 | (項目自体が無かった) | ★**3パックに打撃音が1つも無い** |

さらに、**長さを測って初めて分かったこと**がある。

★★★**`click_002`〜`005` は長さが 0.01 秒しかない。**ほとんど聞こえない。
指示書は `tap` の候補に `click_001〜005` を挙げていたが、そのまま採用していたら
**鳴らない音を4つ仕込むところだった。**

★実際に当てたのは **`select_001 / 002 / 007 / 008`**(0.043〜0.047 秒で4つとも長さが揃っている)。
`select_003 / 004 / 005` は 0.38 秒、`select_006` は 1.9 秒で、これらは別の音である。

★**教訓**: 音は**長さ・音量・種類数が全部素材に依存する**。
ファイル名の並びから決められるのは候補までであり、**採用は実物を測ってからにする。**

## 4. ★★散らし(裁定286)

`tap` と `place` だけが複数のファイルを持つ。鳴るたびに選び、**2連続で同じものは鳴らさない**。

★裁定71(音は情報を持つ)は、散らしても**折れない** —— `tap` が4通りあっても
**4通りとも `tap` である**。意味は1つのままである。
むしろ**頻度の高い音ほど、意味がすでに摩耗している** ——
毎手鳴る `tap` は「タップした」を語る前に、まず**耳に残り続ける**。散らす価値はそこにある。

★逆に `decisive`(1試合1回)や `dice` を散らすのは害のほうが大きい。
滅多に鳴らない音が毎回違うと、**「これは前と同じ出来事か?」という迷いが生まれる。**
**珍しい音は、珍しいからこそ同一であることが情報である。**

★★**表の形は2通りにしなかった。**`files` は**必ず配列**である(1つしかない音も要素1)。
そうすれば表は1行1音のままで、**「何通りあるか」が表の上で読める。**

## 5. ★★★通常モードの音(裁定287・288)

### 5-1. 構造の違い

| | 手動モード | 通常モード |
|---|---|---|
| 描画 | 差分を採ってから描く | **`render(view)` で毎回まるごと描き直す** |
| fx 層 | ある(32a・32b・35・38) | ★**無かった** |
| 音の材料 | `fx.kind` の列 | ★**存在しなかった** |

マスターは **(A) 差分の採取層を作る**を選んだ。★クロエの推しは (B)(`send()` + `render()` の2本立て)
だったが、**採られなかった。**推しの根拠は「音のためだけなら (A) は過剰」だったが、
その前提が弱い —— 通常モードにいずれ演出を入れるなら、(B) の取り付け点は**そのとき捨てることになる。**
**裁定68 が守ろうとしていたのは「発火点を増やさないこと」であって「安く済ませること」ではない。**

★★**範囲は「差分の採取まで」に絞られた。**`fxDiff` / `fxDiffSeat` が
`fx.kind` の列を出すところまでで、fx 層(ゴースト・遷移)は作っていない。
音はその列を読むだけであり、**演出を乗せる土台は次のバッチに残る。**

### 5-2. ★★★取り付け点は `onMessage` であって `render` ではない

これが今回いちばん重要な発見である。

```js
function onMessage(frame) {
    ...
    sfxForDelivery(latestView, message.view);   // ★ここ
    latestView = message.view;
```

★`render(latestView)` は**画面の操作のたびにも呼ばれる**(通常モードには15箇所ある)。
あそこで差分を採ると、**「配信」と「再描画」を区別できない。**
`onMessage` だけが「サーバから来た出来事」の入口である。

★★**差し替え前の `latestView` が、そのまま「前回の盤面」である。**
新しい状態変数を1つも増やさずに差分が採れる。
手動モードで `fxSpawn` が「盤面で起きたことは全部1つの列に集まっている」を利用したのと、
**これは同じ形の利用**である ——
新しい集約点を作るのではなく、**既にある集約点を読む。**

★**番人を置いた**: 「描き直しただけでは鳴らない」。
壊し検証のケース11(`render` の先頭で音を鳴らす)がこれを狙っている。

### 5-3. 何を差分として採るか

手動モードのように全ゾーンのカードを `instanceId` で追うことは**していない**。
通常モードのビューは、**場のミニオンだけが `instanceId` を持ち**、
手札・マナ・墓地は枚数と中身の列で来る。

| 出来事 | 採り方 | 音 |
|---|---|---|
| LPの増減 | `lp` の差 | `lpDown` / `lpUp` |
| ドロー | `handCount` の**増加** | `draw` |
| マナに置いた | `totalMana` の**増加** | `place` |
| 場に出た | `minions` に無かった `instanceId` | `place` |
| 場を去った | `minions` から消えた `instanceId` | `place` |
| タップ | 居場所が変わっていないミニオンの `tapped` 変化 | `tap` |
| 決着 | `status` が `FINISHED` へ**変わった配信でだけ** | `decisive` |
| マリガン終了 | `mulligan` が true → false | `shuffle` |

★追えるものだけを追い、残りは**枚数の増減**で採る。音が要るのは「何が起きたか」であって
「どのカードがどこへ動いたか」ではない(裁定72: 音の語彙は粗くてよい)。

★**相手の席も同じように採る。**差分層は誰の手かを区別しない ——
手動モードも差分由来なので相手の手で鳴っている。
★★**これは実装で決めた部分である**(裁定287 が (A) を選んだことの素直な帰結)。
**通話が前提(裁定16)なので相手の手は声で伝わる**という理由で
「自分の手だけ鳴らす」形もありうる。**実機で聞いた印象を伺いたい**(8章)。

★**裁定8 も効かせた。**差分が8件を超えたら何も鳴らさない ——
1手で盤面が大きく動いた配信は、音では語れない。

### 5-4. ★★差分に現れない出来事は `send()` から鳴らす

**攻撃は view の差分に現れない。**現れるのはHPの減少・消滅という**結果**だけで、
「攻撃した」はどこにも書かれていない。したがって `send()`(ユーザーの操作が全部通る1箇所)から鳴らす。

★★**これは手動モードの `commit`(確認モーダルの [実行])とまったく同じ形である。**
裁定68 の「取り付けは2箇所」が、通常モードでもそのまま成り立っている。

```js
function sfxForAction(action) {
    if (action === 'attack' || action === 'leader-attack') sfxPlay('attack');
    else if (action === 'end-turn') sfxPlay('commit');
}
```

★★**カードのプレイをここで鳴らしてはいけない。**差分が `appear` として語るので、
鳴らすと**1つの操作で2音**になる。裁定70 が守っているものが崩れる。
番人を置いた(「差分が語る操作は send では鳴らさない」)。

★`attack` は `SFX_PRIORITY` に入れていない。差分から来ないので競合しない(`commit` と同じ)。

### 5-5. 通常モードの表は9種である

★★**手動モードの11種と同じものではない。**この表は「**そのモードで鳴る音**」の一覧であり、
**鳴らない音を載せると表が嘘をつく。**

- 手動モードにあって通常モードに無い: `flip` / `dice` / `deal`
  —— 「めくり」「先後のダイス」「ひと配り」という出来事が通常モードには無い
  (先後は `chooseOrder` の**選択**であって振るものではない。初期ドローは手札が増えるので `draw` が語る)
- 通常モードにあって手動モードに無い: `attack`

## 6. ★★複製の扱い(裁定289)

音の設定 UI と音のセクションは、`manual-battle.js` / `manual-battle.html` の**複製である**。
共有の JS ファイルにすると**版数の系統が5つ目**になる(音声ファイルで4つ目になった)。
裁定111 が共有 JS を退けたのと同じ理由である。

★★**61 の教訓を効かせた。**「カードフェイスの実装が2つあった」で問題だったのは、
**複製を作ったこと自体ではなく、複製だと書き残さなかったこと**である。そこで:

1. 両方のファイルの冒頭に「これは複製である。片方だけ直さないこと」と書いた
2. 落とし穴(`notes/qte-pitfalls.md`)に節ごと足した
3. ★★**番人を2つ置いた** —— 「両モードに共通して載っている音は同じファイル・同じ gain である」
   「珍しさの順序が両モードで同じである」

★★**番人は「共通部分の一致」を測っている。**片方にしか無い音(`attack` / `flip`・`dice`・`deal`)は
**モードの違いであって、ずれではない**。全体一致で測ると、モードの違いを足すたびに番人が落ちる。

★`localStorage` の鍵は **`qte-manual-sound` のまま共有する**。
音量は人の性質であり、モードごとに合わせ直させるものではない(裁定31 の筋)。
★改名(`qte-sound`)も筋は通るが、**既に音量を合わせた人の設定が1回消える**ほうが実害が大きい。

## 7. 壊し検証(裁定116)

`tools/batch62_break_check.py` に**14ケース**。★**軸ごとに1件ずつ**当てている(57 の教訓)。

★★**照合先が 55〜61 と違う。**今回の番人はほぼ全部 verify(Node)側にあるので、
このスクリプトは surefire の XML ではなく**`verify.js` の出力行**を読む。
音は JUnit では測れない(37 以来の形)。

| 軸 | ケース |
|---|---|
| 読み込み失敗(283) | 読み込めていない音でも鳴らそうとする |
| 合成の撤去(283) | 合成のコードが戻ってきている(保険の復活) |
| 版数(284) | JS の版数を使い回す / 版数を付けない |
| 出所の記録(285) | `CREDITS.md` から1行消える / 実在しないファイルを名指す |
| 表の複製のずれ(289) | 通常モードだけ gain を変える / 珍しさの順序をずらす |
| 散らし(286) | 珍しい音まで散らす / 2連続で同じものを鳴らす |
| 通常モードの取り付け点(287) | `render` で音を鳴らす / 差分の上限を見ていない |
| 1操作2音にしない(70) | `play-card` でも `send` から鳴らす / 攻撃で鳴らない |

★★**結果は 14ケース中 OK 14 / NG 0 / EMPTY 0 / SETUP-NG 0** である。
狙った番人が全部落ちた —— **59・60 の教訓(「壊しても落ちないときは改変が当たっているかを疑う」)に
該当する項目は無かった。**

★1件だけ、実装の順序を工夫して確実性を上げた箇所がある。
「散らした音が2連続で同じものを鳴らす」は、素直に壊すと**確率的にしか落ちない**
(ランダムに選ぶので、たまたま連続しないことがある)。
改変を「**常に添字0を返す**」にして、**必ず2連続になる**ようにしてある。
★**壊し検証の改変は、狙った状態を確実に作れる形にすること。**

### 7-1. ★★★踏んだ穴 —— 「全部 OK」と「実装が元に戻っている」は別のことである

**14ケース全部が OK と出た後、`battle.js` に改変が1つ残っていた。**
ケース11(`render` の先頭で音を鳴らす)の復元が効かず、
**後続のケースがその汚染された内容を「元の姿」として保存した**ためである。

★★**14ケースは全部 OK のままだった。**汚染された状態でも、狙った番人はどちらにせよ落ちるからである。
**スクリプトの答えは、この事故を1文字も語らなかった。**

★気づいたのは、その後の**最終の verify で5件落ちた**ときである。
落ちた1件が「★★★描き直しただけでは鳴らない」——
**62 でこのバッチのために置いた番人が、このバッチの事故を検出した。**
(残る4件も「音が2つ鳴っている」= `render` の音が混ざったことによる巻き添えである。)

★★**これは 60 の教訓の兄弟である。**60 は「改変した Java がコンパイルできないと
前回の XML が残り、それを読んで NG と誤読する」を見つけ、**走らせる前に結果を消す**ようにした。
今回は**走らせた後に実装が戻っているかを確かめていなかった。**

**手当て**: `tools/batch62_break_check.py` に2つ足した。

1. `write()` が**書き戻せたことを自分で読み返して確かめる**(失敗したら例外で止まる)
2. 全ケース終了後、**対象ファイルが開始時の姿に戻っているかを1つずつ突き合わせる**。
   戻っていなければ、OK が何件出ていようと**このスクリプトは失敗である**

★★**教訓として一般化するなら: 状態を書き換える道具は、書き換えを戻せたことまでを含めて
自分で答えなければならない。**「やった」と「戻した」は別の主張である。
