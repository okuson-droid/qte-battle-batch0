## 2. ★★★自陣と敵陣の見分け(穴1)

### 2-1. なぜ 68 の後にこれをやるのか

68 で【召喚時】【登場時】の対象が**割り込みへ移り**、盤面から選ぶ場面が **15枚ぶん**増えた。
さらに裁定305 により **自分自身も候補に入る**ようになった。

つまり **68 は「盤面を押す」遊びを増やした**。上段と下段が同じ見た目のままだと、
65 の時点では「見づらい」だっただけのものが、69 の時点では **誤クリックが実害になる**。

### 2-2. ★色の値を1つも新しく決めていない

やったのは **クラス2つ**である。

```html
<div id="opp-minions" class="minion-row auto-minions auto-field-opponent"></div>
<div id="my-minions"  class="minion-row auto-minions auto-field-self"></div>
```

```css
.auto-minions { border-radius: 8px; border-left: 3px solid transparent; padding-left: 7px; }
.auto-field-opponent { background: rgba(220, 53, 69, 0.09); border-left-color: #dc3545; }
.auto-field-self     { background: rgba(13, 110, 253, 0.11); border-left-color: #0d6efd; }
```

★`#dc3545` と `#0d6efd` は **`.opponent-side` / `.my-side` が持っていた値**である。
ここで別の赤・別の青を選ぶと、**同じ盤面に2系統の「相手の色」が並ぶ**。

★★**同じ値が2箇所に在ること自体は裁定130 が許す形である** ——
CSS には「他のルールの色を参照する」機構が無い(カスタムプロパティに切り出す手もあるが、
そのために既存の2行を書き換えるほうが影響が広い)。
**1箇所に置けないなら、一致を番人が見張る**(65 の流儀)。
verify 69-2 が **実測した色どうしを突き合わせる** ——

```js
fieldStyle.opp.edge === fieldStyle.oppStripLine   // #opp-minions の左端 === .opponent-side の上線
fieldStyle.my.edge  === fieldStyle.myStripLine    // #my-minions  の左端 === .my-side の下線
fieldStyle.oppStripLine !== fieldStyle.myStripLine // ★空振りでないことの証拠(裁定186)
```

★**期待値(`#dc3545` という文字列)を書いていない。**書けば、実装を変えたときに
**番人のほうを書き換えて緑にできてしまう**(裁定41)。

### 2-3. ★上下の padding を書かなかった

この2行の高さは **43-1(1280×800 の1画面に収まる)の前提そのもの**である。
`border-left` と `padding-left` は横にしか効かないので高さを動かさない。
実測でも行の高さは 134px のまま、`scrollHeight` は 800 のままだった。

## 3. ★★★ホバープレビュー(穴2)

### 3-1. 器はもう在った

44 のコメントにはこう書いてある —— 「**ホバープレビュー(Batch 44・B-1)。まずはリーダーから**」。
`#auto-hover` / `.auto-hover` / `attachHover()` はすべて 44 が作りきっており、
**呼び出しがリーダー2箇所で止まっていた**だけである。

★これは 65 の教訓「**『番人が無い』と思ったら、まず在るかどうかを見る**」の、
**器についての形**である(67 の《ツイン・ストライク》で `MinionView` に文明を足そうとして、
45 の注釈に「card-library から引く」と書いてあったのを見つけたのと同じ)。
69 が足したのは `attachHover(el, minionFace)` と `attachHover(el, handFace)` の **2行**である。

### 3-2. ★拡大とホバーは同じ面を出す

`createMinionEl` は拡大用のデータを作る式を持っていた(【起動】の文と「下:」を足す)。
ホバー用にもう1つ書くと、**片方だけに【起動】が付く**形で黙って離れていく。
式を `minionFace` という名前の関数に1本化して、`attachZoom` と `attachHover` の両方へ渡した。

### 3-3. ★★★対象を選んでいる最中は出さない(マスター確認)

`.auto-hover` は **`right: 300px; top: 64px` の固定位置**に出る。
場のミニオンにホバーすると、プレビューは**盤面の上に重なる**。
68 で盤面から対象を選ぶ場面が増えたので、選んでいる最中に大きな面が降りてくると
**候補が隠れる** —— `pointer-events: none` なのでクリックは通るが、**見えないものは押せない**。

判定は1箇所に閉じた。

```js
function hoverBlocked() {
    return !!pending || !!evolution || !!tabooPay || hasPendingChoice()
        || !!(latestView && latestView.mulligan);
}
```

★★★**5つ目(`hasPendingChoice()`)を最初の実装で書き忘れていた。**
マスターが心配した「候補が隠れる」は **いちばん割り込みで起きる**のに、
最初は宣言時の `pending` しか見ていなかった。
壊し検証の軸4 の2件目が、この形を名指しで測っている。

★割り込み中かどうかの判定は `hasPendingChoice()` が既に持っている。
**同じ式を書き写さずに呼ぶ**(裁定130)。

### 3-4. ★出す側のガードだけでは足りない

判定を置く場所は**2つ**要った。

| 場所 | 何を止めるか |
|---|---|
| `attachHover` の `onmouseenter` と 350ms のタイマーの中 | **これから出す**のを止める |
| `render()` の入口(`if (hoverBlocked()) hideHover();`) | **もう出ている**のを消す |

★面が出たあとに問い合わせが届く経路がある。
片方だけだと「手を止めているのに面が降りたまま」になる。
★タイマーの中にも判定が要るのは、**待っている 350ms のあいだに問い合わせが来る**ためである。

## 5. ★★パイルの枚数バッジ(穴4)

### 5-1. ★44 の設計を1つだけ変えた

44 は `pileEl` のコメントにこう書いている ——
「数字を書き込む既存のコードは1行も変えずに、書き込み先だけが移る」。
そのため**書き込みが8箇所に散っていた**(両席 × 山札・墓地・消滅・禁忌)。

「0枚なら暗くする」という規則をその8箇所に書けば、**7箇所直して1箇所忘れる**事故がいつでも起きる。
→ 書き込みを `setPileCount(id, count)` の**1本に通した**(裁定130)。

```js
function setPileCount(id, count) {
    const el = document.getElementById(id);
    if (!el) return;
    el.textContent = count;
    el.classList.toggle('auto-pile-count-zero', Number(count) === 0);
}
```

★**0 の判定を「文字列が '0' か」で書いていない。**初期表示の `'-'` も同じ欄に入る。
数として読み、`'-'` は `NaN` なので暗くならない —— それでよい(**まだ何も届いていない状態**である)。

★番人は2層である。verify 69-8 が**同じ盤面の中で 0枚と2枚のバッジの色を比べ**(色の値は書かない)、
`Batch69BoardTest` が **直書きが1つも残っていないこと**と **8箇所すべてが1本を通ること**を読む。

### 5-2. ★山札0枚を特別扱いしなかった(採らなかった案)

山札切れは敗北の直前であり、そこだけ光らせたくなる。採らなかった理由は、
**そこだけ例外を作ると「0枚は暗い」という読み方そのものが壊れる**ためである。
危険の告知はログと LP が担う層であり、**1つの印に2つの意味を持たせない**。

## 6. ★★★接続バーは作らなかった(穴5)

マスター確認のうえで、**69 では作らない**と決めた。候補 H(通常モードの切断の扱い)へ丸ごと譲る。

理由は、手動モードの Batch 33 が**自分で書いている**とおりである ——

> **番人は `send()` であり、オーバーレイではない。**

**安全側に見える簡易版**だからである。
簡易版は「足りない」と分かる形で足りないが、これは「足りている」と読ませてしまう。

| 10 | 山札のバッジだけ直書きへ戻す(**verify と JUnit の2件**) | verify 69-8 / `Batch69BoardTest` |
| 11 | 中段の巻きを止める | verify 69-9 |

★軸6 と軸10 が **2件ずつ**なのは、**照合先が2層あることの証拠**である ——
同じ改変で「サンドボックスの番人」と「マスターの手元の番人」が**両方とも**落ちることを確かめている。

### 9-1. ★裁定304 の罠は 69 には無いが、別の形が在る

69 が触ったのは CSS と JS だけなので「条件を落とすとコンパイルが通らない」は起きない。
ただし **JS では別の形で同じ罠が起きる** —— 文を消して構文を壊すとページ全体が死に、
狙った検査どころか全部が落ちる。**それは OK ではなく EMPTY である。**
69 の改変は **独立した1文の削除**か **値・式の置き換え**だけにしてある。

### 9-2. ★壊しどころが無い項目(裁定196 の正直な扱い)

- **接続バー** …… 69 では**作っていない**(6章)。無いものは壊せない。
- **ホバープレビューの出る位置** …… 「候補を隠さないこと」は**位置ではなく、出さないこと**で
  担保している(軸4)。位置を変える改変は、隠れるかどうかが**盤面の中身に依存する** ——
  壊し検証の答えが盤面次第で変わるものを、測れるふりをして測らない。
- **右列の中段が溢れたときに「気づけるか」** …… 巻けることは測れる(軸11)が、
  **人が気づくか**は機械には測れない。実機確認の依頼として残してある。

### 9-3. ★実装中に壊し検証以外で1件見つけた

verify を初めて通したとき、**手札のホバーだけが出なかった**。
原因は実装ではなく**検査の書き方**で、43-3(禁忌の帯の開閉)を試したあとの状態が残っており、
`.auto-taboo-strip`(`position: absolute` で手札の上に重なる)が開いたままだったのである。

★**実マウスの検査は「何の上に居るか」まで決めておく。**
`tabooOpen = false; syncTabooRow();` を先に置き、
さらに **帯が畳まれていること自体を検査の条件に入れた**(条件にしないと、
次に誰かが状態を残したときに**また同じ原因で落ちて、実装を疑う**ことになる)。

★68 の 9-1(検査の並び順)と同じ種類の収穫である ——
**壊し検証や新しい検査は、実装ではなく番人の書き方の誤りを見つけることがある。**

## 10. ★★★69 の教訓 —— 「途中」

64 は**時間**、65 は**空間**、66 は**予定**、67 は**写し**、68 は**代用**だった。
**69 は「途中」である。**

- 44 は「**まずはリーダーから**」と書いてホバーの器を作り、そこで止まった。
- 45 は右列を**横に**詰めて、**縦が余ったこと**を見なかった。
- 44 は枚数の書き込みを8箇所に散らしたまま「書き込み先だけが移る」と書いた。

★**どれも、そのバッチとしては正しく完了している。**
だから試験は緑であり、誰も赤くしない。

★★**時間・空間・予定・写し・代用は「離れていく」形の欠陥である** ——
前提が動いたのに実装が付いていかない。
**途中は動かない。動かないから気づかれない。**
65 が見つけたのは、その**動かなさ**である。

★★★だから **「まずは〜から」「簡易版」「今はこうしておく」と書いた実装は、
書いた本人が次の一歩を書き残すだけでは足りない** ——
**次に誰かがその場所を測ったときに見つかる形**にしておくのがよい。
69 が verify に「空白が埋まっている」「ホバーが場と手札に出る」を置いたのは、
**もう一度止まったら赤くなる**ようにするためである。

## 11. 理解確認 Q&A

**Q1. CSS を触っただけなのに、なぜ JUnit を2件足したのか。**
A. **回る場所が違うからである。**verify は Playwright が要り、マスターの手元では回らない。
「フェイズが増えたのに進行表が6つのまま」「バッジの書き込みが直書きへ戻った」の2つは
**壊れたら致命的で、しかもファイルを読むだけで測れる**。
★逆に「色が違って見えるか」「空白が埋まっているか」は JUnit に置かなかった ——
実測でしか測れないものを文字列で測ると、**「書いてあるが効いていない」を緑にしてしまう**。

**Q2. 自陣と敵陣の色を、なぜ新しく選ばなかったのか。**
A. **既に決まっていたからである。**`.opponent-side` の赤と `.my-side` の青は Batch 8 以前から在る。
別の赤・別の青を選ぶと、**同じ盤面に2系統の「相手の色」**が並ぶ。
★値を2箇所に置くこと自体は避けられない(CSS に参照の機構が無い)ので、
**一致を verify 69-2 が実測どうしの突き合わせで見張る**(裁定130・65 の流儀)。

**Q3. 「対象を選んでいる最中はホバーを出さない」は、やりすぎではないか。**
A. やりすぎではない。`.auto-hover` は**固定位置**に出るので、
盤面の候補と**重なる位置が盤面の中身によって変わる**。
「重なったときだけ出さない」は判定が盤面依存になり、**測れないものになる**。
★出さないと決めれば、**選んでいる最中に大きな面が要る場面が無い**という事実で正当化できる。
★★実際に危ないのは割り込みであり、69 の最初の実装は**そこを見落としていた**(3-3)。

**Q4. 右列の中段が溢れる件は 69 と関係ないのに、なぜ直したのか。**
A. **69 が置いた進行表が、その箱の最後の子になったからである。**
関係が無いまま放置すると、次に「進行表が変な位置に居る」という報告が来たときに、
**進行表の実装を疑う**ことになる —— 原因はそこではないのに、である。
★★それに、直し方が1行で、**巻けるようにするだけなら何も失わない**。
「気づけるか」は別の穴として書き残した(9-2)。

**Q5. 接続バーを作らなかったのは、逃げではないか。**
A. 逃げではない。**帯だけ作るほうが逃げである。**
帯は宣言であり、操作を止めるのは `send()` のガードである(手動モードの 33 が自分でそう書いている)。
ガードの無い帯は「**安全側に見える簡易版**」であり、
人はそれを見て安心するのに操作は相手に届かない。
★通常モードに切断の追跡が無いことは 66 が既に明文化した穴であり、
**69 が新しく作った穴ではない**。候補 H が丸ごと引き受ける。

**Q6. `battle.css` の版数を5枚とも上げたのはなぜか。1枚(battle.html)でよいのでは。**
A. **版数はファイルに付くものであって、ページに付くものではない。**
1枚だけ上げると、同じ `battle.css` が**ページによって別の版数で要求される** ——
古い版数で要求したページだけが、ブラウザのキャッシュから 49 を受け取り続ける。
★69 の変更は `.auto-*` だけなので実害は通常モードの盤面に限られるが、
**「実害が出る組み合わせを数えてから決める」のは、次に誰かが共通部分を触ったときに破れる**。

**Q7. 進行表に [次のフェイズへ] を置かなかったのはなぜか。押しやすいのに。**
A. **押せる条件の判定が2箇所に増えるからである**(裁定130)。
今その操作を出すかどうかは `renderControls` が決めており、
そこには観戦者・割り込み中・自分の番か、という3つの条件が入っている。
進行表にも入口を作れば、**同じ3条件を2箇所で守る**ことになる。
★進行表は**位置を伝える表示**であって、操作の入口ではない。

**Q8. clone のコミットメッセージが `batch67` だったのに、なぜ作業を止めなかったのか。**
A. **止める理由は「メッセージが古いこと」ではなく「中身が古いこと」だからである。**
68 が作ったはずのファイル7つと、撤去したはずのメソッド1つを実際に確かめ、
`mvn test` が **754件**(68 の値)で緑になることまで見た。
★v75 の手順は「`git log -1` の日付を確かめること」だが、
69 の実測では**日付は新しく、メッセージだけが古かった** ——
確かめるべきは日付でもメッセージでもなく、**そのバッチが作ったはずのものが在るか**である。
この読み替えを v76 の手順に書いてある。
