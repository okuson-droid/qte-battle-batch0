## 1. 剛火の将 —— 常在の体力修正を、どこに置くか

### 1-1. 何が変わったか

- 旧: 「起動能力(1ターンに1回): 自分のライフを2減らす。このターン中、次に手札から使用する
  火文明ミニオンのコストを-1する(0にはならない)。場にある【速攻】を持つカードのHPを+2する。」
- 新: 「場にある【速攻】を持つカードのHPを+2する」

起動能力が丸ごと消えた。その**登録は Batch 55 が削除済み**であり(rework-triage.md 2章)、
58 がやったのは (a) 残っていた常在効果の実装と (b) 割引の死んだコードの掃除である。

### 1-2. ★「盤面参照型の体力修正が出た時点で StatCalculator へ移す」を、移さずに済ませた

`MinionInstance.getMaxHp` の説明文には Batch 12 から次の一文が書いてあった。

> 現行の体力修正がすべて固定値(+1 / +2)であり、手札枚数や墓地枚数のような
> 盤面の参照を必要としないためである。……**盤面参照型の体力修正が出た時点で StatCalculator へ移す。**

《剛火の将》はその「盤面参照型」に見える。しかし**よく読むと2つの参照が混じっている**。

| 参照するもの | 動くか |
|---|---|
| どちらかのリーダーが《剛火の将》か | **対戦中に変わらない**(リーダーは交代しない) |
| そのミニオンが【速攻】を持つか | **動く**(効果で後から付く) |

動かないほうを**場に出る瞬間に1度だけ写し**、動くほうを**読むたびに見る**——
これで `getMaxHp` の中に閉じたまま、常在として正しく振る舞う。

- `StatCalculator.rushHpBonus(GameState)` …… 規則の正(誰に何点付くか)
- `MinionInstance.rushHpBonus` …… 写した加算量
- `MinionInstance.getMaxHp` …… `hasKeyword(Keyword.HASTE)` を読むたびに見て加算

★これは Batch 52 の《不敗鉄人闘太》(`statPerUnderCard`)と**まったく同じ流儀**である ——
値は `EvolutionSpec` が持ち、場に出るときに1度だけ写し、実際の加算は読むたびに束を数える。
先例がある形をもう一度使ったので、`getCurrentHp` の呼び出し元(破壊判定・ビュー・
`HP_5_OR_LESS` フィルタ)は**1箇所も書き換えていない**。

★**Batch 12 の一文は今も有効である。** 手札枚数のように「読むたびに盤面が動く」体力修正が
出たら、そのときは本当に `StatCalculator` へ移すことになる。

### 1-3. ★実体を作る入口を1本にした

写し忘れを構造で防ぐため、`new MinionInstance(...)` を呼ぶ2箇所
(`GameService.summonToField` = 召喚 / `GameActions.putIntoFieldByEffect` = 効果による登場)を
**`GameActions.newFieldMinion` 1本**に集約した。

```java
public MinionInstance newFieldMinion(GameState state, CardMaster master, boolean fromTaboo) {
    MinionInstance minion = new MinionInstance(master, state.getTurnNumber(), fromTaboo);
    minion.setRushHpBonus(stats.rushHpBonus(state));
    return minion;
}
```

副作用として `GameActions` が `StatCalculator` を1つ持つようになった。
`StatCalculator` はカードマスタしか見ないので循環はしない。

★**壊し検証のケース4がこの分担を測っている。** `newFieldMinion` の写しを潰すと、
**召喚の経路から出たミニオンだけ**が常在を失う —— 試験の足場
(`AutoGameFixture.putOnField`)は別に写しているので、他の試験は落ちない。
「どちらの経路が抜けたか」まで見分けられる形になっている。

### 1-4. ★【速攻】は HASTE であって RUSH ではない

`Keyword` は `HASTE("速攻")` と `RUSH("突進")` を**別々に**持っている。
実装中に一度取り違え、《スカイ・スワロー》のHPが上がらずに試験が落ちた。

**壊し検証のケース3に、この取り違えをそのまま残してある。**
将来この行を「RUSH のほうが名前として自然だ」と直す人が出たとき、番人が止める。

### 1-5. 両者参照と累積

本文は「**場にある**【速攻】を持つカード」であり「自分の」と書いていない。
裁定156(2) により**両者の場**に効く(旧台帳の注記も「記法規約どおり両者参照」と書いている)。

さらに**両者のリーダーが《剛火の将》なら常在が2つ重なって +4** になる。
常在の既定の累積であり、このカードだけの特例ではない
(《サービスブレイク・メリィナ》の「自分の他のミニオンのAttack+1」と同じ扱い)。

★**「相手の場のミニオンにも書き込まれること」には壊しどころが無い。**
加算量は場に出るすべてのミニオンへ無条件に写しており、側で分ける分岐が構造として存在しない。
壊せるのは「どちらのリーダーを数えるか」(ケース2)のほうである。

### 1-6. `pendingFireMinionDiscount` の掃除

起動能力が消えたので、割引を運んでいた仕掛けは全部死んだ。4箇所から落とした。

| ファイル | 落としたもの |
|---|---|
| `PlayerState` | フィールド `pendingFireMinionDiscount` と `startTurnReset()` のリセット |
| `GameService.playMinion` | 「次に使う火文明ミニオン1体で消費する」分岐 |
| `StatCalculator.effectiveCost` | 火文明ミニオンのコスト-1(下限1)の分岐 |
| `SpellDisposition` | 説明文の「同じ方式の先例」としての言及 |

★`PlayerState.pendingSacrificeCount`(死者蘇生)の説明文がこれを先例として引いていたので、
**その参照だけを別の言い方に書き直した**。消すのではなく訂正する(落とし穴の書き方の決まりと同じ)。

### 1-7. 「効果未実装」の印が0枚に戻った

`EffectImplementationTest.効果未実装のカードは剛火の将だけである` を
**`効果未実装のカードは1枚も無い`** に書き換えた。

★名指しのままにしなかったのは、**別のカードの実装が抜け落ちたときに素通りする**からである。
「剛火の将ではない1枚」が現れても `containsExactly("剛火の将")` は落ちる —— が、
落ちた理由が「剛火の将が実装された」なのか「別の1枚が壊れた」なのか読み取れない。
0枚を測る形なら、落ちた時点で「何かが未実装になった」だけが確実に言える(裁定196)。

## 3. 英知の継承者 —— 引いた後に選ばせる

- 旧: 「【召喚時】【知識】を持つカードを1枚手札から捨てても良い。そうしたら【知識】を行う。」
  (任意。捨てて1ドローなので手札の増減は0)
- 新: 「【召喚時】カードを4枚引く。その後カードを3枚捨てる」(必須。差し引き+1)

### 3-1. TargetSpec を消して割り込み(a9)へ移した

捨てるのは**引いた後の**手札からである。使用宣言時に選び終える `TargetSpec` では表現できない。
《海淵獣ラカブ》(3枚引いて1枚捨てる)とまったく同じ形に移した。

```java
register("QTE-M-WATER-19", TriggerType.ON_SUMMON, ctx -> {
    ctx.actions().drawCards(ctx.room(), ctx.owner(), 4);
    int count = Math.min(3, ctx.owner().getHand().size());
    requestDiscard(ctx, count, count, ResumePoint.WISDOM_HEIR_DISCARD, ...);
});
```

★`ResumePoint` は**分けてある**(`WISDOM_HEIR_DISCARD`)。
《ラカブ》《潮獣コアンチ》《アクア・サーチ》と処理は同じだが、共有すると
ログに出す名前を決められなくなる(`ResumePoint.TIDE_COANCHI_DISCARD` の説明)。

### 3-2. `Math.min(3, 手札の枚数)` を挟んである理由

4枚引いた直後なので手札は必ず3枚以上ある —— **ように見える**。
しかし《断罪の大天使》は「相手の3枚目以降のドローを墓地送りに置換」するので、
**引けなかった状態で解決に来ることがある**。あるだけ捨てる(裁定191・217 と同じ形)。

## 5. ストーム・カイザー —— 代替コストが0でない【特殊召喚】

- 旧: 「このターン中に自分がカードを4枚以上使用している時、コストを支払わずに場に出せる。」
- 新: 「【速攻】/【特殊召喚】(このターン中に自分がカードを5枚以上使用している時、
  コストを1払って場に出せる)」

3点が変わった。条件 4→**5**枚、代替コスト 0→**1**、そして**【速攻】が付いた**
(印刷コストも 5→7、体力も 4→2 に変わっているが、これは `manual-cards.json` から読むので実装不要)。

```java
specialSummons.put("QTE-M-WIND-8", new SpecialSummonSpec(
        (state, player, handIndex) -> player.getCardsUsedThisTurn() >= 5,
        1, TargetSpec.of(), ctx -> { }, ctx -> { },
        "このターン中に自分がカードを5枚以上使用: コスト1で召喚します"));
```

★**新しい仕組みは要らなかった。** `SpecialSummonSpec` は Batch 3 の時点から `mpCost` を
持っており、《極炎竜 ヴォルカニクス》が既に 1 を使っている。`of(...)` の短縮形が
`mpCost = 0` 固定なので、7引数の完全な形に書き換えただけである。

★使用枚数の数え上げは**自身を含まない**(裁定1)ので「5枚以上」はそのまま `>= 5` である。

★**壊し検証を2件に分けてある**(条件の5枚とコストの1)。1件にまとめると、
マナが十分にある盤面では条件だけを戻しても落ちてしまい、コストの軸が測られない。

## 6. 風弾の跳弾 —— 本文の順序は入れ替わったが、解決の順序は変わらない

- 旧: 「自分のミニオンを1体**手札に戻す**。そうしたら相手のミニオン1体に**2**ダメージ。
  このカードのコストを**+3**してもよい。そうした場合このカードを墓地に置く代わりに手札に戻す。」
- 新: 「このカードのコストを**+2**してもよい。そうした場合このカードを墓地に置く代わり手札に戻す。
  自分のミニオンを1枚**破壊する**。そうしたら相手のミニオン1体に**3**ダメージ。」

### 6-1. 3つの軸

| 軸 | 旧 | 新 | 効き方 |
|---|---|---|---|
| 自分側のコスト | 手札に戻す | **破壊する** | 取り返しがつかなくなった(【破壊時】は誘発する) |
| ダメージ | 2 | **3** | 除去の射程が広がった |
| 追加コスト | +3 | **+2** | 使い回しが安くなった(合計 4 → 3) |

★rework-triage.md は「**解決順が逆転**」と書いているが、これは**本文の並びの話**である。
追加コストは使用宣言に付随する二者択一であり(`EnhancedCostSpec` の説明)、
支払いは効果の解決より前に必ず終わっている。本文のどこに書かれていても同じ順序で解決する。
実装では `ctx.enhanced()` の判定を先頭へ移したが、これは**本文の読みやすさに合わせただけ**で
挙動は変わらない。

### 6-2. 「そうしたら」を条件として書いた

```java
boolean destroyed = false;
for (var t : ctx.targets().get(0).minions()) {
    ctx.actions().destroyMinion(ctx.room(), t.owner(), t.minion());
    destroyed |= !t.owner().getMinionZone().contains(t.minion());
}
if (!destroyed) { /* ログを出して終わり */ return; }
```

★**現行のカードプールでは偽になる盤面を作れない。**
自分のミニオンの破壊は必須の対象であり、《聖光の守護聖》の「相手の効果では破壊されない」は
自分のミニオンには掛からない。それでも分岐を残しているのは、本文が「そうしたら」と
書いているからである(裁定217 の系)。

★57 の《絶望の連鎖》と**同じ立場のもの**が、これで2件目になった。
《大天使 ミカエル》(区分5・裁定272 待ち)の「戦闘時ダメージを受けない」が入っても
効果破壊は止まらないので、観測できるようになるのは「効果では破壊されない」を
自分のミニオンに掛けられるカードが出たときである。

## 7. カース・ボーン —— 闇の資源が裏向きマナから墓地へ寄った

- 旧: 「【召喚時】自分のマナゾーンの表向きのカード1枚を、裏向きにする。
  裏向きにできなかったとき破壊する。」(1/2/1)
- 新: 「【召喚時】自分のミニオンを1体破壊する。破壊したミニオンのコストと同じ数
  山札の上から墓地に置く。【還元】」(2/1/1)

★**参照するゾーンが裏向きマナ → 自分の場に、産物が裏向きマナ → 墓地に変わった。**
Ver1.1 全体で闇の資源が「裏向きマナ」から「墓地」へ寄っており、
《冥府の禁皇》(裏向きマナ→墓地)・《マナを貪る怨霊》(マナ裏返し→墓地から裏向きマナへ)も
同じ向きに書き換わっている。**このカードは闇の裏向きマナを作る起点だった**ので、
起点が消えたことは闇文明全体の遊び味に効く。

### 7-1. 対象を割り込みで選ばせた理由

`TargetSpec` にすると、**自分の場に他のミニオンが1体も居ないときに召喚そのものが弾かれる**
(48 の落とし穴)。宣言時の検証は場に出る前に走るので、**自身が候補に居ない**からである。

割り込み(`ResumePoint.CURSE_BONE_SACRIFICE`)なら解決時に問い合わせるので、
**候補には自分自身が含まれる**。他に何も居なければ自分を破壊するしかない ——
Ver0.4 の「裏向きにできなければ自壊する」という性格がそのまま引き継がれた形になる。

★候補が1体(=自分だけ)なら問い合わせずに自動決定する
(《地砕きの突撃兵》《降臨の伝道師》《風護の杖》と同じ流儀)。

### 7-2. コストは印刷コストであり、破壊する前に読む

```java
Integer printedCost = victim.getMaster().cost();
int millCount = printedCost == null ? 0 : printedCost;
ctx.actions().destroyMinion(...);
if (millCount > 0) { ctx.actions().mill(...); }
```

- **印刷コスト**である。場のミニオンには動的コストの概念が無い
  (コストが動くのは手札にある間だけ。`StatCalculator` の《透キ通ル・アヤカシ》の注)。
- **破壊する前に読む**。破壊した後では場から居なくなっており、
  「破壊したミニオンのコスト」を数えようがない(裁定216 と同じ向きの読み方)。

### 7-3. 【還元】との合わせ技

自分を破壊した場合、カース・ボーン自身は**墓地ではなく裏向きでマナへ**行く
(`sendToTrashOrRestore` が【還元】を見る)。
2コストのミニオンが、盤面に何も残さない代わりに**マナを1枚増やしつつ墓地を2枚肥やす**——
闇のセルフミル系(《群がる死霊王》《墓場の怨念集合体》《悪夢》)の燃料として噛み合う。

★試験ではここを明示的に測っている(墓地には**ミルした2枚だけ**が入り、
カース・ボーンはマナゾーンの末尾に裏向きで居る)。

## 8. 地脈の覚醒 —— 空欄からの実質新規実装

- 旧: 本文が**空欄**。【還元】だけを持ち、解決時の固有処理は無かった。
- 新: 「自分のマナからカードを1枚手札に加える【還元】
  (「地脈の覚醒」の効果はターンに1回のみ発動する)」

### 8-1. 候補は表向き・裏向きの両方

本文が向きを限定していないためである(裁定211)。
《地砕きの突撃兵》の「自分のマナから1枚選び手札に戻す」とまったく同じ扱いであり、
`GameActions.returnManaToHandAt` をそのまま使っている。

### 8-2. ★自分自身は候補に入らない

【還元】でマナへ置かれるのは**効果の解決より後**なので、候補を作った時点ではまだマナゾーンに居ない。
またマナゾーンの**末尾に足されるだけ**なので、選択待ちの間に既存の位置がずれることもない。

★これは偶然ではなく、`GameService.playSpell` が
「効果の解決 → 使用後の行き先(墓地/還元/消滅)」の順で進むことから出てくる。
順序を入れ替えると、**唱えたばかりの《地脈の覚醒》を自分で拾い直せる**ようになってしまう。

### 8-3. ターン1回制限は「発動」だけを止める

```java
if (!ctx.owner().tryUseLeylineAwakening(turn)) {
    ctx.room().addLog("【地脈の覚醒】: このターンは既に発動しているため、効果は発動しません");
    return;
}
```

★**2枚目を使用すること自体は止めていない。**
本文は「効果は…発動しない」であって「使用できない」ではないためである。
2枚目は何も起きずに【還元】だけを残す(コスト2を払ってマナを1枚増やす、だけのカードになる)。
★この読みは**裁定276 として確認を依頼している**(下記10章)。実装は本文どおりの側を採った。

★制限は**ターン番号を刻んで**持つ(`PlayerState.leylineAwakeningTurn`)。
真偽値にしないのは裁定156(3) —— 「ターンに1回」は毎ターンリセットされるが、
`startTurnReset()` が走るのはターンプレイヤーだけである。
`recordManaPlacement` と同じ考え方であり、これで4つ目・5つ目の先例になる。

★**判定と記録を1つのメソッド(`tryUseLeylineAwakening`)にしてある。**
分けると「判定したが記録し忘れる」経路が生まれる ——
このカードは同じターンに2枚目を使えるので、実際に踏める。

## 9. 番人の追加と、構造の手当て

### 9-1. `registerWindCards()` を分割した

《風弾の跳弾》の書き換えでこのメソッドが 330 行になり、`check_structure.py` が
△要確認を出した。スペルとウェポンを `registerWindSpellsAndWeapons()` へ分けた
(Batch 57 が闇文明で行ったのと同じ処置。**中身は1行も動かしていない**)。

### 9-2. `AutoGameFixture.putOnField` も常在の値を写す

足場が `new MinionInstance(...)` を直接呼んでいるため、
本物の入口(`GameActions.newFieldMinion`)と同じ値を写す必要がある。
写さないと **「召喚したときだけ効いて、最初から置いたミニオンには効かない」** という、
盤面には存在しない状態を試験が作ってしまう。

### 9-3. `tools/batch58_break_check.py`(19ケース・OK 19)

★**改変は「軸」ごとに1件ずつ当てた**(57 の教訓)。
《風弾の跳弾》の3つの軸には3件、《ストーム・カイザー》の2つの軸には2件を別々に当てている。

★**壊しどころが無い項目**は、その理由をスクリプトの冒頭に書き残した。

- 《剛火の将》の「起動能力を持たない」…… 登録が**無いこと**を測る試験であり、
  壊すには登録を足すことになる。それは実装の改変ではなく別のカードを作る行為である。
- 《背水の烈火使い》の【守護】・《知恵の双翼》の【知識】【守護】…… キーワードは
  テキストから作られる(裁定158)。コード側に壊す分岐が存在しない。
- 《剛火の将》の常在が相手の場のミニオンにも書き込まれること…… 側で分ける分岐が
  構造として無い。

★**`EXPECTED_NG` は空である。** 57 は1件(《絶望の連鎖》の「そうしたら」)を持っていたが、
58 で同じ立場のもの(《風弾の跳弾》の「そうしたら」)は**壊し検証の対象にしていない** ——
観測できないと分かっているものに改変を当てても、得られるのは既知の NG だけである
(理由は本書 6-2 と `EXPECTED_NG` の空であることを対にして記録した)。

## 10. 積み残しと申し送り

### 10-1. ★新しい裁定依頼1件(裁定276)

《地脈の覚醒》の「ターンに1回のみ発動する」が、
**(a) 2枚目の使用そのものを禁じるのか、(b) 使用はできるが効果が発動しないだけか**。
本文どおりの (b) で実装済みなので、**58 はこの回答を待っていない**。
(a) だった場合は `GameService` 側の使用可否に判定を1つ足すことになる。
全文は `notes/batch55-ruling-requests.md` の末尾にある。

### 10-2. 区分5 の残り7枚

裁定268〜274 が付き次第、次のバッチで消化する。
