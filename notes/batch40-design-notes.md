## 1. ★★★autosave は「今の状態を写す」だけでは裁定119 を満たさない

### 1-1. 写すだけだと、読み込んだ瞬間に写しも入れ替わる

裁定119 はこう言っている。

> [デッキ読込] に確認は足さない。**優先順位9 の autosave が入れば組みかけは失われない**ので、
> 問い自体が要らなくなる。

素直に読むと「編集内容を localStorage に写しておけばよい」に見える。**足りない。**
写しが1枠しか無いと、デッキ読込のあとその1枠は**読み込んだデッキ**になる。
組みかけはブラウザのメモリからも localStorage からも消える。
これは 38 までの「黙って捨てる」と同じ結果であり、
**確認を足さない理由が成り立たなくなる。**

したがって枠を2つ持つ。

| 鍵 | 中身 | いつ書くか |
|---|---|---|
| `qte-deckmaker-draft` | **今**の編集内容 | 変わるたび(renderAll の末尾) |
| `qte-deckmaker-undo` | **置き換えられる直前**の内容 | デッキ読込・文明変更の直前 |

退避があるときだけ、トップバーに **[元に戻す]** が現れる。
これが「失われない」の実体である —— 保存されていることではなく、**取り戻せること**が答えである。

### 1-2. ★★[元に戻す] は入れ替えである

押すと、退避を今の状態に当て、**今だった状態を退避へ書く**。
つまりもう一度押せば戻る。

- ★**取り消せる操作に確認は要らない。** 押し間違いが1クリックで戻るなら、
  問いを1つ増やすほうが害である(裁定113 と同じ理屈)。
- ★片道にすると「元に戻す、を元に戻せない」という別の後悔を作る。
  この画面で失うものは常に「組みかけのデッキ」1つなので、2つの状態を往復できれば足りる。

**機械判定あり**(もう一度押すと読み込んだほうへ戻る)。

### 1-3. ★★autosave を入れると、既にある確認の本文が嘘になる

39 の確認モーダルの本文はこうだった。

> メイン文明を 水 に変更する。**組みかけのデッキは失われる。**

[元に戻す] が入った今、これは事実ではない。36 の 3-3 は
**「確認の本文に嘘を書かない」**と決めている。文言を直した。

> メイン文明を 水 に変更する。組みかけのデッキは空になる(**[元に戻す] で戻せる**)。

★一般形: **仕組みを足したら、その仕組みを説明していた文言のほうが古くなる。**
直すのはコードではなく文言である。

### 1-4. ★★★保存より先に初期化が走る、を踏まないこと

これは autosave を後付けするときの定番の事故である。

起動の流れはこうなっている。

```
fetch(/manual/api/card-library) → loadLibrary() → resetDeck() → renderAll() → autosave
```

**renderAll が autosave を呼ぶ**ので、ライブラリが届いた時点で
「空のデッキ」が localStorage に書かれる。そのあとで復元しようと読んでも、
**読む前に空で上書きされている。**

直し方は1行である —— **保存してある内容は、ライブラリより先に読む。**

```js
const pendingDraft = parseSnapshot(readStore(DRAFT_KEY));   // ★fetch より前
buildStaticUi();
fetch(LIBRARY_URL).then(...)
```

★番人は「再読込しても組みかけが残っている」1項目である。順序を誤ると必ず落ちる
(7章の 6 で実測した)。

### 1-5. ★★1つの形(スナップショット)ですべてを表す

autosave・退避・復元・文明変更・デッキ読込は、見た目には5つの機能だが、
**やっていることは2つしかない**。

- `snapshot()` —— 今の編集内容を1つの値にする
- `applySnapshot(s)` —— その値を画面に当てる

置き換えは `replaceDeck(s) = stashUndo(); applySnapshot(s)` の1本にした。
**デッキ全体が入れ替わる経路はこれ1つだけである**(設計判断28)。

★これが効くのは「項目を足したとき」である。たとえばデッキ名は
snapshot に入れてあるので、autosave にも退避にも復元にも**自動的に乗る**。
形が5つに分かれていたら、5箇所のうち3箇所だけ直る日が来る。

★`applySnapshot` は**退避しない**。退避するかどうかは呼ぶ側の判断である ——
復元(起動時)と [元に戻す] は「捨てているものが無い」ので退避しない。

### 1-6. ★autosave の発火点は1つである

`renderAll()` の末尾1箇所だけで呼ぶ。デッキを変える経路はすべて renderAll を通るので、
**新しい経路を足しても保存し忘れない**(裁定68「発火点を増やさない」と同じ形)。

★ただし renderAll は絞り込み・並べ替え・検索の1打鍵ごとにも走る。
localStorage への書き込みは同期なので、**実際に変わったときだけ書く**
(直前に書いた JSON と比較する)。29 の「描画関数の中で幅を実測しない」と同じ考え方である。

★デッキ名の入力欄だけは renderAll が読まない唯一の状態なので、そこからも呼んでいる。
**入力のたびに renderAll を回すことはしない** —— 名前を打つたびに
プールの150枚を作り直す理由が無い。

### 1-7. ★鍵は部屋に紐づかない(裁定31)

`qte-deckmaker-draft` / `qte-deckmaker-undo`。
この画面には部屋という概念がそもそも無い。既存の鍵は
`qte-manual-occupant-{roomId}` / `qte-manual-help-seen` / `qte-manual-sound` の3つで、
部屋に紐づいているのは occupantId だけである(あれは席の身分証だからである)。
**機械判定あり**(鍵の一覧を見て、部屋IDらしきものが混ざっていないことを確かめる)。

★localStorage は例外を投げうる(プライベートモードの一部・容量超過)。
盤面の 0-1 章と同じく**握りつぶす** —— 保存できないことで編集が止まってはいけない。

## 2. ★★★マナカーブ —— 区切りを2つ持たない

### 2-1. 目盛りはコストフィルタと同じ `COST_KEYS` である

レビューの「コストは**フィルタ**であって**可視化**ではない」は、
裏を返せば**同じコストという軸が2つの用途に使われる**ということである。

- フィルタ: 0 / 1 / … / 9 / 10+ の11個(38 から)
- カーブ: ここで別の区切り(0〜7 / 8+ など)を選ぶと、
  **「6でフィルタした結果」と「カーブの6」が別のものを指す。**

同じ配列を両方が読む(設計判断28)。**機械判定あり** ——
カーブのラベルとフィルタのボタンの文言が一致することを見ている。

### 2-2. ★★数えるのはメインデッキだけである

禁忌デッキのカードもコストの数字を持っているが、**支払い方が違う**(総合ルール 2-3)。

> 禁忌コストの支払い方法: 表向きのマナをコスト数だけ裏向きにする /
> すでに裏向きのマナを直接墓地へ送る

同じ横軸に並べると、「7コストが3枚ある」が**2つの別の意味**を持つことになる。
カーブは「何ターン目に何が置けるか」を読むための絵であり、
その読み方が通用しない札を混ぜると絵として嘘になる。

★**機械判定あり。** 検証は禁忌にコスト3の札を1枚入れたうえで、
**カーブの3の列が動かないこと**を見ている。
「メインだけを渡している」という式ではなく、**結果の数**を測る。

### 2-3. ★0枚の列も残す

棒が消えると目盛りの位置が動き、隣とくらべる用途に使えなくなる。
0の列には細い線だけを残して**軸**にしてある。
★空のデッキで何も出ないのは可視化ではない —— 「何も入っていない」も情報である。

### 2-4. ★色は `battle.css` の `:root` から読む(裁定108)

`civColor(mainCiv)` が読んだ値を `--curve` という1つのカスタムプロパティに立て、
グラデーションは CSS 側で作る。**JS は「どの色か」を選ぶだけで「何色か」を知らない。**

★7章の 3 が示すとおり、**この結線の項目だけでは直書きを検出できない**
(たまたま同じ値を書けば通る)。直書きを止めているのは 39 が置いた走査の番人である。
逆に、`--civ-fire` を改名すると結線の項目だけが落ちる(7章の 3b)。
**2つは別のものを見ている。**

### 2-5. 統計は4つの内訳と平均コスト

平均コスト・ミニオン・進化・スペル・ウェポン。
★**進化ミニオンをミニオンに畳まない。** メイン40枚には算入するが(Batch 24 の裁定)、
出せる条件が違う以上、組む側にとっては別の札である。

## 3. ★★★検証一覧 —— 止めるのではなく、理由を見せてから通す

### 3-1. 保存を止めない

手動モードは**未実装のカードを場に出して試すための場所**であり、
サーバの読み込みも違反を**警告に留めている**(`ManualDeckImporter.validate`)。
デッキメーカーだけが「40枚でなければ書き出させない」と言い出すのは筋が通らない。

だから [デッキ保存] を押したときの動きはこうである。

- 条件を満たしている → **そのまま書き出す**(38 までと同じ)
- 満たしていない → **検証一覧を出す。** その中に [このまま保存する] がある

★[このまま保存する] を**一覧と同じ画面に置いた**のが要点である。
保存の手前に確認を挟むだけなら「何が足りないか」は分からないままで、
レビューの指摘(**「何が足りないか」の一覧が無い**)は解けない。

★**機械判定あり。** 不正なデッキで [デッキ保存] を押したとき、
**ファイルが1つも作られていないこと**を見ている(ボタンを押したかどうかではなく結果を測る)。

★39 の `selectCiv` / `applyCiv` と同じ形である(裁定112)——
関門(`exportJson`)と実行する中身(`writeDeckFile`)を分け、
**通る道と通らない道で同じ1本**を呼ぶ。

### 3-2. 項目はサーバと同じ5つである

`ManualDeckImporter.validate` が出す警告と1対1に対応させた。

| 項目 | 壊れる経路 |
|---|---|
| リーダーが1枚 | 組み始め |
| メインデッキ 40枚 | 組みかけ・デッキ読込 |
| 禁忌デッキ 8枚 | 組みかけ・デッキ読込 |
| メインの同名 4枚まで | **デッキ読込のみ** |
| 禁忌の同名 1枚まで | **デッキ読込のみ** |

★★下2つが**読み込みでしか壊れない**ことが、この機能が要る理由そのものである。
右クリックの追加は `changeCount` が上限で止める。
しかし**デッキ読込は外から来たファイルであり、UI の制約を1つも通っていない**
(設計判断27)。自分で組んだデッキだけを見るなら、38 までのカウンタで足りていた。

### 3-3. ★★文明の規則は項目に立てない

総合ルールの構築条件には「メインはリーダーと同一文明」「禁忌は他文明」もある。
**立てなかった。**

この画面では**メインと禁忌の区別が「文明が `mainCiv` と同じか」で決まっている**。
違反という状態が構造上作れない —— 他文明の札を読み込めば、それは自動的に禁忌側に数えられる。

★**守られていることを毎回報告する行は、本当に見るべき行を埋もれさせる。**
5行のうち2行が常に ✓ で意味を持たないなら、残り3行も読み飛ばされ始める
(裁定113「確認を増やすほど1つ1つが軽くなる」と同じ現象が、一覧の中で起きる)。

### 3-4. ★★規定枚数の正はサーバである。だから Java から読んで突き合わせる

`MAIN_SIZE=40` / `TABOO_SIZE=8` / `MAX_SAME=4` / `TABOO_SAME=1` は、
Java の `MAIN_DECK_SIZE` / `TABOO_DECK_SIZE` / `MAIN_NAME_LIMIT` / `TABOO_NAME_LIMIT` と同じ値である。

★**これは複製ではない。** 層が違い、役割が違う ——
サーバ側が正であり(設計判断27: クライアントのチェックは操作補助にすぎない)、
こちらは「組んでいる最中に見える」ためだけに在る。
★**しかし黙って離れていける点は複製と同じである。**
そこで検証が **Java のソースから定数を読んで**、ブラウザ上の値と突き合わせている。
期待値(40 や 8)は検証にも書いていない —— **正から読んだ値どうしを比べる**(裁定110)。

★38 まで禁忌の同名上限は `changeCount` の中に `1` と直書きされていて、名前が無かった。
**名前が無い値は突き合わせようがない。** `TABOO_SAME` を作ったのはそのためである。

### 3-5. ★★2つ目のモーダルは、39 が用意した形にそのまま乗った

39 は覆うものが1つしか無い時点で `modalStack` を入れておいた(裁定47)。
40 で足したのは **markup と中身の描画だけ**である ——
Esc・× ・フォーカスのトラップ・復帰・`role="dialog"` は1行も書いていない。

- 出口の id は `-close` で終わる(裁定34・35)。× と Esc はこれを `click()` する。
- 開閉は `openInfoModal` / `closeInfoModal` を通す(裁定51)。
- ★**初期フォーカスは [閉じる] を名指しする**(裁定52)。既定(× を除いた最初)だと
  [このまま保存する] に載る。**この画面の用件は読むことである** ——
  盤面の操作説明が × を名指ししているのと同じ理由である。
- ボタンには動詞を書く(裁定55)。「このまま保存する」/「保存する」。

★**機械判定あり**(初期フォーカス・Tab・Esc)。7章の 9 のとおり、
`openInfoModal` を通さずに `hidden` を直接操作すると3項目が同時に落ちる。
**規約に載せていないモーダルは静かに増えない。**

### 3-6. ★色だけで良否を伝えない

レビュー A-1 は「デッキメーカーの検証も ok/bad の色のみ」を挙げていた。
ヘッダのボタンは **「検証 OK」/「検証 3 件」** と文字で言い、
一覧の各行は **✓ / !** の記号を持つ。色は補助である。

★状態のクラスを `v-ok` / `v-bad` にしたのは、カウンタの `.ok` / `.bad` と
**名前を分けるため**である。あちらは「同じ値になったか」、こちらは「検証を通ったか」で
意味が違う。同じ名前にすると、片方の色を変えたときにもう片方が黙って動く(裁定32 と同じ話)。
