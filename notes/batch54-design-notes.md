## 0. このバッチが決めたこと(要約)

裁定152 は「賢魂：n を持つミニオンは、スペルとしても使うことができる」とだけ定めており、
**実装上の含意は P4 で個別に確認する**ことになっていた。着手前にまとめて15件の裁定を仰ぎ、
そのうえで実装した(裁定247〜259)。

**中核の判断は1つである ——**

## 1. テキストを割る(`CardTextKeywords`)

### 1-1. なぜ抽出層に手を入れたのか

53 まで、`CardTextKeywords.extract` は**本文全体**から【】を拾っていた。
賢魂を持つ7枚のうち《白ノ霊知者》だけが、賢魂より後ろにキーワードを持つ。

```
【進化】（風文明のミニオン1体）【召喚時】カードを2枚引く。ミニオンを1体選び破壊する。
【賢魂：2】自分のミニオン1体の攻撃力+1する。【還元】
```

53 の実装では、このカードは**ミニオンとして【還元】を持って**いた ——
場で破壊されると墓地ではなく裏向きでマナに置かれていたのである。

**マスター裁定(B1)は「賢魂の効果の一部」を選んだ**(裁定248)。
つまり **スペルとして使い終わればマナへ、ミニオンとして破壊されれば墓地へ**行く。

### 1-2. 引いた線

```java
public static Set<Keyword> extract(String text)      // 【賢魂：n】の手前まで
public static Set<Keyword> soulKeywords(String text) // 【賢魂：n】の後ろだけ
public static Integer soulCost(String text)          // n(全角・半角の両方を読む)
public static String soulText(String text)           // 後ろの本文(確認ダイアログ用)
```

**★規則は1箇所にしかない。** 読み方の規則はこのクラスだけが持ち、
`CardEffectRegistry` も `battle.js` もテキストを1文字も割らない(裁定158・裁定234)。

★境目が7枚すべてで正しく取れることは `SoulSpellTest.賢魂の手前のキーワードはミニオンの姿に属する`
が測っている。**「後ろにキーワードを持つカードは《白ノ霊知者》1枚だけ」**という形で、
カードデータが増えたときに気づけるようにしてある。

### 1-3. ★n をコードに書かなかった

`SoulSpellSpec` は**効果と対象要求だけ**を持ち、コストを持たない。
n は `CardTextKeywords.soulCost` が唯一の出どころである。

両方に書けば、カードデータを直したときにコードが古いままになる日が必ず来る。
これは裁定158(キーワードの正はテキスト)の延長であり、
`SoulSpellTest.賢魂の登録とテキストは一致している` が**登録とテキストの食い違い**を止める。

### 1-4. ★全角の「１」

《グレイヴガールズファン》だけが `【賢魂：１】` と全角で書かれている(他の6枚は半角)。
**カードデータは書き換えず、読む側で両方を取る**(マスター確認済み・裁定257)。

表記ゆれをデータの側で直すと、手動モードとデッキメーカーの表示も一緒に動く。
読む側で吸収すれば、**正は1つのまま**である。

## 2. 賢魂の使用は「スペルの使用」である(裁定152・裁定247)

裁定152 の「その使用はルール上『スペルの使用』として扱う」を、
**具体的に何が起きるか**まで確定させた(マスター裁定 A2)。

| | 内容 | 実装 |
|---|---|---|
| (1) | `cardsUsedThisTurn` と `spellsCastThisTurn` を進める | `afterCardUsed(..., isSpell=true)` |
| (2) | `ON_CARD_USED` を発火する | 同上 |
| (3) | 「スペルを唱えられない」に止められる | `RuleGuards.spellDenial` |
| (4) | スペルのコスト軽減・増加を受ける | `StatCalculator.effectiveSoulCost` |
| (5) | `ON_NEXT_SPELL` のオーラを消費する | `playSoulCard` の中 |

### 2-1. ★コスト計算を写さなかった

`StatCalculator.effectiveCost` は 150行ほどの軽減・増加の連なりである。
賢魂のために書き写せば、次にスペルの軽減が1枚増えたとき**片方だけが直される**(裁定163)。

そこで**基準コストと種別を差し替えて同じ計算へ流す**形にした。

```java
public int effectiveCost(state, owner, card)                 // (card.cost(),  card.type())
public int effectiveSoulCost(state, owner, card, soulCost)   // (soulCost,     CardType.SPELL)
private int effectiveCost(state, owner, card, baseCost, asType)   // 本体
```

★本体の中でカードIDを見ている分岐(《悪夢》《死者蘇生》など)は、
賢魂を持つ7枚のIDと一致しないので自然に素通りする。**条件を足していない。**

★**キーワードによる軽減はそのまま乗る**(マスター裁定 A3・裁定249)。
《戒律のガーディアン》の「【守護】を持つカードのコスト-1」は、
《グレイヴガールズファン》を賢魂として使うときにも効く ——
キーワードはカードが持つものであって、使い方で消えたりしない。

### 2-2. ★入口を分けた(`play-soul`)

`playCard` は**カードの種別**で分岐する。賢魂は「同じ種別のカードに2つの使い方がある」
という話であり、種別からは決まらない —— **どちらの姿で使うかはプレイヤーの宣言**である。

宣言を引数の真偽値で運ぶこともできたが、そうすると `playCard` の冒頭の検証
(ミニオンとして場に出せるか・進化素材が足りるか)を賢魂のときだけ飛ばす分岐が中に増える。
**入口を分ければ、どちらの規則を通るかが呼び出し位置そのもので決まる**(裁定207 の再適用)。

WebSocket の宛先も2つある: `play-soul` / `play-taboo-soul`。

### 2-3. `playConditions` は見ない

「代償を払えなければ使用できない」(《禁忌の代償》《絶望の連鎖》)の表は
**ミニオンとしての姿に紐づく条件**であり、賢魂の7枚は1枚も登録していない。
将来そういうカードが出たら `SoulSpellSpec` 側に条件を足すこと ——
姿ごとに分けるのが本筋である。

## 3. 使い終わったカードの行き先

### 3-1. 3つの行き先と、1つの「動かすな」

| 状況 | 行き先 |
|---|---|
| 通常(手札から) | 墓地。ただし**賢魂の姿が**【還元】を持つならマナへ |
| 禁忌デッキから | **消滅**(総合ルール3-6)。【還元】も置換も効かない |
| 効果自身が場に出した | **動かさない**(`SpellDisposition.KEPT_BY_EFFECT`) |

`SpellDisposition` に4つ目の値 `KEPT_BY_EFFECT` を足した。
他の2値(`TO_HAND` / `TO_DECK_BOTTOM`)が**置き換え先**を指すのに対し、
これだけは**「もう動かすな」という指示**である ——
場に出たカードをさらに墓地へ送ると、場と墓地の両方に同じカードが居ることになる。

### 3-2. ★【還元】の判定を引数にした

`GameActions.disposeUsedSpell` は `spell.hasKeyword(RESTORATION)` を見ていた。
賢魂を持つカードは2つの姿を持ち、キーワードは姿ごとに違うので、この形では区別が消える。

```java
public void disposeUsedCard(room, player, card, fromTaboo, boolean restoration)
```

★**還元の判定を呼び出し側で計算しないこと。**出どころは
`CardTextKeywords.extract` / `soulKeywords` の2つだけである。

### 3-3. 禁忌からの賢魂(マスター裁定 A6・裁定250)

**退けるマナは n 枚である。** 賢魂として使うならコストは n だからである。
★禁忌の支払いは**マナ枚数**で行うため、コスト軽減は乗らない(印刷の n をそのまま使う)。

## 4. ★禁忌由来の印を効果へ運んだ(`EffectContext.fromTaboo`)

《スタンディングテント》の【賢魂：2】は**使用しているカード自身を場に出す**。
禁忌デッキから使えば、**禁忌由来のまま場に立つミニオン**が生まれる ——
これは「効果による出す」から生まれる初めての例である。

印を持たせないと、そのミニオンが場を離れたとき**墓地へ行ってしまう**(消滅しなければならない)。

そこで `EffectContext` に `fromTaboo` を足し、
`GameActions.putIntoFieldByEffect` に5引数版(素材 + 禁忌由来)を足した。

★**他のすべての「効果で出す」は手札・墓地・マナ・山札から来るので、禁忌由来でありえない**
(禁忌カードはそれらのゾーンを通らない)。だから既定は `false` のままでよい。

★`EffectContext` のコンストラクタが3つになった副作用として、
`tools/check_records.py` の**既知の誤検出が3件から4件に増えた**(中身は同じ性質である)。

## 5. 7枚の実装

進化4枚の**素材条件は 52 で登録済み**である。54 が足したのは効果だけである。

| カード | ミニオンの姿 | 賢魂の姿 | 置き場所 |
|---|---|---|---|
| グレイヴガールズファン(闇5) | 【守護】のみ | 1引く → 1ミル | `soulSpells` |
| スタンディングテント(闇6) | 【守護】【召喚時】2引く | **自身を場に出し2ダメージ** | `triggers` + `soulSpells` |
| 英霊・タイガラム(光7・進化) | 【召喚時】手札の守護を1体出す /【守護】 | 2引く | `targetSpecs` + `triggers` + `soulSpells` |
| 黒ノ霊導者(風5・進化) | 【守護】のみ | 自分1体破壊 → 相手1体に3ダメージ | `soulSpells` |
| 白ノ霊知者(風4・進化) | 【召喚時】2引いて1体破壊 | 自分1体のAttack+1 /【還元】 | `triggers` + `soulSpells` |
| 愚乱怒土地(土6・進化) | 【威圧】のみ | 上2枚を見て1枚マナ・1枚手札 | `soulSpells` |
| 勝阿外(土9) | 【常在】スペル封じ + Attack加算 | マナ加速 + 条件つき1引く | `RuleGuards` + `StatCalculator` + `soulSpells` |

### 5-1. 《スタンディングテント》—— `null` の2つの意味(50 の教訓の再適用)

```java
if (ctx.actions().isFieldEntryBlocked(...)) { return; }   // → 墓地(マスター裁定 B6-2)
MinionInstance placed = ctx.actions().putIntoFieldByEffect(..., ctx.fromTaboo());
ctx.owner().setPendingSpellDisposition(SpellDisposition.KEPT_BY_EFFECT);
if (placed != null) { ctx.actions().damageMinion(..., placed, 2); }
```

★**`putIntoFieldByEffect` の `null` には2つの意味がある**(落とし穴「50 の教訓」) ——
(a) 場に出られなかった、(b)《光霊・モアニール》が山札の下(禁忌なら消滅ゾーン)へ置いた。
(a) はカードの行き先が未定なので墓地へ送らねばならず、(b) はもう置いてあるので
**送るとカードが2枚に増える**。

**先に `isFieldEntryBlocked` を見て (a) を分ける**ことで、
`null` が返ったら必ず (b) だと分かる形にしてある(神の福音と同じ作法)。

### 5-2. 《黒ノ霊導者》——「そうしたら」は実際に破壊できたことを指す

**自分のミニオンが1体も居なくても使用できる**(マスター裁定 B3-1・裁定251)。
その場合は何も起こらない —— だから前半の対象要求も `upTo` である。

破壊が《大天使ミカエル》などの置換で成立しなかった場合、3ダメージは与えない。
`destroyMinion` は成否を返さないので、**破壊の前後で場に居るか**を見る(2種のオニと同じ形)。

★対象は2つとも**使用宣言時にまとめて選ぶ**(マスター裁定 B3-4)。
割り込み(`PendingChoice`)を1つ増やさずに済む。

### 5-3. ★《白ノ霊知者》の【召喚時】を `TargetSpec` にしなかった

理由が2つある。

1. **このカードは進化ミニオンである。** 宣言時の検証は**素材を場から外す前**に走るので、
   素材にしたミニオンを破壊対象に選べてしまい、解決の頃にはそれが場に居ない。
2. 候補ゼロで**召喚そのものが弾かれる**(48 の落とし穴)。

割り込み(`ResumePoint.HAKUNO_REICHISHA_DESTROY`)にした。
候補は**両者の場**である(側の限定が無い。裁定156(2)・マスター裁定 B2-1)。
進化した自身が場に居るので、候補が0体になることは実際には起きない。

★**進化ミニオンに宣言時の対象指定を付けるのは、一般に危険である。**
54 は《英霊・タイガラム》にだけ `targetSpecs` を付けたが、
あちらの対象は `Kind.HAND`(手札)なので素材とぶつからない。

### 5-4. 《愚乱怒土地》—— マナ上限のときは山札の上に戻る

**マスター裁定(B7-2・裁定255)は「山札の上のまま」である。**
墓地に落とすと「山札から墓地へ」という経路が1つ増える。

★既存の `GameActions.placeTopOfDeckInManaFaceUp` が以前から同じ形
(置けなければ山札の上へ戻す)であり、**規則を2つ作っていない**。
54 は裏向き版(`placeCardInManaFaceDown` / `placeTopOfDeckInManaFaceDown`)を足しただけである。

★**裏向きの経路は `fireManaPlaced` を発火しない。** 51 以前からの非対称をそのまま踏襲した
(《豊穣の地霊主》は表向きの配置しか見ていない)。**裁定を仰いでおらず、P5 の宿題のままである。**

### 5-5. 《勝阿外》——【常在】は保存しない

「相手はスペルを唱えられない」は `RuleGuards.spellDenial` に置いた。
《断罪の聖導者》が**ターンの刻印**なのに対し、こちらは**場に居るあいだずっと**である
(マスター裁定 B8-1)。状態として保存せず、問われるたびに場を見る ——
保存すると、場を離れたときに解除し忘れる。

「相手の手札の枚数このミニオンの攻撃力+1」は《英霊・ニュウキロ》と同じ書き方であり、
**相手の手札1枚につき Attack +1** と読む(マスター裁定 B8-3)。

賢魂：2 の「自分のマナが3枚以下のとき」は**1枚置いた後**の枚数で見る(マスター裁定 B8-4)。
マナ上限・山札切れで置けなかった場合も**ドローの判定は行う**(B8-5。
前半と後半が「そうしたら」で繋がっていないため)。

### 5-6. ★`IMPLEMENTED_CARDS` に《勝阿外》を入れなかった

このカードは【賢魂：2】のほうで `soulSpells` に載っており、`isRegistered` が既に真を返す。
`RuleGuards` / `StatCalculator` の `IMPLEMENTED_CARDS` に入れると、
**外しても何も落ちない宣言**が2つ増えるだけである。

★**53 の《リボーンライヴ・ノア》とまったく同じ判断である**(裁定176 の正しい読み方)。
定数の宣言には理由をコメントで残してある。

## 6. 印(効果未実装)が 0 になった

`EffectImplementationTest` の書き換えは、**数から不変条件へ**の移行である(裁定209)。

| 53 まで | 54 から |
|---|---|
| `効果未実装のカードは7枚である` | **`効果未実装のカードは1枚も無い`** |
| `印が付くカードはすべて賢魂を持つ` | **`賢魂を持つ7枚はすべて実装済みである`** |
| `Batch52と53が賢魂待ちとしてP4へ送った7枚には今も印が付く` | **`Batch52と53がP4へ送った7枚は54で実装された`** |

★47〜53 のあいだ、この試験は**残りの枚数**を主張していた。実装が進むフェーズでは
その種の題材はバッチごとに必ず書き換わる。0 になった今は
**「効果の文があるカードは、すべてエンジンが処理を持っている」**という不変条件そのものを測れる ——
こちらは実装が増えても書き換える必要がない。
落ちたときは名前が並ぶので、「新しいカードを足して登録し忘れた」という形で現れる。

★`tools/report_effects.py` の `REGISTRY_MAPS` に `soulSpells` を足した。
**進化の素材条件(`evolutions`)と違い、賢魂は「そのカードの効果そのもの」なので数える**
(裁定233 との線引き)。足し忘れると `NG: 未知の登録先がある` で止まる ——
53 が仕込んだこの検査が実際に働いた。

## 7. 手札 UI の2導線

### 7-1. 形

《特殊召喚》と同じく `confirm()` 1つである。

```
【賢魂：1】カードを1枚引く。その後自分の山札の上から1枚目を墓地に置く

OK = スペルとして使う(コスト1) / キャンセル = ミニオンとして出す
```

★**実効コストが n と違うとき(軽減・増加)は「コスト1 → 実効0」の形で両方を出す。**
押す前に何マナ払うかが分かるようにするためである。

★**賢魂の確認は、進化素材の選択より前に置く。**賢魂として使うなら素材は要らない(A5)。
順序を逆にすると、賢魂で使いたいだけなのに素材を選ばされる。

★手札と禁忌の両方に `★賢魂:n` のバッジを出す。
光らせる判定(`playable`)も「ミニオンとして払えるか **または** 賢魂として払えるか」に広げた。

### 7-2. ★マスターに見てほしいこと(実機確認)

添付の3本のデッキで1試合ずつ。**★JavaScript を変えたのでキャッシュクリア(Ctrl+F5)が必要である。**

`decks/batch54-dark-check-deck.json`(リーダー = 演舞の墓守):

1. **《グレイヴガールズファン》の手札クリックで「賢魂：1」の確認が出る**
   (全角の「１」が正しく 1 と読めていること)。
2. **《スタンディングテント》を賢魂：2 で使うと、そのカード自身が 1/6【守護】として場に出る。**
   このとき**【召喚時】の2ドローは起きず**、2ダメージを受けた状態(体力4)で立つ。
   ★ミニオンとして6マナで召喚したときは 2ドローが起き、ダメージも無いこと。
3. **禁忌の《勝阿外》を賢魂：2 で使える**(マナを**2枚**退けるだけ。印刷コストの9枚ではない)。
   使い終わったカードは**消滅ゾーン**へ行く(墓地ではない)。

`decks/batch54-wind-check-deck.json`(リーダー = 疾風の導き手):

### 8-1. ★NG 1件が教えたこと —— 試験が2つの理由を混ぜていた

`GameService.requireSoul` は2段の検査を持つ。

```java
if (!CardTextKeywords.hasSoul(master.text())) throw ...「このカードは【賢魂】を持ちません」
SoulSpellSpec soul = effects.soulSpellOf(master.id());
if (soul == null)                             throw ...「この【賢魂】の効果は未実装です」
```

試験が `hasMessageContaining("【賢魂】")` としか書いていなかったため、
**1段目を丸ごと消しても2段目が拾ってしまい、落ちなかった。**

文言まで測る形(`"このカードは【賢魂】を持ちません"`)に直して OK になった。
★裁定196 の (a)「試験が足りない」であり、
**同じ語を含む2つの理由を1つの試験で測ってはいけない**という一般則である。

あわせて `賢魂の登録とテキストは一致している` を新設した ——
2段目が拾うのは「テキストに賢魂はあるが未登録」だけであるべきで、
その不変条件を別に測っておけば、上の混同が二度と起きない。
