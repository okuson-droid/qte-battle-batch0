## 1. 初回ヘルプの自動表示

### 1-1. なぜ「自動表示」で足りるのか

レビューは A-3 で「初回自動表示 + コーチマーク + `title`」を提案していたが、
その後の前提更新(裁定16)で**コーチマークは作らないと決めてある**。
Discord 通話が前提であれば、初見の人は画面の指示ではなく**隣の人の声**で学ぶ。
声で教えるときに欠けているのは手順の提示ではなく、
「読むものがあると知っていること」と「物の名前」の2つだけである。
前者が自動表示、後者が `title` にあたる。

### 1-2. 実装

`manual-battle.js` に **0-1章**を新設した。

```js
const HELP_SEEN_STORAGE_KEY = 'qte-manual-help-seen';
function hasSeenHelp()  { /* localStorage 読み。例外は握りつぶす */ }
function markHelpSeen() { /* localStorage 書き。例外は握りつぶす */ }
function openHelpIfFirstVisit() { if (hasSeenHelp()) return false; openHelpModal(); return true; }
```

呼び出しは `resolveOccupant().then(...)` の中、`client.activate()` の直後1箇所。

### 1-3. 決めたこと(4点)

1. **キーは部屋ごとにしない。**
   `qte-manual-occupant-{roomId}` が部屋ごとなのは「どの席の誰か」が部屋ごとに違うからである。
   一方「操作説明を読んだ」のは**人の性質**であって部屋の性質ではない。
   部屋ごとにすると、部屋を作り直すたびに同じ説明が出る。
2. **席が決まってから開く。**
   席選択ゲートは z-index 1060、操作説明モーダルは 2000 である。
   ゲートの上にヘルプを重ねると「名前を入れる画面が説明に隠れる」。
   入室に失敗した場合は呼ばれない(読むべきは説明ではなく失敗の理由である)。
3. **接続の完了は待たない。**
   説明を読むのに盤面は要らない。待つと「接続が遅い日だけ出ない」という
   再現性の無い挙動になる。
4. **開いた時点で「見た」と記録する。閉じるのを待たない。**
   閉じずにタブを落とした人へ次も出すのは、親切ではなく**同じ邪魔の繰り返し**である。

### 1-4. localStorage が使えない環境

読み書きとも try/catch で握りつぶす。結果は「毎回出る」か「一度も出ない」のどちらかで、
どちらも対戦の続行を妨げない。**ヘルプの表示は対戦より優先されるものではない。**
読めないときは「まだ見ていない」側に倒してある(出しすぎるほうが、出ないより害が小さい)。

## 2. 動的生成要素への `title`

### 2-1. 何のために付けるのか

**「教える側が名称を言えるようにする」**である。
通話しながら教えるとき、教える側が困るのは操作の難しさではなく
「その左下の…灰色の…枠」という**指し方**である。
ポインタを載せればカード名とゾーン名が出れば、それを読み上げればよい。

ついでに操作も書いた。この盤面の規約(**左=見る / 右=動かす**)は業界慣習と逆であり
(22 で意図的に反転した)、慣習からの類推が効かない。
ヘルプの表に書いてあるだけでは、**ヘルプを閉じた瞬間に参照できなくなる**。

### 2-2. 文言を1箇所に集めた

これが今回いちばん大きい変更である。33 までの `title` は、
15箇所に**生の日本語文字列が直接代入されていた**。
規約を変えたときに全部を直せる保証が無い(設計判断28 に違反している)。

```js
const TITLE_HINTS = {
    zoom: '左=拡大', zoomTop: '左=一番上を拡大', draw: '左=1枚ドロー',
    tap: '右=タップ/アンタップ', openZone: '右=一覧', deckFullscreen: '右=全面表示',
    zoomRight: '右=拡大', dragMove: 'ドラッグ=移動', dragTop: 'ドラッグ=一番上の1枚',
    evolve: '重ねると進化', flip: 'Shift+クリック=裏返す',
    multi: 'Ctrl/⌘+クリック=複数選択', hidden: '対戦部屋では非公開', /* ほか */
};

function tileTitle(name, ...hints) {
    const ops = hints.filter(Boolean).join(' / ');
    const label = (name || '').trim();
    if (!label) return ops;
    return ops ? `${label} — ${ops}` : label;
}
```

- **名前を先頭に置く。** ツールチップは幅で切られることがあり、
  切られて困るのは操作の続きではなく名前のほうである。
- **空の hint は捨てる。** 呼び出し側が条件式で `null` を渡せるようにするためで、
  これが無いと呼び出し側に `if` が増え、文言がまたバラける。

**★新しいタイルを作ったら、文字列ではなく `TITLE_HINTS` の組み合わせで書くこと。**
これは**機械判定がある**(下の 2-4)。

### 2-3. 付けた場所

| 要素 | title の例 |
|---|---|
| 場のミニオン | `連撃の巨岩(タップ済み) — 左=拡大 / 右=タップ/アンタップ / ドラッグ=移動(重ねると進化) / …` |
| 手札・共有ゾーン | `知識の守護者(手札) — 左=拡大 / 右=拡大 / ドラッグ=移動 / …` |
| マナ | `カース・ボーン(マナ) — 左=拡大 / 右=タップ/アンタップ / …` |
| リーダー | `蒼海の賢者(席Aのリーダー) — 左=拡大 / 右=タップ/アンタップ / ウェポンをここへ落とすと装備` |
| 山札 | `山札(34枚) — 左=1枚ドロー / 右=全面表示 / ドラッグ=一番上の1枚` |
| 墓地・消滅ほか | `墓地(3枚) — 左=一番上を拡大 / 右=一覧 / ドラッグ=一番上の1枚` |
| 相手の[山][禁][確][手] | `相手の禁忌(8枚) — 左=一番上を拡大 / 右=一覧 / 対戦部屋では非公開` |
| 相手のマナ(裏の束) | `相手の裏向きマナ 3枚 — タップ済み` |

**裏向きのカードは名前を出さない。**
ツールチップは公開範囲の外にある仕組みではなく、画面に出ているものの読み上げにすぎない。
**見えていないものを title で教えない。**

**fx層(演出のゴースト)には付けない。**
数百ミリ秒で消えるものにツールチップは出ないし、実要素と二重に出る危険がある。

### 2-4. 検証(4項目)

1. 動的生成された盤面の要素に `title` が付く(場・手札・マナ・パイル・リーダー)
2. **★title は名前で呼べる**(カード名・ゾーン名が実際に入っている)
   ── 空でない `title` を数えるだけの判定は `title=" "` でも通るため、中身を見る
3. `title` に操作の書き方(左 / 右 / ドラッグ)が入る
4. **★★文言は `tileTitle` 経由である**
   ── `manual-battle.js` の中に「日本語を `.title` へ直接代入している行」が
   1つも残っていないことを見る。これが 2-2 の番人である

## 3. ロビーのダークテーマ統一

### 3-1. 31 の教訓が直撃する範囲である

31 で分かったのは「ハーネスが Bootstrap を落とす以上、
**Bootstrap に任せた見た目はハーネスに現れない**」ということだった。
今回の素直な実装は `<html data-bs-theme="dark">` を足すだけだが、
それだけだと**ハーネスは白いロビーのまま**になり、
「ハーネスでだけ違う画面」を検証することになる。

そこで**二段構え**にした。

- **主要な色はテンプレート自身の `<style>` に書く。** ここは Bootstrap を落としても残るので、
  実ページとハーネスの**両方に効く**。
- `data-bs-theme="dark"` は仕上げ(フォーム部品の細部・チェックボックス等)に使う。

`verify/build_harness.py` の `lobby_stub` も同時に直した(背景・ボタン・帯の色)。
スタブに背景を書いてあるのは保険ではなく**宣言**である。
テンプレート側の指定が消えたときに、ハーネスが黙って白へ戻らないようにするためである。

### 3-2. 色は盤面と同じ値を使う

`#212529`(背景)/ `#f8f9fa`(文字)。**近い色を新しく作らない。**
2つの黒があると、どちらが正か分からなくなる。

カードだけは本文よりわずかに明るい面(`#2b3035`)にした。
同じ色だと枠線だけが仕切りになり、**CDN 障害で枠線が消えたときに構造ごと消える**。

### 3-3. Bootstrap の色モードが直してくれないもの

- `.btn-outline-secondary`(文字 `#6c757d`)→ 黒地で 3.4:1。盤面と同じ `btn-outline-light` に変更
- `.btn-outline-primary`(文字 `#0d6efd`)→ 黒地で 2.6:1。`#6ea8fe` に置換
- `.text-muted` / `.form-text` → `#adb5bd`(黒地で約 7.4:1)

### 3-4. 隣の画面も直した

ロビーだけ直すと、**白→黒のフラッシュが経路を変えて戻る**
(ロビー → カード一覧 が白のままなので)。
ロビーから1クリックで行く `manual-cards.html` も同じ色に揃えた。

`manual-deck-maker.html` は独自パレット(第3のデザイン系統・レビュー B-2)であり、
色を揃えるだけでは済まない。**このバッチでは触っていない。**

### 3-5. 検証(3項目)

1. **★★ロビーの背景が盤面と同じ黒である**
   ── 見るのはクラス名ではなく**実際に解決された色**である。
   「`bg-dark` が付いている」を見る判定は、Bootstrap の代替が漏れていても通ってしまう。
   31 で踏んだのはまさにその穴である
2. **★ロビーの文字もコントラスト比 4.5:1 以上**(盤面と同じ1本の条件)
3. 手動モードのカード一覧もダークテーマである(サーバ描画なので静的検査)

## 4. `og:image` の設定化(裁定24)

### 4-1. なぜ設定に出すのか

33 ではテンプレートに公開URLを直書きした。
直書きは「公開URLが変わったら人間が2枚のテンプレートを直す」運用に依存する。
ホスティング先を変えた瞬間に、**共有リンクのプレビュー画像だけが黙って壊れる**。
黙って壊れる箇所を主動線(Discord への貼り付け)に置かない、というのが 33 からの方針である。

`qte.manual.pure-element-id` と同じ「環境依存の値は設定へ」の系列である。

### 4-2. なぜ SpEL の bean 参照を採らなかったか(**マスター裁定: b でなく a**)

ハンドオフでは2案を挙げていた。

| 案 | 形 | 失敗したとき |
|---|---|---|
| SpEL | `th:content="${@environment.getProperty('qte.public-base-url')} + '/og-image.png'"` | **テンプレート全体が 500**。manual-battle と manual-lobby の主要2枚が落ちる |
| ControllerAdvice | `th:content="${ogImageUrl}"` | **属性が消えるだけ**。ページは生き残る |

サンドボックスでは実サーバを起動できないので、
「解決に失敗すると全ページが落ちる変更は入れない」と決めてある(**裁定23**)。
SpEL 案は Java 変更ゼロを守れる代わりに、この裁定に真正面からぶつかる。
Java を1ファイル増やすほうが**失敗が狭い**ので、そちらを採った。

### 4-3. 実装

```java
@ControllerAdvice
public class PublicUrlAdvice {
    private static final String OG_IMAGE_PATH = "/og-image.png";
    private final String ogImageUrl;   // 設定が空なら null

    public PublicUrlAdvice(@Value("${qte.public-base-url:}") String publicBaseUrl) { ... }

    @ModelAttribute("ogImageUrl")
    public String ogImageUrl() { return ogImageUrl; }
}
```

```properties
qte.public-base-url=https://qte-battle-batch0.onrender.com
```

- **base URL ではなく完成した画像URLをモデルに載せる。**
  テンプレート側で `${publicBaseUrl} + '/og-image.png'` と連結すると、
  **パス `/og-image.png` が2枚のテンプレートに写る**(設計判断28)。
  連結は `PublicUrlAdvice` 1箇所で行い、テンプレートは完成品を受け取るだけにする。
- **末尾のスラッシュは吸収する。** 設定者の書き癖であって意味の違いではない。
- **設定が空でも起動は失敗しない。** `pure-element-id` と同じ判断である。
  空のときは `og:image` の行だけが消える。
  **相対URLへ退化させない**のが要点で、相対URLの解決はクローラ依存であり(裁定22)、
  「壊れているかどうかが貼ってみるまで分からない」状態を作るくらいなら、
  タグごと無いほうがクローラの挙動は予測可能である。

### 4-4. 検証の式を差し替えた

33 の判定は `content="https://` の直書きを見ていたので、**設定化したら落ちる判定**だった。
見るべきものが変わったので、次の3つに差し替えた。

1. `og:image` が `${ogImageUrl}` を参照している、かつ**直書きが残っていない**
   ── 片方だけ設定化して片方が直書きのままだと、公開URLを変えたときに
   **1枚だけ古い画像を配る**という一番分かりにくい壊れ方をする
2. 設定に絶対URLが入っている(`qte.public-base-url` が `https://…` の形)
3. **URL の組み立ては `PublicUrlAdvice` の1箇所だけである**
   ── テンプレートが `/og-image.png` を持っていたら、連結がテンプレート側へ漏れている

## 5. 検証ハーネスへの追加

### 5-1. 「操作説明が全面に出る」問題

初回自動表示を入れると、ハーネスは**毎回モーダル(z-index 2000)が開いた状態**で始まる。
33 までの全項目がクリックできなくなる。

スタブの既定を「**操作説明をすでに見た人**」にした。
そのうえで `?firstvisit` を付けたときだけ localStorage に**触らない**ようにしてある。

```js
if (!new URLSearchParams(location.search).has('firstvisit')) {
    localStorage.setItem('qte-manual-help-seen', '1');
}
```

★スタブが毎回キーを**消す**形にしなかったのは、それだと「2回目は開かない」を作れず、
検証がスタブの挙動を見るだけになるからである。
「触らない」にしておけば、検証側が localStorage を操作して初回と2回目を作り分けられる。

### 5-2. イベントは実際の入口から起こす(33 の教訓の踏襲)

初回/2回目は、フラグを直接倒すのではなく
**localStorage を消してページを開き直す**ことで作る。
フラグを倒して確かめると、自動表示のコードを消しても検証が通ってしまう。

### 5-3. 追加した14項目

- 初回ヘルプ 4項目(初回は開く / 開いた時点で記録 / 2回目は開かない / [?] はいつでも開ける)
  + JSエラー1項目
- `title` 4項目(付いている / 名前で呼べる / 操作が入る / `tileTitle` 経由である)
- ロビー 3項目(背景が黒 / コントラスト 4.5:1 / カード一覧も黒)
- `og:image` の設定化 2項目(設定に絶対URL / 組み立ては1箇所)

差し替えは2項目(`og:image` の判定、数値チップの `title` 文言)。
