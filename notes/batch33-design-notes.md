## 0. このバッチが何を直したか

商業水準レビューは、通話前提という前提の更新のもとで優先順位を組み替えた。
そのうえで**最優先**に置かれたのが本バッチの1章である。

> 通話は続いているのに盤面だけ死んでいる、が最悪の事故になる。
> 「相手の声は聞こえるが、こちらの操作が相手に届いていない」状態を双方が数分
> 気づけないのは、無言アプリの切断より体験上の実害が大きい。

Batch 28 で「無言の `location.reload()`」を潰したとき、同じ性質の欠陥が
`send()` に残っていた。**切断中の `send()` は接続を一切見ておらず、
死んだソケットへ無言で publish していた。** 例外は出ない。ログにも出ない。
人間には「押したのに何も起きない」としか見えない。
28 の宿題が2バッチ越しにここで終わる。

2章は共有導線である。マッチング経路が「Discord に部屋のリンクを貼る」1本に
確定した以上、**貼ったリンクの見え方は主動線の品質そのもの**である。
32 まで、部屋IDは手で範囲選択させ、リンクを貼っても素のURLが出るだけで、
URLを打ち間違えると英語の Whitelabel Error Page(白背景)に飛ばされていた。

## 1. 切断中のロック

### 1-1. 欠陥の構造

レビューの指摘(A-2)を実装の言葉に直すと3つである。

| 症状 | 実体 |
|---|---|
| 切断中も盤面が完全に操作できる | 操作の入口に接続の判定が無い |
| 死んだソケットへ無言で publish | `send()` に接続の判定が無い |
| 再接続を知らされない | `onConnect` が初回と再接続を区別していない |

3つとも「判定が無い」であり、UIの飾りが足りないのではない。
したがって直し方も、**判定を1つ作ってそこに全部を通す**形になる。

### 1-2. ★★番人は `send()` であって、オーバーレイではない

本バッチで最も重要な設計判断である。

「切断中は操作できない」を実現する方法は2つある。

- (a) **画面を覆って触らせない**(オーバーレイ)
- (b) **送信の口で弾く**(`send()` のガード)

(a) だけで済ませると、覗き見の導線を1つ足した瞬間に穴が開く。
モーダルが1つオーバーレイより上の z-index を持っていた、というだけでも開く。
本アプリの z-index は既に 1030〜1960 の7層あり、
「全部より上」を保ち続けることを安全装置の根拠にはできない。

そこで **(b) を番人とし、(a) は宣言に格下げした。**

```js
function send(action, payload, options) {
    if (!isConnected()) {
        if (!(options && options.quiet)) {
            showToast('切断中 — 操作は相手に届きません');
            flashDenied(document.getElementById('connection-status'));
        }
        return false;            // ★publish しない
    }
    client.publish({ ... });
    return true;
}
```

手動モードのすべての状態変更は `send()` を通る(操作の型は
`ManualOperationService.apply` が握る、というサーバ側の原則の
クライアント側の対応物である)。**入口が1つなので、番人も1つで足りる。**

この判断の帰結として、オーバーレイには [盤面を確認する] を置いた。
畳んでも安全性は1ミリも落ちない——**落ちない構造にしたことが、
そのボタンを置ける根拠である。**

### 1-3. オーバーレイは「宣言」である

```
z-index: 1970   切断オーバーレイ ← 盤面側の全レイヤーより上
z-index: 1960   開始シーケンスのモーダル
z-index: 1050   全面表示
z-index: 1040   帯
```

背景は不透明ではなく `rgba(0, 0, 0, 0.72)` にした。
盤面が透けることで「盤面が消えたのではない・触れなくなっただけ」が伝わる。
28 の部屋消失画面(`showRoomLostFatal`)が不透明なのは、あちらが
「この盤面はもう無い」の宣言だからであり、**2つの画面の透明度の差そのものが
意味の差**になっている。

### 1-4. ★席選択ゲートとは z-index で競わせない

部屋消失(`showRoomLostFatal`)は `client.deactivate()` を呼ぶ。
当然 `onWebSocketClose` が走るので、素直に書くと
**「この対戦は戻りません」と「再接続を待ってください」が同時に出る。**
人間はどちらを信じてよいか分からなくなる。

重ね順で解決しようとすると、どちらが上かを未来にわたって守り続ける約束になる。
そうではなく、**出す/出さないの判定を1箇所に置いて排他にした。**

```js
function updateOfflineLock() {
    const offline = !isConnected() && !connectionFatal && !isGateVisible();
    ...
}
```

`connectionFatal`(部屋消失)と `isGateVisible()`(入室前・席替え中)が
そのまま「切断の案内を出さない条件」である。
呼ぶ場所は `onConnect` / `onWebSocketClose` / `onStompError` /
`closeGate` / `openJoinGate` / `openSeatChangeGate` / `showGateFatal` / 覗き見ボタン
の8箇所だが、**判定はこの関数の中の1行にしかない。**

### 1-5. 再接続の通知と、接続の帯

```js
const reconnected = connectionEstablishedOnce;   // ★初回か再接続かを区別する
connectionEstablishedOnce = true;
setConnBar(reconnected ? '再接続しました。盤面を同期しています' : null, 'ok', CONN_BAR_MS);
```

初回の接続で「再接続しました」と出したら、それは**嘘の宣言**である。
32b でターンの帯について確定した裁定——
「巻き戻しでターンの合図を出さない。あれは描画ではなく宣言だからである」——
と同じ理屈がここにも効く。**宣言は事実に一致していなければ、無いほうがましである。**

帯(`.manual-conn-bar`)は要素1つ・状態3つ(切断中 / 復帰 / 無し)である。
**全幅の帯ではなく中央のピルにした**のは、全幅だとヘッダ1行を丸ごと覆い、
切断中でも使える導線(部屋リンクのコピー)まで隠れるためである。
盤面を覗くために畳んだのだから盤面の上へは降りられない。
その両方を満たす置き場所がヘッダの中央だった。

### 1-6. `isConnected()` が `client.connected` だけを見ない理由

```js
function isConnected() {
    return client.connected === true && !socketDown;
}
```

`onWebSocketClose` が呼ばれる時点でライブラリ内部のフラグが既に倒れている保証を、
**こちらは持てない**(StompJS の実装詳細である)。
倒れていなければオーバーレイは出ず、しかも**音を立てずに**出ない。
32b の「クラスも computed style も正しいのに何も動かない」と同じ種類の壊れ方である。

そこで、自分で観測した事実(`socketDown`)を and で重ねた。
**判定関数は1つのまま**であり、参照する事実が2つになっただけである
(「判定を2箇所に書かない」には触れていない)。

### 1-7. 矢印(`dragcue`)だけは無言で捨てる

ドラッグ軌跡は1回のドラッグで何十回も飛ぶ揮発メッセージである。
これに毎回トーストを出すと、**本当の警告が埋もれる**。

```js
send('dragcue', { ... }, { quiet: true });
```

捨てること自体は他と同じである。黙って捨ててよいのは
「元々ビューでもログでもないもの」に限る、という線引きにしてある
(21c 7-2 で矢印を揮発と定めたのと同じ区分)。

## 2. 共有導線

### 2-1. 部屋リンクの組み立ては1箇所

```js
function roomShareUrl() {
    return `${location.origin}/manual/battle/${ROOM_ID}`;
}
```

経路 `/manual/battle/{roomId}` はサーバの `ManualLobbyController#battle` と対になる。
文字列を2箇所で作ると、片方だけ直したときに
**黙って壊れたリンクを配る**——しかもリンクは他人の手に渡ってから壊れているとわかる。

### 2-2. コピーボタンは3つ、振る舞いは1つ

| 場所 | 何をコピーするか | 想定 |
|---|---|---|
| ヘッダ [リンクをコピー] | 部屋URL | Discord に貼る |
| ヘッダ [IDをコピー] | 部屋ID | 鍵つき部屋の入室 |
| 席選択ゲート [リンクをコピー] | 部屋URL | **部屋を作った直後に最初に見る画面** |

用途が違うのでIDとリンクは分けた。配線は `bindCopyButton` の1箇所である。

`navigator.clipboard` は**安全なコンテキスト(https / localhost)でしか使えない**。
素の http で開発しているときに黙って何も起きないのが最悪なので、
使えない場合と例外の場合の両方で `document.execCommand('copy')` へ落とし、
**成否は必ずトーストで告げる。**

★ゲートのコピーボタンは `#seat-gate-buttons`(席選択の委譲リスナーが付いている)
の**外側**に置いてある。中に置くと `data-seat` の無いボタンを押した扱いになり、
「席に着かない」が送信される(28 の [入り直す] ボタンで踏んだ罠)。

### 2-3. アイコンとメタ情報

favicon が無いと、全ページでブラウザ既定アイコン + 毎ロード404になる。

| ファイル | 用途 |
|---|---|
| `favicon.svg` | 標準。盤面と同じ暗色地にカード3枚 |
| `favicon-32.png` | SVG を読めない古いブラウザ |
| `apple-touch-icon.png` | iOS のホーム画面(180×180) |
| `og-image.png` | OGP / Twitter カード(1200×630) |

**PNG は手で描かず、生成手順のほう(`tools/make_brand_assets.js`)を置いた。**
色や文言を直すときに元データがどこにあるか分からなくなる状態を作らないためである。
ラスタライズは Chromium で行う(ImageMagick の SVG 実装は簡易であり、
角丸や `rotate` の再現が保証されない)。

`description` / `theme-color` / アイコンは**全9テンプレート**に入れた。
ついでにタイトルの製品名を「… — クイン・タブーエレメント」に統一している
(レビュー B-2 の「製品名が3種類」の一部)。

### 2-4. ★Thymeleaf フラグメントにしなかった理由

9テンプレートに同じ meta を書くのは重複である。素直には
`th:replace="~{fragments/head :: meta(...)}"` にしたい。**やらなかった。**

- **サンドボックスから Maven Central へ到達できず、実サーバを起動できない**
  (ハンドオフ3章)。
- ハンドオフ3章には
  「★★Thymeleafテンプレートのインライン式に注意(24 hotfixで踏んだ)。
  ★テンプレートを変えたら実サーバを通して確認すること」とある。
- フラグメントの解決失敗は**全ページを落とす**。確認できない変更で
  全ページを人質に取るのは割に合わない。

実際に共有されているのは `theme-color` とアイコン3行だけであり、
`title` / `description` / OGP は**本来ページ固有の内容**である。
重複しているように見えて、共有すべき情報は多くない。

★`og:image` は絶対URL(`https://qte-battle-batch0.onrender.com/og-image.png`)で
書いた。相対URLを解決するかは**クローラ依存**であり、
「貼ってみるまで分からない」ものを主動線に置かない。
公開URLをテンプレートに直書きした点は 5章の質問1で扱う。

### 2-5. カスタムエラーページ

`templates/error.html` を置くだけで Whitelabel Error Page は置き換わる。
Spring Boot の `ErrorMvcAutoConfiguration` は、
**`error` という名前のテンプレートが存在する場合に Whitelabel の設定ごと無効化する**
(`ErrorTemplateMissingCondition`)。したがって
`@ControllerAdvice` も `ErrorController` も**書いていない**。Java 変更ゼロである。

決めたこと:

- **外部CDNを使わない。** エラーページは**CDNが落ちているときにも出る**ページである
  (レビュー C-2 が指摘したとおり、CDN 障害 = 全スタイル消失)。
  外部依存を持たせると「エラーページが崩れる」という二重の事故になる。
  必要なスタイルは40行に満たないので、その場に直接書いた。**機械判定あり。**
- **例外メッセージとスタックトレースを出さない。** `application.properties` で
  `never` に固定した(既定値と同じだが、決めたことを残す)。
  利用者に必要なのは「何が起きたか」と「次にどこへ行けるか」だけであり、
  内部構造はそのどちらでもない。
- **404 だけ文面を分ける。** 実際に一番出るのが「部屋のリンクが古い」だからである。
  部屋がメモリ上にしか無いこと(=作り直しが必要なこと)をその場で言う。
- API(`Accept: application/json`)はこのテンプレートを通らない。
  Spring が内容交渉で JSON を返す経路を選ぶため、
  クライアントの `showTransientError` の扱いは従来どおりである。

## 3. 検証(301 → 319)

追加した18項目のうち、性格の違うものを挙げる。

| 項目 | 何の番人か |
|---|---|
| 切断中は `send()` が publish しない | **本バッチの中心**。無言の publish が復活したら落ちる |
| 切断中の操作を無言で捨てない | トーストが出ること(28 の「無言をやめる」の継承) |
| **盤面を覗いても `send()` のガードは効く** | **1-2 の設計そのもの**。オーバーレイを安全装置にしたら落ちる |
| 矢印は切断中も無言で捨てる | 警告を埋もれさせない線引き |
| 初回の接続では「再接続しました」と言わない | 宣言が嘘にならないこと |
| **切断の判定を外すと項目64は成立しない** | **検出器が生きている確認**(31・32b の作法) |
| 部屋消失のときは切断の案内を重ねない | 1-4 の排他 |
| 全テンプレートに favicon・theme-color・description | 「1枚だけ入れて満足」を防ぐ |
| `og:image` が絶対URLである | 相対URLの解決はクローラ依存 |
| エラーページは外部CDNに依存しない | 2-5 の決めごと |
| 接続の帯・オーバーレイの文字が 4.5:1 以上 | 30/31 の**1本の条件**に合流させた |

★最後の1つについて。30 で入れた「盤面のラベルはすべて 4.5:1 以上」は
`targets` 配列に載っているセレクタしか見ない。32a で fx層の文字を足したとき、
`#manual-root` の外にあるため**網から静かに漏れかけた**。
今回の切断オーバーレイと帯も同じ性質なので、**足すと同時に `targets` に登録した。**
新しい文字を作ったら必ずここへ足すこと。

★切断は `client.onWebSocketClose()` を**実際の入口から**呼んで作っている。
フラグを直接倒すと、`onWebSocketClose` の中身(`socketDown` の記録・
`updateOfflineLock` の呼び出し)を消しても検証が通ってしまう。

★検証ハーネスの STOMP スタブに `connected` を持たせた。
これが無いと**32 までの全項目が一斉に落ちる**(すべての操作が「切断中」として
捨てられるため)。ハーネスは実物の性質を持たねばならない、という
20c 以来の「代替の漏れ」の罠がここにも出た。

## 5. 申し送りと質問

### マスターにお願いすること

1. **`mvn test`**(サンドボックスから Maven Central へ到達できないため)。
2. **実サーバでの目視。**★テンプレート9枚に手を入れたので、
   ハンドオフ3章の「テンプレートを変えたら実サーバを通して確認すること」に該当する。
   見てほしいのは次の4点。
   - 各ページが従来どおり開くこと(meta の追加で壊れていないこと)
   - 存在しないURL(例: `/manual/battle/ZZZZZZ` ではなく `/nothing`)で
     **ダークテーマのエラーページ**が出ること(白い英語ページでないこと)
   - 部屋のURLを Discord に貼って、**カード(画像+タイトル+説明)が出ること**
   - [リンクをコピー] が実際にクリップボードへ入ること(https 環境での確認)
3. **切断の実機確認。**開発者ツールの Network を Offline にする、または
   サーバを一時停止して、オーバーレイ → [盤面を確認する] → 復帰 の流れを見てほしい。

### 質問(まとめて3件)

**Q1. `og:image` の公開URLをテンプレートに直書きした点。**
現在 `https://qte-battle-batch0.onrender.com/og-image.png` をベタ書きしている。
相対URLはクローラ依存で確実でなく、サーバ側で絶対URLを組み立てるには
Java か SpEL(`@environment`)が要る。後者は実サーバで確認できない今回は避けた。
- (a) このままでよい(Render のURLは変わらない前提)
- (b) `application.properties` に `qte.public-base-url` を置いて参照する
      (テンプレートに SpEL が入る。次バッチで実サーバ確認とセットで)

**Q2. 切断オーバーレイの [盤面を確認する] を残すか。**
畳んでも `send()` のガードは効くので安全性は落ちないが、
「触れてしまうが送られない」状態を作るのは事実である。
- (a) 残す(長い切断中に自分の手札を読めるほうがよい)
- (b) 削る(切断中は一切触らせない、で統一する)

**Q3. レビュー優先順位3(勝敗の帯+ターン帯の退役)を次バッチにするか。**
本バッチは1と2を消化した。3は「declare が何も描画しない」を潰すもので、
**ターン帯の退役(2026-08-12 裁定)とセット**である。
規模は小〜中で、`diffViews` と `fxBuildTurn` の配線を外して帯の描画機構を
勝敗へ転用する形になる。
- (a) 次は 3 をやる
- (b) 先に 4・5(初回ヘルプ自動表示 / ロビーのダークテーマ統一)をまとめてやる
- (c) 10(部屋の永続化。規模大)へ進む

### 本バッチで**やらなかった**こと(意識的に)

- `beforeunload` による離脱防止(A-2 の最後)。**通話前提では「戻る」で抜けても
  声で復帰を伝えられる**うえ、離脱防止ダイアログはブラウザ標準の文言しか出せず、
  制御できない画面を1つ増やすことになる。次バッチ以降でマスターの意見を聞きたい。
- `online` / `offline` / `visibilitychange` の捕捉。STOMP の再接続
