## 4. どう直したか

### 4-1. 《アルキンティス》—— 「【X】の◯◯」は参照である

`CardTextKeywords` の参照除外に **「の」** を足した。

```java
Pattern.compile("^(を持|を与|を付|付与|を行|を得|を失|の)")
```

★**実害が出ていたのは1枚だけである。**《アルキンティス》は**ウェポン**なので、
【知識】が付くと「ウェポンの【知識】は装備時に発動する」(2-9)を通って**装備しただけで1枚引いた**。
残る3枚(《潮獣ビシャカワ》《ロロイヨ伯爵》《戒律のガーディアン》)は
種別や読み手の都合で挙動に出ていなかったが、**規則は1つである**(裁定130)——
「実害が出ていないほう」を残す理由が無い。

★★★**169枚の凍結(`keyword-baseline.json`)は1枚も動かなかった。**
唯一かすったのが《戒律のガーディアン》で、本文は
「**【守護】**自分の光文明スペルのコスト-1、自分の光文明の**【守護】の**コスト-1。」——
**先頭が付与、2つ目が参照**である。
★**出現ごとに判定する書き方**(`keywordsIn` のループ)がこれを守っていた。
番人として `Batch73TextImplTest#戒律のガーディアンは守護を持ったままである` を置いた。

### 4-2. 《詠唱の疾風騎士》—— 器ではなくカードで塞いだ

`ON_TURN_END` は**両者の場を回す**(意図した設計)。
一方 `spellsCastThisTurn` を 0 に戻す `startTurnReset` は**ターンプレイヤーにしか走らない**ので、
自分のターンに5回撃つとその値は相手のターン中ずっと 5 のまま残る。

→ **カード側に自ターン判定を足した**(《安らぎのガーディアン》が同じ形で先に書いている)。

★★**器の側(リセットの範囲)は直していない。**
`spellsCastThisTurn` / `cardsUsedThisTurn` の読み手を全部数えたところ、
**相手のターン中に読まれるのはこの1件だけ**であった
(他はすべて使用条件・ON_SUMMON・コスト計算で、自分のターンにしか走らない)。
★**読み手が増えたときは器の側を見直すこと**をコメントに書き残した。

### 4-3. 《悪夢》—— 数え方の共有が、本文の違いを消していた

72 まで `nonSpellCountInTrash(owner)` を読んでいた。これは
**《墓場の怨念集合体》の数え方の流用**であり、あちらは本文が明示的に「スペル以外の」と書いている。

> ★**別のカードの数え方を借りると、本文の違いが借り先に吸収される**(68 の教訓・代用)。

### 4-4. 《這い寄る生霊》—— 移行の「後に」書かれた

Ver1.1 で自壊は消えた(台帳 0085)。ところが
`notes/batch48-design-notes.md` 137行が
「自壊は既存の `destroyAtEndOfTurn` を使う。這い寄る生霊は『特殊召喚で出したときだけ』」と書いており、
**Batch 48 が移行の後に新しく実装している**。

> ★★★**「古い実装が残っていた」より始末が悪い。**
> 移行の後に書かれたものは、**移行の取りこぼしを探す目では見つからない**。

### 4-5. 《降臨の伝道師》—— 67 が塞いだ穴の3枚目

本文「【守護】**ミニオン**」の種別を見ていなかったので、
**《英霊・タイガラム》(光・【守護】・コスト7 の進化)が素材ゼロで場に立っていた**(裁定226 違反)。

67 は《聖なる降誕の儀式》《神の福音》で同じ穴を塞いだが、**山札から出すこの経路は見ていなかった**。
→ 73 は **67 と同じ暫定処置**(進化を候補から外す)で塞いだ。
★恒久の対処は裁定依頼 A と一緒である。

### 4-6. 《詠唱の宝珠》—— 新しい器を作らずに済んだ

本文どおりにするには「**次の自分のターンの終了時まで**」という期限が要る。
★**新しい `Expiry` は作らなかった** —— 既存の `AFTER_TURN_NUMBER` で表せる。
付与するときに**次の自分のターン番号**を計算して渡すだけである。

```java
return state.turnPlayer() == owner ? now + 2 : now + 1;
```

★自分の手番中に外れたなら2つ先、相手の手番中なら1つ先。
**相手のターン中にスペルは唱えられない**ので、これで本文どおりになる。

★★**`ON_NEXT_SPELL` は使い手を失って消えた**(裁定178)。
`GameService` の2箇所にあった「1枚唱えたら使い切る」も落ちた。
★消したものは `PersistentAura` の Javadoc に書き残してある(裁定196)。

★★**「番人が無い」と思ったらまず在るかどうかを見る**(65 の教訓)は、**器にも効く**。

### 4-7. 《墓穴の呪い》—— 閾値が解決の途中でしか決まらない

「墓地以下の体力」の閾値は**2枚ミルした後**の墓地の枚数である。
したがって宣言時の `TargetSpec` では表せず(`Filter` に「体力 n 以下」も無い)、
**解決の途中で候補を組んで問う**のが唯一の形になる。

★候補が2体以下なら問わずに壊す(選ぶ余地が無い)。
★★**少なく選ぶことは許す**(`upTo`)—— 裁定277 の前例に揃えた。

★★★**55 はセルフミルの枚数(3→2)だけを直し、破壊の側を見ていなかった。**
同じ行の同じカードで、**直した箇所と直していない箇所が隣り合っている**。

### 4-8. 《風のマナ変換》—— 1枚のカードの中で扱いが割れていた

前半(手札に戻す表向きのマナ)は**末尾を自動で選び**、
後半(裏向きで置く手札)は**12b の時点から問い合わせていた**。

★裁定299(効果の解決中に生じる選択は本人に問い合わせる)の適用漏れであり、
64 が《嵐の呼び手》で直したのと同じ形が**このカードだけ取り残されていた**。

> ★★**同じカードの中に自動決定と問い合わせが同居している形は、いちばん見つけにくい。**
> 「このカードは問い合わせている」と一目で見えてしまうからである。

★後半へ進む処理は `manaConvertReturnThenPut` に**1箇所へまとめた** ——
分けて書くと「候補が1枚のときだけ後半が走らない」という穴が開く(66 の教訓)。

## 5. ★★★WS の受け口 —— 箱型にすることと、畳むことは別である

72b は《賢魂》の不具合を直したとき、宿題を1つ残した ——
**まだ原始型で受けている項目が6つある**。いまはどの入口も送っているので落ちないが、同じ地雷である。

### 5-1. ★畳んでよいのは、畳んだ先が「何もしない」に落ちるときだけ

| 項目 | 無いときに畳むと | 73 の扱い |
|---|---|---|
| `enhanced`(72b) | false = **通常の使用**。`play-soul` は送らないのが正しい | **畳む** |
| `goFirst` | false = **後攻を選んだ**。やり直せない | **断る** |
| `handIndex`(2箇所) | 0 = **手札の1枚目をプレイする** | **断る** |
| `trashIndex` | 0 = **墓地のいちばん古い1枚**を出す | **断る** |
| `tabooIndex` | 0 = **禁忌デッキの1枚目**。使うと消滅ゾーンへ行き二度と戻らない | **断る** |
| `ManualDragCue.active` | false = **矢印を消す**。何も起きない | **畳む** |

> ★★★**既定値が「何もしない」にならない項目は、畳まずに断る。**

★`active` を畳んだ理由はもう1つある —— **この宛先はエラーを返さない**。
`ManualWsController.dragCue` は `dispatch` を通らず、盤面に無いカードも黙って捨てる(設計書 7-2)。
**断っても届かないのだから、断る意味が無い。**

### 5-2. ★★例外の型が肝である

```java
private static <T> T required(T value, String field) {
    if (value == null) {
        throw new IllegalArgumentException("操作に必要な項目が送られていません: " + field);
    }
    return value;
}
```

★素の自動開封(`Integer` → `int`)に任せると `NullPointerException` になり、
`execute` はそれを捕まえない —— **また無言に戻る**(72b の宿題が名指しで警告していた形)。
★壊し検証の**軸7**がこの判断そのものを測っている。

### 5-3. ★★★試験の書き方が、壊せるかどうかを決める

`Batch73PayloadGuardTest` は最初 `new ChooseOrderRequest(id, null)` と書いていた。
すると**受け口を原始型に戻す壊し検証がコンパイルを壊し**、報告書が1つも生まれない
(裁定304 の EMPTY)。

→ **箱型の変数を経由して渡す形**に変えた。

```java
private static final Integer 送られてこない整数 = null;
private static final Boolean 送られてこない真偽 = null;
```

これなら原始型に戻しても**自動開封で実行時に倒れる**ので、壊し検証が観測できる。

> ★★**「壊せない」の原因が実装ではなく試験の側にあることがある。**

### 8-3. ★壊しどころが無いもの(裁定196 の正直な扱い)
