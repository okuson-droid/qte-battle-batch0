## 1. ★着手時に伺って確定した4件(裁定342〜345)

| 番号 | 論点 | 確定した内容 |
|---|---|---|
| **342** | 通常モードの「無人」をどう判定するか | **1段である。**「席にも観戦者にも、繋がっている人が1人も居ない状態が続いたら、部屋ごと消す」。<br>★**席を空ける段は作らない**(手動モードとの決定的な違い) |
| **343** | 対戦中(`GameState` が在る)の部屋も消してよいか | **消す。**部屋はメモリ上にしか無く、残すと両者が帰った対戦中の部屋がロビーに永久に並ぶ |
| **344** | 部屋消失をどう伝えるか | **`WsMessage.type = "ROOM_LOST"` を足す。**ERROR の本文照合で代用しない |
| **345** | 部屋が消えたと知ったあと、画面はどこへ導くか | **ロビー(`/auto`)へ戻す。**手動モードの「入り直す」とは違う |

### 1-1. ★★★裁定342 の理由(次の人がいちばん蒸し返しやすい)

手動モードは**2段**である。

```
手動: 切断から5分 → 席を空ける → 在室者0が5分 → 部屋を消す
通常: 誰も繋がっていない状態が5分 → 部屋を消す
```

★**席を空ける段が要らない理由は3つある。**

1. 対戦中に席が空いても、**誰も座れない**(`GameRoom.takeSeat` が `gameState != null` を断る)。
2. WAITING 中に席を空けることには意味があるが、それは Batch 72 が
   **退室**という明示的な操作として作った —— **切断は退室ではない**。
3. 席と `GameState` の2人は**1対1**であり、対戦中に席が消えると盤面の持ち主が消える
   (72 が「対戦中は退室できない」と決めた理由そのものである)。

> ★★★**同じ穴を塞ぐことと、同じ形で塞ぐことは別である**(71 の教訓)。
> 手動モードの2段は<b>あちらの席が「盤面の入れ物」の席だから</b>成り立っている。

### 1-2. ★★裁定345 が手動モードと違う理由

手動モードの `showRoomLostFatal` は **[入り直す]**(ページの再読み込み)を出す。
あちらは**猶予切れで席が空いただけで、部屋はまだ在る**ことがあるからである。

通常モードは席を空けないので(裁定342)、`ROOM_LOST` が来たときは
**部屋が本当に無い**。再読み込みしても同じゲートが出るだけなので、ロビーへ戻す。

## 2. ★75 が実装で決めたこと(裁定を仰がなかったもの)

読みが1つに定まったので、作業を止めずに実装した(リファレンス 1-7 の流儀)。
**間違っていたら戻す。**

| 決めたこと | 根拠 |
|---|---|
| 猶予は **5分**である | 短いと「回線が一瞬切れただけで対戦が消える」、長いとロビーに死に部屋が並ぶ。★手動モードの `EMPTY_ROOM_TTL` と同じ値になったが、**写したのではなく理由から決めた**(71 の教訓)。★★手動モードの2つ(GRACE_PERIOD + EMPTY_ROOM_TTL)を足して10分にはしない |
| 掃除の周期は **1分**である | 手動モードと同じ。部屋数は多くても数十であり、走査コストは無視できる |
| **観戦者も「繋がっている人」に数える** | 裁定342 が「席にも観戦者にも」と言っている。観戦者だけが見ている部屋は無人ではない |
| 決着後(`FINISHED`)の部屋も**同じ規則**である | 72 が決着後の退室を作ったので「盤面が在るのに誰も居ない」は日常的に起きる。そこに例外を作らない |
| 接続の記録は **`GameRoom` が持つ**(席にも観戦者にも置かない) | 「繋がっているか」は席の性質でも観戦者の性質でもなく、**どちらでも同じ**である。両方の型に足すと同じ規則が2箇所に書かれる(設計判断38)。★`Spectator` が record で状態を持てないのは**理由ではなく結果**である |
| 掃除は**消したことを誰にも配信しない** | 宛先の一覧を持っていたのは部屋であり、そもそも誰も繋がっていないから消している。戻ってきた人が `ready` を撃った瞬間に `ROOM_LOST` を受け取る |
| **手動モードの文字列照合は直さない** | 手動モードは停止中である。通常モードを型で運ぶようにしたが、あちらを揃えるのは「手動モードを再開するとき」の工事である(片肺・71 の教訓)。★下の 3-1 に申し送りとして残す |
| **「相手が切断中」をビューに出さない** | `RoomView` は接続を1つも持たない。出すのはビューを1つ増やす工事であり、M+N とは別である。★下の 3-2 に残す |

## 3. ★次のバッチへの申し送り

### 3-1. ★★手動モードの部屋消失は、いまも**本文の文字列**で判定している

```js
// manual-battle.js
if (msg.message === 'この部屋に入室していません') {
    showRoomLostFatal();
```

★**サーバの文言を1文字直しただけで、黙って効かなくなる。**
しかも効かなくなっても画面は「エラーが出た」ように見えるので、**誰も気づかない**
(74 の「効きすぎている実装は別の規則の陰に隠れる」の裏返しの形である)。

★通常モードは 75 で型(`ROOM_LOST`)に移した。
★★**手動モードを再開するときに、まずここを揃えること。**
★★★**通常モードが本文で判定していないこと**は壊し検証の軸15 が見張っている ——
誰かが「手動モードに合わせよう」と戻したら赤くなる。

### 3-2. ★★通常モードには「相手が切断中」の表示が無い

`RoomView` は接続の状態を1つも持たない。75 は**それを変えていない**。

- 手動モードは在室者一覧に切断中の印が出る(だから切断のときに配信する)。
- 通常モードは配信しても**ビューが1バイトも変わらない**ので、
  `GameDisconnectListener` は**配信しない**。

★**症状**: 相手がタブを閉じても、こちらには「相手が動かなくなった」としか見えない。
5分経てば部屋ごと消えるので**永久に待つことは無くなった**が、
<b>その5分のあいだ、何が起きているかは分からない</b>。

★直すなら `RoomView.SeatView` に真偽値を1つ足すだけである
(`deckLoaded` / `ready` と同じ形)。**配信を1行足す必要も出る。**

### 3-3. ★★猶予の起点は「無人になった時刻」である —— 作成時刻ではない

`GameRoom.emptySince` は `null` を「誰か繋がっている」の意味に使っている。
`markConnected` が `null` を書き、`noteSessionsChanged` が
**まだ立っていなければ**時刻を立てる。

★★**`markConnected` の `emptySince = null` を落とすと、起点が部屋の作成時刻のまま動かない** ——
すると<b>1時間遊んだ部屋が、切断した瞬間に掃除の対象になる</b>。
★番人は `猶予は無人になった時刻から数える` である。

★★★**この番人は最初、`createdAt` と比べていて空振りした。**
`createdAt` と `emptySince` は**別々の `Instant.now()`** で初期化されるので、
壊れていても数ナノ秒ぶん小さくなり、不等式が通ってしまう ——
**「壊した」と「効いた」は別である**(74 の教訓)の、新しい顔である。
★直した形は<b>切断の直前に控えた時刻</b>と突き合わせるもので、閾値を1つも持たない。

### 3-4. ★2つの切断リスナーが同じイベントを受ける

`ManualDisconnectListener` と `GameDisconnectListener` は
**どちらも `SessionDisconnectEvent` を受け、どちらも全部屋を走査する**。
台帳が別なので、片方で見つかればもう片方は空振りする。

★台帳を1つにまとめないのは 21a からの設計判断である
(「通常モードの部屋を探す処理が手動モードの部屋を見つけてしまう」経路を作らない)。
★★部屋数が数百に増えたら `sessionId → 部屋` の索引を足す余地はあるが、
**今の規模では過剰設計である**。
