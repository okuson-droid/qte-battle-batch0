## 0. 指摘の原文(そのまま)

## B. 「今プレイ中のカード」を出す(指摘2)

### B-1. ★69 の決めごとと矛盾しない —— 別のものである

69 は「**対象を選んでいる最中はホバープレビューを出さない**」と決めた。
指摘2 が求めているのは**その裏側**である ——
選択中に出さないのは「**手を乗せた先**」のプレビューであって、
「**今プレイしているカードそのもの**」は、むしろ**出しっぱなしにしてほしい**。

★つまり2つは別物である。

| 何を出すか | いつ | 動き |
|---|---|---|
| ホバープレビュー(44・69) | 手を乗せている間 | 乗せた先で**入れ替わる** |
| ★**プレイ中の表示**(指摘2) | 解決が終わるまで | **固定**。手を動かしても変わらない |

★★**だから同じ器(`#auto-hover`)を使い回してはいけない。**
使い回すと「乗せた先で入れ替わる」性質を引き継いでしまい、
**プレイ中のカードが手の動きで消える**。要素をもう1つ持つべきである。

### B-2. ★出どころは既に在る

「今何を解決しているか」を知っているのはサーバである。
`view.you.pendingChoice` の `prompt` には既にカード名が入っており(64・68)、
割り込みを跨ぐ文脈は `PendingChoice.payload` が運んでいる(裁定130・64)。

★ただし **`pendingChoice` はカードIDを運んでいない**(運んでいるのは prompt の文字列と候補である)。
**面を描くにはカードIDが要る**(`cardFace` は card-library から引く)。
★★**ここが「器を足すか、既に在る口を探すか」の分かれ目である**(設計判断28・67 の教訓)。
`PendingChoice` に `sourceCardId` を1つ足すのが素直だが、
**足す前に payload で足りないかを確かめること。**

### B-3. ★スペルだけではない

指摘の文は「スペルをプレイしていて」だが、
68 以降は**ミニオンの【召喚時】も割り込みで問う**ので、
**同じ表示がミニオンにも要る**(むしろそちらのほうが枚数が多い —— 15枚)。
★★マスターに確認すること: **ミニオンの【召喚時】の解決中にも出してよいか。**
(わたし(クロエ)の見立てでは出すべきである。「今どのカードの効果を解決しているか」は

## C・D・E. プレイの入口を2つにする(指摘3・4・5)

★**この3件は1つの設計である。**入口が2つになり、**マナの払い方がその2つで違う**。

| 入口 | 操作 | マナ |
|---|---|---|
| **ドラッグ&ドロップ** | 手札(または禁忌)から**盤面へ落とす** | ★**自動で払う**。ドラッグ中に**払う予定のマナが強調表示**される |
| **クリック** | カードをクリック | ★**手動で選ぶ** → [確定] で成立 / [キャンセル] で不成立 |

### C-1. ★★★器はどちらも既に在る(65 の教訓: まず在るかどうかを見る)

- **ドラッグ&ドロップ** …… **手動モードには在る**(`manual-battle.js`。
  HTML5 の `draggable` / `dragstart` / ドロップ先の `.zone-drop-*`)。
  ★**通常モードには1つも無い**(`battle.js` に `draggable` は0件)。
  ★★**19b の hotfix2 と 20a の教訓がそのまま効く** ——
  合成 `DragEvent` では測れないので、verify は `page.mouse.down/move/up` で測ること。
  ★★★**20a の A4 が特に効く**: `dragstart` の `e.target` は指を置いた要素ではなく、
  ブラウザが祖先方向へ探して見つけた `draggable=true` の要素である。
  実際に指が置かれた場所は `document.elementFromPoint` で取る。
- **「マナを手動で選んで確定」** …… **通常モードに既に在る**。
  **禁忌コストの支払い**がまさにその形である ——
  `tabooPay` / `pickTabooMana` / `.taboo-payable` / `.taboo-picked` /
  `finishTabooPayment` / `cancelTabooPayment`。
  ★★**指摘5 は「禁忌でやっていることを通常のカードにも広げてほしい」と読める。**
  ★ただし**確定ボタンが無い**(禁忌は必要枚数に達した瞬間に自動で確定する)。
  指摘5 は明示的に「確定ボタンを押したら」と言っているので、**そこは新しい**。

### C-2. ★★★いちばん大きい変更 —— サーバが「どのマナを払うか」を受け取れない

今の `GameService.payCost` はこうである。

```java
for (ManaCard mana : player.getManaZone()) {
    if (remaining == 0) break;
    if (!mana.isTapped()) { mana.tap(); remaining--; }
}
```

★**マナゾーンの先頭から、未タップのものを順にタップする。**
つまり「**どれを払うか**」という概念がサーバに無い。

★★指摘4(自動で払う)は**今のままで成り立つ**。
必要なのは「**その規則の結果をクライアントが先読みして強調表示する**」ことだけである。
★★★**しかしそれは「同じ規則を2箇所に書く」ことである**(裁定130)——
クライアントが「先頭から順に」を書き写せば、
**サーバの払い方が変わった日に、強調表示だけが黙って嘘になる**。
★★★★**67 の教訓「写し」と同じ形なので、番人が要る** ——
候補としては次の2つである。

1. **サーバが「次に払われるマナの添字列」をビューに載せる**(`you.plannedManaIndexes` など)。
   ★クライアントは規則を1つも持たない(裁定234 の筋)。**わたし(クロエ)はこちらを推す。**
2. クライアントが書き写し、**verify が Java の `payCost` と JS の実測を突き合わせる**
   (65 の流儀)。★**ただし「先頭から順に」は正規表現で読みにくい。**

★★指摘5(手動で選ぶ)は**サーバの口を変える**。
`play-card` に「払うマナの添字列」を足し、**指定が在ればそれを払う / 無ければ従来どおり**になる。
★★★**ここで払い方の規則が2箇所(自動と手動)に増える。**
禁忌の支払いが既に添字列を運んでいる(`manaIndexes`)ので、**その形に揃えるのが素直**である。

| `battle.css` | ドロップ先の見え方 / 払う予定のマナの強調 / プレイ中のカードの面 |
| `battle.html` | ドロップ先の器 / 確定・キャンセルの導線 / プレイ中のカードの面の器 |
| `GameService` | `play-card` が払うマナの指定を受ける / 自動払いの規則(表向き優先・一時マナ優先)|
| `GameViewBuilder` | ★**「次に払われるマナ」をビューに載せる**なら、ここが出どころ |
| `PendingChoice` | ★**プレイ中のカードID**を運ぶなら、ここか payload |
| verify | ★**実マウスのドラッグ**(合成イベントを使わない・19b/20a の教訓)|
| JUnit | 払うマナの指定を受ける口 / 自動払いの規則 |

★**大きさは「中〜大」である。**サーバの口が変わる(C-2)ので、
65・66・69 のような**クライアントだけのバッチにはならない**。

## ★次のバッチへの申し送り

1. **A-1 を最初に潰す。**「場のカードに出ない」が反映漏れなのか実環境の問題なのかを、
   版数(`battle.js` v=32 / `battle.css` v=50)で確かめること。
   ★**直っているものを直そうとしない。**
2. **A(ホバーの取りこぼし)は小さい。**単独で先に片付けてもよい ——
   ただし**出す位置の決め方**(A-3)だけは先に決めること。
3. **B〜E は1つのバッチにする。**マナの払い方という1つの規則を、
   ドラッグとクリックの2つの入口が共有するためである。
4. **C-3 の5件はマスターに伺う。**とくに **1(裏向き)・3(禁忌)** は、
   自動化すると**取り返しのつかない損**が出る形である。
5. ★★**「まずはドラッグだけ」で止めない**(69 の教訓・**途中**)。
   入口を2つにすると決めたなら、**両方を同じバッチで通す**か、
   **止めた側が測られる形**(verify に「クリックの入口も生きている」を置く)にすること。
