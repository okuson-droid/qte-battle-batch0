## 1. ★着手時に伺って確定した2件(裁定353・354)

| 番号 | 論点 | 確定した内容 |
|---|---|---|
| **353** | 「どちらの姿で使うか」の6箇所を、どの器で問うか | **2択の器を新設し、× / Esc は「やめる」にする** |
| **354** | フォーカストラップをどの形で入れるか | **手動モードの 36 の層のスタックを写す** |

### 1-1. ★★★裁定353 の理由 —— [キャンセル] が「通常プレイする」を意味していた

素の `confirm()` は `battle.js` に **7箇所**あった。
★★**うち6箇所は「両方の分岐に意味がある宣言」である** ——
72 の `askConfirm` は<b>実行する側しかない器</b>であり(裁定54)、そのままでは載らない。

★<b>いちばん効いたのは具体的な症状である</b>:

> **特殊召喚を持つカードをドラッグして場に落とし、[キャンセル] を押すと、通常プレイで出てしまう。**
> つまり<b>ドラッグを取り消す手段が1つも無かった</b>。

★★**[キャンセル] というボタンが「通常プレイする」を意味するのは、
裁定55(ボタンには動詞を書く)の真逆である** ——
文言を読み飛ばした人が、<b>やめたつもりでカードを使ってしまう</b>。

★★★**だから出口を3つにした**: A の姿 / B の姿 / **やめる**。
★<b>やめても失うものは何も無い</b> —— 宣言の時点でサーバへは1バイトも送っていない。

★検討して採らなかった案が2つある。

- **`askConfirm` に `onCancel` を足すだけ。** ★[キャンセル] と × が同じ意味になり、
  <b>「やめた」つもりで通常プレイに入る問題がそのまま残る</b>。
- **2択の器だが × / Esc は B を選んだとみなす。** ★ボタンの文言は良くなるが、
  <b>「やめる」は依然として作れない</b>。

### 1-2. ★★裁定354 の理由 —— ベタ書きは段が増えるほど壊れる

77 まで、通常モードの Esc は**優先順を5段ベタ書きした if の列**だった。
★★**フォーカストラップは1つも無かった**(裁定50 が通常モードだけ未実施だった)。

★78 は<b>宣言モーダルを1つ足す</b>ので、ベタ書きなら6段目になっていた。
★★36 が書いた理由がそのまま効く ——
「画面を覆うものは複数ある。<b>それぞれが自分で判断すると、重なったときに2つ同時に閉じる</b>」。

★<b>「同じ穴を塞ぐことと、同じ形で塞ぐことは別である」</b>(71 の教訓)は今回も検討した。
★★<b>ここは「同じ形」でよい</b>と判断した —— 通常モードの覆いは**12種**あり、
手動モードの7種より<b>多い</b>。ベタ書きが破綻する理由はこちらのほうが強い。

## 2. ★78 が実装で決めたこと(裁定を仰がなかったもの)

読みが1つに定まったので、作業を止めずに実装した(リファレンス 1-7 の流儀)。
**間違っていたら戻す。**

| 決めたこと | 根拠 |
|---|---|
| **墓地からの特殊召喚(7箇所目)だけは「確認」のまま** | 墓地から出す道に「もう一方の姿」は無い(通常プレイできない)—— 選択肢は<b>やるか、やめるか</b>だけである。72 の器がそのまま使える。★ボタンの文言だけ動詞にした(裁定55) |
| **初期フォーカスは [やめる]** | A も B も<b>どちらも送る側</b>である。Enter を押しただけで片方が選ばれてはいけない(裁定52 の筋)。★72 が確認モーダルで [キャンセル] に置いたのと同じ形 |
| **確認モーダルの初期フォーカスも `data-initial-focus` へ移した** | 77 までは `.focus()` を直に呼んでいた —— 行き先は同じだが、<b>閉じたあとの戻り先を誰も決めていなかった</b>(裁定50 の残り半分) |
| **トラップするのはモーダルだけ**(確認・宣言・情報・音・2つのゲート) | 36 と同じ線引きである |
| **拡大・ログ・切断オーバーレイは<b>層に積むが閉じ込めない</b>** | 拡大は焦点可能な要素が0、ログは配信のたびに作り直す(36 が帯・全面表示を外した理由)。★★<b>切断は 71 の判断そのものである</b> —— 操作を止めているのは `send()` のガードであって覆いではなく、<b>[盤面を確認する] で畳める</b>。閉じ込めると矛盾する |
| **それでも切断オーバーレイを<b>層には積む</b>** | z-index 1970 は確認(1965)より<b>上</b>である。積まないと<b>見えていない確認モーダルにフォーカスが閉じ込められる</b> ——<b>重ね順の真実と、層の真実を一致させる</b>(裁定56) |
| **情報モーダルに Esc を効かせた** | [閉じる] を持っているのに、77 までキーボードだけでは出られなかった。★裁定35 の一般化(Esc は × と同じ資格)からすれば<b>効くのが正である</b> |
| **デッキゲートは Esc を効かせない** | [閉じる] が無い(出るなら [ロビーへ戻る])。★<b>出口の有無という1つの事実から、× と Esc の2つが同時に決まる</b>(裁定34・JOIN の席選択と同じ) |
| **部屋消失のゲートも Esc を効かせない** | 出る道は [ロビーへ戻る](遷移)しかなく、<b>閉じても部屋は戻らない</b>(裁定345) |
| **問いの本文から「OK = / キャンセル =」の尾を落とした** | あれは素の `confirm()` が<b>ボタンの文言を決められない</b>ための名残である(36 が捨てた理由2)。★いまはボタンに動詞が載る |
| **禁忌の賢魂のボタンは「マナ n 枚」と書く** | 禁忌はコスト軽減を受けない。★<b>入口で言い方が違うことに意味がある</b>(手札は実効コスト) |
| **答えが返った時点でカードを引き直して照合する**(`stillThere`) | ★★★<b>78 が新しく開けた穴の手当てである</b>(下の 3-1) |
| **「通常プレイする」を選んだあとに強化を問い直さない** | 77 までの `else if` と<b>同じ振る舞いを保った</b>(74 の教訓・据え置き)。変えるなら裁定が要る話であり、78 の母集団の外である |
| **手動モードは1文字も触っていない** | 停止中である(片肺・71 の教訓)。★<b>78 が写したのは形であって、コードを共有したのではない</b>(裁定111・289 と同じ複製)——<b>片方だけ直さないこと</b> |
| **Java を1行も変えていない** | 宣言は「どの宛先へ送るか」を決めるだけであり、<b>送る本文は 77 と1バイトも変わっていない</b> |

## 3. ★次のバッチへの申し送り

### 3-1. ★★★素の `confirm()` を捨てると、逆の穴が開く(78 が作った新しい注意)

裁定53 の理由3 は「素の `confirm()` は**JavaScript を止める**」だった ——
止まっている間は STOMP の受信も描画も進まない。78 はそれを直した。

★**ところが、直した結果として逆の穴が開く**:
<b>問うている間も配信は届き、盤面が動きうる</b>。
答えが返った時点の「手札の0枚目」は、問うたときの0枚目と**同じカードとは限らない**。

★★77 までのコールバック(投了・席・退室・再戦)は**どれも位置を持たなかった**ので、
この問題に当たらなかった ——
★★★**78 が初めて「手札の何枚目」を非同期の向こうへ運ぶ。**

★手当ては `stillThere(zone, index, cardId)` である ——
答えが返った時点で引き直し、一致しなければ**何もしない**。
★★<b>違うカードを使ってしまうより、何も起きないほうが桁違いにましである</b>
(設計判断49 の「畳まない」と同じ筋)。

> ★★★**次に「非同期の向こうへ位置を運ぶ」ものを作るときは、必ず引き直すこと。**
> 番人は verify 78-9b(宣言のあいだに手札が入れ替わったら、答えても何も送らない)である。

### 3-2. ★★★verify の「時々落ちる2項目」は<b>もう「時々」ではない</b>(候補 U)

76 が見つけ、77 の着手時に再現し、★**78 では4回中2回落ちた**(2回連続で落ちたあと2回連続で通った)。

★★★**実際に有害だった。**78 の作業中、2回連続で落ちたので
<b>わたしは自分が触った CSS を疑い、時間を使った</b> ——
76 が「落ちたときに実装を疑わせるぶん、むしろ有害である」と書いたそのままである。

- 落ちるのは `★★★組みかけは黙って捨てられない([元に戻す] が現れる・40・裁定119)` と
  `★条件を満たしたデッキは検証が OK になる(40)` の2件で、**必ず揃って落ちる**。
- 落ちたときの証拠は毎回 `{"main":"7/40", ...}` である ——
  ★<b>デッキの組み立てが終わる前に読んでいる</b>形に見える。

★★**78 はデッキメーカーを1文字も触っていない**ので直していない(母集団の外である)。
★★★<b>次にデッキメーカーを触るバッチで、必ず待ち方を直すこと</b>(候補 U)。
★<b>頻度が上がっている以上、もう「あとで」ではない。</b>

### 3-3. ★★手動モードの層(36)と通常モードの層(78)は<b>複製である</b>

裁定111・289 と同じ落とし穴が1つ増えた —— **片方だけ直さないこと**。
★共有しなかったのは、版数の系統を増やさないためである(裁定289 と同じ理由)。
★★<b>ただし通常モードの側には手動モードに無いものが2つある</b>:

- **切断オーバーレイを「積むが閉じ込めない」層として扱う**(手動モードに対応物が無い)
- **デッキゲートが配信のたびに開き直す**(`renderDeckGate`)——
  ★`pushModalLayer` の「二重に積まない」「フォーカスが中にあるうちは触らない」が
  <b>こちらでは日常的に効く</b>。

### 3-4. ★通常モードの層は<b>開いた順</b>で決まる(77 までの優先順とは違う)

77 までの Esc は「確認 → 席替えゲート → 拡大 → 音 → ログ」の**固定の優先順**だった。
★78 からは**開いた順のスタック**である(36 と同じ)。
★★<b>実際に重なる組み合わせは今のところ多くない</b>が、
順が変わりうることは書き残しておく。
