## 2. 足場(このバッチが作った仕組み)

### 2-1. ★★★「場以外から自分の墓地へ」を入口の分離で表した(裁定207)

《カムバックキーパー》は「**場以外から**自分の墓地に置かれたとき」に反応する。
これは既存のどの発火口でも拾えない —— 場を離れる処理
(`leaveFieldByDestruction` → `sendToTrashOrRestore`)を通らないからである。

**素直な案は「墓地に置く処理を1本にまとめて、引数で場かどうかを渡す」である。採らなかった。**

引数で分けると、新しい墓地送りを書く人が**毎回どちらかを選ぶ**ことになる。
選択を間違えても例外は出ない —— ただ「破壊されても永久に戻ってくるミニオン」が生まれるだけである。
そこで**入口を2本に割った**。

| 入口 | 何のため | カムバックキーパー |
|---|---|---|
| `GameActions.sendToTrashOrRestore`(既存) | 場を離れたカード・使用済みのカード | 反応しない |
| **`GameActions.putIntoTrashFromElsewhere`(新設)** | 手札・山札・マナから墓地へ | **反応する** |

呼び出し位置そのものが答えになるので、**取り違えようがない**。
これは裁定163(同じ規則を2箇所に置かない)の裏返しである ——
**違う規則は、違う入口に置く。**

★新設した入口に寄せたのは次の**13箇所**である:
`GameActions` の3箇所(`drawCards` の断罪の大天使による置換 / `mill` / `destroyFaceDownMana`)/
手札からの discard 7箇所(手札を喰らう大蟹・英知の継承者・海皇ポセイドン・背水の烈火使い・
再起の炎陣・血の対価・ダークネオンステージ)/ `resolveChoice` の3箇所
(選択の追い風・アクア・サーチ・潮獣コアンチ)。

★**【還元】は適用しない。** 行き先の分岐は「場を離れたカードと使用済みのカード」のための
仕組みであり、手札から捨てられたカードは従来から素直に墓地へ行っていた。
ここで還元を効かせると**このバッチと無関係な既存カードの挙動が変わる**。

### 2-2. ★★★`TriggerType` を足さなかった(裁定206。194 の2度目)

`notes/ver11-migration-plan.md` 2-1 は、このイベントを「P2 で足す3つの `TriggerType` の
3つ目」と見込んでいた。**また外れた。3つのうち2つが外れたことになる。**

理由は 49 とは別である。あちらは「使い手がリーダーだけだった」だが、こちらは**もっと硬い**——

> `CardEffectRegistry.fire` は<b>場に居るミニオンの表を引く</b>仕組みである。
> カムバックキーパーが反応するのは「自分が墓地に置かれた瞬間」であり、そのとき場に居ない。
> トリガー型として登録しても、**引く相手が居ないので永久に発火しない。**

つまり `TriggerType` は<b>できない</b>のであって、<b>やらないほうがよい</b>のではない。
器の形は「場に限定されないゾーン横断トリガー」(設計判断15)であり、
黄泉還る水龍の `fireManaLeft` と同じ**専用の発火口**になる。

★**反応するのはこのカード自身が置かれたときだけである**(マスター裁定203)。
発火口はカードIDを引数で受け取り、自分でなければ何もしない。
「墓地にあれば何かが捨てられるたびに戻る」形にすると、墓地肥やしと組んで無限に近くなる。

### 2-3. 「墓地から場へ」も1本に集約した

《演舞の墓守》の【常在】は**経路を問わない**(マスター裁定204)。
実装するには、まず**墓地から場へ出す経路を1本にする**必要があった。

50 の前は、`GameActions.reviveFromGrave` を通る蘇生と、
`trash.remove(...)` + `putIntoFieldByEffect(...)` を直書きする2箇所
(黄泉還る水龍・ゾンストライカー)が混在していた。**後者を前者に寄せた。**

もう1本の経路である「墓地からの召喚」(黄泉の召喚主)は召喚なので
`reviveFromGrave` を通らず、`GameService.summonFromGrave` から同じ発火口を呼ぶ。

★**この2本目は、現行のカードプールでは到達しない。**
演舞の墓守も黄泉の召喚主も<b>リーダー</b>であり、1人が両方を持つことはありえない。
それでも置いたのは、裁定204 が「経路を問わない」と決めたからである ——
**書かずに済ませると、次に読む人が裁定をもう一度掘り返すことになる。**
6章の「答えていないこと」に、試験できていない旨を明記した。

### 2-4. `reviveFromGrave` が実体を返すようになった / 「場の末尾」を3箇所やめた

発火口に「出たミニオン」を渡す必要があるので、戻り値を `boolean` → `MinionInstance` に変えた
(49 の `putIntoFieldByEffect` と同じ変更である)。

ついでに、**戻り値を使わず「場の末尾」を取っていた3箇所**を直した。
49 の設計解説 2-3 が「`ON_ENTER` の中でさらに場が増えると末尾が別人になりうる」と
書いていたとおりの形が、まだ残っていた。

| 箇所 | 直す前 | 実害 |
|---|---|---|
| 不滅のネクロマンサー | 末尾に【突進】 | 別のミニオンが【突進】を得る |
| 死者蘇生 | 末尾に【突進】 | 同上 |
| **降臨の伝道師** | **末尾に3ダメージ** | ★**関係の無いミニオンが3ダメージを受ける** |

★**降臨の伝道師のそれは実害のあるバグだった。** 50 の範囲外だが、
戻り値を導入したついでに直せる形だったので直した。
★**器を変えると、同じ形の古い書き方が自動的に浮かび上がる。**

### 2-5. 登場の置換とダメージの肩代わり(光霊・モアニール)

1枚で2つの置換を持つ、このバッチでいちばん重いカードである。
**判定は `RuleGuards`、実行は `GameActions` / `GameService`** に分けた
(このクラスの冒頭の設計方針: 判定層は状態を変えない)。

| 置換 | 判定 | 実行位置 |
|---|---|---|
| マナより重いミニオンは山札の下へ | `RuleGuards.isEntryToDeckBottom` | `GameService.summonToField` / `GameActions.putIntoFieldByEffect` |
| リーダーへのダメージを肩代わり | `RuleGuards.leaderDamageInterceptor` | `GameActions.damageLeader` / `GameService.attack` / `leaderAttack` |

★**`putIntoFieldByEffect` が `null` を返す理由が2つになった**のが、このバッチで
いちばん危ない副作用である。

- (a) 場が満杯・踏み倒し禁止 … **カードは宙に浮いたまま**(呼び出し側が行き先を決める)
- (b) モアニールの置換 … **すでに山札の下に置いてある**

`null` だけを見て手札に戻すと、(b) で**カードが2枚に増える**。
そこで「出せなかった分は手札に戻す」2枚(神の福音・ギガマウス・バイト)を、
**呼ぶ前に `isMinionZoneFull()` を自分で見る**形に揃えた。
★神の福音は「出した数だけ引く」ので、戻り値で実際に出たかを数えるようにも直した。

★**肩代わりの位置は大地の守護盾の隣である。** 短絡評価により、守護盾が先に肩代わりした場合は
モアニールを消費しない。順序は「軽減(正義の御盾)→ 肩代わり」——
軽減で0になったダメージは**受けていない**ので、肩代わりの出番が無い。

### 2-6. 場全体の攻撃回数(英術・バンユー)

裁定200 が「**場全体で合計1回**」と決めたため、既存の攻撃回数では表せない。
`MinionInstance.attacksUsedThisTurn` は「そのミニオンが何回殴ったか」であり、
数えている量が違う。そこで `PlayerState` に2本足した。

```java
private int minionAttackLimitedOnTurn = 0;   // 制限が掛かるターン番号(0なら制限なし)
private int minionAttacksUsedThisTurn = 0;   // 場全体の攻撃宣言の回数
```

★**制限のほうは `startTurnReset()` で戻さない。** 凍結(`cannotAttackOnTurn`)・
スペル封じ(`spellSealedOnTurn`)と同じ**ターン番号の刻印**であり、
戻すと「制限を掛けられた本人のターン開始で制限が消える」という間の抜けたことになる。
回数のほうだけを戻す。★壊し検証13番がこの取り違えを捕まえる。

## 4. 試験(`DarkLightVer11EffectTest`・44件)

足場は 48 で作った `support/AutoGameFixture` をそのまま使う。方針も 48・49 のままである。

1. **本物の入口から起こす**(裁定187)。`playCard` / `specialSummon` / `attack` /
   `endTurn` / `nextPhase`。
2. **裁定を名指しで固定し、「そうでない側」も測る**(裁定181)。
   「戻ってくる」だけを測ると**いつでも戻ってくる**実装でも通る ——
   だから「場で破壊されたときは戻らない」を並べて置く。
3. **数ではなく結果を見る。**ドロー数は**山札の減り**で測る。

★**カムバックキーパーだけは経路ごとに測っている**(手札から / 山札から / 場から / 他のカード /
場が満杯)。入口の分離(2-1)が正しく効いているかは、**経路を全部通してみるしか確かめようがない。**

### 4-1. ★`EffectImplementationTest` の題材の名指しをやめた(裁定209)

「効果が未実装のスペルに印が付く」は、47(潮獣ビシャカワ)→ 49(英術・グラーニス)→ 50 と、
**3バッチ続けて同じ理由で書き換えている**。実装が進むフェーズでは必ず陳腐化する。

名指しをやめ、**不変条件**を測る形に変えた ——
<b>解決処理を持たないスペルは、印が付くか、ルール側で宣言されているかのどちらかでなければならない。</b>

★**これは同語反復ではない。** `isRegistered` は9つの表を見ており、`spellEffects` が空でも
`targetSpecs` や `playConditions` に載っていれば「登録あり」と答える。つまり
**対象指定だけ書いて解決処理を書き忘れた**スペルは、印が付かないままここをすり抜けようとする。

★**書いた瞬間に1件見つかった。**《ピュア・エレメント》は `spellEffects` を持たず、
`GameService.playPureElement` が直接処理する唯一のスペルである ——
**この試験を書いて初めて表に出た事実**であり、宣言のほうで実装済みと答えていることを確認した。
