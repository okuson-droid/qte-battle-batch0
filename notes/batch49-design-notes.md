## 2. 足場

### 2-1. ★★「場にミニオンが出た」に `TriggerType` を足さなかった

`notes/ver11-migration-plan.md` 2-1 は、このイベントを **P2 で足す3つの `TriggerType` の
2つ目**として見込んでいた。使い手を実際に読んで、方針を変えた。

| 使い手 | 種別 | 本文 |
|---|---|---|
| ロロイヨ伯爵(水) | **リーダー** | 【常在】ターンに一回【守護】のミニオンが場に出るたびカードを1枚引く。(潜伏も同様) |
| 英皇アントマルエル(光) | **リーダー** | 【常在】場にミニオンが出た時自分の手札が6枚以下だったらカードを1枚引く |

**2枚ともリーダーの【常在】である。ミニオンもウェポンも1枚も反応しない。**

`TriggerType` は<b>カード(ミニオン・ウェポン)の表に載せるための分類</b>であり、
リーダーの常在能力はこれまで一度も表に載せていない ——
`fireManaPlaced`(豊穣の地霊主)・`fireOwnMinionDestroyed`(妖ノ長・ストク)のように、
**専用の発火口へ直接書く**のが既存の形である。
ここで `TriggerType` を足すと、**誰も登録しない値**が1つ増える ——
裁定178 が戒めた「使い手のいない器」そのものになる。

したがって **`CardEffectRegistry.fireAnyMinionEntered(EffectContext)` という発火口だけ**を作った。
ミニオンやウェポンがこのイベントに反応する日が来たら、そのバッチが `TriggerType` を足せばよい。

★**計画書の見立てが外れたこと自体は問題ではない。**47 の着手時にも同じことが起きている
(【常在】は1つの仕組みではなかった)。**器の形は、使い手を読んでからでないと決まらない。**

**発火位置は `ON_ENTER` と同じ2箇所**である。

| 場所 | 何のとき |
|---|---|
| `GameService.summonToField` | 召喚(通常・特殊) |
| `GameActions.putIntoFieldByEffect` | 効果による「出す」(蘇生・手札から出す) |

**★両者のリーダーを見る。**テキストが「自分の」と書いていない誘発は両者を見る(裁定156(2))ので、
**相手のミニオンが場に出てもロロイヨ側が引く**。
`ctx.owner()` は「場に出たミニオンの持ち主」であって「反応する側」ではないため、
ドロー先は必ず watcher 側で指定する。ここを間違えると、
**相手の召喚で相手が引く**という逆の挙動になる(検証 3・4 が番人)。

### 2-2. `PlayerState` の2つのターン刻印

ロロイヨの「ターンに一回」を、**【守護】と【潜伏】で独立に**持つ(裁定156(1))。

```java
private int guardEntryDrawTurn = -1;
private int stealthEntryDrawTurn = -1;
```

**★真偽値ではなくターン番号である。**理由は 48 の `tryConsumeDestroyHeal` とまったく同じ ——
裁定156(3) により毎ターンリセットされるのに、`startTurnReset()` は**ターンプレイヤーにしか走らない**。
そしてこのカウンタは裁定156(2) により**相手のターン中にも消費される**。
ターン番号を刻んでおけば、リセットという操作そのものが要らなくなる。

★48 で1枚(ストク)、49 で2枚。**この形はもう3つ目である。**
「ターンに1回・両者のターンで別々に」は【常在】の定番であり、
今後もリーダーの常在が出るたびに増える見込みである。

### 2-3. `putIntoFieldByEffect` が実体を返すようになった

ギガマウス・バイトが「出した3体に【突進】を与える」ために、出したミニオンの実体を要る。

**「場の末尾を取る」形にしなかった。**`ON_ENTER` の中でさらに別のミニオンが場に出ることがあり
(黄泉還る水龍)、末尾が別人になりうる。戻り値なら取り違えようがない。

★呼び出し箇所は本番8箇所あるが、**どこも戻り値を使っていなかった**ので、
`void` → `MinionInstance` の変更で壊れるものは無い(出せなかったときは `null`)。

### 2-4. `TargetSpec.Filter.WATER_CIVILIZATION`

★**この列挙体は名前のままクライアントへ送られる。**`battle.js` は受け取った名前を
`switch` で分岐して「その手札を選べるか」を決めている。
したがって **Java に足して JS に足し忘れると、サーバは通すのにクライアントが光らせない**
(=そのカードを永久に選べない)。実際にこの穴を通ったので、verify に番人を置いた(5-2)。

文明を引数に取る1つのフィルタにまとめる案は採らなかった。
送る形(列挙体の名前)と受ける形(`switch` の `case`)の**両方を作り直す**ことになり、
既存の `LIGHT_CIVILIZATION` を使う2枚(神の福音)にも波及する。値を1つ増やすほうが安い。

## 3. カード6枚

### 3-1. ロロイヨ伯爵(QTE-M-WATER-29・リーダー)

> 【常在】ターンに一回【守護】のミニオンが場に出るたびカードを1枚引く。
> ターンに一回【潜伏】のミニオンが場に出るたびカードを1枚引く

裁定156 が細目をすべて決めている。実装はそれをそのまま置いただけである。

| 細目 | 実装 |
|---|---|
| (1) 守護と潜伏のカウントは独立 | `PlayerState` の刻印を2本持つ |
| (1) 両方持つ1体で2枚引く | `if` を2つ並べる(`else if` にしない) |
| (2) 相手のミニオンでも誘発 | 発火口が両者のリーダーを回す |
| (3) 毎ターンリセット | ターン番号の刻印(2-2) |
| ★裁定193: 効果で出しても誘発 | 発火口が `ON_ENTER` と同じ2箇所にある |

**★判定は `hasKeyword` である。**印刷キーワードだけでなく、
効果で付与された【守護】(そよ風の加護など)を持つミニオンも「【守護】のミニオン」である。

★**「そうでない側」を必ず測ること。**「相手のミニオンでも引く」だけを固定すると、
**全プレイヤーが引く**実装でも通ってしまう。試験には
「ロロイヨでないリーダーは引かない」を並べて置いた(裁定181)。

### 3-2. 海獣リューグー(QTE-M-WATER-35)

> 【知識】【突進】【召喚時】自分の場に【潜伏】を持つミニオンが居るならカードを1枚引く

**【知識】の1ドローは `fire()` が自動処理する**(自身が KNOWLEDGE を持つため)。
ここに書いたのは【召喚時】の条件つき1ドローだけである(聖域の案内人と同じ分担)。

「自分の場に」と書いてあるので相手の場は見ない。
自身は【潜伏】を持たないので、場を素朴に見て自分を数えてしまう心配もない。

### 3-3. 潮獣ビシャカワ(QTE-M-WATER-36・スペル)

> 自分の【潜伏】の数自分のリーダーのHPを1回復を行う。

**数えるのは自分の場の【潜伏】ミニオンである。**手札や墓地は数えない ——
「自分の」に続く場所の指定が無いキーワードの数え上げは、
既存カードがすべて場を指している(影潜む水刺客「自分の場の潜伏の数」・双流の幻術師)。

0体なら回復量0であり、スペルとしては空撃ちになる(使用そのものは妨げない)。

### 3-4. 潮獣コアンチ(QTE-M-WATER-37・スペル)

> 自分のリーダーのHPを2回復。カードを1枚引き、カードを1枚捨てる。

捨てる対象は**引いた後の手札**から選ぶので、使用宣言時に選び終える `TargetSpec` では表現できない。
アクア・サーチと同じ a9(割り込み選択)を使う。捨てるのは必須なので `PendingChoice.one`(min=1)。

★**再開先(`ResumePoint`)をアクア・サーチと共有しなかった。**
形はまったく同じだが、共有すると「どちらのカードの続きなのか」が状態から失われ、
ログに出す名前を決められなくなる。将来どちらかの挙動だけが変わったときにも、
分岐を後から割ることになる —— 列挙体が1つ増える代償のほうが安い。

### 3-5. ギガマウス・バイト(QTE-M-WATER-38・スペル)

> 自分の手札の枚数このカードのコスト-1
> 自分の手札から水文明のミニオンを3体場に出す。それは【突進】を得る。

本文が3箇所で読めるので、まとめて裁定を仰いだ(裁定184 の運用)。

**★裁定190: 数える手札には、このカード自身を含む。**
印刷コスト15から手札の枚数を引く。手札7枚なら 15 - 7 = 8 である。
実装は `owner.getHand().size()` をそのまま読むだけでよい ——
`GameService.playSpell` は **検証 → `payCost` → `removePlayedAndTargets`** の順に進むので、
コストを計算する時点でこのカードも、選んだ3体も、まだ手札にある。
したがって**選択の有無でコストは動かない**。

**★裁定191: 手札の水ミニオンが3体に満たなくても「居るだけ出す」。**
0体でも使用できる(空撃ちになる)。実装は `Requirement.upTo(Kind.HAND, Side.SELF, 3, ...)` ——
この形の javadoc がそもそも「『好きな数だけ』『あるだけ』選ばせる要求」と書いてあり、
神の福音(手札から光の守護ミニオンを最大2体)がすでに同じ形で動いている。

**★裁定192: 出す3体はプレイヤーが選ぶ。**コスト15のフィナーレで何を出すかは勝敗に直結するので、
自動決定(闇文明の `AutoChoice`)ではなく本人に選ばせる。
UI は既存の対象選択(手札を光らせて選ぶ)がそのまま使える。

**★効果による「出す」なので【召喚時】は発動しない**(`ON_ENTER` のみ)。
水鏡の幻術師(【召喚時】2ドロー)を出しても引かない —— 検証 19 が番人である。

★場の空きが足りず出せなかったぶんは**手札に戻す**(神の福音と同じ扱い)。

★【突進】は「得る」なので**恒久の付与**にした(「そのターンの間」とは書かれていない)。
実際に意味を持つのは出したターンだけだが、**書かれていない期限を勝手に足さない**。

### 3-6. アルキンティス(QTE-M-WATER-39・ウェポン)

> 【常在】自分の場の【知識】の枚数Attackを+1する

**影潜む水刺客(自分の場の潜伏の数だけ Attack+1)とまったく同じ形**で、
数える対象だけが【知識】に変わる。`StatCalculator.effectiveWeaponAttack` に1つ足すだけである。

★**【常在】は保存しない。**評価するたびに場を見る(計画 2-1 の (a))。
場が減れば攻撃力も戻る(検証 20 の2件目)。**`PersistentAura` は今回も要らなかった。**

### 5-2. ★verify 49-1(フィルタの Java↔JS 突き合わせ・2項目)

`TargetSpec.Filter` を Java に足して `battle.js` に足し忘れると、
**サーバは通すのにクライアントがその手札を光らせない**。
遊びに効くのに、これまで誰も見ていなかった(裁定130 が戒めた形の実例)。

測り方は**期待値を書かず、互いを突き合わせる**。

- Java 側 … `TargetSpec.java` の `enum Filter` から値名を拾い、
  そのうち `CardEffectRegistry` の **`Kind.HAND` の要求で実際に使われているもの**に絞る
  (`IGNORES_STEALTH` と `HIGHEST_ATTACK_OPPONENT` は手札の絞り込みに現れないので、JS に無くてよい)
- JS 側 … `battle.js` の `case 'XXX':` を拾う
- 差分が空であること

★★★**空振りを第3の答えとして持つ**(裁定186)。抽出の正規表現が壊れて0件になると、
「差分なし」で緑になってしまう。そこで

1. **3つの集合がいずれも空でないこと**を条件に含め、
2. **このバッチが足した `WATER_CIVILIZATION` が照合の対象に入っていること**を別項目で測る。

2 が要るのは、1 だけでは「Java 側の抽出が古い値だけを拾っている」状態を見抜けないからである。

★判定が落ちることを2通り確かめた(裁定116)。

| 壊した内容 | 落ちた項目 |
|---|---|
| `battle.js` から `WATER_CIVILIZATION` の分岐を消す(Java にだけ足した状態) | 2項目とも。`missingInJs: ["WATER_CIVILIZATION"]` と出た |
| Java の抽出の正規表現を壊して0件にする | 2項目とも。**空振りが緑に化けなかった** |

## 8. ★このバッチで確定した裁定

- **190. ★「このカードのコスト-手札の枚数」は、手札にあるそのカード自身も数える(マスター裁定)。**
  ギガマウス・バイト。裁定1(使用カウンタは自身を含まない)とは**逆向き**である ——
  あちらは「使い終わった枚数」を数えており、自分はまだ使い終わっていない。
  こちらは「今の手札の枚数」であり、自分はそこに居る。
  ★**「自身を含むか」はカードごとに決まるのではなく、数えている対象が何かで決まる。**
- **191. ★「N体場に出す」は、足りなければ居るだけ出す(マスター裁定)。**
  「N体出せなければ使用できない」ではない。裁定(喚ビ集ウ・アヤカシ・48)の一般形であり、
  **候補の不足はカードの使用そのものを妨げない**。
  場の空きが足りない場合も同じ扱いで、出せなかったぶんは手札に戻る。
- **192. ★「手札から出す」対象はプレイヤーが選ぶ(マスター裁定)。**
  自動決定(`AutoChoice`)は闇文明の既存カードのための仕組みであり、既定ではない。
  ★**盤面に残るものを決める選択は、本人にさせる。**
- **193. ★★「場に出るたび」は召喚に限らず効果による「出す」も含む(マスター裁定)。**
  `ON_ENTER` と同じ範囲である。【召喚時】と書かれていない登場の誘発は、
  蘇生・手札から出す・進化(P3)のどれでも起きる。
- **194. ★★★器の形は、使い手を全部読んでから決める。**(2-1)
  計画書は「盤面全体のミニオン登場」を `TriggerType` として見込んでいたが、
  使い手2枚はどちらも**リーダーの【常在】**で、ミニオンもウェポンも反応しなかった。
  `TriggerType` はカードの表に載せるための分類なので、足せば**誰も登録しない値**が増える。
  ★裁定178(器を作るバッチでは使い手も一緒に実装する)の続きであり、
  あちらが「使い手のいない器を作るな」なら、こちらは**「使い手を読む前に器の種類を決めるな」**である。
  ★47(【常在】は1つの仕組みではなかった)に続き、**計画書の見立てが外れたのは2度目**である。
  計画は枚数と依存関係を見積もるためのものであって、**形の設計はバッチの中でやり直してよい。**
- **195. ★★クライアントへ名前のまま送る列挙体は、両側に居ることを機械で測る。**(2-4・5-2)
  `TargetSpec.Filter` は Java の値名がそのまま `battle.js` の `case` になる。
  片側だけに足しても**どちらも例外を出さない** —— ただ手札が光らなくなるだけである。
  ★裁定130(同じ規則が2箇所にあるとき、期待値を書かず互いを突き合わせる)の適用先が、
  「同じ値を2箇所に書いた」ではなく**「片方が他方の名前に依存している」**に広がった。
- **196. ★★「壊したのに落ちない」を見たら、まず改変が当たっているかを疑う。**(5-4)
  落ちない理由は3つある —— (a) 試験が足りない、(b) 改変が当たっていない、
  (c) 改変が意図した誤りになっていない。**(b)(c) を先に潰さないと (a) の判断は信用できない。**
  ★裁定186(検証スクリプトは「仕事をしていない」を自分で区別できなければならない)を、
  <b>壊し方の側</b>にも適用する。確認用スクリプトは
  OK / NG / EMPTY / SETUP-NG の**4値**で答えさせること。
- **197. ★「無かった」と言えることも成果である。**(6-2)
  裁定188 の洗い出しを2回目として実行し、`unlimitedCopies` に乗ったままの分岐を3箇所見つけた。
  どれも**死んでいるだけで挙動は正しい**ので直さなかったが、
  **見て、無害だと判断した**ことを書き残す。次のバッチが同じ場所をもう一度洗わずに済む。
