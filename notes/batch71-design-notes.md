## 2. ★★★番人は `send()` であって、オーバーレイではない(33 の 1-2)

「切断中は操作できない」を作る方法は2つある。

- (a) **画面を覆って触らせない**(オーバーレイ)
- (b) **送信の口で弾く**(`send()` のガード)

★**(a) だけで済ませると、覗き見の導線を1つ足した瞬間に穴が開く。**
通常モードの重ね順は 1000〜1500 の5層あり、「全部より上」を未来にわたって守り続けることを
**安全装置の根拠にはできない**。

→ **(b) を番人とし、(a) は宣言に格下げした。**
その帰結として、オーバーレイに **[盤面を確認する]** を置ける ——
畳んでもガードは効いたままであり、**安全性は1ミリも落ちない**。
★**落ちない構造にしたことが、そのボタンを置ける根拠である。**

★★**壊し検証の軸7 がこの判断そのものを測っている。**
ガードの根拠を「オーバーレイが出ているか」に差し替えると、
**71-1 は緑のまま通り、71-4 だけが落ちる** —— それがこの軸の意味である。

### 2-2. 判定は `client.connected` だけを見ない(33 の 1-6)

```js
function isConnected() {
    return client.connected === true && !socketDown;
}
```

`onWebSocketClose` が呼ばれる時点でライブラリ内部のフラグが既に倒れている保証を、
**こちらは持てない**(StompJS の実装詳細である)。
倒れていなければオーバーレイは出ず、しかも**音を立てずに**出ない。

★**判定関数は1つのまま**であり、参照する事実が2つになっただけである(裁定130 に触れていない)。

## 3. ★★★70 が増やした実害 —— 送れなかったのに畳んでしまう

**本バッチで実害がいちばん大きいのはここである。**

ハンドオフ v77 は「ドラッグの途中で相手が落ちても盤面は静かなままである」と書いていた。
それも本当だが、**もっと痛いものが 70 の中に埋まっていた。**

70 は入口を2つにするために、**ローカルにしか無い状態**を3つ作った ——
確定待ち(`manaPay`)・進化素材の選択(`evolution`)・対象選択(`pending`)である。
69 までの書き方はどれも「**先に畳んでから送る**」であった。

```js
const pay = manaPay;
manaPay = null;              // ← 畳む
send('charge-mana', { ... }); // ← 送る(切断中は届かない)
```

★切断中にこれを踏むと、人からはこう見える ——
**[確定]を押した。何も起きない。しかも選んだマナが消えている。**

→ **`send()` は送ったかどうかを返し、呼び出し側はそれを見る**(33 の `send` の Javadoc は
「呼び出し側が分岐したくなった場合のため」と書いていたが、手動モードには使い手が居なかった。
**通常モードには居る。**)

| 場所 | 送れなかったら |
|---|---|
| `confirmManaPayment`(確定待ち) | **元へ戻す**(`restoreManaPayment`)。選んだマナも残る |
| `confirmEvolutionSelection`(進化素材) | **元へ戻す**。選んだ素材も残る |
| `commitRequirement`(対象選択) | **最後の要求だけ巻き戻す**(3-2) |
| `submitMulligan` / `keepHand` | 選んだ枚数を捨てない |
| `toggleChoicePick` / `confirmChoice`(割り込み) | 選んだ候補を捨てない |

### 3-1. ★★先に畳んでから進み、失敗したら戻す(順序の話)

最初の実装は「**送れたときだけ畳む**」と書いた。**落ちた。**

`beginSelection` は途中で `render()` を呼ぶ。確定待ちを抱えたまま進むと、
**その render が確定待ちの案内を描いてしまう** ——
「対象を選んでください」ではなく「払うマナを選んでください」が出る。

→ **先に畳んでから進み、送れなかったら元へ戻す。**
戻し方は `restoreManaPayment` 1本に置いた(裁定130)——
`confirmManaPayment` には出口が4つあり、戻す処理を出口ごとに書くと、
**次に出口が増えたときに片方だけ古いままになる**。

★★**これは verify が教えてくれた。**書いた時点では「送れたときだけ畳む」で正しいつもりだった。

### 3-2. ★★★対象選択は「最後の1要求」だけ巻き戻す —— 死に止まりを作らない

対象選択だけは、そのまま保つと**もう一度撃つ入口がどこにも無い**。
要求は全部埋まっており、再送のきっかけになる操作が存在しないからである
(送信は「最後の対象を選んだ瞬間」に起きる)。

→ 送れなかったら `pending.collected.pop()` して、**最後の要求を選び直せる状態**に戻す。

★**プレイそのものは畳まない。**払うマナ・進化素材・ここまでに選んだ対象は残り、
巻き戻るのは**最後の1要求ぶん**だけである。

★★**「保つ」と「止まらせない」は両立させなければならない。**
状態を大事に抱えた結果、人が次に何もできなくなるなら、それは保っていない。

## 4. 宣言のほう(オーバーレイと帯)

### 4-1. 帯はヘッダ行の中に置いた

```css
.auto-conn-bar { flex: 0 0 auto; }
```

★**位置指定を1つも持たない。**ヘッダの flex に並ぶだけである。

★★**`position: fixed` を持たない = z-index も要らない。**
手動モードの帯が 1975(オーバーレイより上)を持っているのは保険だが、
通常モードでは**保険の要る重なりが構造的に起きない** ——
帯とオーバーレイは**同時に出ない**からである(出す判定は `updateOfflineLock` 1箇所であり、
オーバーレイが出ている間は帯を出さず、畳んだら帯だけになる)。
★**重ね順の約束を1つ増やさない。**

★`flex: 0 0 auto` にしたのは、spacer に押し潰されないためである。
★★**`0 0 0px` ではない** —— 70 が踏んだとおり、flex アイテムの `min-width` は `auto` であり、
`0px` を書いても中の文字が枠を押し広げる。**ここで欲しいのは「自然な幅で縮まない」である。**

### 4-2. ★★規則は1つ、名前は2つ

`battle.css` は**両モードの共有ファイル**である。切断オーバーレイの見た目は
両モードでまったく同じなので、**値を2度書かなかった**。

```css
.manual-offline,
.auto-offline { position: fixed; inset: 0; z-index: 1970; ... }
```

★裁定289 は「UI は複製する」と決めたが、あれは**JS ファイルの話**である
(共有 JS にすると版数の系統が増える。裁定111)。
**CSS は既に1ファイルを共有している**ので、複製する理由が無い ——
複製すれば 67 の教訓(**写し**)がそのまま当てはまり、
片方の色を直した日にもう片方が黙って古いままになる。

★**名前が2つなのは、手動モードの markup を触らないためである。**
通常モードは `.auto-*` を名乗る決まりなので(43 以来)、そちらに合わせた名前を足した。

★★**帯だけは「置き場所」が違うので、そこだけ分けてある** ——
見た目(色・字・角丸)は共有し、位置指定をモードごとに書く。

### 4-3. 拒否の合図: トーストを作らなかった(マスター確認)

手動モードは `showToast` + `flashDenied` で拒否を告げる。
通常モードには**どちらも無い**ので、写すなら器を2つ増やすことになる。

★**増やさなかった。**理由は、ガードが火を噴く場面では**宣言が既に出ている**からである ——
覆っているならオーバーレイが、畳んでいるなら帯が、切断中であることを言っている。
足りないのは「**いま押したそれ**が弾かれた」だけであり、それは明滅で指せる。

```js
flashDenied(document.getElementById('auto-conn-bar'));
flashDenied(document.getElementById('connection-status'));
```

★★**明滅が「実際に効いている」ことまで測っている**(verify 71-2b)——
`.auto-denied` を付けたあとの **computed な `animation-name`** を読む。
★これは 70 が見つけた穴(`.mana-chip` は 44 から1度も当たっていなかった)と同じ形を
**ここで作らないため**である。**クラスの数を数えるだけでは「書いてあるが効いていない」を緑にする。**

### 4-4. ★★★ゲートは2枚あり、扱いが違う(通常モード固有)

手動モードには席選択ゲートしか無い。**通常モードには2枚ある**(66)。

| ゲート | 切断の案内 | 理由 |
|---|---|---|
| 席選択(`#seat-gate`) | **出さない** | まだ盤面に入っていない人に「盤面が操作できません」と言っても意味が無い(33 の 1-4) |
| デッキ読み込み(`#deck-gate`) | ★**出す** | **入室後**であり、読み込みの最後に `send('ready')` を撃つ —— 切断中はそれが届かないので、ファイルを選んでも**「相手のデッキ待ち」の顔のまま黙って止まる** |

★★**手動モードをそのまま写すと、こちらまで抑止してしまう。**
**壊し検証の軸11 が、その写し間違いを名指しで捕まえる。**

### 4-5. ★★部屋消失(`connectionFatal`)は作らなかった

手動モードの `updateOfflineLock` は `connectionFatal`(部屋消失)を見て排他している。
**通常モードにはその旗を立てる人が1人も居ない** ——
`showRoomLostFatal` にあたるものを 66 は作らなかったからである。

★**旗だけを作らなかった。**作れば、それは 70 が見つけた `.mana-chip` と同じもの
(**書いてあるのに効いていない器**)になる。裁定178 の筋である。

★★**ただし穴として書き残す。**通常モードでサーバが再起動すると、
STOMP は再接続を試み続け、購読しても盤面が二度と来ない ——
人には「再接続中」のまま永遠に見える。**これは 71 の範囲を超えている**(部屋消失の**検出**が要る)。
候補として 6章に残した。
