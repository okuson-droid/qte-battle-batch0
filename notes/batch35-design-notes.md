## 1. なぜ Java を触ることになったのか

### 1-1. 宣言は盤面に痕跡を残さない

手動モードの宣言は「ログに1行足すだけ」の操作である
(`ManualDeclaration` の javadoc)。盤面には**一切触らない**し、履歴にも積まない。
これは 21 の設計として正しい——アプリは勝敗を判定しないからである。

ところが 32a で決めた演出の大原則がこうなっている。

> **★★演出のイベント検出は「ビューの差分」である。ログを材料にしないこと。**

宣言は盤面の差分に**現れない**。だから、この原則のままでは決着を検出できない。
32a の書きぶりを素直に読むと、逃げ道は2つしかない。

- (a) ログの本文を読む(「〜を宣言した」を正規表現で拾う)
- (b) 盤面の差分に現れるようにする

### 1-2. どちらも採らず、**構造を1つ足した**

(a) は 21a が捨てた道である。あのとき文字列ログをやめたのは
「名前がどこに埋まっているかを文字列から復元することになり、必ず破綻する」からだった。
表示側で同じことを始めるのは、捨てた理由を忘れているだけである。

(b) は もっと悪い。`ManualGameState` に「決着した」というフラグを持たせると、
盤面に触らないはずの操作が盤面を変えることになり、`copy()`・履歴・リセットの
面倒を全部引き受ける。**Undo で決着が取り消せる**という、誰も望まない仕様まで付いてくる。

採ったのは第3の道である。**ログに構造を残し、ビューにその構造を載せた。**

> **★裁定40(本バッチ): 「ログを材料にしない」が禁じているのは書式であって構造ではない。**
> 演出の材料にしてよいのは、書式に依存しない**構造**である。
> 構造が無いなら、読み取り側で復元するのではなく**書く側に足す**。

こう置き直すと、32a の原則は今も1文字も破れていない。検出は相変わらず
「前後のビューの比較」1本であり(3-2)、比べる相手が盤面から
`declarations` へ増えただけである。

## 2. 配信の形(Java)

### 2-1. 変更したファイル

| ファイル | 変更 |
|---|---|
| `manual/ManualLogDeclaration.java` | **新規**。宣言ログが持つ構造(席 + 内容) |
| `manual/view/ManualDeclarationView.java` | **新規**。配信に載る宣言1件 |
| `manual/ManualLogEvent.java` | 構成要素を1つ追加 + `declaration(...)` ファクトリ |
| `manual/ManualOperationService.java` | `declare` が新しいファクトリを通る |
| `manual/view/ManualGameView.java` | `declarations` を追加 |
| `manual/view/ManualViewBuilder.java` | ログの末尾60行と**同じ1周**で宣言を拾う |

### 2-2. `ManualLogEvent` に構成要素を足した

```java
public static ManualLogEvent declaration(ManualSeatId actorSeat,
        ManualLogDeclaration declaration, String text) { ... }
```

★**主語は `actorSeat` ではない。** `actorSeat` は「誰が押したか」であり、
全公開部屋では1人が両席を操作するため null になりうる。
宣言の主語は `request.seat()` であって、これは別物である。
`ManualLogDeclaration` が持っているのはこちらの席である。

★**`plain()` から DECLARE を作れなくした。**

```java
if (kind == ManualLogKind.DECLARE) {
    throw new IllegalArgumentException("宣言は declaration(...) で記録すること: " + kind);
}
```

構造の欠けた DECLARE 行は、**ログには出るのに帯も強調も出ない**という壊れ方をする。
「動いてはいるが何かが足りない」は、いちばん気づきにくい。
`plain()` が既に「マスク対象の種別を本文だけで記録できない」を型で止めていたので、
同じ場所に同じ形で1つ足した。**入口を塞ぐのが最も安い番人である。**

### 2-3. ビルダーは「同じ1周」で拾う

```java
for (ManualLogEntry entry : entries.subList(Math.max(0, logTotal - LOG_TAIL), logTotal)) {
    log.add(new ManualLogView(...));
    ManualLogDeclaration mark = entry.event().declaration();
    if (mark != null) { declarations.add(new ManualDeclarationView(entry.seq(), ...)); }
}
```

★別に `room.getLog()` を走査して宣言を集めることもできたが、**やらない**。
それをすると `declarations` の `seq` が「配っていない行」を指しうる。
クライアントは `seq` で強調する行を選ぶので(4章)、ズレたときの症状は
**「決着行の1つ手前が光る」**あるいは**「どこも光らない」**である。
同じ範囲から同じ1周で作れば、そのズレは**原理的に起きない**。
検証にも「`declarations` の seq は必ず配った行のどれかを指す」を入れてある
(`ManualVersusTest`)。

### 2-4. `label` を載せている理由

`ManualDeclarationView` は列挙値(`WIN`)と表示名(`勝利`)の両方を運ぶ。
一見すると重複だが、**表示名の正は `ManualDeclaration.getDisplayName()` の1箇所**である
(設計判断28)。列挙値だけを渡すと、クライアントに「WIN→勝利」の対応表がもう1枚できる。
文言を直したときに片方だけ古くなる、あの形である。

列挙値のほうは**見た目の出し分けにしか使わない**。
色を表示名で分岐させると、文言を直した瞬間に色が消える。

## 3. 決着の帯(fx層)

### 3-1. 32b の帯をそのまま引き継いだ(裁定17)

裁定17 は「帯の描画機構は勝敗の帯へ転用する」と定めている。実際に引き継いだのは:

- 位置決め(`center-line` の中心。取れなければ `manual-root`)
- 出し方・消し方(`fxRegister` + `opacity` の遅延遷移)
- 鍵の作り方(席にもカードにも属さない `'declare'` 1本。連続宣言でも帯は1本)
- fx層の座席
- コントラストの機械判定の対象であること

★**注記**: 裁定17 の文中にある「z-index 1040 の座席」は、正確には
`.manual-band`(ゾーンの帯)の値である。決着の帯が座っているのは
**fx層(1030)**であり、32b のターン帯が居たのと同じ場所である。
ハンドオフの重ね順の一覧は前者を指しているので、混同しないこと。

変えたのは3点だけである。

| 項目 | ターン帯(32b) | 決着の帯(35) |
|---|---|---|
| 出ている時間 | 900ms | **2200ms** |
| 文字 | 20px | **26px** |
| 色 | 常に #ffd166 | **宣言の種類で4色** |

時間と大きさを増やしたのは、決着が**1試合に1回しか出ない**からである。
ターンは何十回も出る合図なので、目に留まる最小限でよかった。

### 3-2. 検出は「番号が増えたときだけ」

```js
const wasDeclared = fxLatestDeclaration(prev);
const nowDeclared = fxLatestDeclaration(next);
if (nowDeclared && (!wasDeclared || nowDeclared.seq > wasDeclared.seq)) {
    out.declared = nowDeclared;
}
```

これは 32b の `turnNumber > prev.turnNumber` と**同じ形**である。検出機構ごと転用した。

★この条件が守っているのは「二度決着しない」である。宣言は決着後も
`declarations` に載り続けるので、**そのあとの配信すべて**——再接続の resync、
相手がカードを1枚動かしただけの配信——で帯が出てしまう。
ログの `seq` が単調増加する(29)ので、比較は番号の大小で足りる。

★初回の配信(`prevView` が null)では `applyView` が差分そのものを採らない。
決着後にページを開き直しても帯は出ない——出るべきでもない。**そのために
ログの強調がある**(4章)。

### 3-3. ターン帯の退役(裁定17)

外したもの:

- `diffViews` の `turnAdvanced` 検出
- `fxEffects` の `'turn'` 詰め込み
- `fxBuildTurn` と `FX_TURN_MS`
- `fxBuild` の `'turn'` 分岐
- CSS の `.manual-fx-turn`
- verify の項目57・58・59・62 のターン帯部分

★**`turnNumber` そのものは残してある。** 配信にも載るし、記帳としてのターン番号は
手動モードの成果物である。外したのは**検出と帯への配線**だけである。

★退役は「消したら終わり」ではない。**戻ってこないことの番人**を1項目立てた
(5章の項目58-2)。押し忘れでずれた帯が「嘘をつく演出」として復活するのを、
機械が止める。

### 3-4. 盤面は止めない

裁定16 の軽量版として、盤面ロックは作っていない。帯は数秒で消え、
そのあとも普通に操作できる。決着したあとに盤面を並べ直して見せ合う使い方があり、
通話ではそれをしながら喋る。**止めると、そこで会話が終わる。**

### 3-5. 差分8件超のときは帯も出ない(特例を作らなかった)

裁定11(「ターンの帯は上限の特例にしない。要らない特例を作らない」)を踏襲した。
宣言は盤面に触らないので、通常は差分1件であり上限に触れない。
触れうるのは**長い切断からの復帰**——resync で盤面が総入れ替えになり、
そこに新しい宣言が乗っている場合である。このとき帯は出ないが、
**ログの決着行は必ず残る**。特例を1つ増やすより、二重の伝達経路のうち
静かなほうが生き残るほうが素直である。

## 4. ログの決着行

帯は数秒で消える。**後から見返せる決着**がログ側の役目である
(レビュー S-3 の「ログに埋もれる決着」への答え)。

```js
const decisive = new Set((declarations || []).map((d) => d.seq));
...
if (decisive.has(e.seq)) { line.className = 'manual-log-decisive'; }
```

★**行の中身は一切読まない。** 指すのは `seq` だけである(1-2 と同じ理由)。

★**差分追記(29)と両立している。** 宣言の行と `declarations` は
サーバが同じ範囲から作るので**必ず同じ配信に乗る**(2-3)。
だから追記のその場で印を当てられる。作り直し(再接続で seq が飛んだとき)でも
全行を回すので、印は同じ1行にだけ復元される。**ここは検証を2つ立てた**
——「追記のとき」と「作り直しのとき」の両方で落ちることを確かめてある。

★色を宣言の種類で変えていない。ここは**節目の印**であって勝敗の表明ではない。
1行だけ色が違うことに意味があり、4色に散らすと目印としては弱くなる。

★2戦目を始めても1戦目の決着行は光ったままである。これは意図している——
ログは消えない記録であり、「そこで1戦終わった」は事実だからである
(新しい配信でも `seq` は増えないので、帯が出直すことはない)。

## 8. 次のバッチへの申し送り

- **★★宣言を新しく増やすときは `ManualLogEvent.declaration(...)` を通すこと。**
  `plain()` は DECLARE を弾く。帯の色は `manual-fx-declare-<列挙値の小文字>` で足す
  (既定色があるので、足し忘れても「色の無い帯」にはならない)。
- **★★★ターン帯を復活させないこと(裁定17)。** 番人は項目58-2 である。
- **★fx層に新しい文字を作ったら `verify.js` の `targets` に足すこと**(32a からの規約)。
- **★決着行の強調は `seq` で指している。** ログの本文に依存していないので、
  サーバの文言を変えても壊れない。逆に、`declarations` の作り方を
  「配ったログの範囲」から外すと静かに壊れる(2-3)。
- 効果音(レビュー S-2 / 優先順位8)を入れるとき、決着はいちばん自然な取り付け点である。
  `fxBuildDeclare` が唯一の発火点になっている。
