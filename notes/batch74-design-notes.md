### 2-4. ★★★B-6 は「順序」の問題だった

効果の中で進めると **2回目が1回目より先に数えられる**。

★そこで `pendingSpellDisposition` とまったく同じ受け渡しを使った ——
効果が `PlayerState.pendingExtraSpellCasts` に +1 を書き、
`GameService.afterCardUsed` が読んで消費し、その回数ぶん「使用した」を追加で起こす。

> ★**カードIDはエンジンに1文字も現れない**(設計判断36)。
> 「回帰の風穴なら2回数える」と書くのではなく、
> 「解決中に追加で唱えたスペルの数」という**性質**を器にした。

### 2-5. ★★★B-12 は「呼び出し元の無い関門」である

《聖光の守護聖》の本文は「自分の**リーダーと**自分のミニオンすべては」だが、

★**現行の235枚に、リーダーを破壊するカードは1枚も無い。**
`destroyLeader` に相当する入口も無く、リーダーが場を去る道は「LPが0以下」1本である。
つまり **この関門を通る本物の経路は存在しない**。

★それでも実装したのは、**「いつ直すか」を書いても実装は自分では動かない**(66 の教訓)から。
★★ただし **器だけを作ったのではない** ——「相手由来か」の推定は
`RuleGuards.causedByOpponent` に切り出して**ミニオン側と共有**しており、規則は1箇所である。

> ★★**番人は `RuleGuards` を直接叩いている。**
> <b>それは「本物の入口を通っている」ことの証明にはならない</b>(裁定187 の例外)。
> 「本物の入口から観測できない挙動」の**4件目**として落とし穴に書き残した。

### 2-6. ★★B-13 は「破壊」の定義が要った

裁定336 は3つのことを同時に決めている。

1. 誘発するのは**破壊されたときだけ**である(「場を離れたとき」ではない)
2. **ウェポンの付け替えは破壊扱いである**
3. **禁忌由来のウェポンは決して破壊にならない**(消滅ゾーンへ行くため)

`(room, owner, weapon, byDestruction, fromTaboo)` に広げただけである。
★★**共通の後始末(ウェポン攻撃力の加算・「攻撃した」の記録)は無条件のまま残した** ——
あちらは3経路すべてで走らなければならない。

> コメントには「発注者確認済み」と書いてあったが、それは **Ver0.4 時代の確認**である ——
> <b>写しは、写し元が変わっても自分では変わらない</b>(67 の教訓)。

## 3. A —— 進化ミニオンの一族(裁定341)

### 3-1. ★★★13枚を個別に直していない

直したのは**3種類だけ**である(裁定130)。

| # | 場所 | 何をしたか |
|---|---|---|
| 1 | `TargetCandidates.rejectReason` の `MINION_CARD` | `== CardType.MINION` → `type().isMinion()`(**1行**) |
| | `battle.js` の写し2箇所 | `matchesFilters` と手札のハイライト |
| 2 | 各経路の合流点 | `effectPutSequence`(手札・山札)/ `requestManaSummon`(マナ)/ `resolveTrashRevive`(墓地)を**出どころ非依存の1本**へ寄せた |
| 3 | `GameActions` の2つの入口 | `reviveFromGrave` と `putManaCardIntoField` に**素材を受ける口**を作った |

★**手書きの `== CardType.MINION` を `isMinion()` へ揃えた箇所は6つ**
(《禁忌の代償》の使用条件 /《死者蘇生》の使用条件と候補 /《サモンズライト》の候補 /
《灰ノ霊呼者》の候補 /《降臨の伝道師》の公開 / マナの4枚のラムダ /
`GameService.summonFromGrave` の関門)。
**これらは規則ではなく「そのカードの条件」なので、1箇所にまとめる対象ではない。**

### 3-2. ★★★暫定だったことの意味

73 の絞り込みは**種別の読み違いではなかった**。裁定308(b) は
「`Filter.MINION_CARD` による除外は暫定である」と**明記していた** ——
理由は「墓地・マナ・山札の経路に素材を確保する段が1つも無いから」である。

> ★★**「暫定でこうしておく」は、前提が消えても自分では戻らない**(64 の教訓・**時間**)。
> ★★★**74 が見つけた新しい顔**: 暫定は<b>正しい理由で置かれていた</b>。
> だから **暫定を外すには、置かれた理由のほうを先に解消しなければならない** ——
> 1行直すだけでは、裁定226 の穴が13枚ぶん同時に開く。

### 3-3. ★★出どころを型に持たせた

```java
private enum EffectPutSource { HAND, HAND_SELECTED, TRASH, MANA, DECK }
```

★`FieldEntryOrigin`(HAND / OTHER)とは**別物である** ——
あちらは**【召喚時】が発動するか**だけを表す2値であり(裁定311)、
こちらは**どのゾーンからどうやって取り出すか**を表す。

★★**`HAND` と `HAND_SELECTED` を分けたのが要点である。**
`TargetCandidates.selectionFrom` は `Kind.HAND` の選択を
**手札から取り除いた状態で**効果へ渡す(Batch 4 からの規約)。
同じ扱いにすると**二重に抜こうとして失敗する** ——
<b>出どころは同じ「手札」でも、取り出し方が違う</b>。

★★★**出せなかったときに手札へ戻す責任も、この型が持っている**
(`returnUnplacedCard`)。宣言時に選ばれた手札は<b>どのゾーンにも居ない</b>ので、
戻さないと**カードが消える**(51 の「先に取り除くと行き先の無いカードが生まれる」)。

### 3-4. ★★★payload の欄を1つに畳んで実際に踏んだ

素材を問う割り込みは `PendingChoice.payload`(文字列1本)に文脈を畳んで運ぶ。
最初、進化カードのIDと「取り出し方(locator)」を**同じ欄に入れていた**。

> ★**マナだけは locator が「位置」であってカードIDではない。**
> `evolutions.get("15")` を引いて素材の仕様が見つからず、
> **マナの経路でだけ**「素材を問わずに黙って不発になる」という症状が出た。

★★**1つの欄に2つの意味を持たせると、片方でしか壊れない。**
★壊し検証の**軸30**にこの形を残してある。

### 3-5. ★《黄泉の召喚主》だけは「召喚」である

本文が「ミニオンを墓地から**召喚してもよい**」と書いているので、
**通常の進化召喚とまったく同じ扱い**になる ——
<b>素材は使用宣言のときに選ぶ</b>(割り込みではない)。したがって【召喚時】も発動する。

| 経路 | 素材を選ぶ時点 | 【召喚時】 |
|---|---|---|
| 手札からの進化召喚 / 特殊召喚 / 禁忌 | **使用宣言のとき** | 発動する |
| 《黄泉の召喚主》の墓地からの**召喚** | **使用宣言のとき**(★74) | 発動する |
| 効果による「出す」(手札) | 解決中の割り込み | 発動する(裁定311) |
| 効果による「出す」(墓地・マナ・山札) | 解決中の割り込み(★74) | 発動しない |

★WS の受け口(`GraveSummonRequest`)は **1文字も変えていない** ——
`materialIds` は Batch 52 から在り、この入口が読んでいなかっただけである。
★★したがって `WsRequestPayloadTest` の表に足す行は無い ——
**増えたのは「送ることがある」という事実だけ**である(設計判断52 の但し書き)。

### 3-6. ★★宣言時には「素材が今あるか」で絞れない

手札から**割り込みで**選ばせる経路(《神の福音》《聖なる降誕の儀式》《灰ノ霊呼者》
《降臨の伝道師》)は、**素材を今すぐ確保できる進化だけ**を候補にする(裁定308(b))。

★**宣言時の対象指定では、それができない。**
`TargetSpec.Filter` はカードの**静的な性質**しか見ず、しかも同じ規則が
`battle.js` にも写っている(裁定195)。盤面の規則を足すと
**クライアントに盤面の判断を持たせること**になり、裁定234 に反する。

★したがって宣言時に素材の足りない進化を選んだ場合は、
**出す段で素材を問い、足りなければ出ない** ——
「場が満杯で出せなかった」と同じ普通の不発である(裁定191・302)。
