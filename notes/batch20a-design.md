## 0. 経緯

手動モード フェーズ1(一人回し)の運用中に、マスターから次の3点の不便が報告された。

1. 山札から墓地・マナへカードを送るとき、いったんドローして手札を経由しなければならない。
2. 裏向きにしたマナを他のゾーンへ移しても裏向きのまま残り、墓地や場でも中身が見えない。
3. リーダーのLPの変更が `prompt()` による数値の打ち直ししかない。ATK/HPは数値入力欄の
   スピナーでクリック増減できるのに、LPだけそれができない。

いずれもフェーズ1の日常操作に直接効く箇所であり、フェーズ2へ進む前に解消する。

## 2. 仕様

### 2-1. 山札からのドラッグ(A1〜A4)

山札のカード型パイル(`createCardPile` の `DECK` 分岐)を**ドラッグの起点**にする。
ドラッグして他ゾーンへ落とすと、**山札の一番上の1枚**がそのゾーンへ移る。

- **対象は常に一番上の1枚**とする(A1)。複数選択中であっても山札ドラッグは1枚であり、
  `selected` の内容を参照しない。山札は非公開ゾーンであり「どの1枚か」を選べない以上、
  複数選択の対象になりえないためである。
- **山札の一番上は `zones.DECK` の index 0 である。** ★墓地・消滅などの公開パイルが
  `pile[pile.length - 1]` を最上段として扱うのと**逆**である点に注意する
  (`ManualGameService.drawCards` が `deck.remove(0)` で引くのに合わせている)。
  実装時にこの取り違えが起きやすい。
- **山札が空のときはドラッグを開始しない**(A2)。`draggable` を立てず、
  誤って掴んだ場合も何も起きない。左クリック(ドロー)時の既存挙動と揃える。
- **マナへ落とした場合の向きは、落とした先の表/裏ストリップで決まる**(A3)。
  既存の `registerDropTarget(track, seatId, 'MANA', null, faceDown)` がそのまま効くため、
  山札側に特別な処理は要らない。
- **パイル内の「上へ」「下へ」枠とシャッフルボタンはドラッグの起点から除外する**(A4)。
  これらの子要素に `draggable = false` を明示し、掴んでも山札ドラッグが始まらないようにする。
  除外しないと、山札へ差し込むためのドロップ枠を掴んだ瞬間に山札ドラッグが始まってしまう。

送信する操作は既存の `move` そのままである。

```js
send('move', { cardIds: [topCard.instanceId], toSeat, toZone, toIndex, faceDown });
```

### 2-2. 山札全面表示のボタン(B1・B2)

`createDeckRow` のボタン群に6つを追加し、計10個にする(B1)。

| 段 | ボタン |
|---|---|
| 1段目 | 一番上へ / 一番下へ / 手札へ / 場へ / 墓地へ |
| 2段目 | 消滅へ / 禁忌へ / 一時公開へ / マナ(表)へ / マナ(裏)へ |

- **2段のボタン並びとする**(B2)。ドロップダウンにまとめるとクリックが1回増えるため採用しない。
  段組みは `flex-wrap` で行い、行数を決め打ちしない(将来ゾーンが増えても崩れない)。
- マナへの2つだけ `faceDown` を明示して送る(表=`false` / 裏=`true`)。残りは `null` を送り、
  表裏は 2-3 の正規化に委ねる。
- 既存の `sendDeckMove(instanceId, seatId, zone, index)` を `faceDown` を取れるよう拡張する。

### 2-3. 裏向きの自動表向き化(C1〜C5・D1・D2)

**`ManualOperationService.move` に、移動先ゾーンによる表裏の正規化を追加する。**

| 移動先ゾーン | 表裏の扱い |
|---|---|
| FIELD / WEAPON / TRASH / LOST / REVEAL / HAND | **表向きへ正規化する**(C1・C2) |
| TABOO / DECK | 正規化しない(現在の向きのまま)(C3) |
| MANA | 正規化しない。従来どおり要求の `faceDown` で決まる(C4) |

- **クライアントが `faceDown` を明示している場合は、そちらを優先する。** 正規化は
  `request.faceDown() == null` のときだけ働く。マナのストリップへのドロップや
  2-2 のマナ用ボタンが意図した向きを上書きされないようにするためである。
- **手札(HAND)も表向きに正規化する**(C2)。設計書4-4の「手札のカードにShift+クリック=公開」は
  フェーズ2で相手ビューに見せるための機能であり、フェーズ1の全公開段階では
  裏向きの手札は持ち主自身にも中身が見えず不便であるほうが実害が大きいと判断した。
  ★フェーズ2で手札の `faceDown` に「公開」の意味を与える場合は、この規則を見直すこと。
- **進化スタックの素材(`materials`)にも同じ正規化を適用する**(C5)。
  素材は `ManualBoardIndex` 経由で同じ `ManualCardInstance` として扱われるため、
  スタックごと移動する場合は上に乗るカードと素材の両方を走査する。
- **正規化はサーバで行う**(D1)。クライアント側だけで実装すると、盤面ドラッグ・帯からの
  ドラッグ・全面表示のボタン・複数選択の一括移動という4つの経路すべてに同じ処理を
  書く必要があり、必ずどれかが漏れる。`move` は全経路が通る唯一の関門である。
- **設計書5-1「手動モードで判断を実装しない」には抵触しない**(D2)。禁止しているのは
  勝敗・コスト支払い・戦闘解決といった**裁定**であり、本件は「同じ盤面を見ている」ことを
  保証するための表示状態の正規化である。裁定の余地が生まれる箇所ではない。

ログ文言は現行の `(表向き)` / `(裏向き)` の付記をそのまま使う。正規化で表向きになった場合も
`(表向き)` と出す(何が起きたかが履歴に残るようにするため)。

### 2-4. LPの増減UI(E1)

#### 現状の非対称

- **ATK / HP は既にクリックで増減できる。** `openStatModal` が開くモーダルの入力欄は
  `statInput` が `input.type = 'number'` で生成しており、ブラウザが標準の上下スピナー
  (増減の矢印)を描画する。これをクリックすれば1ずつ増減する。
- **LPだけが `prompt('LPを入力', seat.lp)` である。** `prompt()` はテキスト入力の
  ダイアログでありスピナーを持たない。数を打ち直すしかない。

**要望の正体はこの非対称であり、不足しているのはLP側のUIだけである。**
サーバ側は `ManualOpRequest.Lp` が `value` と `delta` の両方を持ち、
「直接指定と増減のどちらか一方だけ」を受け付ける実装が既に済んでいるため変更不要である。

#### LPモーダルの新設

`prompt()` を廃止し、`stat-modal` と同じ体裁のモーダルを新設する。リーダータイルの
LP表示をクリックすると開く。

```
┌─ 席A のLP ───────────────┐
│   LP  [    20 ]▲▼        │
│  [-5] [-1]   [+1] [+5]   │
│                  [閉じる] │
└──────────────────────────┘
```

- **数値入力欄は `statInput` をそのまま流用する**(`type="number"`)。これだけで
  ATK / HP と同じスピナーによるクリック増減が手に入り、要望の最低線を満たす。
  確定時は `send('lp', { seat, value })` を送る。
- **加えて `-5 / -1 / +1 / +5` のボタンを置く。** `send('lp', { seat, delta })` を送る。
  ★これは要望に明示されていない追加である。LPは戦闘ダメージでまとまった値が動くことが多く、
  スピナーの1ずつでは押す回数が嵩むため有用と判断した。不要であればボタンだけ削れば、
  スピナーによる増減(=ATK/HPとの同等化)は残る。
- **ボタンを押してもモーダルは閉じない。** 連続してクリックできることが本要望の主眼である。
- 表示中の数値は再配信された `latestView` から更新する。専用の再描画経路は作らず、
  モーダルが開いている間は `renderAll` の末尾で数値だけ差し替える。
- `value` と `delta` を同時に送ってはならない(サーバが例外を投げる)。

**★ATK / HP 側は変更しない。** 既にスピナーで増減できるためである。

## 3. 実装上の注意

- **山札の最上段は index 0、公開パイルの最上段は末尾。** 2-1 で述べたとおり逆である。
- **`draggable` の除外を忘れないこと**(A4)。除外しないとシャッフルボタンや
  「上へ/下へ」枠が使えなくなる。
- **`onDragStart` を経由すること。** 19b hotfix2 の `setTimeout(..., 0)` による
  `manual-drag-active` の非同期付与は、山札ドラッグでも必要である。独自に
  `dragstart` を書かず既存の `onDragStart` を呼ぶ(帯・全面表示から盤面へ落とす経路と同じ)。
- **静的ファイルのキャッシュバスティングを上げること。** `manual-battle.js` v=5→v=6、
  `battle.css` v=13→v=14。
- **検証は実マウス操作で行うこと。** 合成 `DragEvent` はブラウザのドラッグ機構を通らず、
  中断系の不具合を再現できない(19b hotfix2)。
