## 1. 層を1本のスタックで持つ(0-3章)

### 1-1. 画面を覆うものは既に7種類ある

情報モーダル(7枚)・確認モーダル(新)・席選択ゲート・帯・全面表示・
マリガン・在室者ポップオーバー。**「今 Esc が誰のものか」をそれぞれが
自分で判断すると、重なったときに2つ同時に閉じる。**

そこで `modalStack` を1本だけ持ち、開いた順に積む。
いちばん上の層だけが Esc とフォーカスを握る。

```js
const modalStack = [];   // { el, trap, escape, restore } を開いた順に

function pushModalLayer(el, options) { ... }
function popModalLayer(el) { ... }
```

`escape` は「Esc で呼ぶもの」、`trap` は「フォーカスを閉じ込めるか」、
`restore` は「開く前にフォーカスがあった場所」である。

### 1-2. ★★Esc は × と同じ資格しか持たない(裁定35 の一般化)

34 hotfix は × について「独自に `d-none` を付けず、[閉じる] を `click()` する」と決めた。
理由は後片付け(LPモーダルの `lpModalSeatId` 等)が2箇所に散るからだった。
**Esc にもまったく同じ理由が当てはまる。** そこで Esc も [閉じる] を `click()` する。

```js
const closeBtn = el.querySelector('[id$="-close"]');
pushModalLayer(el, { escape: closeBtn ? () => closeBtn.click() : null });
```

こう書くと、**[閉じる] を持たないモーダルでは Esc も効かない**が自動的に成り立つ。
開始シーケンスの2つ(start-method / start-order)がそれである(裁定34)。
「× を付けるのは [閉じる] を持つものだけ」という 34 の決めごとと、
「Esc が効くのは [閉じる] を持つものだけ」という 36 の決めごとが、
**出口の有無という1つの事実から同時に決まっている**。覚えることは増えていない。

★`[id$="-close"]` という引き方も 34 hotfix の規約をそのまま使っている。
この規約には既に機械判定(「[閉じる] を持つものには必ず ×」)が乗っており、
Esc も同じ規約に相乗りした形である。

### 1-3. ★★★Esc は下の層へ落とさない

いちばん上の層に出口が無ければ、**そこで止まる**。下を探しに行かない。

```js
if (e.key === 'Escape') {
    e.preventDefault();
    if (top.escape) top.escape();   // ★無ければ何もしない。下は見ない
    return;
}
```

落とすと何が起きるか。開始モーダル(閉じられない)が出ている裏で帯が開いていると、
Esc で**画面のいちばん上は閉じないのに、裏の帯だけが消える**。
利用者から見れば「Esc を押したら、見えていないところで何かが起きた」である。
**モーダルとは「その上で完結する」から modal なのであって、
下へ抜ける経路を作った時点でモーダルではない。**

★これは検証を2つに分けてある(5-1 の項目)。「上だけ閉じる」を見る項目は
**この誤りを検出できない**(確認モーダルが上にあるときは、落とす実装でも
同じ結果になる)。「出口の無いモーダルが上のとき何も閉じない」を別に立てて初めて番人になる。

### 1-4. ★トラップするのはモーダルだけである

| 覆うもの | Esc | フォーカスのトラップ |
|---|---|---|
| 情報モーダル(7枚) | [閉じる] があるものだけ | する |
| 確認モーダル | する([キャンセル]) | する |
| 席選択ゲート | [やめる] が出ているときだけ | する |
| 帯・全面表示 | する | **しない** |
| マリガン | **しない**(裁定34) | しない |
| 在室者ポップオーバー | する | **しない** |

帯・全面表示を閉じ込めないのは、**配信のたびに中身を作り直すから**である
(`refreshOverlay`)。フォーカスを持った要素が再描画で消えるので、
閉じ込めの維持がビューの更新と競合する。
「盤面が更新されるたびにフォーカスが飛ぶ」ほうが、閉じ込めが無いことより害が大きい。
**Esc は document 上の1本なので、この競合とは無関係に効く。**

在室者ポップオーバーを閉じ込めないのは、**画面を覆っていないから**である。
裏を触れる物の中へフォーカスを閉じ込めると、見た目と挙動が食い違う。

マリガンだけ Esc も効かないのは、あれが開始シーケンスだからである(裁定34)。
画面だけ閉じられるとサーバ側の状態が残り、
**盤面が固まったまま、固まっている理由だけが画面から消える**。

### 1-5. ★開閉を classList の直接操作から関数へ移した

```js
function openInfoModal(id)  { el.classList.remove('d-none'); pushModalLayer(el, ...); }
function closeInfoModal(id) { el.classList.add('d-none');    popModalLayer(el); }
```

層への出入りが開閉と**同じ1行**に載っていないと、
「開いたのに積まれていない」= Esc もトラップも効かないモーダルが静かに1枚増える。
**これは機械判定にした**(`-modal').classList.add/remove('d-none')` が残っていないこと)。

★`toggleStartModal` だけは**サーバの状態が開閉を決める**唯一のモーダルであり、
配信のたびに開閉が走る。`pushModalLayer` が二重に積まないので層は1つのままである。

## 2. フォーカスの3点(初期・トラップ・復帰)

### 2-1. 初期フォーカスの既定は「× を除いた最初の焦点可能要素」

× は**出口であって用件ではない**。数値モーダルを開いた人の用件は数値の入力である。
既定でそこへ入れば、`data-initial-focus` を書く必要は無い。

```js
const list = focusablesIn(el);
const body = list.filter((n) => !n.classList.contains('info-modal-x'));
(body.length > 0 ? body[0] : list[0]).focus();
```

例外は2枚あり、`data-initial-focus` 属性で名指しする。

| モーダル | 名指し | 理由 |
|---|---|---|
| 操作説明 | `#help-modal-x` | 本文の焦点可能要素が [閉じる] しか無く、既定だと**開いた瞬間に最下部までスクロールする**(`focus()` は要素を見える位置へ送る) |
| 確認 | `#confirm-modal-close` | 既定だと DOM 順で [実行] に載る。**破壊的操作でそれをやってはいけない** |

★「開いた瞬間に最下部へ飛ぶ」は実際に踏んだ挙動である。
検証にも `scrollTop === 0` を1項目立ててある。

### 2-2. ★position: fixed に offsetParent は使えない

「画面に出ているか」の判定に `offsetParent !== null` を使うと、
`.info-modal` は position: fixed なので**出ていても null** になる。
矩形の有無(`getClientRects().length > 0`)で見る。

### 2-3. トラップは Tab の折り返しと focusin の網の2枚である

Tab / Shift+Tab は `keydown` で折り返す(末尾の次は先頭、先頭の前は末尾)。
これだけでは足りない。**裏の要素が自分でフォーカスを取りに来る経路**
(クリック・ブラウザの挙動)は `keydown` を通らないので、
`focusin` でも外へ出たら引き戻す。

2つあるのは冗長だからではなく、**入口が2つあるから**である。
検証もそれぞれ別項目にしてある(片方を消したときに片方だけが落ちることを確認済み)。

### 2-4. ★復帰はいちばん上の層を降ろすときだけ

サーバ由来で勝手に閉じるもの(開始シーケンスのモーダル)は、
**下の層から抜けることがある**。そのときにフォーカスを戻すと、
上に出ているモーダルからフォーカスを奪う。

```js
const layer = modalStack.splice(index, 1)[0];
if (index !== modalStack.length) return;   // ★上でなければ戻さない
if (layer.trap) restoreFocus(layer.restore);
```

★戻り先が消えている場合(カードのタイルなど)は body へ落とす。
盤面のカードは `<div>` であって焦点を取れないので、
実際に戻り先が意味を持つのは [?] のようなヘッダのボタンからの往復である。

### 2-5. ★★配信のたびにフォーカスを当て直さない

`pushModalLayer` は既に積まれている層について、
**フォーカスが中にあるうちは何もしない**。
開始シーケンスのモーダルは配信のたびに `openInfoModal` を通るので、
無条件に当て直すと**入力中に先頭のボタンへ飛ぶ**。
当て直すのは、中身の作り直しでフォーカスを持った要素が消えたときだけでよい。

### 2-6. `role="dialog"` と `:focus-visible`

`.info-modal-body` と `.manual-gate-body` に
`role="dialog" aria-modal="true" aria-labelledby="<見出しのid>"` を付けた。
見出しに id が無かった2枚(札・操作説明)には id を足してある。

キーボードの居場所は `:focus-visible` の枠で見せる。
**Bootstrap にも指定はあるが、検証ハーネスは Bootstrap を落としている**(裁定39)。
フォーカスの移動そのものを見る検証を入れる以上、
見え方の指定もこちら側に持っていないと、実物とハーネスで別物になる。
`:focus` ではなく `:focus-visible` にしたのは、マウスで押しただけのときに枠が出ると
22 のクリック規約(左=見る)の邪魔になるためである。

### 2-7. ★「2つの流儀」は今回そろえていない

レビューは「閉じるボタンのみのモーダル」と「背景クリックで閉じる帯」が
1つのアプリに同居していることを指摘している。**今回は揃えていない。**

- 情報モーダルに背景クリックを足すと、**開始シーケンスの2つにも足すか**という
  問いが立つ。あれは出口を作らないのが意図なので、足せない。
  「背景クリックで閉じるモーダルと閉じないモーダル」が生まれるだけである。
- 確認モーダルの背景クリックは、**取り消しの意思表示として弱すぎる**。

代わりに揃えたのは**出口の有無**である。出口があるものには × と Esc の両方があり、
無いものにはどちらも無い。**流儀の数ではなく、規則が1本であることのほうが重要である。**
→ 7-3 の Q1 で判断を仰ぐ。

## 3. 確認モーダル(0-4章)

### 3-1. 素の confirm() を捨てた理由は3つある

1. **OSの見た目が出る。** 黒い盤面の上に白いダイアログが出て、
   33〜34 で揃えたテーマがそこだけ崩れる。
2. **ボタンの文言を決められない。** [OK] / [キャンセル] しか出せないので、
   何が起きるのかを問いの本文に全部書くことになる。
3. **★★JavaScript を止める。** 止まっている間は STOMP の受信も描画も進まない。
   通話しながら「ちょっと待って」と言われて手が止まる数十秒、
   **相手の操作がこちらの画面に一切反映されない。**
   これは裁定16(通話併用が前提)の下では単なる見た目の問題ではない。

### 3-2. ★★コールバックで受ける(Promise ではない)

置き換える6箇所は**すべて**「取り消したときは何もしない」である。
真偽値や Promise を返せば呼び出し側に必ず `if` が1つ増えるが、
**使う分岐は片方しかない**。

```js
askConfirm('盤面をリセットして引き直す。Undo では戻せない。',
    'リセットする', () => send('reset', {}));
```

既存の `if (confirm(...)) { ... }` と1対1で対応する形が、いちばん読み替えが要らない。

★**ボタンには動詞を書く。** 「はい」ではなく「リセットする」「席を立つ」。
問いを読み飛ばしてもボタンだけで何が起きるか分かる、というのが
`confirm()` では書けなかったことの中身である。

★**問いは1つずつ。** 開いている間の `askConfirm` は捨てる。
問いを重ねると、答えたのがどちらの問いなのか画面から分からなくなる。

### 3-3. 置き換えた6箇所

| 場所 | 本文 | ボタン |
|---|---|---|
| [リセット] | 盤面をリセットして引き直す。Undo では戻せない。 | リセットする |
| [退室] | この部屋から退室する。席は空き、盤面はこの端末から見えなくなる。 | 退室する |
| [席を立つ](観戦可) | 席を立って観戦に移る。席は空き、以後は盤面を操作できない。 | 席を立つ |
| [席を立つ](観戦不可) | この部屋は観戦できないため、席を立つと退室になる。 | 席を立って退室する |
| 開始まわりの [リセットして最初から] ×2 | 盤面をリセットして最初からやり直す。Undo では戻せない。 | リセットする |

★「Undo では戻せない」は事実である。`ManualGameService.resetRoom` が
`room.getHistory().clear()` を呼んでいる。**確認の本文に嘘を書かない。**

★最後の2つは文言が同じなのに**別々の場所に書かれていた**
(起動時に束ねるほうと、マリガンのオーバーレイが動的に作るほう)。
`bindStartReset(button)` 1本に寄せた(設計判断28)。

### 3-4. ★★z-index は 1965 である

`.info-modal` の 1000 のままにできない。**マリガンのオーバーレイ(1950)と
開始モーダル(1960)からも確認が出る**ので、1000 だと
**問いが下に潜り、押せないボタンを待つ**ことになる。

上げ先を 1965 にしたのは、**切断オーバーレイ(1970)より下**に置くためである。
切断中は「操作が相手に届かない」のほうが上位の情報であり、
その上に確認を重ねると「実行しても何も起きない問い」を最前面に出すことになる。
裁定18 のとおり操作を止めているのは `send()` であって重ね順ではないが、
**案内の順位は別に決まる。**

★この重ね順は**座標で機械判定している**(34 hotfix の教訓
「測るのは式ではなく結果である」)。z-index の値を読む判定は、
値を変えたときに検証も一緒に変わって番人にならない。
★判定はマリガン(1950)の上で行う。開始モーダルは確認と DOM 順で前後するため、
**z-index を 1000 に戻しても同じ結果になり、番人にならなかった**(5-3 で確認済み)。

### 3-5. ★出口は [キャンセル] 1つである

`confirm-modal-close` という id にしてあるのは 34 hotfix の規約に載せるためで、
× の結線と「[閉じる] を持つものには必ず ×」の機械判定がそのまま効く。
Esc も同じ [キャンセル] を `click()` する。**閉じ方は1つのままである。**

## 6. hotfix: 見出し帯が中身に8px重なっていた(34 から)

### 6-1. 症状

`.info-modal-head` が、**モーダルを開いた瞬間から**直後の中身に8px かぶさっていた。
実測(操作説明・35 の main でも同じ): 帯の下端 196 / 直後の中身の上端 188。

### 6-2. 原因

34 hotfix は帯を `position: sticky; top: 0` にしたうえで、
`margin: -16px -16px 8px` で本文の padding を打ち消そうとした。
左右はこれで正しいが、**上は効かない**。

> `position: sticky` の位置は、スクロール容器の**パディングボックス**で頭打ちになる。

`.info-modal-body` には `padding-top: 16px` があるので、
帯の自然位置を負マージンで16px引き上げても、sticky がその16pxを押し返す。
ところが**後続の中身は自然位置のまま流れる**。差の8px(16 − 帯の下マージン8)が重なりになる。

★34 の検証は「最下部までスクロールしても × が見えている」を見ていた。
これはスクロール**した後**の話であり、スクロールしていないときの重なりは網の外だった。

### 6-3. 直し方

負マージンで押し上げるのをやめ、**上のパディングを帯に譲る**。

```css
.info-modal-body:has(> .info-modal-head) { padding-top: 0; }
.info-modal-head { margin: 0 -16px 8px; padding: 12px 16px 8px; }
```

帯の自然位置とパディングボックスの上端が一致するので、sticky が押し返すものが無くなる。
16pxぶんの余白は帯自身が持つ(見出しの上の見た目の余白は 12px で変わらない)。

- **左右の負マージンはそのまま。** あれは「帯を端まで伸ばす」ためのものであり、
  sticky の位置とは関係が無い。34 の判断は左右については正しい。
- **`:has()` を使ったのは、見出し帯を持たないモーダル(開始シーケンスの2つ)から
  上の余白を奪わないためである。** クラスを1つ足して呼び分けると、
  「帯を足したらもう1つクラスも足す」という覚えごとが増える。
  ★`color-mix()`(30)と同じ世代の機能であり、対応環境の前提は変わらない。

**★一般形: `position: sticky` の要素を負マージンで持ち上げようとしない。**
持ち上がらないうえ、**後続だけが持ち上がる**。
