## 1. 解いている問題

マスターの指摘は次のとおりである。

> 通常モードは、カードをプレイしてからの処理が一瞬で行われ、何が起きたのかが
> 非常にわかりづらい。商業タイトルであれば、処理が一つずつ人間の認識できる
> 演出として行われる。

症状を構造に置き換えると、原因は3つ重なっている。

| # | 構造 | 実コードでの根拠 |
|---|---|---|
| 1 | **1操作の解決がまるごと1回の配信に畳まれている** | 配信は `GameWsController:359` の**1箇所だけ**である(3-1) |
| 2 | **差分は順序を持たない** | fx 層の材料は前後2つのビューの突合である(80) |
| 3 | **大きく動くと演出が丸ごと消える** | `FX_LIMIT`(= `SFX_DIFF_LIMIT` = 8)を超えた配信は何も出さない(80) |

★3が最も悪い。**派手なカードほど何も起きない。**
演出が要る場面で、演出が構造的に消える形になっている。

「一つずつ認識できる」ためには **順序**・**段階**・**間** の3つが要る。
前後2点の差分はこの3つを1つも持っていない。**表示側の工夫では届かない。**

## 2. ★★★母集団 —— 作業を始める前に実コードで数えた

★症状を母集団にしない(79 の教訓)。数えたのは
**「サーバが1操作の解決中に通る、順序のある地点の全体」**である。

★★母集団を **3段**で取った(80 の作法) ——
**A: 配信はどこから出ているか** / **B: 段の境目になりうる地点はどこか** /
**C: クライアントはそれを受け取れるか**。

### 2-1. 母集団A —— 通常モードの配信点

| # | 地点 | 件数 | 備考 |
|---|---|---|---|
| A1 | `GameBroadcaster.broadcast(GameRoom)` の呼び出し | **1件**(`GameWsController:359`) | ★`execute()` の中。**ロックの外**である |
| A2 | `sendError` / `sendLeft` / `sendRoomLost` | 各1件 | 盤面を運ばない |
| A3 | 手動モードの配信 | ★**別クラス**(`ManualBroadcaster`) | ★**本バッチの変更は手動モードに1文字も届かない** |

★★★**「1操作 = 1配信」は構造として保証されている。**
`execute()` は `synchronized (room.getLock())` の中で `action.apply(room)` を走らせ、
**抜けてから1回だけ** `broadcast(room)` を呼ぶ。
解決の途中の状態は、その時点でもうサーバのどこにも残っていない。

★これは「たまたま1回」ではなく「1回しか呼びようがない」形である。
段を作るには、**解決の最中に何かを記録する**しかない。

### 2-2. ★★★母集団B —— 段の境目になりうる地点

| # | 候補 | 件数 | 判定 |
|---|---|---|---|
| B1 | **`GameRoom.addLog(String)`** | 定義**1箇所**(`GameRoom:453`)/ 呼び出し**243件** | ★**採る** |
| B2 | `CardEffectRegistry.runEffect` | 1箇所 | 粗すぎる。連鎖の**中**が見えない |
| B3 | 効果のラムダの中に明示的な区切りを書き足す | 243箇所相当 | ★論外(裁定68 に真っ向から反する) |
| B4 | `GameActions` の移動・破壊の各プリミティブ | 多数 | ★**B1 が既にそこを通っている**(下記) |

呼び出しの内訳は次のとおりである。

| ファイル | 件数 | 性格 |
|---|---|---|
| `CardEffectRegistry` | 131 | カード個別の効果が語ること |
| `GameService` | 56 | ターン・フェイズ・戦闘の進行 |
| `GameActions` | 56 | 移動・ダメージ・破壊のプリミティブ |

### 2-3. ★★★段の正は「ログ行」である

`GameActions` のログを実際に読むと、粒度がそのまま答えになっている。

```
【%s】に%dダメージ
【%s】が破壊されました
%sのリーダーに%dダメージ(残りLP %d)
【%s】が手札に戻りました
【%s】は破壊されなかった
%sが【%s】へ進化しました(素材%d体・下に%d枚)
```

★**これは「人間に伝える価値がある出来事」の一覧そのものである。**
ログ行は最初から「1つずつ認識できる単位」として書かれていた。
マスターが求めている粒度と、既にサーバが持っている粒度が一致している。

したがって本バッチの中心命題はこうである。

> **★★★ログ行が1つ増えるたびに1段である。**

この選び方には、たまたま都合がよい以上の意味が4つある。

1. **★発火点を1つも増やさない**(裁定68)。境目を決めるのは `addLog` の**1箇所**であり、
   243件の呼び出し側は1行も変わらない。新しいカードを足しても、
   そのカードがログを書けば自動的に段になる。
2. **★順序が「作られる」のではなく「そのまま在る」。** サーバが解決した順に
   ログが積まれる。クライアントは何も推測しない(裁定62・演出は観測できたことだけを語る)。
3. **★段とログが必ず一致する。** 画面の演出と、右列のログの行が1対1で対応する。
   ★**演出で何が起きたか分からなくても、同じ瞬間のログ行が必ず答えを持っている。**
4. **★書き忘れが起きない。** 「ログに書いたのに演出が出ない」も
   「演出が出たのにログに無い」も、構造的に発生しない。

★★**採らなかった案の理由も書き残す。** B2(カード単位)は粗すぎる ——
1枚のカードが「3ダメージ → 破壊 → ドロー」と連鎖したとき、
その3つを分けられなければ問題は解けていない。
B3 は裁定68 が守ろうとしているものを正面から壊す。

### 2-4. 母集団C —— クライアントの受け口

| # | 地点 | 実測 | 判定 |
|---|---|---|---|
| C1 | `battle.js:4455 onMessage` | ★**配信の唯一の入口**である | ★ここをキューの入口に変える |
| C2 | `fxCaptureDelivery` → `render` → `fxSpawn` | onMessage の中で1往復 | ★**1段につき1往復**に変える |
| C3 | fx の語彙(`move`/`draw`/`vanish`/`appear`/`lp`/`tap`/`flip`/`sink`/`declare`) | 9種(80) | ★**1文字も変えない** |
| C4 | `FX_LIMIT` = 8 | 超えたら何も出さない | ★**緩めない**(下記) |

★★★**80 が作った fx 層は、そのまま使える。**
段ごとの差分は小さいので、`move` / `vanish` / `lp` / `draw` が段ごとに正しく発火する。

★★**`FX_LIMIT` を緩める必要が無い。** 8件を超える配信が**発生しなくなる**からである。
これは 38 の裁定83「例外を作るな、道を作れ」と同じ形であり、
上限も抑制も1文字も触らずに問題が消える。

### 2-5. ★★★Batch 81 は、この道を一度退けている

**着手時に台帳を読んで見つけた。** 裁定360 の「採らなかった道」に、こう書いてある。

> ★**採らなかった道**: 「公開しました」の確認を挟む(裁定113 に触れる)/
> **解決の途中で配信する口を作る(配信の口が2つになり、止めないなら結局見えない)。**

★★**つまり本バッチがやろうとしていることは、81 が検討して退けた道である。**
退けた理由は括弧の中の2つであり、**その2つに答えられないなら 84 を書いてはいけない。**

★★★あわせて、裁定357 の Batch 81 追記はこうも書いている。

> 通常モードは**効果の解決中に配信を1度も行わない**
> (`GameWsController` の `action.apply` → `broadcast` は1往復である)。
> ★**材料があっても、それを見せる「配信の機会」が無い**。

★**本書 2-1 の母集団Aは、81 のこの記述と1文字も食い違っていない。**
81 は同じ構造を見て「その口は作らない」と決め、84 は「その口を作る」と決めた。
**同じ事実から違う結論が出ているのだから、何が変わったのかを書く義務がある。**

#### 2-5-1. 「配信の口が2つになる」への答え

★★★**口は2つにならない。**

`broadcast` の呼び出しは**今も `GameWsController:359` の1箇所のまま**である。
84 が増やしたのは**1メッセージに載る段の数**であって、**配信の口ではない**。

★これは 3-3 で「N回 `convertAndSend` する案」を退けた判断が、そのまま効いている ——
あのとき退けた理由は順序と割り込みだったが、**裁定360 への答えにもなっていた**。
★★**設計の途中で偶然そうなったのではなく、退けた理由が3本あったということである。**

#### 2-5-2. 「止めないなら結局見えない」への答え

★★★**止める。**

81 の時点では、止める仕組みがどこにも無かった —— 配信が届けば `render` が即座に走り、
次の配信も即座に走る。そこへ途中の配信を足せば、**速く流れるものが増えるだけ**である。
81 の判断は、その前提のもとで正しい。

84 が入れるのは配信の口ではなく、**間**である。

| | 81 が想定した形 | ★84 の形 |
|---|---|---|
| 段の届き方 | 途中の配信が**複数回** | 1メッセージの中の**列** |
| 段の見せ方 | 届いた順に即座に描く | ★**1段ずつ、間を空けて描く**(4-2) |
| 人の操作 | 止まらない | ★**止める**(4-3・裁定365) |
| 長さの保証 | 無い | ★**総再生時間に上限**(4-4・裁定364) |

★★**「口を作るか」ではなく「間を作るか」が本当の論点だった。**
81 は口の話として検討して退け、84 は間の話として採る。

> ★★★**同じ工事に見えて、運ぶものが違う**(裁定84 の一族)。
> 81 が退けたのは**配信**であり、84 が足すのは**再生**である。

#### 2-5-3. ★裁定360 は失効しない

84 が段を作ると、《降臨の伝道師》の0枚・1枚のように
**「同じ配信の中で入れて消える」公開領域**も、段としては観測できるようになる。

★★**それでも「公開はログでも伝える」(裁定360)は残す。**
84 の段は `prefers-reduced-motion` で再生されず、上限で畳まれもする(4-4)。
**ログはどの経路でも必ず残る。** 裁定360 が守っているのはそこであり、
演出が増えたことは「ログが要らなくなった」を意味しない。

★★★**演出で伝わるようになったものからログを外さないこと。**
これは 84 以降のバッチへの申し送りである。

## 3. サーバ側の設計

### 3-1. 記録は「外から差し込む」

段のスナップショットを作るには `GameViewBuilder` が要る。
しかし `GameRoom` / `GameState` は**意図的に Spring のビーンにしていない**
(`GameState` の冒頭コメント)。ここにビルダーを注入すると、その方針が崩れる。

→ **記録係を `execute()` が差し込み、抜けるときに必ず外す。**

```java
// GameWsController#execute
List<StepFrame> steps = new ArrayList<>();
try {
    synchronized (room.getLock()) {
        room.setStepRecorder(line -> steps.add(captureFrame(room, line)));
        try {
            action.apply(room);
        } finally {
            room.setStepRecorder(null);   // ★必ず外す
        }
    }
    broadcaster.broadcastSteps(room, steps);
} catch (...) { ... }
```

```java
// GameRoom#addLog —— 変更はこの2行だけである
public void addLog(String message) {
    log.add(message);
    if (log.size() > 60) log.remove(0);
    if (stepRecorder != null) stepRecorder.accept(message);   // ★足すのはここ1行
}
```

★★**`GameRoom` はビルダーを知らない。** 知っているのは「記録係が居れば呼ぶ」だけである。
★★★**外すのを `finally` に置く。** 例外でルール違反が返る経路(`execute` の catch)を通っても、
記録係が居残らない。居残ると**次の操作の段に前の操作が混ざる**。

### 3-2. ★★1段が持つもの

★**スナップショットそのものを段に載せるのではない。** 視点フィルタは
`GameViewBuilder.build(room, viewerId)` が担っており、**閲覧者ごとに中身が違う**。
段の記録の時点では誰に送るかが決まっていないので、
**閲覧者ごとにビューを作るのは配信の直前**にする……とすると、
その時点では既に最終状態しか残っていない。

→ **記録の時点で、閲覧者ぶんまとめて作る。**

```java
record StepFrame(String logLine, Map<String, GameView> byViewer) {}
```

★これが本バッチで最も高くつく判断である。実測が要る(3-4)。

★★**採らなかった案**: `GameState` の深いコピーを段ごとに取り、
あとからビューを作る。**退けた** —— コピーの正しさを保つ責任が新しく生まれ、
`MinionInstance` / `StackedCard` / `PersistentAura` の参照関係を1つ間違えると
**盤面が静かにずれる**。演出のためにゲーム状態の複製を導入するのは釣り合わない。

### 3-3. ★配信の形 —— 1メッセージに段の列を載せる

★**N回 `convertAndSend` する案は採らない。**

| | N回配信 | ★**1メッセージに列**(採用) |
|---|---|---|
| 順序 | STOMP の順序に依存する | **配列の順序**であり、依存が無い |
| 途中で相手の操作が割り込む | ★**混ざりうる** | 混ざらない(1操作 = 1メッセージのまま) |
| 既存の「1操作 = 1配信」 | ★**壊れる** | **保たれる** |
| 検証 | 受信回数を数える項目が全部書き換わる | 影響が小さい |

```java
public record WsMessage(String type, GameView view, List<GameStep> steps, String message) {}
public record GameStep(int seq, String logLine, GameView view) {}
```

- `view` は**従来どおり最終状態**である。★**この欄の意味を変えない** ——
  変えると、`type` の分岐を読むすべての箇所が影響を受ける。
- `steps` は**途中の段だけ**を持つ。段が無い操作(席に着く等)では**空**である。
- ★★**`steps` が空でも画面は必ず動く。** 従来どおり `view` を描くだけになる。
  **退化の経路が最初から在る**(裁定の形: 判定できないものは静かに退化する)。

### 3-4. ★★★測ってから決めること(実装の1段目で必ず行う)

| 測るもの | なぜ | 落ちたときの手 |
|---|---|---|
| **1操作あたりの段数の分布** | 上限の値を実測で決める | —— |
| **1メッセージの実バイト数** | 29 の実測は18〜27KB / 1ビュー。★**段数倍になる** | 3-5 |
| `GameViewBuilder.build` の所要時間 × 段数 × 閲覧者数 | ロックの中で走る。**長いと相手の操作が待たされる** | 3-5 |

★★**測る前に最適化を書かない。** 29 が実測を残したのと同じ理由である。

### 3-5. ★配信量が問題になったときの手(順序を決めておく)

1. **盤面が変わらない段のビューを省く**(ログ行だけを載せる)。
   「【X】は破壊されなかった」のような段は、**語ることがログ行しかない**。
2. **段の上限を設け、超えたぶんは畳む**(先頭 n 段 + 最終状態)。
3. 差分符号化。★**最後の手**である —— ビューの形を変えることになり、
   `GameViewBuilder` と `battle.js` の両方に新しい規則が生まれる。

★1と2で足りる見込みだが、**3を採る日が来たら本書を改訂すること。**

## 4. クライアント側の設計

### 4-1. `onMessage` をキューの入口に変える

```
現在:  onMessage → fxCaptureDelivery → latestView 差替 → render → fxSpawn
本案:  onMessage → キューへ積む
       再生器   → 1段取り出す → fxCaptureDelivery → latestView 差替 → render → fxSpawn
                → 段に応じた時間だけ待つ → 次へ
```

★★**1段の中身は今と1行も変わらない。** 変わるのは
「いつ呼ばれるか」だけである。`fxCaptureDelivery` / `render` / `fxSpawn` の
順序も役割も 80 のままである。

★★★**キューは複数のメッセージにまたがって FIFO である。**
再生中に相手の操作が届いたら、そのメッセージの段を**後ろに継ぎ足す**。
★捨てない —— 捨てると、**表示されない盤面変化**が生まれる。

### 4-2. ★段の長さ

★**一定にしない**(引継ぎ文書の指摘のとおり、これが「緩急」の正体である)。
既にある `FX_*` の定数から引く。

| 段が語ること | 長さ | 定数 |
|---|---|---|
| 何も動かない(ログ行だけ) | 短い | 新設(★200ms 程度から測る) |
| タップ・裏返し | `FX_TAP_MS` = 200 | 既存 |
| 移動・出現・消滅 | `FX_MOVE_MS` = 340 | 既存 |
| ドロー | `FX_DRAW_MS` = 380 | 既存 |
| LP増減 | `FX_LP_MS` = 700 | 既存 |
| 決着 | 長い | 既存 |

★★**定数を新しい表に写さない。** 段の長さは
**その段の fx が既に持っている長さ**を読む。写すと正が2つになる。

★**下限を置くかどうかは 84c の実機調整で決める**(裁定・Q1 = c)。
84b は「fx の長さをそのまま使う」で実装し、**調整の取り付け点だけ1箇所に作っておく**。
★★取り付け点を作らずに 84c を迎えると、調整のために再生器を書き換えることになる。

### 4-3. ★★再生中の入力を止める

★これは演出の都合ではなく**事故の防止**である。
再生中、人が見ているのは**古い盤面**である。そこでクリックできると、
既に居ないミニオンを対象に選ぶ操作が飛ぶ。

- 再生中は盤面の操作を受け付けない(送信の手前で落とす)。
- ★**画面にそれと分かる形を出す**(裁定の形: 押せない理由が読めること)。
- ★★**問い合わせ(`pendingChoice`)は最終状態に載っている**ので、
  キューを消化しきった時点で自然に現れる。**特別扱いが要らない。**

### 4-4. ★★★飛ばさない —— そのぶん「長くならないこと」を設計で保証する

**飛ばす出口は作らない**(裁定・Q2)。

★★理由は推測ではなく形として書いておく。飛ばしの出口を作ると、
**演出は「飛ばされる前提のもの」になる** —— 長さの調整が甘くても
出口が吸収してしまうので、長さそのものを詰める動機が消える。
出口が無ければ、**長さが唯一の設計変数になる**。

★★★**したがって、総再生時間の上限は設計で保証しなければならない。**
飛ばしが在れば「長すぎたら人が抜ける」で済んだが、無いなら逃げ場が1つも無い。
再生中は操作もできない(4-3)ので、**上限を外した実装は、そのまま操作不能時間の上限を外す**。

#### 4-4-1. ★3-5 の2 は「配信量の手」ではなく「時間の手」に格上げする

初版は「段の上限を設け、超えたぶんを畳む」を**配信量が問題になったときの手**として
2番目に置いていた。**Q2 の回答により、これは常時必要な仕組みになった。**

| | 初版 | ★本版 |
|---|---|---|
| 3-5 の 1(盤面が変わらない段のビューを省く) | 配信量の手 | 配信量の手(裁量は Q5 = a) |
| 3-5 の 2(**段の上限で畳む**) | 配信量の手 | ★★**時間の保証。常時効かせる** |

#### 4-4-2. 畳み方

- **上限に達したら、以降の段は演出せずに最終状態へ落とす。**
  ★★**捨てるのではなく畳む** —— ログ行は全部そのまま残るので、
  **人は何が起きたかをログで追える**(2-3 の性質3がここで効く)。
- ★**上限は段数ではなく累計時間で数える。** 段の長さが一定ではない(4-2)ので、
  段数で数えると短い段ばかりの連鎖と長い段ばかりの連鎖で待ち時間が桁違いになる。
- ★★上限値は 84c の実機調整で決める(Q1 = c と同じ場所)。
  **設計時点では値を書かない。** ★ただし**上限の仕組みは 84b で入れる** ——
  値の調整と仕組みの有無は別の話である。

#### 4-4-3. 飛ばしではない経路は残す

| 経路 | 挙動 | 理由 |
|---|---|---|
| `prefers-reduced-motion` | ★**最初から段を再生しない**(最終状態だけ描く) | 飛ばしではなく「そもそも再生しない」。既存の `fxAllowed()` の隣に置く |
| 再接続・`ROOM_LOST` | ★**キューを捨てて最終状態へ** | 飛ばしではなく**復旧**である。古い段を再生し続けるほうが嘘になる |
| `ERROR` の受信 | 段を持たないので、従来どおり | —— |

★★**この3つを「飛ばし」と混同しないこと。** 飛ばしは
**人が演出を打ち切る出口**であり、作らないと決めたのはそれである。

### 4-5. ★相手の操作の段も再生する(裁定・Q4 = a)

相手の手番の解決も、自分の手番とまったく同じに再生する。

- ★**扱いを分けない。** 自席か相手席かで再生の有無を変えると、
  「どちらの手か」を判断する条件が新しく1つ生まれる。
- ★★**むしろこちらが本題である。** 自分の操作は何をしたか自分で知っているが、
  相手の手は**何もかも初見**である。
- ★★★**割り込みの問い合わせと相性がよい。** 相手の【破壊時】等でこちらに
  問い合わせが来る場合、`pendingChoice` は**最終状態にしか載っていない**ので、
  **段を全部見せ終わってから問いが出る**。
  「何が起きたか分からないまま選ばされる」が構造的に起きない。
  ★これは狙って作った性質ではなく、3-3 で `view` の意味を変えなかったことの帰結である。
  **検証項目に固定すること**(6章 項目13)。

## 10. 積み残し・次の一歩

### 10-1. ★★儀式4種は、84 のあとも「材料」が足りない

裁定357 は、通常モードで儀式(配り・マリガン・ダイス・シャッフル)を作らない理由を
2つ挙げていた。**84 はそのうち1つだけを解消する。**

| 足りないもの | 84 のあと |
|---|---|
| **配信の機会**(解決の途中で見せる口) | ★**解消される** |
| **材料**(`ManualLogRite` に相当する構造) | ★**残る** |

★★**「口ができたから儀式が描ける」と読まないこと。**
儀式を描くには 38 と同じ工事(サーバに観測できる形を足す)が別途要る。
★80 の申し送り 3-3「儀式を描きたくなったら、先にサーバへ観測できる形を足すこと。
順番を逆にしない」は、**84 のあとも1文字も変わらない。**

### 10-2. 84c で決める値

- 段の長さの下限(裁定363)
- 総再生時間の上限(裁定364)
- 3-5 の1を効かせるかどうか(裁定367 の裁量の範囲内)

★★**どれも「仕組みは 84b、値は 84c」である。** 84b の時点で
**調整の取り付け点を1箇所に作っておくこと**(4-2)。

### 10-3. ★手動モードへ持ち込まない

★★手動モードは人が1手ずつ動かすので、**段に分ける対象がそもそも無い**
(1操作 = 1つの出来事である)。裁定358 が「手動と通常で値を揃えない」と決めたのと
同じ理由で、**この仕組みも通常モード専用である。**
★「両モードに作る」(裁定111・289 の一族)は**ここには効かない** ——
あれは**同じ性質のものが片方にしか無い**ときの規則である。
