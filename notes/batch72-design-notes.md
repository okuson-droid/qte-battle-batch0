## 1. 66 が「席を立てない」と書いた理由は、半分しか掛かっていなかった

`LobbyController` の Javadoc にはこう書いてある。

> **席を立てない。**観戦者からプレイヤーへの昇格・その逆は作っていない ——
> 通常モードの席は `GameState` の2人と1対1であり、
> 試合が始まったあとに動かすと盤面の持ち主が消える。

★**この理由は「試合が始まったあと」にしか掛かっていない。**
72 は理由の掛かる範囲だけを守り、掛からない時間帯(WAITING)を開けた。

★★**66 の記述が誤りだったのではない。**66 の時点では受付を作ったばかりで、
「出る」側の要望がまだ出ていなかった —— 理由と結論が同じ幅で書かれていただけである。
★64 の教訓(「暫定でこうしておく」は前提が消えても戻らない)と似ているが、
こちらは**理由のほうが結論より狭かった**という形である。

### 1-1. ★★★id は変えない

席と観戦者を行き来しても `playerId` / `spectatorId` は**同じ文字列のまま**である。
理由は3つある。

1. id は**配信の宛先**である(`/topic/room/{roomId}/player/{id}`)。
   変えると、購読を張り直すまでビューが1通も届かない。
2. id は**localStorage の値**である(`qte-auto-occupant-{roomId}`)。
   変えると、書き換えに失敗した端末が二度と戻れない。
3. 「同じ人である」ことを表すのは id であって、席ではない。

★★**型は別のままである。**66 が `PlayerSlot` と `Spectator` を別の型にしたのは
「席を見るのを忘れた分岐が観戦者をプレイヤーとして扱う」のをコンパイル時に止めるためであり、
その理由は 72 でも生きている。**id を共有し、型は分ける。**

★★★**不変条件: 1つの id は、席と観戦者のどちらか一方にしか居ない。**
両方に居ると `GameBroadcaster.broadcast` が**同じ宛先へ2回配信する**。
どちらからも消えていると**1回も届かない**。
★**画面からは決して見えない事故である。**番人は
`Batch72SeatTest#同じidが席と観戦者の両方に現れることはない` と
`#席を立った人はもう配信の宛先ではない`(宛先がちょうど1つであることを数える)。

### 1-2. ★観戦にも名前を必須にした(66 の挙動を変えた)

66 は観戦の名前が空欄なら「観戦者」に寄せていた。
72 で観戦者が席に着けるようになったので、そのままだと
**相手に「観戦者」という名前の対戦相手が現れる**。

★しかも `join` は名前を必須にしているので、**同じ席に着くのに経路によって必須が違う**
という状態になる(設計判断28)。
→ **既定名の分岐を足すのではなく、消した。**`spectate` も名前を必須にする。

### 1-3. ★★マスターに4件まとめて伺った(71 の流儀)

実装を1行も書く前に、1280×800 の端の盤面で実測したうえで伺った。

| 質問 | 回答 |
|---|---|
| 観戦を許さない部屋で席を立ったら | **席を立てない。退室ボタンは別で用意する** |
| 投了はいつ押せるか | **いつでも** |
| 再戦を押したとき相手の側はどうなるか | **申し込み → 承諾の2段** |
| 取り返しのつかない操作の確認 | **確認モーダルを作る** |

★★**この4件は実質的な裁定である。**カード本文の読みではないので
`notes/qte-rulings.md` へは起こしていない(裁定は 1〜323 のままである)。
★**324 番として記録するかはマスターに伺いたい**(6-2)。

## 3. ★★★投了 —— 決着の5つ目の入口

`GameActions.finish` が決着の唯一の口である(裁定130)。
72 まで通っていたのは4経路(山札切れ・効果によるLP0・ウェポン攻撃・ミニオン攻撃)で、
**投了が5つ目**になった。

### 3-1. ★★★いつでも押せる(マスター確認)

相手のターン中でも、割り込み待ちでも、マリガン中でも通る ——
**`requireTurnPlayer` を通さない。**

★これは手動モードの「**リセットは絶対に止めない**」と同じ筋である:
> **詰まったときの逃げ道は、詰まりの原因になっている規則に左右されてはいけない。**

★`requireTurnPlayer` は「相手が選択中です」でも弾く(裁定214 の対)。
ここに置くと、**割り込みが解決できなくなって盤面が固まったときに投了もできない**。

★★壊し検証の軸10 がこの判断そのものを測っている ——
`concede` に `requireTurnPlayer` を足すと、
`投了は相手のターン中でも押せる` だけが落ちる。

### 3-2. ★★★決着したら「待ち」をたたむ(finish に置いた)

72 が投了を「いつでも押せる」ものにしたことで、
**割り込み待ちのまま決着する盤面が初めて作れるようになった。**

待ちを残したまま決着すると、決着後の画面に「1体選んでください」の問いと
[この内容で確定] が出続け、しかも **`resolveChoice` は決着を見ていないので押せば通る**
(64 の設計にその判定は無い)。

→ `finish` で次をたたむ:

- 両者の問い合わせの待ち行列(`PlayerState.clearPendingChoices`)
- 保留していた戦闘(`pendingAttack`)
- ターンの受け渡しの保留(`turnHandoffPending` / `pendingNextPlayerId`)
- 「いま解決しているカード」(`resolvingCardId`。70 の面が決着後に出続ける)

★★**「投了のときだけたたむ」と書かなかった。**同じ状態は理屈のうえでは他の4経路でも
作れる(誘発の途中でLPが0になる)—— **起きにくいだけ**である。
口が1本なのだから、掃除も1箇所に置く(裁定130)。

★★**盤面そのものは1つも触らない。**場・手札・LP は決着後もそのままである ——
決着後も盤面を読めることは手動モードの裁定44 が決めた性質であり、通常モードでもそこは変えない。

★壊し検証は**出口ごとに当てた**(71 の教訓)—— 軸11(問い合わせの待ち)と
軸12(保留していた戦闘とターンの受け渡し)である。

## 4. ★★★退室 —— 手動モードの形が写せなかったところ

### 4-1. あちらの退室は失敗しない

手動モードは `send('leave', {}); forgetOccupant(); location.href = '/';` と
**送って即座に遷移する**。それが成り立つのは、**あちらの退室が失敗しないから**である
(`ManualRoom.leave` は誰でもいつでも通る)。

**通常モードの退室は失敗しうる。**対戦中の着席者は断られる ——
黙って抜けられると、相手には「相手が動かなくなった」としか見えない。
それは 71 が潰した「気づきにくい事故」と同じ形である。抜けるなら**投了して勝ちを渡してから**である。

### 4-2. ★★同じ形で写すと、断られた端末が戻れなくなる

同じ形で書くと、断られたときの理由(`sendError`)が
**ロビーへ遷移したあとの端末**へ届き、誰も読まない ——
しかも localStorage は既に消えているので、**席に着いたまま戻れなくなる**。

★★★**71 の教訓「同じ穴を塞ぐことと、同じ形で塞ぐことは別である」の2例目である。**
71 は「値と置き場所」を写さなかった。72 は**手順そのもの**を写せなかった。

### 4-3. → 受理されたことを本人へ1通返す

`GameBroadcaster.WsMessage` に **`type = "LEFT"`** を足した(3つ目の型)。
クライアントはそれを見てから localStorage を消して遷移する。

★**退室した本人はもう `broadcast` の宛先ではない**(席にも観戦者にも居ない)ので、
別に送るしかない。`GameWsController.execute` に `onSuccess` を1つ足した ——
**「配信では届かない相手が居るか」が、増やしてよい唯一の根拠である。**

★**ERROR で代用しない。**ERROR は「拒否された理由」であり、画面はそれを出して**その場に留まる**。
退室はその逆(受理されたのでページを離れる)であって、
同じ型に2つの意味を載せると**どちらの向きか分からない分岐**が増える。

★★**この形は切断にも強い。**送れていなければ返事も来ないので、ローカルでは何も起きない ——
設計判断49 がそのまま効く(**畳むものが無いので「戻す」処理も要らない**)。

### 4-4. ★★部屋は残る(直していない)

通常モードには無人部屋の掃除が無い(66 の積み残し。手動モードの `ManualCleanupScheduler`
にあたるものが無い)。72 は退室を作ったが掃除は作っていない ——
**それは「退室できるようにする」とは別の工事である。**
★候補として 6章に残した。

## 5. ★★★再戦 —— 同意の仕組みを新しく作らないか、作るか

### 5-1. 作らない案もあった

片方が押しただけで盤面を捨てる形も採れた。捨てたところで
**両者がデッキを読み直すまで試合は始まらない**ので、
「デッキを読むこと」が同意を兼ねる —— という筋も通る。
★器を1つも増やさずに済む案であり、実装量は半分である。

**採らなかったのはマスターの選択である。**理由は、それが
**相手の見ている画面を相手の同意なしに消す**からである ——
決着した盤面は、まだ読まれている最中かもしれない。

### 5-2. 旗を立てる人が居るから作った

`GameRoom.rematchOfferedBy` は1本の旗である。

- 立てる: `GameService.rematch(OFFER)`
- 倒す: `ACCEPT` / `DECLINE` / `GameRoom.leave`

★★**71 が `connectionFatal` を作らなかった判断(裁定178)の裏返しである。**
あちらは「旗を立てる人が1人も居ない」から作らなかった。こちらは居る。
★**退室で倒すのを忘れると、誰も答えられない問いが残り続ける**(壊し検証の軸9)。

### 5-3. ★捨てるもの・捨てないもの

`GameRoom.resetForRematch`:

| 捨てる | 捨てない |
|---|---|
| 盤面(`gameState`) | 席・名前・id |
| ダイスの勝者 | `ready`(購読の旗) |
| 申し込みの旗 | 部屋の属性(名前・観戦・鍵) |
| 両席のデッキ | |
| ログ | |

★★**`ready` は「WebSocket の購読が済んでいるか」という事実**であり、
再戦で購読が切れるわけではない。倒すと**意味を取り違えた旗**になる(壊し検証の軸16)。

★★**デッキを外すのはマスターの指定である**(「デッキを読み込みなおして再戦」)。
外さないと `bothReady` がその場で真になり、**[応じる] を押した瞬間に次の試合が始まる**。
★同じデッキで続けたい人にはひと手間だが、**デッキを変えられることのほうが価値が高い**。

★★**ログを消すのは 60行のリングバッファだからである。**
残すと前の試合の行が新しい試合に混ざり、「―― ターン1 ――」が2回出るログを人が読むことになる。

### 5-4. ★申し込みは「席」で配る

`RoomView.rematchOfferedBySeat` は `"A"` / `"B"` / `null` である。
★**viewer 目線(「自分が申し込んだか」)に加工しない。**
席で持てば `viewerSeat` と比べるだけで自分か相手かが決まり、
**観戦者にも同じ値がそのまま届く**(誰が申し込んだかは部屋の公開情報である)。
加工して送ると、観戦者ぶんの意味をもう1つ決めることになる(設計判断9)。

## 6. ★★確認モーダル —— 裁定53 を通常モードでも守る

36 が素の `confirm()` を捨てた理由は3つあった。

1. OS の見た目が黒い盤面の上に出る
2. ボタンの文言を決められない
3. ★★★**JavaScript を止める** —— 止まっている間は STOMP の受信も描画も進まない

通話しながら遊ぶ前提(裁定16)では **(3) がそのまま効く**。

### 6-1. ★★CSS は共有した(71 の「規則は1つ、名前は2つ」)

```css
.info-modal.manual-confirm,
.info-modal.auto-confirm { z-index: 1965; }
```

★裁定289 の「UI は複製する」は**共有 JS を避けるための判断**(裁定111)であり、
`battle.css` は既に両モードが読む1ファイルなので複製する理由が無い。

★★**1965 は切断オーバーレイ(1970)より下**である ——
切断中は「操作が相手に届かない」のほうが上位の情報であり、
その上に確認を重ねると**「実行しても何も起きない問い」を最前面に出す**ことになる(裁定56)。
★通常モードの最大 z-index が 1970 であることは、事前実測で確かめてある(2章)。
検証(72-6)は**値を読まず、実際に覆われるか**で測る。

### 6-2. ★確認を置いたのは4つだけである

**投了 / 席を立つ / 退室 / 再戦に応じる。**

★**再戦の [申し込む] と [断る] には置いていない** —— 申し込みは旗を立てるだけ、
辞退は倒すだけで、どちらも取り返しがつく。
★★**全部に確認を出すと、確認そのものが読み飛ばされるようになる。**

★初期フォーカスは [キャンセル] である(裁定52)。**破壊的操作の [実行] に載せてはいけない** ——
Enter で通ってしまう(壊し検証の軸25)。

### 6-3. ★音は鳴らさない

手動モードは確認の [実行] を音の取り付け点にしている(37 の 0-5)。
通常モードの取り付け点は **`send()` と `onMessage` の2つだけ**である(裁定68・287)。
★3つ目を増やすと、62 が「配信と再描画を区別する」ために引いた線が1本増える。
★投了は差分に現れる(`status` が FINISHED になり `decisive` が鳴る)ので、
ここで鳴らすと**1つの出来事に2音**になる(裁定70)。

### 6-4. ★★片肺として書き残す(71 の教訓)

- **通常モードには宣言のための素の `confirm()` が7箇所ある**(【賢魂】・特殊召喚・強化)。
  72 はそちらを直していない —— あれは「どちらの姿で使うか」という**宣言**であって、
  取り返しのつかない操作の確認とは層が違う。
  ★**ただし理由(3)(JS を止める)は宣言にも効く。**次に手を入れる人はここを見ること。
- **フォーカストラップ(裁定50)は作っていない。**通常モードには `modalStack` も
  焦点の閉じ込めも**元から無い**(`#info-modal` も `#sound-modal` も持っていない)。
  72 は初期フォーカス(裁定52)だけを守った。
  ★**作っていないものは壊せない** —— 壊し検証の軸にも入っていない。

## 7. 番人の置き方(設計判断45)

★★★**「回る場所」を選ぶ前に、そこまで届くかを確かめた**(70 の教訓)。
**71 とは逆で、72 は Java を変えている。**

| 層 | 何を置いたか | 件数 |
|---|---|---|
| **JUnit**(Eclipse で回る) | 席の移動・不変条件・退室の断り方・投了・決着の後始末・再戦・ビュー | **+28** |
| **verify**(実測。Playwright) | ボタンの出し分け・重なり・確認モーダル・決着の面・席替えのゲート・遷移 | **+31** |

★**JUnit にしか照合先が無いもの**: `GameRoom` の状態。
verify のハーネスは Java を起こさない(`verify/fixture.js` が組んだビューを渡す)ので、
`GameRoom` を壊しても**あちらには1件も届かない**。

★**verify にしか照合先が無いもの**: ボタンの出し分け・矩形・確認・遷移。
MockMvc が測れるのは「テンプレートに箱が在るか」= **宣言**だけである。
