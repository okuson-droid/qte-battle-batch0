## 3. ★★★どう直したか —— 規則を1箇所に置く

### 3-1. `CardType.isMinion` を新設した(裁定130)

《禁忌の墓地利用》の「ミニオンでないカード」の判定は、**2箇所**に要った ——
使用条件(`CardEffectRegistry.playConditions`)と対象の検証(`GameService.checkFilter`)である。

同じ規則を2箇所に書くと、片方だけが直された状態が何バッチも続く(裁定130・60 の実例)。
そこで述語を `CardType` に1つ置いた。

```java
public boolean isMinion() {
    return this == MINION || this == EVOLUTION;
}
```

★**「ミニオンでない」を `!= MINION` と書いてはいけない。**
その書き方は進化ミニオンを「ミニオンでないカード」に数えてしまう ——
総合ルール 2-1 のとおり、進化はミニオンの一種である。

### 3-2. ★Filter を2つ足した(裁定195 の踏襲)

| 足した値 | 使い手 | 対象の種類 |
|---|---|---|
| `WIND_CIVILIZATION` | 《ツイン・ストライク》 | **場のミニオン** |
| `NON_MINION_CARD` | 《禁忌の墓地利用》 | **墓地のカード** |

**絞り込みは Filter で行う。**効果側で「風文明でなければ何もしない」と書くと、
選べるのに不発という形になる(裁定302: 成立しない選択肢は並べない)。

### 3-3. ★★MinionView を太らせずに済んだ —— 器は既に在った

`WIND_CIVILIZATION` は**文明フィルタで初めて場のミニオンに当たる値**である。
ところが `MinionView` は文明を運ばない(現在値と可否だけを運ぶ)。

最初は「`MinionView` に `civilization` を足す」と考えたが、`battle.js` を読んだら
**そこに答えが書いてあった**。

> ★MinionView は文明とテキストを運ばない(現在値と可否だけを運ぶ)。サーバの
> ビューを太らせる代わりに、既にある口(card-library)から引く —— Java 変更ゼロで済み、

45 が書いた注釈である。`autoLibrary` から引く形にして、**Java の変更は0行**で済んだ。

> ★★**「番人が無い」と思ったら、まず在るかどうかを見る**(65 の教訓)の**器の版**である ——
> **器が無いと思ったら、まず在るかどうかを見る。**

(66 までは `card &&` と書いてあり、場のミニオンでは必ず false になっていた)。
挙動は変わらない —— この2値は手札でしか使われないためである。

### 3-4. 《生贄を求める邪鬼》の要求は2つに分けた

**`TargetSpec.combined` ではない。**あれは「要求をまたいで合計 n 枚」を表す形

## 4. ★★★番人 —— 「未実装0枚」の隣に何を置いたか

裁定303 が言うとおり、`report_effects.py` は**登録が在るか**しか見ていない。

### 4-1. ★★★突き合わせ台帳(本命)

`src/test/resources/text-impl-review.json`。番人は `CardTextReviewTest`(5件)。

```json
"QTE-M-EARTH-11": {
  "textHash": "d7491b6596b3eaa5",
  "reviewedIn": "batch67",
  "note": "★Ver0.4 のまま残っていた。コスト3以下 → 4以下に直した(裁定303 の2例目)"
}
```

**本文と実装が一致しているかは、機械には測れない。機械に測れるのは「人が突き合わせたか」である。**
台帳は突き合わせた時点の本文のハッシュを覚え、
**本文が変わったのに突き合わせ直されていないカード**を赤にする。

★★**46b の一括移行のときにこの番人が在れば、235枚が一斉に赤くなっていた。**

★**この台帳は「過去」を保証しない。**初回登録の `reviewedIn` は当時の記録からの推定であり、
当時の本文のハッシュは残っていない(Ver0.4 台帳は Batch 60 で削除した)。
内訳は **batch67 が47枚 / batch64 が1枚 / batch55-59 が121枚 / batch47-53 が66枚**である。
**保証するのは未来だけ**であり、そのことを台帳の `_note` にも書いてある。

★★**更新の道具には理由を必須にした**(`tools/mark_text_reviewed.py --card ... --note ...`)。
`--note` を省くとエラーになる。**台帳は緑にするための書類ではなく、点検の記録である**(裁定196 の精神)。
★`--all` を作っていないのも同じ理由である。

★★**赤くなったときにやることは「ハッシュを更新して緑にする」ではない。**
その旨は試験の Javadoc とツールの docstring の両方に書いた。

### 4-2. ★★数値の照合(補強)

`tools/check_card_text_numbers.py`。**本文の数値がそのカードの実装に現れているか**を見る。

## 5. ★★★番人そのものの穴が2つ出た

Filter を2つ足したので、verify 49-1(Java と `battle.js` の Filter の一致)が
見張ってくれるはずだった。**見張っていなかった。**

### 5-1. ★範囲が足りない番人は、無い番人と変わらない

66 までの 49-1 は、突き合わせる相手を
**「Java の Filter のうち、`Kind.HAND` の要求で実際に使われているもの」**に絞っていた。
`IGNORES_STEALTH` のような「手札に現れない値」を除くための、正しい配慮である。

ところが 67 が足した2値は **`Kind.MINION` と `Kind.TRASH`** であり、
**どちらも手札の要求に現れない** —— つまり**足しても番人の目に入らなかった**。
しかも `battle.js` の `matchesFilters` は場のミニオンも墓地のカードも同じ関数を通るので、
足し忘れれば**選べないカードが出る**。

★直した形: **JS の2箇所を別々に測る**。

| 測る先 | 相手 |
|---|---|
| `matchesFilters`(手札・場・墓地のすべてが通る) | **Java の全 Filter** |
| 手札のハイライト(手札しか通らない) | **`Kind.HAND` の Filter** |

66 までは `battle.js` **全体**から `case` を拾っていたので、**片方だけに書いても緑になった**。
裁定130 が求める「一致を機械が見張る」に届いていなかったということである。

### 5-2. ★★★誤った抽出と広すぎる照合が、互いの間違いを隠していた

5-1 を直した瞬間、**既存の穴が1つ落ちた** —— `EVOLUTION_MINION` が
「手札のフィルタなのにハイライトに無い」と出たのである。

調べたら、**抽出のほうが誤っていた**。66 までの正規表現は

```js
new RegExp(`Kind\\.HAND[^;]*?Filter\\.${f}\\b`, 's')
```

であり、**1つの文に `Kind.HAND` の要求と `Kind.MINION` の要求が並ぶカード**
(《機神兵長茶爺》の【起動：1】)では、`Kind.MINION` 側の Filter まで拾っていた。

つまり **52 から誤検出していた**。それが表に出なかったのは、
照合先が「`battle.js` 全体」という**広すぎる集合**だったからである ——
`matchesFilters` に `EVOLUTION_MINION` があるので緑になっていた。

> **★★誤った抽出と広すぎる照合は、互いの間違いを隠す。**
> ★片方だけを直すと、隠れていたもう片方が表に出る。**それは番人が壊れたのではなく、直り始めた音である。**

区切りを「次の `Kind.` か `;` の早いほう」にして、1つの要求の中だけを見るようにした。

## 9. 理解確認 Q&A

**Q1. 「本文どおりか」は機械には測れないのに、なぜ番人を2本も置いたのか。1本でよいのでは。**
A. **守れる範囲が違うからである。**台帳は「人が見たか」を覚えるだけで、
**見たときに何が正しいと判断したか**は覚えていない —— 人が見落とせばそのまま通る。
数値の照合はその見落としを一部だけ拾う機械の目である。逆に、数値の照合は
**数が現れない差**(「全て回復」→2回復)を1つも捕まえられない。
★2本の関係は 8-1 に実例として出ている ——
判定だけを壊してログを正しく書くと、数の番人はすり抜け、台帳だけが(次に本文が変わったときに)残る。

**Q2. 台帳の初回登録は「見たことにする」だけではないのか。それでは嘘ではないか。**
A. **半分そうである。だから正直に書いた。**48枚は 67 で実際に読んだ(reviewedIn = batch67)。
残る187枚は P5 と P2・P3 が本文を見ながら実装したという**記録**であって、
67 の私が読んだわけではない。台帳の `_note` にも試験の Javadoc にもそう書いてある。
★**それでも台帳には意味がある** —— 保証しているのは過去ではなく**未来**だからである。
以後、本文が1文字でも変われば必ず赤くなる。46b の移行にこれが在れば、
今回の7枚は3バッチ前に見つかっていた。

**Q3. 7枚を直したのに既存の700件が1件も落ちなかったのは、なぜ「重い」のか。**
A. **番人が1つも居なかったという意味だからである。**普通、仕様を変えれば既存の試験が落ちる ——
落ちた試験を書き換えるのが作り直しの作業である(rework-triage 5章)。
1件も落ちないということは、**そのカードの挙動を誰も測っていなかった**ということでしかない。
★63 まで《大地震》は「コスト3以下」で動いていて、それを咎めるものが
JUnit にも verify にも `report_effects.py` にも1つも無かった。

**Q4. 《ツイン・ストライク》の文明の絞り込みは、効果側で「風文明でなければ何もしない」と書けば
`Filter` を増やさずに済んだのでは。**
A. 済まない。**選べるのに不発**という形になり、裁定302(成立しない選択肢は並べない)に反する。
★さらに悪いのは、`Filter` を増やさない判断が **`battle.js` を触らずに済む**ように見えることである ——
版数を上げずに済んで得をした気になるが、実際には
「サーバは受け付けるのに何も起きない」というもっと分かりにくい状態を作る。

**Q5. verify 49-1 を作り替えたのは、番人を消したことにならないか(裁定196)。**
A. ならない。**測る性質は1つも減っていない** —— 66 までの1件が測っていた
「Java の Filter が JS に居る」は、67 の2件に**そのまま含まれている**。
増えたのは「どちらの JS に居るか」の区別である。
★裁定196 が求めるのは「何を測らなくなったかを書け」であり、
67 は**何も測らなくなっていない**。5章にそう書いた。

**Q6. 誘発の種別の番人を作らなかったのは、逃げではないか。**
A. 試作して**誤検出だらけだった**という実測がある(4-3)。参照と印を区別できず、
発火口が `TriggerType` でないものが多く、印を持たない効果もある。
★**そのうえ、この軸は台帳が上位互換である。**誘発の種別が変わるということは本文が変わるということで、
本文が変われば台帳が赤くなり、人が突き合わせる。
★**3本目を諦めたのは、諦めたほうが強いからである。**
★もし将来作るなら、裁定159 の規則を2箇所に置かないために **JUnit で `CardTextKeywords` を使う**こと。

**Q7. 48枚を読み終えたが、残る187枚はどうするのか。**
A. **台帳の `reviewedIn` がそのまま次の母集団になる。**
`python3 tools/mark_text_reviewed.py --stale batch67` で、
まだ 67 が読んでいない188枚が出る。新カード66枚(`batch47-53`)の目視校正が候補 D′ の残りであり、
**そちらは Ver1.1 の本文を見ながら実装されたぶん素性がよい**と見込んでいる ——
今回の7枚がすべて Ver0.4 由来だったことが、その見込みを裏づけている。
