## 2. 設計判断

### 2-1. ★ ビルド時変換ではなく1回きりのオフライン変換とした

`manual-cards.json` を**リポジトリにコミットする**。CSV は `tools/csv/` に原本として残すが、
アプリは読まない。

理由は文字コードである。CSV は Shift_JIS であり、Java でも Python でも
「読み手のロケール」に依存する余地が残る。Render のビルドは Docker のマルチステージであり、
ローカルの Windows と同じロケールである保証がない。
**壊れるとしたら本番だけで壊れる**という最悪の形になる。

変換を人の手に置くと、CSV を差し替えたのに再変換を忘れる事故が起こりうる。
これは JSON の `meta.generatedAt` と CSV の更新日を見比べれば気づけるため、
本番でだけ文字化けする危険と引き換えにするなら許容できる。

### 2-2. ★ 台帳との突合は「名前の正規化」を第一とし、CSV 8列目は照合にのみ使う

CSV の8列目にも台帳IDが入っているが、これを無条件に信じない。

- 名前で突合できた場合、8列目と食い違えば**名前突合を採用**し、食い違いを報告する。
- 名前で突合できず8列目に値がある場合のみ、8列目が台帳に実在することを確認して採用する。
- どちらも駄目なら報告する。

**理由は「人が手で書いた列を検証なしに取り込まない」という一点である。**
今回は食い違い0件だったが、0件であることを機械が言うのと、
確かめずに0件だと思っているのとは別物である。

なお設計書1-3 は「名前を突合キーにしない」と述べているが、これは
**CSV ↔ 画像 ↔ デッキファイルの突合**についての規約である。
台帳には画像IDが存在しないため、台帳との対応づけは名前でしか作れない。
`ledgerCardId` は**将来の対応表**であって実行時の識別子ではないため、
多少の危うさを報告で担保する形で足りる。

### 2-3. ★ 種別ごとの数値の有無をスクリプトが強制する

設計書3-1 の「スペルとリーダーは attack/hp を null、ウェポンは hp を null」を
**変換時に強制**し、CSV に値が入っていたら null に落としたうえで報告する。

これをアプリ側の判定に任せると、「型としては Integer だが種別によっては意味がない」という
暗黙の規約が全コードに散る。**データの形をデータの入口で決める**方が、
参照側が増えたときに壊れない。

リーダーの `cost` は CSV の `0` をそのまま入れる。設計書3-1 が null を指定しているのは
attack/hp だけであり、勝手に広げない。台帳が `cost: null` なのは表現差である(設計書1-4)。

### 2-4. ★ 画像IDは不透明なキーである — SHA256 を再計算して検証してはならない

設計書1-6 は「ファイル名 = 画像ID = ユドナリウムの `imageIdentifier` = 画像ファイルの SHA256」
と述べているが、**リポジトリの244枚のうち7枚でこれが成立しない。**

- PNG のチャンク CRC は244枚すべて正常である。**画像は壊れていない。**
- ユドナリウムが保存時に再エンコードしている、あるいは元ファイルのハッシュを名前に
  引き継いでいる、といった経路が考えられる。

実害はないが、規約としては重要である。
**画像の同一性を確かめる目的で `sha256(file) == filename` を検査してはならない。**
検査すべきは「その名前のファイルが存在するか」だけである。
変換スクリプトも `ManualCardsController` もこの方針で書いてある。

### 2-5. `meta.backImageId` を JSON に持たせた

裏面画像は234行すべて同一の1種類であり、カードの属性ではない。
カード側に持たせると235個の同じ64桁文字列がぶら下がる。
一方 Java に直書きすると、裏面を差し替えたときに再コンパイルが要る。

そこで **JSON のトップレベル `meta` に1つだけ持たせ、`ManualCardRepository.getBackImageId()`
で取り出す**形にした。スクリプトは234行の5列目が全部同じであることを確認しており、
2種類以上あれば生成を中止する。

カード1件の形は設計書3-1 のとおりで変えていない。

### 2-6. ★ カードIDに CSV の行番号を使ったことの副作用

`QTE-M-EARTH-30` の `30` は CSV の行番号である。設計書3-2 のとおり3ブロック構造が
IDに保存される(実際、**進化ミニオン18枚はすべて各文明の30〜32行目**に並んだ)。

副作用として、**CSV の行を挿入・削除すると以降のカードのIDがずれる。**
カードを追加するときは**末尾に足す**こと。並べ替えたい場合は、
IDが変わることを承知のうえで(まだ状態を持つバッチが無いうちに)行う。

現時点ではIDを永続化している箇所が無いため、17b 以降より前に整理するなら安全である。

### 2-7. 型を通常モードと共有しなかった

`ManualCardType` / `ManualCivilization` は `master` パッケージの `CardType` / `Civilization`
と値がほぼ同じだが、別に定義した。

- 手動モードには `EVOLUTION`(進化ミニオン)がある。台帳側の `CardType` に足すと、
  通常モードの switch と判定がすべて「知らない種別」を抱えることになる。
- 設計書2-1 が述べるとおり、**同居させると片方の要求がもう片方の欠陥になる。**

`ManualCardMaster` と `CardMaster` の対応は `ledgerCardId` だけで足りる。

### 3-1. `tools/csv/.gitattributes` を置いた理由

リポジトリ直下の `.gitattributes` が `* text=auto` を指定している。
PNG は git がバイナリと判定するため無事だが、**CSV はテキストと判定される。**
Shift_JIS には改行と衝突するバイトが無いため今すぐ壊れはしないものの、
「原本」として置くファイルを git の推測に委ねる理由が無い。`-text` で明示的に止める。

### 3-2. ★ カードIDを Java の文字列リテラルに書かないこと

`tools/check_all.py` の項目3 は、Java 中の `"QTE-…"` を台帳の実在IDと照合する。
**手動モードのIDは台帳に存在しないため、書くと必ず偽陽性になる**
(正規表現の都合で `"QTE-M-NONE-01"` は `QTE-M` として報告される)。

そのためテストはピュア・エレメントを**文明で引いて**検証している。
`repository.findByCivilization(NONE)` である。IDで引く必要が出た場合は、
先に `tools/check_all.py` に除外規則を入れること(6章)。

## 5. ✅ 理解確認

<details>
<summary>Q1. なぜ CSV をビルド時に読まず、生成物の JSON をコミットするのか</summary>

CSV が Shift_JIS だからである。読み込みが実行環境のロケールに依存する余地があり、
Render の Docker イメージとローカルの Windows で挙動が変わりうる。
**壊れるとしたら本番でだけ壊れる**という最悪の形になる。
オフラインで1回変換し、UTF-8 の JSON をコミットすれば、その危険が消える。
</details>

<details>
<summary>Q2. なぜ画像IDをカードIDにしないのか</summary>

画像IDは内容ハッシュ(に相当するもの)であり、**カードを作り直すと変わる**からである。
光18・19 で実際に起きている。状態の識別子が勝手に変わると、
保存した盤面や履歴が指す先を失う。加えて64桁はログでもデバッグでも読めない。
</details>

<details>
<summary>Q3. なぜ `text` と `keywords` を持たせないのか</summary>

新カード66枚にはテキストデータが存在せず、既存168枚ぶんも Ver.0.4 以降の変更で信用できない。
**半分だけ値があるフィールドは「値がある方だけ使ってしまう」不具合を生む。**
手動モードは効果を判定しないので、そもそも要らない。人間が拡大画像で読む。
</details>

<details>
<summary>Q4. リーダーの cost は CSV が 0、台帳が null である。どちらを入れたか</summary>

CSV の 0 を入れた。設計書3-1 が null を指定しているのは attack/hp だけであり、
指定されていない項目に判断を広げない。設計書1-4 もこれを「表現差であり実質の差分ではない」
と整理している。
</details>

<details>
<summary>Q5. 画像が本物か確かめるために SHA256 を再計算してよいか</summary>

**駄目である。** リポジトリの244枚のうち7枚は、ファイル名と実際の SHA256 が一致しない
(CRC は全枚数正常なので画像自体は健全である)。
画像IDは**不透明なキー**として扱い、確かめるのは「その名前のファイルが存在するか」だけにする。
</details>

<details>
<summary>Q6. カードを1枚追加したい。CSV のどこに足すか</summary>

**末尾である。** カードIDが `QTE-M-<文明>-<CSV行番号>` であるため、
途中に挿入すると以降のカードのIDがすべてずれる。
</details>

<details>
<summary>Q7. `manual-cards.json` のピュア・エレメントの画像IDが間違っていた。どう直すか</summary>

JSON を直接編集しない。`tools/convert_manual_cards.py` の `PURE_ELEMENT` 定数の
`imageId` を直し、スクリプトを再実行する。
JSON は生成物であり、手で直すと次の再変換で消える。
</details>
