## 2. 設計判断

### 2-1. `battle.css` を追記することにした理由(見込みからの変更)

18b の次バッチ予告は「既存ファイルの変更は無し(manual-battle.js/htmlへの追記が中心)」
という見込みだった。実装を始めた段階で、帯・全面表示・検索ボックスに必要なスタイルを
`element.style.cssText` で JS 内に直書きする案と、`battle.css` に追記する案を比較し、
後者を選んだ。理由は次の2点である。

1. 帯のカード(`manual-band-card`)・全面表示の行(`manual-deck-row`)は、
   `createBandItem` / `createDeckRow` の中で毎回生成される要素であり、
   インラインスタイルにすると同じ値が何箇所にも散らばる。18b が文明色の計算を
   JS 関数に閉じたのと同じ理由で、**見た目の規則は1箇所に集約するほうが安全**である。
2. 18b 自身が `battle.css` に追記した実績があり(v10→v11)、今回も同じ手続き
   (末尾に「Batch 18c」セクションを追記・バージョンを1つ上げる)を踏襲すれば
   影響範囲は追記分に閉じる。

「既存ファイルの変更は無し」という見込みを裏切る形にはなるが、質問への回答ではなく
実装上の技術判断であるため、ここに理由を明記して報告する。

### 2-2. ゾーンパイルのクリック割り当てを反転した

18b までは「左クリック: 中身があれば最上段を拡大 / 右クリック: 常に空振り」だった。
18c では「左クリック: 帯を開く / 右クリック: 中身があれば最上段を拡大、無ければ
『空です』とログ欄に案内」に変更した(マスター確認済み)。

根拠は設計書 4-4 の一般規約である。「左クリック 手札・開いたゾーンの中身 → 拡大」
「右クリック カード → 拡大」という2つの行があり、**帯の中のカードは拡大が左クリックに
割り当てられている**。ゾーンパイル自体(閉じた状態の箱)をこの規約の外に置くよりも、
「箱を開く動作は左クリック、拡大は右クリック」と山札(左:ドロー/右:全面表示)や
場のタイル(左:タップ/右:拡大)と同じ「主操作は左、補助は右」の並びに揃えたほうが
一貫する。

### 2-3. 帯は生成のたびに描き直す共通関数(`renderBandDom`)に集約した

墓地・消滅・禁忌・一時公開・進化スタックの5種類は、中身の取得元(通常のゾーン配列 vs
`materials` 配列)と検索の有無だけが違い、DOM構造・ドラッグ挙動・選択ハイライトは
完全に同じである。`openZoneBand` / `openEvolutionBand` はそれぞれ中身を集めて
`renderBandDom({ title, seatId, zoneName, items, showSearch })` に渡すだけにし、
帯そのものの組み立て(枠・検索欄・閉じるボタン・カード列)は1箇所に閉じた。

検索欄の入力イベントは、帯全体(`renderBandDom`)を作り直さず**カード列
(`row`)だけを再描画**する。検索欄自体を毎回作り直すと、1文字打つたびに
`<input>` が入れ替わってフォーカスが外れる事故になるためである。

### 2-4. 帯の中のカードは「開いたゾーンの中身」として扱う(タップではなく拡大)

`createBandItem` は `createFieldTile` を使い回さず、`createHandCard` に近い
新しい関数として書いた。理由は、場のタイル(`createFieldTile`)の左クリックは
「タップ⇔アンタップ」だが、帯の中のカードは設計書 4-4 の「開いたゾーンの中身 → 拡大」
に従うべきで、挙動が違うためである。Shift+クリック(表裏)・Ctrl/Cmd+クリック
(複数選択)・ドラッグは共通なので、そこだけ `createHandCard` と同じパターンを踏襲した。

### 2-5. `cardLocation` 索引に進化スタックの素材を追加した(18bの既知の限界の解消)

18b の引き継ぎ書が明記していた「`cardLocation` 索引は最上段のみを対象にしている」を
解消した。`renderStackRow` が最上段のカードを登録するのと同じループの中で、
そのカードの `materials` 配列も同時に登録する(帯を開いているかどうかに関わらず、
盤面を描画するたびに常に登録する)。

これにより、進化スタックの素材を Ctrl/Cmd で選択した状態から**別の進化ミニオンを
ドラッグして重ねる**という組み合わせ操作でも、`registerDropTarget` の
`sameFieldSelection` フィルタが素材の instanceId を正しく拾えるようになった
(素材自身は `isTopLevel()` が false なのでサーバ側の `evolve` 検証には通らないが、
「盤面上のどこにいるカードか」を索引が把握していること自体は一貫性のために必要である)。

### 2-6. 帯からのドラッグはサーバの `move` に丸投げする(特別扱いをしない)

帯の中のカード(通常ゾーンでも進化スタックの素材でも)を `onDragStart` に渡す際、
呼び出し方は場のタイルや手札のカードとまったく同じ `onDragStart(e, card, seatId, zone)`
である。ドロップ先の判定(`registerDropTarget`)も既存のロジックをそのまま使う。

素材の instanceId を渡された `move` 操作がスタックの中まで探しに行く
(`ManualBoardIndex.find` がゾーン直下と `materials` の2段で必ず尽きる設計。
17b/18aで既に実装済み)ため、クライアント側は「このカードが今どこにいるか」を
気にせず、instanceId だけ渡せばよい。**帯という見た目の違いは、ドラッグの送信内容には
一切影響しない。**

一点だけ注意が必要な副作用がある。帯の中のカード(墓地のカードや進化スタックの素材)を
**埋まっている FIELD タイルの上にドラッグすると、`registerDropTarget` は「進化」と
判定して `evolve` を送る。** 墓地のカードや素材(非トップレベル)は `evolve` のサーバ側
検証(`top.isMaterial()` チェック等)に引っかかって拒否されるが、既存の ERROR 配信
(`onMessage` → `showTransientError`)がそのままエラーメッセージを表示するため、
クライアント側で個別に弾く処理を追加していない。5-1 の原則(判断はサーバに1点集約)
に沿った挙動であり、意図した設計である。

### 2-7. 山札全面表示の並べ替えは「外してから数える」補正を送信側で行う

`ManualOperationService.move` は、対象を外してから `toIndex` を適用する
(`detach` → `clampIndex(toIndex, target.size())` → 挿入)。これは同じ配列内での
並べ替えでは「外した1枚ぶん後続の添字が1つ前へ詰まる」ことを意味する。

`createDeckRow` のドロップ処理は、ドロップ先の行の上半分/下半分どちらに落ちたかで
挿入位置(その行の前 or 後)を求めたあと、**ドラッグ元の位置より後ろであれば
1つ引く**補正を先取りしてから送信する。これによりサーバ側の「外してから数える」
規約と結果が一致する。

この補正は単一カードのドラッグでのみ正しく動く前提で書いている(複数選択のまま
山札内で並べ替える操作は今回サポートしていない。5章参照)。

### 2-8. 山札の順序は index 0 = 一番上(次に引く1枚)

`ManualGameService.drawCards` が `deck.remove(0)` で引いている(=配列の先頭が
山札の一番上)ことをコードで確認し、全面表示の一覧も同じ向き(先頭 = 一番上)で
描画した。既存の「上へ/下へ」のミニドロップ枠(`toIndex: 0` / `toIndex: 999999`)
とも向きが一致する。

### 2-9. 検索は行の再描画のみで、一覧側の入力欄もフォーカスを失わない

山札全面表示の検索欄も帯と同じパターンで、`input` イベントのたびに一覧
(`list.innerHTML`)だけを作り直し、検索欄自体には触らない。フィルタで隠れた
カードも「検索中は並べ替えを無効にします」という注記とともに、ボタン
(一番上へ/一番下へ/手札へ/場へ)は使える状態のまま残す設計にした
(2-7の補正がフィルタ状態と噛み合わないのを避けるための切り分け)。

## 4. 既知の限界(要確認・未対応)

- **★山札全面表示のドラッグ並べ替えは単一カードのみ対応。** 複数選択したまま
  山札内で並べ替える操作は、添字補正が「外した1枚ぶん」の前提で書かれているため
  未対応。複数カードの並べ替えは頻度が低いと判断し、範囲外とした。
- **★検索中は山札のドラッグ並べ替えを無効にしている。** フィルタで隠れた行を
  挟むと表示上の位置と実際の配列添字がずれるため。ボタン(一番上へ/一番下へ/
  手札へ/場へ)は instanceId 指定なので検索中でも機能する。
- **相手席(B席)の小型ゾーンバーは18bから変わっていない。** マスター確認により
  今回のスコープ外(0-2)。クリックしても何も起きない状態が残る。
- **帯・全面表示ともに、開いている間サーバからの再配信で自動的に描き直る。**
  ただし進化スタックの帯は、素材が0枚になった瞬間に自動で閉じる
  (`renderEvolutionBand` が空を検知して `closeOverlay()` する)。ゾーンの帯は
  0枚になっても閉じずに「(なし)」と表示したままにする(墓地などは0枚から
  増えることが多いため、開いたままのほうが自然と判断した)。
- 18a/18b由来の既知の限界(`CardMasterLoadTest` の `hasSize(72)`、
  `check_records.py` の `TARGETS` 未登録、`check_structure.py` の `src/test` 未対応、
  `check_undeclared.py` の `BUILTINS` 未登録2件)はすべて変わらず残っている。
