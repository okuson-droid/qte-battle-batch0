## 2026-08-14 確定(Batch 38 実装時。詳細は `notes/batch38-design-notes.md`)

82. **★★★開始シーケンスは「上限で落ちていた」のではなく「数えられてすらいなかった」。**
    `applyView` の入口に `!fxStartLocking(prevView) && !fxStartLocking(view)` があり、
    差分そのものを採っていなかった。**上限(裁定8)を緩めても何も出ない。**
    ★**指摘の文言ではなくコードを読んでから直す。**
83. **★★★「例外を作る」と「別の道を作る」は違う。**
    38 がやったのは、関門を `applyView` から **`diffViews` の中へ移し**、
    その手前で儀式(`out.rite`)だけを採ることである。裁定8 も裁定11 も1文字も緩んでいない。
    ★儀式が上限に引っかからないのは**特例だからではなく、作られる件数が1〜2件だから**である
    (9枚のゴーストは入れ物1つとして `fxRegister` に積む)。**機械判定あり。**
84. **★★★差分は同一性を語り、儀式は員数を語る。**
    開始の配りでは `instanceId` が全部作り直されるので、差分は嘘ではないが無意味である。
    一方、枚数(先攻4 / 後攻5)は総合ルール 2-5 そのものである。
    ★入口が違うのは経路が違うからではなく、**運ぶものが違うから**である。
    ★この性質のおかげで相手席の配りも演出できる(枚数は元から公開情報)。
85. **★★★守れない約束を型に書かない。**
    35 は「DECLARE 行は必ず構造を持つ」を型で守れた(裁定41)。
    START は守れない —— 構造を持たない START 行が正当に存在する(準備の開始・選択権の告知)。
    型で守るのは「**構造を作るならこの入口を通る**」までにし、
    その入口を呼ぶのは `ManualStartService.startLog(actor, rite, text)` の1箇所に集約した。
86. **★★1行に2つの儀式が同居する場合は、主たる儀式 + 別欄で表す。**
    ソロのランダムはダイスと配りが1回の操作である。ログを2行に割ると
    **起きていない操作**が増える(23 1-4)。儀式をリストにすると全ログ行が重くなる。
    → `kind` が主たる儀式、ダイスは独立した欄(`diceA` / `diceB` / `winner` / `label`)。
    ★**画面には推測が1つも要らない**形にすること。
87. **★★★儀式のあいだ開始シーケンスの画面は開かない(保留)。**
    fx層(1030)は開始モーダル(1950/1960)より下にあり、待たせなければ儀式は1pxも見えない。
    ★**z-index の並びを演出の都合で崩さない。層の順序ではなく時間で解く**(裁定83 と同じ形)。
    ★**保留は時刻で明ける**(`FX_RITE_HOLD_MAX_MS` = 2400ms)。
    組み立てが失敗しても必ず開くので、行き止まりが構造的に作れない。**機械判定あり。**
88. **★★保留するのは「開く」だけである。** 閉じるほうは保留しない
    (「儀式のあいだ閉じられない画面」を作らない)。
89. **★★★演出を切っている人(`prefers-reduced-motion`)は待たせない。**
    保留のゲートは `fxDiffNeeded()` ではなく **`fxAllowed()`** である。
    見えていないものの終わりを待たせるのは、操作が遅れるだけである。
    ★裁定69「音は動きではない」の裏側 ——**待つ理由は音ではなく絵にある。機械判定あり。**
90. **★儀式のゴーストは最初に全部作り、飛ばす時刻だけをずらす。**
    途中で作ると、その1枚だけ開始状態が確定しておらず**瞬間移動**する
    (32a の `offsetHeight` は、確定の時点でDOMに在るものにしか効かない)。
91. **★ダイスの帯の内容は最初からDOMにある。** 段階的に現れるのは `animation-delay` であって
    JS がテキストを書き換えるのではない。**「待ってから測る」検証にしない**(31 の規約)。
92. **★0枚のマリガンでも儀式は作る。**「儀式が無い」と「儀式が空だった」を
    画面が区別できなくなると、判断が画面側へ移る。

## 2026-08-14 確定(38 追補のつづき)

98. **★★★名前は最初の例ではなく性質に付ける。**
    `ManualStartRite` → `ManualRiteKind` ほか、型名から `Start` を外した。
    器が表していたのは「開始シーケンス」ではなく
    <b>「差分では語れない、員数と段取りで語る出来事」</b>である。
    ★2つ目の例が出た時点で名前を直すのがいちばん安い。
    ★配信の JSON は1文字も変わっていない(`rites` / `kind` / `dealt`)。
99. **★★シャッフルは「盤面に何も起きない操作」である。**
    枚数もゾーンも変わらず、非公開の並びだけが変わる。差分からは完全な無変化に見える。
    ★サーバ側の変更は `shuffleDeck` の**返り値1つ**、クライアントは
    `fxEffects` に3行と `SFX_FOR_KIND` に1行だけで済んだ ——
    **演出の関数も音も1つも新しく作っていない**(器を1つにしておいた配当)。
100. **★混ざる所作は揺れだけでは足りない。** 散らばった3枚が束へ戻る絵を重ねる。
    ★傾き(`rotate`)を入れているのは、ゴーストが山札のタイルと同じ寸法だからである。
    ★★<b>同じ絵をマリガンの中の混ざる所作にも当てている</b>(同じ出来事に2つの描き方を作らない)。
101. **★★ピュア・エレメントは中央から飛ぶ。** デッキの外から渡されるカードであり、
    山札から飛ばすのは絵として嘘である。**機械判定あり(座標で測っている)。**
    ★出発点の矩形は「中央に、<b>着地点と同じ寸法で</b>」作る ——
