## 1. 設計根拠★

### 1-1. ★相手上段の再構成は「見た目」ではなく矢印の前提条件である

設計書4章はマスター指示による並べ替えとして書かれているが、7章と読み合わせると
それだけではないことが分かる。7-1 はこう書いている。

> 全ゾーンは全閲覧者のレイアウトに何らかのアンカーを持つため、必ず描ける
> (4章の相手上段がこの性質を保証する)。

20c までの相手上段はチップ5つ(山・墓・消・禁・確)とリーダーだけであり、
**相手の手札とマナに対応する要素が画面に存在しなかった**。矢印は
「ゾーン → 画面上の要素」の対応で描くため、要素が無いゾーンは端点にできない。
つまり 4章を先にやらないと 7章は「相手が手札から場へ動かした」という
最も基本的な矢印を描けない。21b の申し送りが「1 → 3 の順で行うこと」と
書いていたのはこのためであり、本バッチもその順で実装した。

副産物として、**相手の手札枚数が画面に出るようになった**。3-3 は枚数を公開情報と
定めているのに、20c までの盤面はそれをどこにも表示していなかった。

### 1-2. ★情報の密度で3段階に分けた

4章の指示は「マナは簡略画像・墓地と消滅も簡略画像・残りはチップ」である。
この分け方には一貫した基準がある。**中身を見る頻度と、見えるかどうか**である。

| 区分 | 表示 | 根拠 |
|---|---|---|
| マナ | 表向きは縮小カード画像を横並び、裏向きは裏面1枚+枚数 | 相手の使えるMPと文明構成は対戦中に最も頻繁に確認する公開情報である |
| 墓地・消滅 | 最上段の縮小画像+枚数バッジ | 「何が落ちたか」は一番上だけ分かれば足り、詳細は帯で見る |
| 山・禁・確・手 | 枚数チップのみ | 中身が**原理的に届かない**。画像を置く場所を用意しても敷くものが無い |

★3段目に画像を置かなかったのは節約ではない。対戦部屋ではサーバが
カードオブジェクトを載せない(3-3)ため、**そこに絵を出せてしまう設計だとしたら
それ自体が情報漏れの証拠**である。表示の形が公開範囲と一致していることは、
後から読む人にとって仕様の説明になる。

### 1-3. ★マナのタップは回転ではなく減光にした(マスター確認済み)

設計書4章は「傾きまたは減光」までしか決めていないので、着手時に確認した。

技術的な理由は高さである。この行には **148px** という上限があり(4章)、
実際の高さはリーダータイル(120px)+ padding で 140px、余裕は 8px しかない。
要素を回転させると外接矩形が伸びる(40×56 を 8度回せば高さは約 61px になる)。
マナの縮小画像は 56px であり回転しても収まるが、**角度を変えたくなったときに
高さ制約と衝突する**。「傾ける表現を選ぶと、以後その角度が高さ予算に縛られる」
という関係を持ち込まないほうがよい。

減光(`filter: brightness(0.45)`)は矩形が変わらないため、この関係が生じない。
なお自席のマナタイル(`.mana-tile.tapped`)は従来どおり回転である。
自席は枠に余裕があり、実物のカードを寝かせる操作に対応しているためで、
**同じ状態を違う記法で描いているのではなく、違う目的の表示である**
(自席=操作対象 / 相手上段=状態の伝達)。

### 1-4. ★「非公開」は無反応にしてはならない(3-5)

20c までは相手のチップをクリックすると `openZoneBand` が呼ばれ、対戦部屋では
**中身が空の帯が開いていた**。これは2重に悪い。

1. 「空である」と「見えない」が同じ表示になる。相手の山札が0枚なのか
   36枚あって見えないだけなのかが区別できない
2. 何も起きていないように見えるため、故障と区別がつかない

3-5 の指示どおり、帯を開かずチップを明滅させ、小トーストで「非公開」と伝える。

★判定材料は **`zones` にキーがあるか**だけである。

```js
function isZoneVisible(seatView, zoneName) {
    return !!seatView.zones
        && Object.prototype.hasOwnProperty.call(seatView.zones, zoneName);
}
```

「対戦部屋か」「相手席か」「観戦の視点は何か」をクライアントで組み立て直すと、
**サーバの公開範囲の定義がクライアントにも書かれることになる**。21a が
「公開範囲の判定を2箇所に書かない」(ハンドオフ3章)と決めた理由がそのまま当てはまる。
21a は非公開ゾーンを「キーごと載せない」形にした(3-3・B1)ため、
その事実を1つ読むだけで足りる。空配列とキーの欠落は区別できる。

★この判定は**右列のパイルにも掛けた**。下段は「自席」だが、公開のみ視点の観戦者に
とっては両席とも非公開である。相手上段だけ直して右列を放置すると、
観戦者の画面では同じ操作が場所によって違う反応をすることになる。

### 1-5. ★先攻選択権を `note` 経路で代用しなかった理由

21b の申し送りは「サーバに専用エンドポイントが無い。ログだけなら `note` 経路で
代用できるが、ログ上『自由メモ』として残る」と書いていた。マスターの判断は
**Java に専用イベント種別を足す**であった。

代用しなかったのは、ログの種別が**後から読むときの信頼性**を決めるからである。
`NOTE` は人間が自由に書ける種別であり、そこに混ぜると
「アプリが振った出目」と「人が書いた文」を区別できなくなる。
先攻の決定は対戦の前提条件であり、誰でも書き足せる欄に置いてよい情報ではない。

★同時に、これは**「判断」の実装ではない**(設計書16 5-1)。ここで行うのは
総合ルール 2-5 の「ダイスを振り、出目の高い側が先攻/後攻を選択する」のうち
**ダイスを振る部分だけ**であり、選んだ結果を盤面へ反映することもターンを進めることも
しない。乱数が公平であることを両者に保証するのが役割である。
シャッフルを「乱数は機械のほうが公平である」という理由でサーバに置いたのと同じ形であり、
だから `rollDie` も `ManualGameService`(乱数源を持つクラス)に置いた。

実装上の細部を3つ。

- **同値は振り直す。** 引き分けを出して押し直させると、押した回数だけログが伸びる。
- **席を受け取らない。** どちらの席でも押せる(6-3)ので引数に不要であり、
  受け取らなければ「相手の席として振った」と偽装する余地も生まれない。
- **`denySeatAction` ではなく `denyOperate` で判定する。** 結果は席の持ち物ではない。
  観戦者は押せない。

### 1-6. ★矢印は「送るもの」を絞ることで成立している(7章)

7-1 が画素座標を送らないと決めているのは、**送っても意味を持たないから**である。
ウィンドウ幅・カードの伸縮(20c)・上下反転(3-2)で座標系は閲覧者ごとに違う。
送った側で正しい座標は、受け取った側では見当違いの位置を指す。

代わりに送るのは3つだけである。

| 送るもの | 誰が決めるか |
|---|---|
| 掴んでいるカードの `instanceId` | クライアント |
| 掴んでいるカードの**ゾーン** | ★サーバが `instanceId` から引き直す |
| ホバー中のドロップ先(席+ゾーン) | クライアント |

★2番目がサーバ側なのは 21a の判断であり、正しい。クライアントに宣言させると
「実際は手札にあるカードを、場にあると偽って矢印の根にする」ことができてしまい、
受信側に余計な情報が渡る。外部から来るデータはすべて検証する(設計判断27)。

クライアント側で新しく作ったのは**ゾーン → アンカー要素の対応表**だけである。

```js
registerZoneAnchor(el, seatId, zoneName);   // 描画関数が自分の作った要素をその場で登録
anchorElement(place);                        // {seatId, zone} から引く
```

★**セレクタの一覧表を別に持たなかった**のが要点である。`#hand-row .hand-row` の
ような文字列の表を作ると、レイアウトを変えたときに片方だけ直して壊れる。
「描いた本人が登録する」形なら、要素が消えれば登録も消える。
`cardLocation` を毎描画で作り直しているのと同じ考え方であり、
`renderAll` の先頭で `zoneAnchors` も作り直している。

鍵の作り方も 21a の表現に揃えた。**共有ゾーンは席が null、リーダーはゾーンが null**
である(`ManualLogPlace` の javadoc)。この2つを特別扱いせず鍵の生成規則に
畳み込んでおくと、`seatId` を無条件参照する罠(ハンドオフ3章)を踏みようがない。

### 1-7. ★矢印はログ・履歴・Undo に触れない(7-2)

ドラッグ中の動きは「起きたこと」ではない。途中で手を離せば何も起きていない。
記録すると、ログが**実際には起きなかった操作**で埋まる。

クライアント側でこれを守るための実装が2つある。

1. `onMessage` は `type === 'CUE'` を**最初に**処理して抜ける。
   `latestView` を書き換えず、`renderAll` も呼ばない。
   矢印が届くたびに盤面を描き直すと、ドラッグ中ずっと相手の画面が再描画され続ける。
2. 消去は `dragend` の1箇所に集約した。`drop` の後にも `dragend` は必ず来るため、
   両方に書くと二重送信になる。

★**消し損ね対策**も 7-2 の要求である。相手のタブが落ちれば `active:false` は
来ない。最終更新から5秒で自動的に消す掃除を1秒間隔で回している。
「消えないゴミが画面に残る」は、機能が無いことより悪い。

### 1-8. ★観戦の2つのトグルは行き先が違う(3-2)

見た目は並んだ2つのボタンだが、性質は正反対である。

| トグル | 行き先 | 理由 |
|---|---|---|
| 全見え / 公開のみ | **サーバ** | 「全部送っておいてクライアントで隠す」形にすると、公開のみ視点の観戦者のブラウザに相手の手札が届く。3-3 が「カードオブジェクトを一切載せない」と決めた意味が消える |
| 上下反転 | **クライアントだけ** | どちらを下に置くかは見る側の都合であり、盤面の事実ではない(10章) |

上下反転の実装は、21b が申し送ったとおり `bottomSeatId()` に条件を1つ足すだけで済んだ。

```js
function bottomSeatId(view) {
    const own = view.viewerSeat || 'A';
    if (!view.viewerSeat && boardFlipped) {
        return own === 'A' ? 'B' : 'A';
    }
    return own;
}
```

★**反転を観戦者に限った**のは 3-1 が「プレイヤーは常に自席=下・切替UIなし」と
定めているためである。プレイヤーに反転を許すと、自分の手札が上段に出た状態で
相手の場へ落とす操作をすることになり、事故が起きる。
席に着いたときに `boardFlipped` を false へ戻すのも同じ理由である。

★そして 21b が確立した形は崩していない。反転しているのは
**どの席ビューをどちらの入れ物へ描くか**だけであり、`cardLocation` /
`registerDropTarget` / 送信ペイロードが受け取る席は相変わらず `seatView.id`(実席)である。
矢印のホバー先に載る席も実席である(検証済み。3章)。

### 1-9. 高さ148pxをどう守ったか(4章)

制約は「現行の高さ(148px)内に収める。溢れる場合はマナ簡略表示の高さを先に削る」である。
結果は **140px** に収まり、マナを削る必要は無かった。内訳はこうである。

| 要素 | 高さ |
|---|---|
| リーダー+ウェポン合体タイル | 120px(★行の高さを決めているのはこれ) |
| マナ簡略表示 | ラベル12 + トラック58 + 枠6 = 76px |
| 墓地・消滅 | 面56 + ラベル12 + 隙間2 = 70px |
| 枚数チップ | 32px |
| 行の padding | 上下8px ずつ |

★マナと墓地の縮小画像を **40×56** にしたのは、カードの縦横比(1 : 1.4)を保った
まま判読できる最小に近いサイズだからである。これ以上大きくすると
ラベルぶんを足したときにリーダーの120pxを超え、行そのものが伸び始める。

## 2. 実装時に踏んだ / 避けた罠

- **★★検証ハーネスに `box-sizing: border-box` が無かった。**
  Bootstrap Reboot は `*, *::before, *::after { box-sizing: border-box }` を当てているが、
  `build_harness.py` の Bootstrap 代替には入っていなかった。そのため
  `.board-side { min-height: 140px }` に padding 16px と border 3px が**加算**され、
  相手上段がハーネスでだけ 159px になった。実物では 140px である。
  20c の「Bootstrap 代替の漏れはハーネスでだけ壊れる」がそのまま再演したかたちで、
  **148px を測ろうとして初めて表面化した**。高さを検証項目にしていなければ、
  以後ずっと「ハーネスの寸法は実物と違う」まま気づかなかった。
  → 代替に1行足して解消。既存91項目は全て回帰なしで通っている。
- **★矢印を足すと「送られたのは1件だけ」の検証が落ちる。**
  ドラッグ1回につき `dragcue` が3〜5通飛ぶため、`msgs.length === 1` で
  数えていた既存の検証が壊れた。件数で確かめている検証は
  `boardMessages()`(揮発メッセージを除く)を通すようにした。
  ★**除いた結果を検証しないままにはしない。** 同じドラッグで
  「開始 → ホバー → 消去」の順に飛ぶこと、ホバー先の席が実席であることを
  新しい検証項目として足してある。
- **`dragover` は毎フレーム飛ぶ。** ホバー先が変わったときだけ送るよう
  1段フィルタを掛け、そのうえで 100ms のスロットルを掛けている(7-2)。
  どちらか片方だけだと、同じゾーンの上で指を動かしている間ずっと送り続ける。
- **矢印のオーバーレイに `pointer-events: none` を忘れない。**
  忘れると、矢印が出ている間だけ盤面にドロップできなくなる。
  ★z-index は帯(1040)より**下**の 1035 に置いた。開いている帯を矢印が
  横切ると帯が読めなくなる。
- **`ManualLogRenderer` の `switch` に `default` があることを確認してから
  列挙体に定数を足した。** 網羅 `switch` 式に `default` が無ければ、
  定数を1つ足しただけでコンパイルが通らなくなる。
- **明滅アニメーションはクラスを外してリフローを1回強制してから付け直す。**
  付けっぱなしだと2回目以降のクリックで再生されず、無反応に見える。
  「無反応を直す」機能が無反応になるのでは意味が無い。

## 3. 検証手順

### 3-1. ★まず手元で `mvn test` を走らせること

**このサンドボックスから Maven Central へ到達できない**(403。ハンドオフ3章の既知の制約)。
21c では **Java を4ファイル変更し、JUnit を4件追加した**。
21b(1ファイル・読み取り専用API)より変更が重いので、必ず実行してもらいたい。

```bash
mvn test
```

期待: 既存テスト + `ManualVersusTest` が **34件**(30 + 21c の4件)通ること。

追加した4件は次のとおり。

| テスト | 何を守るか |
|---|---|
| 先攻選択権はどちらの席でも押せて結果はログにだけ残る | E4。★盤面に触っていないこと |
| 先攻選択権の判定は必ずどちらかの席に決まる | 同値の振り直し(50回まわす) |
| 先攻選択権は視点で変わらずそのまま全員に出る | `plain` 種別であること(5-3) |
| 観戦者は先攻選択権を押せない | 6-1 |

### 3-4. 手元での動作確認

**A. 一人回しの回帰(20c/21b までと同じであること)**

1. `http://localhost:8080/manual` で全公開部屋を作る
2. デッキを読み込む。相手上段(B席)のチップが[山][禁][確][手]の4つ、
   その左に墓地・消滅の画像枠とマナ簡略表示が出ること
3. 相手上段のチップ・画像をクリックすると帯が開くこと(全公開部屋なので全部開く)
4. ヘッダに「先攻決め」「視点」「上下反転」が**出ていない**こと
5. ドラッグ・Undo・Redo・ログ書出が従来どおりであること

**B. 対戦部屋 — 相手上段と非公開(4章・3-5)**

1. 対戦部屋を作り、2つのブラウザで席A・席Bに着く
2. 双方デッキを読み込む
3. 相手上段のチップが「山36 禁8 確0 手4」のように**0でない**枚数を出すこと
4. **相手の[山][禁][確][手]をクリック** → 帯が開かず、チップが赤く明滅し、
   画面下に「山札は非公開」等の小さな帯が1.6秒出ること
5. 相手の墓地画像をクリック → **帯が開いて中身が見えること**(公開ゾーン)
6. 相手が手札をマナへ置く → 相手上段のマナ簡略表示に縮小画像が増えること。
   裏向きに置いたら裏面1枚+枚数バッジになること
7. 相手がマナをタップ → その画像が暗くなること
8. **相手上段が縦に伸びていないこと**(ミニオン行が押し下げられていない)

**C. 対戦部屋 — 矢印(7章)**

1. 席Aで手札を掴んだまま、自分の場の上でしばらく止める
2. **席Bの画面**に、相手の手札チップから相手のミニオン行へ向かう
   半透明の黄色い矢印が出ること。矢印の中ほどに相手の名前が出ること
3. 席Aが手を離す → 矢印が消えること
4. 席Aが場のカード(見えているカード)を掴む → 席Bの矢印の**根が
   そのカード自身**になること(手札のときはチップだった)
5. 席Aがどこにも重ねずに掴んだままにする → 線は出ず、根だけが点線で光ること
6. **矢印が出ている間も席Bが自分のカードをドラッグできること**
7. ログに矢印の行が1行も増えていないこと。Undo が矢印を戻さないこと
8. 席Aのタブを強制的に閉じる → 席Bの矢印が5秒以内に消えること

**D. 観戦(3-2)**

1. 3つ目のブラウザで観戦者として入る
2. ヘッダに「視点: 公開のみ」「下段: 席A」が出ること
3. **「視点」を押す** → 「視点: 全見え」に変わり、両席の手札・山札の中身が
   見えるようになること。ログの相手のカード名も出るようになること
4. もう一度押すと公開のみへ戻り、**中身が消える**こと
5. **「上下反転」を押す** → 上下が入れ替わり、ボタンが「下段: 席B」になること。
   右列のパイルも席Bのものに変わること
6. 反転したまま「席に着く」で空席へ座る → **自席が下に戻る**こと
7. 観戦中はドラッグしても何も起きないこと(21b の回帰)

**E. 先攻決め(E4)**

1. 対戦部屋のヘッダ「先攻決め」を押す
2. ログに「先攻選択権の判定: 席A 5 / 席B 2 → 席A が先攻・後攻を選ぶ」が
   **両方の画面に同じ内容で**出ること
3. 盤面が一切変わらないこと。Undo で戻らないこと
4. 何度押しても引き分けの行が出ないこと
5. 観戦者のヘッダには「先攻決め」が出ないこと(対戦部屋でも席が無ければ
   サーバが弾くが、そもそもボタンは全公開部屋で隠れる)

## 4. 理解確認 Q&A

**Q1. 相手上段の並べ替えは見た目の好みの話ではないのか。なぜ矢印より先にやる必要があるのか。**

A. 矢印が「ゾーン → 画面上の要素」の対応で描かれるからである。20c までの相手上段には
**手札とマナに対応する要素が無かった**。要素が無いゾーンは矢印の端点にできないので、
「相手が手札から場へ出した」という最も基本的な矢印が描けない。
4章は結果として見た目を整えているが、7-1 が明示しているとおり
「全ゾーンがアンカーを持つ」という**性質の保証**が本体である。
だから 1 → 3 の順にしか実装できない。

**Q2. 相手の山札の中身が見えないのは分かる。ではなぜ枚数は出すのか。それも情報では。**

A. 3-3 が枚数を公開情報と定めているからである。隠すべきなのは**何のカードか**であって
**何枚あるか**ではない。現実のカードゲームでも相手の山札の厚みは見えている。
むしろ 20c までのように 0 と表示するほうが**嘘**であり、
「隠す」ではなく「誤った情報を出す」になってしまっていた(21b 1-4 で直した)。
21c はその値を出す場所を、チップと簡略画像として画面に用意した。

**Q3. 「非公開」の判定を、なぜ「対戦部屋かつ相手席か」で書かないのか。そのほうが読みやすい。**

A. 公開範囲の定義がクライアントにも書かれることになるからである。
実際の条件は「対戦部屋 かつ 相手席」だけではない。公開のみ視点の観戦者にとっては
**両席とも**非公開であり、全見え観戦者にとってはどちらも公開である。
条件を書き下すとサーバの `ManualViewpoint.canSeeZone` を移植することになり、
片方を直したときにもう片方がずれる。
21a が「公開範囲の判定を2箇所に書かない」と決めたのはこの型の事故を防ぐためで、
`zones` にキーがあるかを見るだけなら**サーバが出した結論をそのまま使っている**ことになる。

**Q4. 上下反転をプレイヤーにも許してよいのでは。どうせ表示だけなのだから。**

A. 表示だけだからこそ危ない。反転すると**自分の手札が上段に、相手の場が下段に**出る。
その状態でカードを「下へ」ドラッグすると、体感では自分の場だが実際は相手の場である。
送信ペイロードは実席のまま正しく飛ぶので、アプリは何も間違えない。
間違えるのは人間のほうであり、しかも**アプリから見れば正常な操作**なので警告も出ない。
3-1 が「プレイヤーは常に自席=下・切替UIなし」と決めているのはこのためであり、
観戦者は操作しないので同じ危険が無い。

**Q5. 矢印の送信でゾーンをクライアントが宣言しないのはなぜか。掴んでいるのは自分なのだから知っているはずだ。**

A. 知っているが、**知っていることと正直に申告することは別**だからである。
宣言を信じる設計だと、細工したクライアントが「実際は手札にあるカードを、
場にあると偽って矢印の根にする」ことができる。受信側には
「相手が手札の何かを掴んだ」以上の情報が渡ってしまう。
サーバは `instanceId` から所在を引き直せるのだから、引き直すのが正しい。
外部から来るデータはすべて検証する(設計判断27)。

**Q6. 矢印をログに残せば「相手が何を狙っていたか」の記録になって面白いのでは。**

A. それは「起きたこと」ではない。途中で手を離せば何も起きていないし、
迷って3つのゾーンの上を通ればそれも全部記録される。
ログの価値は**盤面の変化と1対1で対応していること**にあり、
起きなかった操作が混ざると、後から読んで何が起きたのか復元できなくなる。
7-2 が「ログ・Undo・履歴に一切残さない揮発メッセージ」と明記しているのはこのためである。

**Q7. 検証ハーネスの `box-sizing` の件は、これまでどうして問題にならなかったのか。**

A. **寸法を検証項目にしていなかったからである。** 20c までの高さの検証は
「盤面全体が900px級に収まる」「センターラインが約130px」のように**余裕のある上限**で
見ていたため、padding と border のぶんズレていても通っていた。
21c で初めて「148px以内」という**8pxしか余裕の無い制約**を測ったところ、
ハーネスが 159px を返して落ちた。実物は 140px である。
★教訓は 20c と同じで、**ハーネスは本物に似ているほど役に立つが、
似ているだけでは足りない**。そして「どこが似ていないか」は、
厳しい検証項目を書いて初めて分かる。

**Q8. 先攻決めでサーバがダイスを振るのは「判断を実装しない」方針に反しないか。**

A. 反しない。振っているのはダイスであって、裁定ではない。
アプリは出目の高い側が先攻を「選べる」と記録するだけで、
先攻を設定することもターンを進めることもしない。総合ルール 2-5 の手順のうち
**人間が手でやると公平性を担保できない部分**(乱数)だけを引き受けている。
山札のシャッフルをサーバがやっているのと同じ位置づけであり、
ウェポンの付け替えのような「アプリが行き先を決める」例外を増やしたわけではない。
