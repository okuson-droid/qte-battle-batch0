## 1. 設計根拠★

### 1-1. 「見えるか」の判定を1つに集約した(`ManualViewpoint`)

情報保護が必要な経路は3つある。盤面ビュー・ログのマスク・矢印の起点フィルタである。
これらが別々の条件式を持つと、いずれ一方だけが更新され、
**「盤面からは隠したのにログには名前が出る」**という形で漏れる。

そこで公開範囲の宣言を `ManualZone.contentsPublic` の1つに置き、
判定を `ManualViewpoint.canSeeZone(ownerSeat, zone)` の1メソッドに集約した。
3経路すべてがこれを通る。

これは 20b の `sharedZones` と `copy()` で学んだのと同じ形の対策である。
**「2箇所に書いたものは必ずズレる」**を前提に、書く場所を1つに減らす。

### 1-2. 非公開ゾーンは「送らない」— 隠すのではなく届かせない

3-3 の「枚数のみ」は3通りに実装できた。

| 方式 | 問題 |
|---|---|
| 中身を送り、クライアントで隠す | 拡大画像・帯・検索・DevTools のどれか1つで漏れる |
| 裏向きのスタブを枚数ぶん送る | 情報量は「枚数のみ」と同じなのに構造だけ複雑になる |
| **カードを一切載せず枚数だけ送る** | 漏れる経路が原理的に存在しない |

3つ目を採った。**届かないものは漏れない**という性質だけが、
画面の経路が何本あるかに依存せずに成立する。
これは設計判断9「盤面配信はプレイヤーごとにフィルタした DTO で行う」の完成形である。

副作用として、`zones` から**キーごと消える**という表現を選ぶことになった。
「空配列を送る」ではなくキーを作らないのは、空配列だと
「本当に0枚」と「見えない」が区別できないためである。枚数は `counts` が別に持つ。

### 1-3. マナの特例をビルダーにだけ置いた

マナは表向きと裏向きが混在し、**表向きのカードは相手にも見えている**。
これを `canSeeZone` が「MANA だけ true」を返す形で実装すると、
同じメソッドを使うログのマスクまで MANA を公開扱いにしてしまい、
裏向きのマナに対する操作でカード名が漏れる。

したがって `ManualZone.MANA.contentsPublic` は **false** のままにし、
「表向きカードの配列 + 裏向きの枚数」という組み立ては
`ManualViewBuilder` の1箇所だけが知る。判定の共有と特例の局所化は両立する。

### 1-4. ログを文字列から構造化イベントへ(`ManualLogEvent`)

20c までのログは「操作した時点で組み立てた1本の文字列」だった。
対戦部屋では同じ行が閲覧者によって違って見えなければならない(5-2)。
文字列のままでは、後から名前だけを抜くことができない。
抜けるようにするには「名前が文字列のどこに埋まっているか」を復元することになり、必ず破綻する。

そこで行の**意味**を保持し、配信とダウンロードの瞬間に文字列へ変換する形にした。

**★マスク規則は1枚ごとに評価する。**
`ManualLogCard` が名前だけでなく**所在**も持っているのはそのためである。
1回の操作に手札の1枚と場の1枚が混ざることは普通に起きる
(2枚まとめて墓地へ送る等)。所在をイベント単位で1つしか持たないと、
そのとき「全部隠す(情報が失われる)」か「全部見せる(手札が漏れる)」しか選べない。

**★配信とダウンロードは同じ `ManualLogRenderer` を通る**(設計書 10章)。
片方だけを構造化すると「ダウンロードだけ完全版」という裏口が残る。
対戦部屋のログ書出は `occupantId` を必須にした。
誰として書き出すのか分からないまま完全ログを返すことが、まさにその裏口だからである。

### 1-5. 権限層は「判断」ではない

設計書16 5-1 は「手動モードで判断を実装しない」と定める。
権限層はこれに反しないのかを最初に整理した。

- コスト・召喚時効果・攻撃可否・勝敗 → **判断**。実装しない(今も切ってある)
- 相手の手札を勝手に動かせない → **判断ではない**。対戦が成立するための前提である

同じ理由で視点フィルタも 5-1 の外に置く。
どちらも「情報保護と盤面同一性の保証」であり、アプリが人間の代わりに
**ゲームの選択をしている**わけではない。

ウェポンの付け替え(20b)は依然として唯一の例外であり、21a で増やしていない。

### 1-6. `ManualActor` を全操作の引数にした理由

権限判定だけなら入口(`ManualWsController`)で済ませる手もあった。採らなかった理由は2つある。

1. **権限は操作の中身と対で決まる。** 「このカードは自席のものか」は
   カードを盤面から引いて初めて分かる。入口で判定すると、入口が
   `ManualBoardIndex` を引き直すことになり、操作を1つ足すたびに
   入口の分岐にも条件を書き足すことになる。
2. **actor はログにも要る。** `ManualLogEvent.actorSeat` は「誰が押したか」であり、
   対象の席とは別物である。相手の場へ自分のカードを落とす操作(6-1 で許可)では、
   対象の席は相手だが押したのは自分である。権限を切っても actor は必要になる。

つまり actor はどのみち必要であり、引数を1つ増やす代わりに
判定が操作の隣に置ける。

### 1-7. 判定は理由を返し、例外は投げない(設計判断34 の型)

`ManualPermissions` の各メソッドは「拒否する理由」を返し、許可なら null を返す。
例外化は `require()` が行う。

これにより**ビューが同じ判定を呼べる**。
`ManualGameView.canUndo` は `ManualPermissions.denyUndo(actor, room) == null` であり、
ボタンの活性と実際の可否が同じ関数を通る。表示と検証がズレる余地が構造的に無い。
光文明で `RuleGuards` に対して行ったのと同じ形である。

### 1-8. 席を持つのは在室者、検査するのは部屋

席の対応は `ManualOccupant.seatId` が持ち、部屋は「二重着席させない」検査だけを行う。
部屋側に `seatA / seatB` の配列を持たせなかったのは、
在室者と席の対応が2箇所に散ると、入室・退室・切断・着席・離席の
5つの経路すべてで同期が要るためである。

**役割(`ManualOccupantRole`)も席から導く形に変えた。**
役割をフィールドとして別に持つと「役割は PLAYER なのに席が無い人」が生まれうる。
導出なら食い違いようがない。

### 1-9. Undo の深さを部屋の種類から決めた

| 部屋 | 深さ | Redo |
|---|---|---|
| 全公開 | 200 | あり |
| 対戦 | 1 | なし |

対戦で1段に絞るのは容量の都合ではない。
**相手の見ている盤面が何手も巻き戻ると、何が起きたのか追えなくなる。**
Redo を切るのも同じ理由で、やり直したければ手で操作し直す。

「直前の操作をした席だけが戻せる」の判定に必要な情報は履歴の中にしか無いため、
`ManualHistory` はスナップショットと**操作した席**を対にして積む。

### 1-10. 矢印は論理アンカーで送る(画素座標を中継しない)

ウィンドウ幅・カードの伸縮(20c)・上下反転(3-1/3-2)で座標系は閲覧者ごとに違う。
座標を送れば、送った側では正しく受け取った側では見当違いの位置を指す。
代わりに「ドラッグ元のゾーン+カード」と「ホバー中のドロップ先ゾーン」を送る。

**★起点のゾーンはクライアントの申告ではなく instanceId から引き直す**
(設計判断27「外部から来るデータはすべて検証する」)。
申告を信じると「実際は手札にあるカードを場にあると偽る」ことができ、
受信側へ余計な情報が渡る余地が生まれる。

**★`dispatch` を通さない。** 矢印はドラッグ中に何度も飛ぶため、
そのたびに盤面を全員へ配ると通信量が跳ね上がる。
ログにも履歴にも Undo にも触れない揮発経路として独立させた。

### 1-11. 無人部屋の掃除(19a の積み残し)

`ManualRoomManager#removeRoom` は 19a で用意されたまま呼び出し元が無かった。
**部屋一覧を作る以上、無人の死に部屋が並ぶのは受け入れられない**ため、
機能を足したこのバッチが後始末の責任も引き受けた。

判定は「在室者0(切断猶予中も含めて0)が5分続いたか」である。
順序が重要で、**先に猶予切れの席を空けてから**無人判定を行う。
逆にすると、最後の1人の猶予が切れた回で無人と判定されず、さらに5分待つことになる。

削除そのものはロックの外で行う。台帳(`ConcurrentHashMap`)を触る処理を
部屋のロックの中に入れると、2つのロックの順序を気にすることになる。

### 1-12. 後方互換 — 20c までの画面がそのまま動く

21a はサーバだけを変えるため、既存の画面が壊れないことを条件にした。

- `POST /manual/api/rooms` に属性を送らなければ従来の全公開部屋
- `POST .../occupants` に席を送らなければ、全公開部屋では空席へ自動着席
- 全公開部屋では視点フィルタも権限も効かない
- 非公開ゾーンの欠落は `seat.zones[Z] || []` が空配列として吸収する
- ログ書出は全公開部屋なら `occupantId` 省略可

**★1箇所だけ 21c で必ず直すこと**: `manual-battle.html` のログ書出リンクに
`occupantId` が付いていない。対戦部屋では 400 になる
(対戦部屋は 21b までUIから作れないため、現時点で実害は無い)。

## 2. 実装時に踏んだ / 避けた罠

- **`placedBySeat` を `copy()` に入れる**(設計書 10章)。テストで固定した
  (`共有ゾーンの所有はUndoでも巻き戻る`)。
- **共有ゾーンから出るときのクリアを忘れない。** set と clear は必ず対で書く。
  忘れると手札へ戻したカードに所有が残り、次に別の席が使えなくなる。
  所有は**素材(進化スタックの下段)にも**付ける。付けないと束から1枚抜いたときに
  所有の無いカードが生まれる。
- **`seatId == null` 問題**(ハンドオフ3章)。新設した `ManualLogPlace` /
  `ManualLogCard` / `ManualViewpoint` はいずれも席が null になりうる前提で書いた。
- **ログの `ManualLogCard` は `detach` する前に作る。** 外した後では所在が引けない。
- **`ManualLogEvent.plain` に非公開のカード名を混ぜない。** `ManualLogKind` の
  `plain` フラグと `ManualLogEvent.plain()` の検査で、種別を取り違えたら例外になるようにした。

## 4. 理解確認 Q&A

**Q1. 相手の手札を隠すのに、なぜ「送ってクライアントで隠す」ではダメなのか。**

A. 隠す経路を全部塞ぐ必要が出るからである。拡大画像・帯・カード検索・
ブラウザの開発者ツール — どれか1つ塞ぎ忘れれば漏れる。しかも塞ぎ忘れは
画面上まったく正常に見えるため、気づけない。
**サーバが送らなければ、経路が何本あっても漏れない。**
守るべき境界を1本に減らすのが情報保護の基本形である。

**Q2. ログの行そのものを相手に配るのはなぜか。自分のぶんだけにすればマスクは要らないのに。**

A. 相手の操作が一切見えないと対戦が成立しないからである。
「相手が手札から1枚場に出した」は、盤面を見れば分かる公開情報でもある。
隠すべきなのは**カード名**であって、**何かが起きたという事実**ではない。
ログを自席ぶんに絞ると、後からログを読み返して試合を再現できなくなる。
ログはこのモードの成果物である(設計書 5-5)。

**Q3. `placedBySeat` を occupantId ではなく席で持つのはなぜか。**

A. 切断して入り直した人、席を立って座り直した人が、自分の置いたカードを
動かせなくなるからである。occupantId は接続のたびに変わりうるが、
席は試合を通じて同じ意味を持つ。**権利は席に属する**というのが 6-2 の確定事項である。

**Q4. 権限層を入れたのに、なぜ「相手のゾーンへ落とす」は許しているのか。**

A. 代行操作が対戦で普通に起きるからである。「相手の場にミニオンを出す」
「相手の墓地へ送る」はカード効果の解決として日常的に必要になる。
禁じているのは**相手のカードを動かす・書き換える**ことだけであり、
これは「相手に代行してもらう」(設計書16 11-3)の一般化である。
落とす方向は非対称に許してよい。

**Q5. Undo が対戦部屋で1段しか無いのはケチっているのか。**

A. 逆である。深く戻せるほうが**相手にとって危険**だからである。
一人回しでは戻す相手が自分しかいないので200手でよいが、
対戦では相手の見ている盤面が勝手に何手も巻き戻ることになる。
「直前の1手を、やった本人が取り消す」までが、相手が追える限界である。

**Q6. 矢印で画素座標を送らないのはなぜか。そのほうが簡単そうに見えるが。**

A. 座標系が閲覧者ごとに違うからである。ウィンドウ幅が違えばカードの大きさが違い(20c)、
自席が下に来るよう上下が反転している場合もある(3-1)。
送り手の画面で「ここ」だった座標は、受け手の画面では別の場所を指す。
**ゾーンという論理的な位置**を送れば、受け手は自分のレイアウト上の
該当要素を自分で見つけられる。相手上段の再構成(4章)は、
全ゾーンが全閲覧者の画面に何らかのアンカーを持つことを保証している。

**Q7. `ManualViewpoint.canSeeZone` を MANA だけ true にしなかったのはなぜか。**

A. 同じメソッドをログのマスクも使っているからである。
MANA を公開扱いにすると、裏向きのマナを裏返す・墓地へ送るといった操作で
カード名がログに出てしまう。マナが「表向きだけ見える」という特例は、
盤面ビューを組み立てる `ManualViewBuilder` の1箇所だけが知っていればよい。
**共有すべき判定と、局所化すべき特例は別のもの**である。

## 5. 21b への申し送り

21b(b系・入口の画面)で作るもの:

1. **ロビー** — 部屋一覧(`GET /manual/api/rooms`)と部屋作成フォーム(1-3)。
   手動の更新ボタン。鍵つき部屋は `roomId` が null で返るので、
   ID入力欄からの直接入室で入る。
2. **席選択画面** — 盤面の前に必ず通す(2-1)。
   埋まっている席はボタン無効化 + 在席者名(一覧 API の `seatAName` / `seatBName`)。
   切断中は「切断中」と表示(ビューの `disconnectSecondsLeft`)。
3. **在室者リストのポップオーバー**(2-3)。ビューの `occupants` に
   `seatId` / `spectatorView` / `disconnectSecondsLeft` が入っている。
4. **席を立つ / 席に着く** — `/app/manual/{roomId}/seat`。
5. **自席=下の描画**(3-1)。ビューの `viewerSeat` を見る。
   ★`cardLocation` / `registerDropTarget` に渡す席は**実席のまま**保つこと(10章)。

21c(b系・盤面の仕上げ)で作るもの:

1. 相手上段の再構成(4章)
2. 非公開チップのフィードバック(3-5)。ビューの `counts` を使う
3. 矢印の描画(7章)。`type: "CUE"` の受信と、ゾーン→アンカー要素の対応表
4. 観戦トグル(全見え/公開のみ + 上下反転)
5. **★ログ書出リンクに `occupantId` を付ける**(1-12 の積み残し)
6. `verify/` の拡張(9章の検証)
