## 1. ★★★着手時に伺った4件(裁定355〜358)

### ★★★裁定355 —— 通常モードの演出は、ゾーン間の移動を「枚数の対 + カード名の一致」で語る

**問**: 「どこからどこへ」を何を根拠に語らせるか。

**答**: **枚数の増減の対を突き合わせ、カード名が照らせたときだけカードの面を飛ばす。**
照らせなければ裏面を飛ばす。★**サーバには1行も触らない。**

★★<b>マスターは最初「サーバに同一性を導入」を選んだ。</b>
★実寸(読む側194・動かす側77・試験503箇所)と、
<b>「77箇所のうち1箇所で同一性を落としても951件は1件も赤くならない」</b>という
測られていない一族の指摘を出したうえで、順番を変える判断になった
(設計解説 0-6 に全文がある)。

- **80(今回)**: 枚数の対で演出を乗せる。★<b>画面が動くようになる。</b>
- **81 以降**: サーバに同一性を入れる。★<b>画面は1ピクセルも変わらないが、
  80 が「結べない」で逃げた場面が語れるようになる。</b>

★★★<b>これは妥協ではない</b> —— マスターが名指しした**ドローと破壊は、
同一性が無くても完全に観測できる**(設計解説 0-6 の表)。
場のミニオンはもともと `instanceId` を持っているからである。

> ★<b>「同一性が要る」と「同一性が在ると楽」は別である。</b>
> 要るかどうかは、<b>見せたいものごとに違う</b>。

### ★★★裁定356 —— 結べなかった出口は「消滅」、結べなかった入口は「出現」として、その場で語る

**問**: 対応が一意に決まらないとき(例: 場から1体消えて、墓地と消滅が両方 +1)どうするか。

**答**: **移動として結ばない。**出口は<b>その場で消える</b>、入口は<b>その場で現れる</b>と描く。

★<b>「何も出さない」ではない。</b>「1枚が場から消えた」は<b>観測できている</b> ——
観測できていないのは<b>行き先だけ</b>である。
★★<b>観測できたところまでを語り、その先は黙る</b>のが正しい
(手動モードの `vanished` / `appeared` とまったく同じ形である)。

★★★**ただし山札だけは例外で、出現も消滅も出さない**(設計解説 0-4)。
山札は中身が1枚も届かない<b>「窓」</b>であり、
そこで出現・消滅を描くと<b>ドローのたびに山札の上で意味の無いフェードが出る</b>。
★手動モードの `fxWindowedZones` が同じ理由で同じことをしている。

> ★<b>山札は「移動の端」にはなれるが、「その場で消えた・現れた」の主語にはなれない。</b>

### ★★★裁定357 —— 80 が置く演出は9種。儀式(配り・マリガン・ダイス・シャッフル)は作らない

**問**: 今回の範囲はどこまでか。

**答**: **移動系 + 状態系の9種**(`move` / `draw` / `vanish` / `appear` / `lp` /
`tap` / `flip` / `sink` / `declare`)。★**儀式の4種は作らない。**

★★<b>作らない理由は「大きいから」ではなく「材料が無いから」である。</b>
手動モードの儀式は **Batch 38 がサーバに `ManualLogRite` を足して初めて描けた**。
通常モードのサーバには相当するものが1つも無く、
<b>差分からは「配られた」と「引いた」を区別できない</b>。
★<b>区別できないものに名前を付けるのは、観測ではなく判断である。</b>

★**マリガンの節目だけは 62 から音が鳴っている**(`fxDiff` が `mulligan` を採っている)——
80 はそこに<b>見た目を足さない</b>。飛翔を描くには「何枚戻して何枚引いたか」が要り、
それは差分からは出てこない。

### ★★★裁定358 —— 演出の時間は手動モードより長い。設定UIは作らない

**問**: 速さと設定をどうするか。

**答**: **手動モードより長くする。**設定UIは作らず、
`prefers-reduced-motion` だけで止める(手動モードと同じ形)。

| | 手動モード | ★通常モード(80) |
|---|---|---|
| 移動 | 220ms | ★**340ms** |
| ドロー | 260ms | ★**380ms** |
| 消滅・出現 | 180ms | ★**260ms** |

★★<b>これはマスターの不満への直接の答えである</b> ——
「一瞬で行われ、どのゾーンからどのゾーンに動いたのかもわかりにくい」。
★<b>手動モードは人が1手ずつ動かすので、動いた本人は何をしたか知っている。</b>
★★<b>通常モードはサーバが解決するので、画面を見ている人は「何が起きたか」を
演出からしか読めない</b> —— <b>だから同じ値ではいけない</b>。

★★★<b>値を揃えないことに番人を置いた</b>(裁定54・設計判断38 の警告)——
「一致が要求ではなく偶然なら、見張ってはいけない」の逆で、
<b>ここは「揃っていないこと」が要求である</b>。
★<b>両モードの定数が同じ値になったら赤くなる</b>(verify 80-x)。

★**設定UIを作らないのは、手動モードとの非対称を作らないためである。**
★★<b>作るなら両モードに作る</b>(裁定111・289 の一族)——
片方だけに作れば、次に音を触る人が<b>片方だけ直す</b>。

## 2. ★80 が実装で決めたこと(裁定を仰がなかったもの)

読みが1つに定まったので、作業を止めずに実装した(リファレンス 1-7 の流儀)。
**間違っていたら戻す。**

| 決めたこと | 根拠 |
|---|---|
| ★★★**取り付け点は `onMessage` の1箇所である** | ★62 が音でそう決めた(裁定287)。★★<b>`render()` は画面の操作のたびにも走る</b>(15箇所)ので、あそこで差分を採ると「配信」と「再描画」を区別できない。★演出も音と<b>同じ列</b>を読む —— <b>発火点を1つも増やさない</b>(裁定68) |
| ★★★**旧位置は `render()` の<b>前</b>に読む** | 描き直したあとでは、出発点の要素はもう存在しない。★手動モードの相分離(29)と同じ形である |
| ★★**ゴーストは通常モードの `cardFace()` で作る** | ★<b>見た目の正は1箇所</b>(25 以来の方針)。手動モードの `.mcard` を持ち込むと、<b>カードフェイスの実装が3つ</b>になる(候補 C は2つのままである) |
| ★★**アンカーは描画関数がその場で登録する** | ★手動モードの `registerZoneAnchor` と同じ形。<b>別途セレクタの一覧を持つと、レイアウトを変えたときに片方だけ直して壊れる</b>。★★とくに<b>パイルは4枚とも同じクラス</b>(`.auto-pile`)なので、添字で引くと並び順を変えた日に黙ってずれる |
| ★★★**上限を超えた配信は何も出さない** | ★手動モードの `FX_BULK_LIMIT` と同じ判断。<b>1手で盤面が大きく動いた配信は演出では語れない</b>。★★62 の音は既に `SFX_DIFF_LIMIT`(8)で同じことをしている —— <b>値を共有する</b> |
| ★★**LP・決着・マリガンは 62 の採り方を1文字も変えない** | ★<b>音が鳴らなくなる</b>。62 の `fxDiffSeat` は音のために書かれたが、<b>それは演出の材料でもある</b>と 62 自身が書いている(裁定287) |
| ★★★**マナの表裏(`flip`)は「同じ位置で `faceUp` が変わった」で採る** | ★マナには識別子が無いので、<b>位置で追うしかない</b>。★★<b>枚数が変わった配信では採らない</b> —— 位置がずれるので、同じ位置の比較が意味を失う(<b>裏返っていないマナを「裏返った」と描く</b>) |
| ★★**進化(`sink`)は `underCardIds` が増えたことで採る** | ★場は `instanceId` を持つので、<b>居場所が変わっていないミニオンだけ</b>を見る(手動モード 32b と同じ切り分け) |
| ★**版数を上げる** | ★★★<b>`battle.js` と `battle.css` を触った</b>ので上げる(7-5)。★`battle.css` は5枚のテンプレートすべてで上げる |

## 3. ★次のバッチへの申し送り

### 3-1. ★★★サーバの同一性は、入れるなら「番人を77本」のバッチである

★設計解説 0-6 に実寸がある。★★<b>数え直さずに再開できるように書き残した</b>(78 の教訓)。

★★★<b>いちばん大事なのは「既存の951件が1件も赤くならない」という性質である。</b>
同一性を入れるバッチで最初に置くべきは実装ではなく、
<b>同一性が保たれていることを測る番人</b>である。

### 3-2. ★★一時公開ゾーンは、ビューに載っているのに画面に1度も描かれていない

`revealedCards` は `GameViewBuilder` が**両席ぶん**作って配信しているが、
★`battle.js` はこの語を**1度も書いていない**(実測 0件)。

★★<b>44 から在って誰も気づいていなかった穴である</b> ——
80 は<b>「届いているか」を先に見た</b>から見つけた(76 の教訓)。
★80 は塞がない(演出の工事ではない)。★★<b>塞ぐ日には演出のアンカーも一緒に増える</b>
(母集団C の C9 が○になる)。

### 3-3. ★★儀式を描きたくなったら、先にサーバへ観測できる形を足すこと

★手動モードは Batch 38 で `ManualLogRite` を足した。★★<b>順番を逆にしない</b> ——
差分から「配られた」と「引いた」を区別しようとすると、
<b>クライアントに判断が入る</b>(38 が避けたことそのものである)。

### 3-4. ★★★サーバが null を入れるのは実装の都合であって、規則ではない

★実装で最初に踏んだ穴である(設計解説 2-2)。
「中身が届いているか」を **`hand` が null かどうか**で見分けていた ——
サーバは相手の手札に null を入れるので、それで合っていると思った。

★★<b>置いた番人が、その日のうちに赤くなった</b>(verify 80-6)。
検証のフィクスチャは相手席にも `hand: []` を入れており、**null では来ない**。

> ★<b>空配列で来ても、一部だけ来ても、
> 枚数と合わなければ名前では語れないのは同じである。</b>
> ★★正しい規則は<b>「枚数 &gt; 届いた配列の長さ なら窓である」</b> ——
> <b>手動モードの `fxWindowedZones` が最初から持っていた語彙</b>である。

★★★<b>次にビューの欄を読むときは、「サーバが何を入れるか」ではなく
「その欄が何を意味するか」で書くこと</b>(67 の教訓・**写し**の、ビューの側の顔)。

### 3-5. ★★★守りが二重にあると、番人は片方しか見ていないことがある

★壊し検証の軸18 が教えた(設計解説 6-1)。
`render()` へ `fxSpawn()` を足しても、**振る舞いを見る番人は緑のままだった** ——
`pendingFx` を**1回で使い切る**ので、2度目以降は何も出ないからである。

> ★<b>守りが二重なのは良いことである。番人が片方しか見ていないのは別の話である。</b>
> ★★<b>振る舞いで捕まらない性質は、構造で測ってよい</b> ——
> 80 は「演出を起こす口は1つだけである」をソースの行数で測る番人を足した。
> <b>70 の教訓(クラスの数を数える検証では見つからない)の、ちょうど裏返しである。</b>

### 3-6. ★演出の時間は「揃っていないこと」が要求である

★裁定358。★★<b>両モードの値が同じになったら赤くなる番人を置いた。</b>
★<b>次に手動モードの時間を触る人は、この番人を読んでから触ること</b> ——
<b>手動モードを 340ms へ上げると、この番人が正しく赤くなる</b>。
