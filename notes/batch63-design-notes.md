## 0. 何が起きていたか

デッキメーカー(`/deck-maker`)で組んだデッキを通常モードのロビーで選ぶと、
ファイル選択欄の下に **「読み込み: (名前なし) / メイン NaN枚・禁忌8枚」** と出て、
[部屋を作成して入室] を押すと **「対応していないデッキファイル形式です(version=0)」** で
ロビーへ戻される。

原因は**カードIDでも構築ルールでもない**。46b で両モードのカードマスタは
`manual-cards.json` に統一されており、IDは完全に同じものである。
違っていたのは**ファイルの欄の名前**だけだった。

| 意味 | デッキメーカー(手動モード) | 62 までの通常モード |
|---|---|---|
| 形式の宣言 | `format: "taboo-elemental-deck"` / `version: 2` | `formatVersion: 1` |
| デッキ名 | `deckName` | `name` |
| リーダー | `leader: { cardId }` | `leaderCardId` |
| メインの枚数 | `main: [{ cardId, qty }]` | `main: [{ cardId, count }]` |
| 禁忌 | `taboo: [{ cardId }]` | `taboo: ["cardId", …]` |

62 までのロビーは `ObjectMapper.readValue(deckJson, DeckDefinition.class)` で
**ファイルを内部表現の record へ直接流し込んでいた**。`DeckDefinition` に
`@JsonIgnoreProperties(ignoreUnknown = true)` が付いているので、
デッキメーカーのファイルも**例外を出さずに読めてしまう** ——
ただし `formatVersion` が無いので 0、`count` が無いので全行 0 枚、という
「読めたが空っぽ」のデッキになる。版数の検査がそこで止めていた、というのが顛末である。

★**「読めない」の正体が「別のものとして読めてしまう」だったことに注意する。**
例外が出ていたなら 62 までに気づけた。

| 問い | 答え |
|---|---|
| 直し方 | **デッキメーカーの形式に一本化する**(サーバ側を対応させるだけ、ではなく) |
| `/deck-builder` | **退役させる** |
| 旧形式 | **完全に撤廃し、`decks/*.json` 12本は変換する** |
| 読み取りのコード | **規約を共有し、コードは複製する**(共通層へ切り出さない) |

★このうち最初の2つが効いている。「サーバが両方読めるようにする」で済ませると、
**形式は2つのまま**であり、デッキを組む場所も2つ残る ——
同じ規則を2箇所へ書き続けることになる(裁定163 の形)。

## 2. ★★ファイルの形と内部表現を分けた(裁定291)

```
62: デッキファイル ──(ObjectMapper)──> DeckDefinition ──> DeckValidator
63: デッキファイル ──(DeckFileReader)──> DeckDefinition ──> DeckValidator
```

見た目は1段増えただけだが、意味が変わっている。

- `DeckDefinition` から **`formatVersion` が消えた。**
  版番号は**ファイルの性質**であって、盤面へ渡すデッキの性質ではない。
- `DeckValidator` から**版数の検査が消えた。**
  あのクラスが見るのは総合ルール第1章(デッキ構築)だけになった。
- ★**62 までの構造は「読める形式が1つしかない」ことの原因そのものだった。**
  内部表現に版番号が生えていたのは、両者が同じものだったからである。

### 2-1. `DeckFileReader` が受け付ける形

デッキメーカーが書くものをそのまま受ける。加えて過渡期の揺れを2つだけ許す
(**手動モードの `ManualDeckImporter.importJson` と同じ寛容さ**である。裁定292)。

- `leader: {cardId}` の代わりに `leaderId` 文字列でもよい
- `taboo` の要素はオブジェクトでもID文字列でもよい
- `qty` が無ければ1枚
- 知らない欄(`exportedAt` / `mainCiv` / 各行の `name`)は黙って無視する

**違うのは読み方ではなく裁き方である。** 手動モードは構築ルール違反を警告に留めて遊ばせ、
通常モードは `DeckValidator` が拒否する —— ルールを強制するモードだからである。

### 2-2. ★version 1 は受け付けない(裁定294)

`taboo-elemental-deck` の version 1 は Verβ 由来の**カード名で書かれた**形式である。
手動モードは検証の道具なので読むが、**ルールを強制する側が名前で解決してはならない** ——
表記ゆれ1文字で別のカードになる(裁定171・173 と同じ筋)。

### 2-3. ★★★読み取りは裁かない(裁定293)

`readMain` は**同じカードIDの行をまとめない**。まとめると
`DeckValidator` の「メインデッキに同じカードの行が重複しています」が
**誰にも当たらなくなる**。

> 検証を1箇所に集める設計は、**その1箇所へ壊れたものが届くこと**を前提にしている。
> 読み取りが黙って直すと、集めた意味が消える。

枚数の上限も総数もこのクラスは見ない。見るのは**行数の上限(200)だけ**であり、
これは構築ルールではなく「外から来るデータへの防波堤」(設計判断27)である。

### 2-4. ★読めなかった理由をそのまま返す

62 までの `parseDeck` は例外を握りつぶして
「デッキファイルの形式が正しくありません」の一言にしていた。
**何を直せばよいのかが分からない。** 63 は読み取りの理由をそのまま画面へ出す。

```
デッキファイルの形式が違います(format: taboo-elemental-deck のみ)。デッキメーカーで保存し直してください
```

## 3. ★★退役は3つを同時に消す(裁定295)

`/deck-builder` の退役で消したもの:

| 種類 | 実体 |
|---|---|
| 経路 | `LobbyController` の `@GetMapping("/deck-builder")` |
| ファイル | `templates/deck-builder.html` / `static/js/deck-builder.js` |
| 案内 | `lobby.html` のリンク(→ `/deck-maker` へ) |

★**どれか1つでも残ると「消したつもり」になる。**
テンプレートだけ消せば 500、マッピングだけ消せばリンクが 404 へ案内し続け、
配信口だけ残れば次に読む人がそれを現役の正だと思う。

`CardApiController` を道連れにしたのは、**この画面のためだけに在った**からである
(javadoc も「デッキビルダー用のカードマスタ提供API」と書いてある)。

書いていた懸念は、これで**構造的に消えた。**

## 4. ★★★測るときは実物を材料にする(裁定296)

63 でいちばん大事な番人は、**デッキメーカーが実際に書き出したファイル**を材料にしている。

### 4-1. verify 63-1: 欄の名前の突き合わせ

1. デッキメーカーのハーネスで 40/8 のデッキを読み込み、[デッキ保存] を押す
2. `URL.createObjectURL` への張り込みで**書き出された JSON の中身**を控える(40 の spy を拡張)
3. `DeckFileReader.java` を読み、**`path("…")` の実引数**を全部拾う
4. 拾った欄名が、控えた JSON の欄(トップ階層 + `leader` + `main[0]` + `taboo[0]`)に
   全部あるかを見る

★**期待値の JSON を verify に書くと、それが3つ目の形式になる**(裁定110 の趣旨)。
★過渡期の別名 `leaderId` だけは、デッキメーカーが書かないので名指しで除いてある。

### 4-2. verify 63-3: ロビーの要約を実物に当てる

`lobby.html` の要約は `deckSummary(deck)` という**名前付きの関数**に切り出してある。
verify はその関数を**ソースから取り出してブラウザで実行し**、
デッキメーカーの実際の書き出しを **40/8 と数えられるか**を見る。

★ソースに `count` が無いことを走査で確かめる形にはしなかった(裁定131)。
★**その場に書いた式は取り出せない。**関数に切り出したのは検証のためである。

### 4-3. JUnit: 同じファイルを両モードが読む

`DeckFileReaderTest.同じデッキファイルを両モードが同じ中身として読む` が
**63 の本体**である。`decks/*.json` の12本を1本ずつ、

- 通常モード(`DeckFileReader` → `DeckValidator`)に通してメイン40・禁忌8
- 手動モード(`ManualDeckImporter.importJson`)に通してメイン40・禁忌8・未解決0
- 両者が**同じリーダーID**を指している

まで測る。★**片方だけを測っても「両方が読める」ことの証明にはならない。**

### 4-4. JUnit: 本物の入口

`LobbyPageTest` は **POST `/rooms` に実物のデッキファイルを載せて**部屋を作り、
リダイレクト先の盤面が 200 で返るところまで通す(裁定187・62 の教訓7)。
マスターが踏んだのはロビーのボタンであり、そこから通らなければ直ったとは言えない。

## 6. ★テンプレートのHTMLコメントは配信される(裁定297)

ロビーのリンクを差し替えるとき、素のHTMLコメントに
「`/deck-builder` は退役」と書いた。**その文字列がページに出て**、
「退役した画面へのリンクが残っていない」を測る `LobbyPageTest` が落ちた。

Thymeleaf の**パーサ水準コメント**(`<!--/*` … `*/-->`)にすると、
説明はソースに残り、配信されるHTMLからは消える。

★裁定114(注釈が番人を黙らせる)の裏返しである ——
**あちらは注釈が番人を通し、こちらは注釈が番人を落とした。**
どちらも「注釈は仕様の説明であって、判定に食わせる材料ではない」の別の顔である。

## 10. 理解確認 Q&A

**Q1. なぜ「サーバが両方の形式を読めるようにする」で済ませなかったのか。**
A. 形式が2つのまま残るからである。デッキを組む場所も2つ残り、
片方に機能を足すたびにもう片方との差が開く。
マスターの裁定は「一本化」であり、**正を1つにする**(設計判断28)の適用先が
データからファイル形式へ広がった、と読むのが正しい。

**Q2. 読み取りのコードを共通層へ切り出さなかったのはなぜか。**
A. 突合先のカードマスタの型が違う(`CardMaster` と `ManualCardMaster`)ためである。
共通化すると通常モードが手動モードの層に依存する。
**共有するのは「ファイルの欄の名前」という規約のほうであり**(裁定111 と同じ形)、
一致していることは verify 63-1 が両方から読んで突き合わせる(裁定110)。

**Q3. 読み取りで同じカードIDの行をまとめないのはなぜか。**
A. まとめると `DeckValidator` の重複検査が誰にも当たらなくなるからである。
検証を1箇所に集める設計は、**そこへ壊れたものが届くこと**を前提にしている。
★壊し検証のケース7・8 が、この2つが噛み合っていることを測っている。

**Q4. `/api/cards` まで消して大丈夫か。**
A. 使っていたのは `deck-builder.js` だけである(grep で確認済み)。
カードの正は `/manual/api/card-library` 1つになった。
★`LobbyPageTest` が 404 を測っているので、**うっかり復活させたら試験が落ちる。**
