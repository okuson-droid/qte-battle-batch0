# Batch 15a 設計解説 — Ver.0.4 の基盤4件と、13c実装の削除2件

対象: Ver.0.4 バランス調整で新しく必要になった仕組みの実装。カード効果の再登録(残り48枚)は 15b 以降で行う。
変更したファイルは Java 6ファイルのみであり、JavaScript・HTML・CSS・カード台帳は無変更である。

---

## ⚡ 結論チートシート

- **ウェポンの寿命**は状態1つ(`PlayerState.weaponAttackedThisTurn`)で足りた。破壊は
  `GameService.finishEndTurnCleanup` から `GameActions.destroyOwnWeapon` を呼ぶだけであり、
  禁忌の消滅は既存の `sendToTrashOrRestore` が自動で処理する。
- **フラグを落とす場所が設計の勘所**である。`GameActions.onWeaponLeftPlay` は破壊・付け替えの
  両方が必ず通る唯一の経路であり、ここで落とすことで「攻撃後に付け替えたら壊れない」という裁定が
  専用の判定を書かずに成立する。
- **ミニオンゾーン上限の横断改修は予想より小さかった。** 定数 `MAX_MINIONS` を直接読んでいたのは
  1箇所だけで、残る8箇所は `isMinionZoneFull()` を経由していた。したがって
  `PlayerState.getMinionZoneLimit()` を新設し `isMinionZoneFull()` の中身を差し替えるだけで、
  呼び出し側は1行も変えずに済んだ。
- **上限は保持せず、参照のたびにリーダーから算出する。** 常在能力は「その瞬間に評価する」という
  設計判断4と同じ扱いに揃えた。
- **ウェポンの新発火口は `TriggerType` に2種追加する形にした**(`ON_ALLY_MINION_ATTACK` /
  `ON_ALLY_MINION_ENTER`)。転記ノートが挙げていた「カードIDのswitch」案は採らなかった。理由は3章。
- **回復の計数は `damageLeader` の形に揃えた。** `healLeader` に発生源カードIDの引数を追加し、
  文明ごとの累計回復量を `EnumMap` で持つ。呼び出し10箇所すべてに発生源を配線した。
- **削除2件は完了。** 大地の巨頭(L011)の `leaderAbilities` 登録と、
  地脈の覚醒(0015)の `StatCalculator` の動的コスト分岐。
- **未確定のまま進めた判断が1件ある。** 回復量を「実際にLPが増えた分」で数えている(4章)。

## ★★★★ 1. ウェポンの寿命 — 状態をどこに置き、どこで消すか

### 1-1. 何が新しいか

Ver.0.4 の総則変更は次の一文である。

> ウェポンは攻撃したらそのターンの終わりに破壊される(禁忌の場合消滅する)

これは耐久度の概念ではない。「攻撃したか / していないか」の2値であり、しかも寿命が
そのターン限りなので、ターンをまたいで持ち越す必要がない。**したがって必要な状態は真偽値1つである。**
耐久値(int)を持たせるとターンをまたいだ減算・回復の管理が要るが、この仕様にはその要件がない。

### 1-2. 状態の置き場所

ウェポンには `MinionInstance` に相当する個体状態の器がない。ミニオンは場に出ると
`MinionInstance` へ昇格して残りHPや攻撃済み回数を持つが、ウェポンは `CardMaster`(不変データ)への
参照が `PlayerState.equippedWeapon` に入るだけである。

そこで、既に同じ理由でプレイヤー単位に置かれている値の隣に並べた。

| 値 | なぜプレイヤー単位か |
|---|---|
| `leaderAttacksUsedThisTurn` | リーダーの攻撃回数。ウェポンに器がない |
| `weaponAttackBonusThisTurn` | 暴風の双剣の加算。ウェポンに `StatModifier` を積めない |
| **`weaponAttackedThisTurn`(新規)** | 同上 |

「装備は1枚まで」というルールがあるため、プレイヤー単位で持っても曖昧さは生じない。

### 1-3. ★ 立てる場所と、落とす場所

**立てる場所**は `GameService.leaderAttack` の攻撃回数インクリメントの直後である。

```java
player.setLeaderAttacksUsedThisTurn(player.getLeaderAttacksUsedThisTurn() + 1);
player.setWeaponAttackedThisTurn(true);
```

判定層(`guards.leaderAttackDenial`)を通過した後であるため、弾かれた攻撃でフラグが立つことはない。
ミニオンの攻撃(`GameService.attack`)では立てない。「攻撃した」はリーダーの攻撃に限る、という
発注者確認済みの裁定どおりである。

**落とす場所がこの実装の設計判断の中心**である。素直に考えると、次の2つの裁定を満たす必要がある。

1. 攻撃したウェポンは、そのターンの終わりに破壊される
2. 攻撃した後に別のウェポンへ付け替えた場合、新しいウェポンは(攻撃していないため)壊れない

2番を素朴に実装しようとすると、「フラグが指しているのはどのウェポンか」を追跡したくなる。
攻撃したウェポンのカードIDを保持して、ターン終了時に装備中のウェポンと照合する、という発想である。
しかしこの方式は、同名のウェポンを付け替えた場合に誤って壊してしまう。

**実際には追跡は不要である。** `GameActions.onWeaponLeftPlay` は、ウェポンが場を離れる
すべての経路が必ず通る1箇所だからである(13aで詠唱の宝珠のために用意された choke point)。

```
destroyOwnWeapon(破壊)        ─┐
GameService.equipWeapon(付け替え) ─┴→ onWeaponLeftPlay
```

ここでフラグを落とせば、「フラグが立っている = 今装備しているウェポンが攻撃した」という不変条件が
常に保たれる。追跡も照合も要らず、2番の裁定は副作用として成立する。

> **★設計根拠。** 既存の choke point を見つけて相乗りできたのは、13a で
> 「ウェポンが場を離れる」経路が既に1本に束ねられていたからである。同じことを
> 束ねられていない状態でやると、`equipWeapon` と `destroyOwnWeapon` の両方に
> フラグ落としを書くことになり、3つ目の経路が増えたときに漏れる。

### 1-4. 破壊の実行

`GameService.finishEndTurnCleanup` の先頭に置いた。

```java
if (p.isWeaponAttackedThisTurn() && p.getEquippedWeapon() != null) {
    room.addLog("【%s】は攻撃したためターンの終わりに破壊されます".formatted(...));
    actions.destroyOwnWeapon(room, p);
}
```

**禁忌の場合の消滅は、ここでは一切書いていない。** `destroyOwnWeapon` が呼ぶ
`sendToTrashOrRestore` が「禁忌由来(消滅) > 【還元】 > 墓地」の優先順位を既に持っており、
`equippedWeaponFromTaboo` を見て消滅ゾーンへ送る。**破壊を呼びさえすれば消滅は自動でついてくる。**

`finishEndTurnCleanup` を選んだのは、これが `endTurn` 本体と、選択待ちが解決した後の
`advanceTurnIfPending` の両方から呼ばれる合流点だからである。ターンエンドトリガーが
割り込み選択を発生させた場合でも、掃除は必ずここを一度通る。

なお、この掃除は両プレイヤーに対して回る。相手側のフラグが立つことは構造上ありえない
(リーダーの攻撃は自分のターンにしか行えない)が、「掃除は両者に行う」というこのメソッドの形を
崩さないため、条件分岐で片側だけにする書き方はしていない。

### 1-5. 副次的な影響

大地の守護盾(0146)は、リーダーへの攻撃を自身の破壊で肩代わりする防御用ウェポンである。
この寿命ルールにより、**「自分のターンに攻撃してから、相手のターンに盾として使う」ことが
できなくなった。** 攻撃したターンの終わりに壊れるためである。これは仕様変更の意図に沿った帰結であり、
実装上のバグではない。

## ★★★★ 2. ミニオンゾーン上限 — 定数を関数に変える

### 2-1. 横断改修は予想より小さかった

引き継ぎ書は「`MAX_MINIONS` 定数を GameService 4箇所 + PlayerState + CardEffectRegistry から
参照している横断改修」と警戒していた。実際に調べると、内訳は次のとおりだった。

| 参照の仕方 | 箇所数 | 改修 |
|---|---|---|
| `isMinionZoneFull()` 経由 | 8箇所 | **不要**(メソッドの中身を変えるだけ) |
| `PlayerState.MAX_MINIONS` の直接参照 | 1箇所(CardEffectRegistry) | 必要 |
| エラーメッセージ内の文字列「6体」 | 4箇所(GameService) | 必要(表示のみ) |

**判定が既にメソッドに包まれていたため、呼び出し側は1行も変えずに済んだ。**
これは「判定点をメソッドに集約する」(設計判断34の考え方)の配当である。定数を直接読む形に
散らばっていたら、8箇所すべてに `player` を持ち回る改修が必要だった。

### 2-2. ★ 保持ではなく算出にした理由

転記ノートは「`PlayerState` にインスタンスフィールド `int minionZoneLimit = 6;` を持たせ、
リーダーが大地の巨頭のときだけ8で初期化する」を候補に挙げていた。採らなかった。

```java
public int getMinionZoneLimit() {
    if (EARTH_COLOSSUS_LEADER_ID.equals(leader.id())) {
        return MAX_MINION_ZONE_LIMIT;   // 8
    }
    return DEFAULT_MINION_ZONE_LIMIT;   // 6
}
```

理由は2つある。

1. **大地の巨頭の新テキストは起動能力ではなく常在能力である。** 本プロジェクトでは常在能力は
   「その瞬間に評価する」扱いで一貫している(設計判断4: 動的ステータスはキャッシュせず毎回再計算)。
   上限だけを初期化時に確定させると、扱いが揃わない。
2. **保持方式は壊れ方が悪い。** 将来「自分のミニオンゾーンの上限を1増やす」ミニオンやウェポンが
   出たとき、保持方式では加算と減算のペアを書くことになり、そのミニオンが破壊された時の減算漏れ、
   バウンスした時の二重減算、といった形でしか壊れない。算出方式なら、その瞬間の場を見て
   足し合わせる関数を1つ書き換えるだけで済む。

リーダーIDの直書きは、リーダーの常在能力に対する既存の扱いに揃えたものである
(`StatCalculator` の詠唱の風詠士、`CardEffectRegistry.fireManaPlaced` の豊穣の地霊主、
`GameService.GRAVE_SUMMONER_LEADER_ID` の黄泉の召喚主が同じ形)。

### 2-3. 「上限の上限」という定数

定数は2つに分けた。

| 定数 | 値 | 用途 |
|---|---|---|
| `DEFAULT_MINION_ZONE_LIMIT` | 6 | 既定の上限 |
| `MAX_MINION_ZONE_LIMIT` | 8 | **到達しうる天井** |

天井が必要なのは死者蘇生(0080)の生贄選択である。`TargetSpec` は起動時に静的に組み立てるため、
プレイヤーごとの値を持てない。

```java
Requirement.upTo(Kind.MINION, Side.SELF, PlayerState.MAX_MINION_ZONE_LIMIT, ...)
```

6のままだと、大地の巨頭のプレイヤーが8体並べたときに生贄を選び切れなくなる。
「土のリーダーが闇のスペルを使う」組み合わせは、**禁忌デッキ経由で実際に成立する**
(禁忌デッキはリーダーと異なる文明のカードで構築する)ため、机上の話ではない。

`upTo` は「0個からmax個まで」の上限指定であり、実際に選べる数は場のミニオン数に制限される。
したがって天井を大きめに取っても、通常のプレイヤーの挙動は変わらない。

### 2-4. 表示側

`battle.js` はミニオンを配列として描画し、`battle.css` は `flex-wrap` で並べている。
**枠を6つ固定で描く実装ではなかったため、フロントエンドは無変更で8体を正しく表示する。**

`GameService` の4箇所のエラーメッセージだけは固定文字列「ミニオンは6体までです」だったため、
`"ミニオンは%d体までです".formatted(player.getMinionZoneLimit())` に変えた。

## ★★★★ 3. ウェポンの新しい発火口 — なぜ switch ではなくトリガー型か

### 3-1. 何が足りなかったか

Ver.0.4 で2枚のウェポンが「自分のミニオン」を見るようになった。

| カード | 新テキスト | 必要な発火 |
|---|---|---|
| 魔剣レーヴァテイン(0061) | 自分のミニオンが攻撃した時、自分のリーダーに1ダメージ | ミニオンの攻撃宣言 |
| 禁忌の冥魔剣(0073) | 自分のミニオンが場に出たとき、相手のリーダーに1ダメージ | ミニオンの登場(ON_ENTER相当) |

ウェポンの既存の発火口は2つしかなかった。

1. 装備時 — `CardEffectRegistry.fireEquip`(`TriggerType.ON_EQUIP`)
2. リーダー攻撃時 — `GameService.leaderAttack` 内のカードIDによる `switch`

どちらも「味方ミニオンに起きたこと」を拾えない。

### 3-2. ★ 採った方針と、採らなかった方針

転記ノートは「`TriggerType` に新種を増やすのではなく、既存のウェポン攻撃時switchと同じ発想が
既存構造との整合性が高い」を候補として挙げていた。**この案は採らなかった。**

採ったのは `TriggerType` に2種を追加し、`triggers` マップに登録する方式である。

```java
// TriggerType
ON_ALLY_MINION_ATTACK,
ON_ALLY_MINION_ENTER

// 登録(各文明の登録メソッドの中)
register("QTE-0061", TriggerType.ON_ALLY_MINION_ATTACK,
        ctx -> ctx.actions().damageLeader(ctx.room(), ctx.owner(), 1, "QTE-0061"));

// 発火(専用の入口)
public void fireAllyMinionEvent(TriggerType trigger, EffectContext ctx) {
    CardMaster weapon = ctx.owner().getEquippedWeapon();
    if (weapon == null) return;
    Consumer<EffectContext> effect = triggers.getOrDefault(weapon.id(), Map.of()).get(trigger);
    if (effect != null) effect.accept(ctx);
}
```

判断の根拠を3つ挙げる。

1. **ウェポンは既に `triggers` マップに参加している。** `fireCardUsed` は装備中ウェポンの
   `ON_CARD_USED` を読んでおり(暴風の双剣)、`fireEquip` は `ON_EQUIP` を読んでいる。
   ここで switch を選ぶと、ウェポンの効果が「マップに登録するもの」と
   「GameService に直書きするもの」の2系統に分かれ続けることになる。
2. **効果の中身の置き場所が変わる。** switch にすると効果本体が `GameService` に書かれる。
   トリガー型なら `registerFireCards` / `registerDarkCards` の中に置ける。
   「ルール本体は"いつ"だけを知り、"何が起きるか"は台帳から引く」という
   `CardEffectRegistry` の冒頭に書かれた原則に沿う。
3. **禁止の指示が `TriggerType` には無い。** 引き継ぎ書は
   「`TargetSpec.Kind` は5種類のまま増やさない」と明記しているが、`TriggerType` について
   同種の指示はない。むしろ `ON_COMBAT_KILL`(13a)のように、
   「向きの違うトリガー」を型で表現してきた前例がある(設計判断31)。

> **★設計根拠。** switch案が持つ「既存構造との整合性」は、正確には
> **「ウェポン攻撃時switchとの整合性」**であって「システム全体との整合性」ではない。
> そのswitch自体が引き継ぎ書に「移設は独立バッチ」と書かれた負債である
> (2章の候補5)。負債に揃えるより、正しい側に揃えて負債を増やさない方を選んだ。

### 3-3. 発火箇所

| トリガー | 発火場所 | 隣にあるもの |
|---|---|---|
| `ON_ALLY_MINION_ATTACK` | `GameService.attack` | `effects.fire(ON_ATTACK, ...)` |
| `ON_ALLY_MINION_ENTER` | `GameService.summonToField` | `effects.fire(ON_ENTER, ...)` |
| `ON_ALLY_MINION_ENTER` | `GameActions.putIntoFieldByEffect` | `effects.fire(ON_ENTER, ...)` |

**`ON_ENTER` の発火箇所と完全に一致させている。** 冥魔剣の「場に出たとき」は【召喚時】ではないため、
召喚・特殊召喚に加えて蘇生や効果による「出す」でも発動する(発注者確認済み)。
`reviveFromGrave` は `putIntoFieldByEffect` に委譲しているため、蘇生も自動的に含まれる。

`GameService.attack` では、既存の `contextOf(...)` のインライン呼び出しをローカル変数
`attackCtx` に括り出した。同じ文脈を2つの発火が共有するためである。

**レーヴァテインの自傷でゲームが終わる場合**、`damageLeader` が `finish` を呼び、
その直後にある既存の `if (state.getStatus() == FINISHED) return;` が戦闘の解決を止める。
新しい発火をこのチェックより前に置いたのはこのためである。

### 3-4. 旧実装の撤去

`GameService.leaderAttack` の switch から `case "QTE-0061"` と `case "QTE-0073"` を削除した。
冥魔剣の旧効果(裏向きマナを1枚表に戻して1ダメージ)は Ver.0.4 で全面置換されたため、
`turnManaFaceUp` の呼び出しごと消えている(メソッド自体は他カードが使うため残る)。

**残すと二重発動になる**ため、この撤去は新登録とセットで必須である。

## ★★★ 4. 回復量の計数 — damageLeader に形を揃える

### 4-1. 何が足りなかったか

鳳凰神ヴォルカニクスレヴォ(0058)の新しい特殊召喚条件は次のとおりである。

> このターン5以上火文明のカードで回復したとき、このカードを手札から0コストとして出せる

既存の `PlayerState.healedCountThisTurn` は**回数**のカウンタであり、量も発生源も持たない。
必要なのは「累計量」かつ「発生源の文明で絞り込める」ことである。

### 4-2. 発生源引数の追加

`GameActions.damageLeader` には既に発生源カードIDの引数がある(反転の炎鏡の自己誘発防止のため
Batch 8 で追加された)。**同じ形に揃えた。**

```java
public void healLeader(GameRoom room, PlayerState player, int amount) {
    healLeader(room, player, amount, null);          // 発生源不明版は委譲
}

public void healLeader(GameRoom room, PlayerState player, int amount, String sourceCardId) {
    int before = player.getLp();
    player.setLp(Math.min(MAX_LP, before + amount));
    int healed = player.getLp() - before;
    player.setHealedCountThisTurn(player.getHealedCountThisTurn() + 1);
    if (sourceCardId != null) {
        player.recordHealedAmount(healed, cards.findById(sourceCardId).civilization());
    }
    ...
}
```

3引数版を残したのは、既存の呼び出しを壊さないためではなく(全10箇所を配線した)、
**将来トリガーやルール処理から発生源のないリーダー回復が発生しうる**ためである。
発生源不明の回復はどの文明にも計上されない。

配線した10箇所は次のとおり。文明は台帳の値である。

| カード | 文明 | 回復量 |
|---|---|---|
| 恵みの雨(0002) | 水 | 4 |
| 潮流の魔導士(0029) | 水 | 3 |
| 蒼海の賢者(L002) | 水 | 2 |
| 背水の炎壁(0057) 【召喚時】 | 火 | 1 |
| 背水の炎壁(0057) 特殊召喚の追加 | 火 | 1 |
| 武具昇華の炎(0043) | 火 | 2 |
| 血の対価(0065) | 火 | 3 |
| 反転の炎鏡(0048) | 火 | 1 |
| 安らぎのガーディアン(0152) 【召喚時】 | 土 | 2 |
| 安らぎのガーディアン(0152) 【ターンエンド時】 | 土 | 4 |

### 4-3. 文明ごとに分けて持つ理由

```java
private final Map<Civilization, Integer> healedAmountByCivilizationThisTurn =
        new EnumMap<>(Civilization.class);
```

合計だけを持って後から絞り込むことはできない。加算してしまった後では、その量がどの文明から
来たのかを復元できないからである。**絞り込みは加算の時点でしか行えない。**

`EnumMap` を選んだのは `Civilization` が列挙体だからである(宣言順のイテレーションと
配列ベースの実装が得られる)。

回数(`healedCountThisTurn`)は残した。Ver.0.4 で参照するカードが無くなったが、

### 4-4. ☆ 未確定のまま進めた判断

**回復量は「実際にLPが増えた分」で数えている。**

int healed = player.getLp() - before;   // LP19で4回復なら healed = 1

- 「回復した」という語の素直な読みである
- 要求量で数えると、**体力が満タンの状態で回復を撃つだけで条件が貯まる**

## ✅ 理解確認

<details>
<summary>Q1. ウェポンが「このターン攻撃したか」を、攻撃したウェポンのカードIDで覚えるのではなく真偽値1つで済ませられるのはなぜか。</summary>

`GameActions.onWeaponLeftPlay` が、ウェポンが場を離れるすべての経路(破壊・付け替え)の
唯一の合流点であり、そこでフラグを落としているためである。

これにより「フラグが立っている = 今装備しているウェポンが攻撃した」という不変条件が常に保たれ、
どのウェポンが攻撃したのかを別途追跡する必要がなくなる。カードIDで覚える方式は、
同名のウェポンに付け替えた場合に誤って壊してしまう欠点もある。
</details>

<details>
<summary>Q2. ミニオンゾーンの上限を、ゲーム開始時にフィールドへ確定させるのではなく、参照のたびに算出しているのはなぜか。</summary>

2つの理由がある。

1. 大地の巨頭の新テキストは常在能力であり、本プロジェクトでは常在能力を
   「その瞬間に評価する」扱いで一貫している(設計判断4)。
2. 保持方式は壊れ方が悪い。将来「上限を1増やす」ミニオンが出たとき、加算と減算のペアを
   書くことになり、破壊時の減算漏れやバウンス時の二重減算という形でしか不具合が出ない。
   算出方式なら、その瞬間の場を見て足し合わせる関数を1つ書き換えるだけで済む。
</details>

<details>
<summary>Q3. 死者蘇生の生贄選択の上限に、プレイヤーの実際の上限ではなく固定値8(MAX_MINION_ZONE_LIMIT)を使っているのはなぜか。また、なぜ6のままではいけないのか。</summary>

`TargetSpec` は `CardEffectRegistry` の起動時に静的に組み立てられるため、
プレイヤーごとの値を持てないからである。したがって「到達しうる天井」を指定するしかない。

6のままだと、大地の巨頭のプレイヤーが8体並べたときに生贄を選び切れなくなる。
死者蘇生は闇のスペル、大地の巨頭は土のリーダーで文明が違うが、
**禁忌デッキはリーダーと異なる文明のカードで構築する**ため、この組み合わせは実際に成立する。

`upTo` は「0個からmax個まで」の指定であり、実際に選べる数は場のミニオン数で制限される。
天井を大きく取っても通常のプレイヤーの挙動は変わらない。
</details>

<details>
<summary>Q4. ウェポンの新しい発火口を、GameService.leaderAttack のようなカードIDのswitchではなく TriggerType の追加で実装したのはなぜか。</summary>

主な理由は、効果の中身の置き場所が変わることである。switch にすると効果本体が
`GameService` に書かれるが、トリガー型なら各文明の登録メソッド(`registerFireCards` 等)に置ける。
「ルール本体は"いつ"だけを知り、"何が起きるか"は台帳から引く」という
`CardEffectRegistry` の原則に沿う。

加えて、ウェポンは既に `triggers` マップに参加しており(`ON_EQUIP`・`ON_CARD_USED`)、
switch を選ぶとウェポンの効果が2系統に分かれ続ける。
なお `leaderAttack` の switch 自体、引き継ぎ書に「移設は独立バッチ」と書かれた負債である。
</details>

<details>
<summary>Q5. 累計回復量を、合計値1つではなく文明ごとの Map で持っているのはなぜか。</summary>

合計に加算してしまった後では、その量がどの文明のカードから来たのかを復元できないためである。
発生源による絞り込みは、加算の時点でしか行えない。

鳳凰神ヴォルカニクスレヴォは「火文明のカードで累計5以上」を条件とするため、
参照する側が後から絞り込める形にしておく必要がある。
</details>

<details>
<summary>Q6. 大地の巨頭の起動能力の登録を「消さずに残しておく」と、具体的に何が起きるか。</summary>

盤面に、新仕様では存在しないはずの能力ボタン
(「コスト4: 手札1枚を表向きでマナに置く」)が表示され続け、実際に使えてしまう。

`GameViewBuilder.buildLeaderAbility` は `effects.leaderAbilityOf(...)` が null かどうかだけで
ボタンの有無を判断しているため、登録が残っている限りビュー側は能力があるものとして扱う。
</details>

<details>
<summary>Q7. 地脈の覚醒の StatCalculator 分岐の削除が「台帳の更新が前提」なのはなぜか。</summary>

削除が安全である根拠が「基礎コストが2に下がったので分岐は常に無意味」だからである。

台帳が旧版(基礎コスト5)のまま分岐だけを消すと、地脈の覚醒は
マナ枚数に関わらず素の5コストスペルになり、マナ加速カードとして機能しなくなる。
この削除は台帳の値とセットで初めて正しい。
</details>
