## 1. ★★★最初に解いた問い(裁定81)

> 裁定8(差分8件超は演出しない)と裁定11(節目の帯は上限の特例にしない)のもとで、
> 総入れ替えである配り直しをどう演出するか。

### 1-1. まず、現状は「上限に引っかかっている」のではなかった

裁定81 とレビュー B-1 は「一括変更(差分8件超)は演出を全抑制」と書いているが、
実装を読むと開始シーケンスはそこまで到達していない。`applyView` の入口に
**もう1つ手前の関門**があったからである。

```js
if (fxDiffNeeded() && prevView && !fxStartLocking(prevView) && !fxStartLocking(view)) {
```

`fxStartLocking` が真の配信では、**差分そのものを採っていない**。
つまり開始シーケンスは「8件を超えたから捨てられた」のではなく、
「そもそも数えられてすらいない」。

★この区別は重要である。**もし上限で落ちているだけなら、上限を緩めれば直る**ように見える。
実際には緩めても何も出ない。裁定81 が「差分の抑制を緩めるのではなく」と書いたのは、
おそらくこの構造を見抜いていたのだと思う。

### 1-2. ★★差分は同一性を語り、儀式は員数を語る

では `fxStartLocking` を外して差分を採ればよいか。**採ってはならない。**
開始の配りは `dealForStart` → `applyImport` を通り、**カードの個体が全部作り直される**。
差分から見えるのは「40枚が消滅して49枚が出現した」であり、これは
1文字も嘘ではないが、1文字も意味が無い。

一方で、**枚数には意味しかない。**

| | 先攻 | 後攻 |
|---|---|---|
| 初期手札 | 4枚 | **5枚** |

これは総合ルール 2-5 そのものである。**開始シーケンスで語るべきものは同一性ではなく員数だった。**

★これが「別の入口」の中身である。入口が違うのは経路が違うからではなく、
**運ぶものが違うから**である。差分は `instanceId` を運び、儀式は席と枚数を運ぶ。

### 1-3. ★★★入口の実装 —— 抑制も上限も1文字も緩めていない

```js
function diffViews(prev, next) {
    const out = { ..., rite: null };
    if (!prev || !next) return out;
    // ★★儀式は差分より先に採る。開始シーケンス中は差分をここで打ち切るためである
    out.rite = fxNewRite(prev, next);
    if (fxStartLocking(prev) || fxStartLocking(next)) {
        return out;           // ← 32 設計書 2-3 の判断はそのまま生きている
    }
    ... 既存の差分検出 ...
}
```

**関門を `applyView` から `diffViews` の中へ移した。** これだけである。

- **裁定8 は無傷。** 開始シーケンス中の差分は1件も採られない(検証項目で `others === 0` を測っている)。
- **裁定11 も無傷。** 儀式は上限(`FX_BULK_LIMIT` = 8)に**特例を作っていない**。
  上限は今も全体にかかっている。儀式が引っかからないのは、
  **作られる件数が最初から1〜2件しかない**からである
  (9枚のゴーストは `fxRegister` に**1本**として積まれる。3-2)。

★★教訓の形にすると: **「例外を作る」と「別の道を作る」は違う。**
前者は既存の規則に穴を開けるので、穴の数だけ規則が読めなくなる。
後者は規則を1文字も触らない。裁定81 が要求していたのは後者である。

### 1-4. ★儀式と差分が同じ配信で出ることはない(が、それに寄りかからない)

儀式が起きる配信は必ず `fxStartLocking(prev)` が真である
(最後のマリガン → PLAYING でも、直前は MULLIGAN で locking だった)。
したがって儀式と差分は同じ配信に同居しない。

★ただし**この性質に寄りかかった書き方はしていない**。上限は儀式を含む全体にかかっており、
将来 locking でない場面に儀式を足しても、勝手に上限を突破することはない。
「今は起きない」を根拠に守りを外すと、起きるようになった日に静かに壊れる。

## 2. サーバ側 —— 材料は構造である

### 2-1. ★★Batch 35 とまったく同じ形である(裁定40 の再適用)

35 は「宣言は盤面に痕跡を残さないので、サーバ側に観測できる形を1つ足した」。
38 はその**裏返し**である —— 開始シーケンスは痕跡を残しすぎるので、
差分から読み取れることが何も無い。

| | Batch 35(宣言) | Batch 38(儀式) |
|---|---|---|
| 差分に現れないのは | 盤面に**触らない**から | 盤面を**全部書き換える**から |
| 足した構造 | `ManualLogDeclaration` | `ManualLogStartRite` |
| 配信に載る形 | `declarations`(seq付き) | `rites`(seq付き) |
| 出す条件 | seq が増えたとき | seq が増えたとき |
| 文言の正 | サーバの `label` | サーバの `label` |

**方向は逆だが、結論は同じである: 材料にしてよいのは書式ではなく構造である。**
ログ本文の「シャッフルして初期ドロー: 席A 4枚 / 席B 5枚」を正規表現で読むのは、
21a が文字列ログをやめた理由を表示側で繰り返すことである。

### 2-2. ★1行に2つの儀式が同居する問題

全公開部屋で「ランダムで決める」を押すと、`chooseMethod` は
**ダイスを振ってそのまま配る**。ログも1行である。

素直に作ると「1ログ行 = 1儀式」が破れる。3つ考えた。

| 案 | 判断 |
|---|---|
| ログを2行に割る | ★退けた。**起きていない操作**が1行増える(23 1-4 と同じ理由)。1回の操作は1行である |
| 儀式をリストにする | ★退けた。「2件以上」が原理的に起きるのは この1箇所だけであり、そのためだけに全ログ行がリストを持つ |
| **主たる儀式 + 別欄のダイス(採用)** | `kind` が主たる儀式、`diceA` / `diceB` / `winner` / `label` は独立した欄 |

```java
public record ManualLogStartRite(
        ManualStartRite kind,          // DICE / DEAL / MULLIGAN
        Integer diceA, Integer diceB, ManualSeatId winner, String label,
        List<ManualStartDeal> dealt) { ... }
```

- 対戦部屋のダイス → `kind = DICE`、`dealt` は空
- ソロのランダム → `kind = DEAL`、ダイスの欄が埋まる
- 席指定 → `kind = DEAL`、ダイスの欄は null

★★**画面には推測が1つも要らない。**「`dealt` が空だからダイスだけなのだろう」という
読み方をさせない。クライアントの分岐は `diceA != null` と `kind` の2つを見るだけである。

★引き継ぎは `ManualLogStartRite.deal(seed, dealt)` の1箇所に閉じ込めた。
呼び出し側(`deal`)は「ダイスを振ったかどうか」を知らずに済む。

### 2-3. ★通し番号は配ったログ行のものである(裁定42 の継続)

`ManualViewBuilder` は宣言と儀式を**ログの末尾60行と同じ1周**で拾う。

```java
for (ManualLogEntry entry : entries.subList(Math.max(0, logTotal - LOG_TAIL), logTotal)) {
    log.add(...);
    ManualLogDeclaration mark = entry.event().declaration();
    if (mark != null) { declarations.add(...); }
    ManualLogStartRite rite = entry.event().startRite();
    if (rite != null) { rites.add(new ManualStartRiteView(entry.seq(), rite)); }
}
```

★別に `room.getLog()` を走査すると、**配った行に無い seq を指しうる**。
35 がこれを裁定にした理由がそのまま2件目に効いた。
JUnit でも「`rites` の seq は必ず `log` のどれかを指す」を測っている。

★儀式は `start` の中ではなく配信の直下に置いた。`ManualStartView` が運ぶのは
「今どのフェーズか」= **状態**であり、儀式は**出来事**である。
そして出来事は `declarations` とまったく同じ作られ方をする。
**同じ作られ方のものを同じ場所に置くと、裁定42 の約束が1箇所で守れる。**

### 2-4. ★★守れない約束を型に書かない

35 は `ManualLogEvent.plain()` が DECLARE を弾くようにした(裁定41)。
「構造の欠けた DECLARE 行」を型で不可能にするためである。

**START では同じことができない。** 構造を持たない START 行が正当に存在する。

- 「ゲーム開始の準備に入った(開始方法を選択中)」— `begin`
- 「… → 席A が選択権を得た」の**前段**にあたる遷移ログ

これらは儀式ではない。だから `plain(START, ...)` は今も通る。

★★**守れる約束だけを型に書いた**: 「構造を作るなら `ManualLogEvent.startRite(...)` を通る」。
そのうえで、その入口を呼ぶのは `ManualStartService.startLog(actor, rite, text)` の1箇所だけにした。
★「全部を型で守れないなら守らない」でも「守れるふりをする」でもなく、
**守れる範囲を正確に線引きして、残りは1箇所に集約する**のが第三の道である。

### 2-5. ★0枚のマリガンでも儀式を作る

「戻さない」を選んでも `ManualLogStartRite.mulligan(seat, 0, 0)` を作る。

★作らないと、画面は**「儀式が無い」と「儀式が空だった」を区別できない**。
前者は演出しない、後者は「何もしなかった」を演出しうる —— 判断が画面側に移る。
サーバが事実を全部運び、**演出するかどうかだけを画面が決める**形を保った。
(現行の実装では 0枚のマリガンはシャッフルの揺れだけを出す。)

## 3. 演出

### 3-1. ★ダイスの帯 —— 35 の帯をもう一度使う

位置決め・座席(fx層 1030)・消し方は `fxBuildDeclare` と同じである。
違うのは**中身が3つの部品**(出目2つ + 結果の文)であることだけ。

★★**見えている内容は最初からDOMにある。** 段階的に現れるのは CSS の `animation-delay`
であって、JS がテキストを書き換えるのではない。

```css
.manual-fx-dice-chip:nth-child(2) { animation-delay: 150ms; }
.manual-fx-dice-note { animation: ... 340ms both; }
```

★理由は 31 以来の規約「**待ってから測る検証にしない**」である。
出目を JS で回して見せる案(カラカラと数字が変わる)は、儀式感は上がるが
「最終値がいつ確定するか」に検証が依存する。
**同じ儀式感を、確定した DOM + 時間差の表示で作れるならそちらを採る。**

★★文言はサーバの `label` をそのまま使う。**対戦部屋のダイスが与えるのは先攻ではなく選択権**であり、
その書き分けをクライアントに写すと条件が2箇所に分かれる(裁定46 と同じ形)。
機械判定あり(クライアントで「席A が先攻」を組み立てると落ちる)。

### 3-2. ★★配り —— 儀式は「1つの演出」である

9枚(先攻4 + 後攻5)のゴーストを出すが、`fxRegister` に積むのは**入れ物1つ**である。

```js
const box = document.createElement('div');
box.className = 'manual-fx-rite';
... ゴーストは全部 box の中 ...
return fxRegister(fx.key, box, fxRiteDuration(fx), () => { ... }, { event: null, onStop: ... });
```

★★これが裁定11 への答えでもある。`FX_LIMIT`(同時8本)の勘定で儀式は**1本**と数えられ、
「儀式だけ上限を無視する」という特例が要らない。後片付けも入れ物ごと1回で終わる。
**検証項目にしてある**(`fxRunning.size === 1`)。

★★**ゴーストは最初に全部作り、飛ばす時刻だけをずらす。**
途中で作ると、その1枚だけ開始状態が確定していないまま終了状態を当てることになり、
遷移が発火しない(32a の `offsetHeight` の idiom が効くのは、確定の時点でDOMに在るものだけである)。
飛ぶ前のゴーストは山札の上に重なっているので、見た目には現れない。

★席ごとの配りは**同時に**走らせる。順番に配ると、席が2つあるだけで待ち時間が倍になる。

★★**相手席の配りも演出できる。** 手札は「窓」のゾーンで中身が届かない(裁定7)が、
枚数は元から公開情報である(`counts`)。ゴーストは `fxGhost(from, null)` で作るので
**裏面以外を描きようがない**。検証項目でも `imageIds` が空であることを測っている。

### 3-3. ★マリガンは往復である

戻す(手札 → 山札)→ 混ぜる → 引き直す(山札 → 手札)の3段で出す。

★戻す枚数と引く枚数は普通は同じだが、**片道にはしなかった**。
マリガンは往復であり、往復であることが読めなければ何をしたのか分からない。
山札が尽きて `drew < back` になる場合(23 1-3)にも、そのまま食い違いが見える。

★シャッフルの揺れは**実要素(山札のアンカー)**に当てる animation である。
32b の規約どおり `onStop` で必ずクラスを剥がす。**機械判定あり。**

## 4. ★★開始画面の保留 —— 層の順序ではなく時間で解く

### 4-1. 問題

fx層は **z-index 1030** である。開始モーダルは 1950/1960、マリガンのオーバーレイは 1950。
配りの儀式が走る配信では、**同じ瞬間にマリガンの画面が開く**。
つまり素直に作ると、儀式は**1pxも見えない**。しかも見えないのは
「配られた本人」だけである —— いちばん見せたい相手に見えない。

### 4-2. 採らなかった案

| 案 | 判断 |
|---|---|
| fx層(または儀式だけ)を 1962 へ持ち上げる | ★退けた。33 で1本に決めた z-index の並びを**演出の都合で崩す**ことになる。次に何かを重ねる人が読む順序が消える。しかも「暗幕の上を飛ぶカード」は絵として意味を成さない |
| 儀式をモーダルの中で描く | ★退けた。ダイスは選択モーダル、配りはマリガン画面、と**3箇所に散る**。fx層という1つの場所を捨てることになる |
| **儀式のあいだ開始画面を開かない(採用)** | 層は1つも動かさない。待つのは**時間**である |

★★**決めごとの数で選んだ。** 層を持ち上げる案は「z-index の並び」という既存の決めごとに
例外を1つ足す。時間で待つ案は、決めごとを1つも増やさない
(増えるのは実装であって規約ではない)。1-3 の「例外を作るな、道を作れ」と同じ判断である。

### 4-3. 行き止まりを構造的に作らない

```js
function riteHolding() { return riteHoldUntil > Date.now(); }
```

★★**保留は時刻で明ける。** 儀式の組み立てが失敗しても、ゴーストが1枚も出なくても、
アンカーが引けなくても、`FX_RITE_HOLD_MAX_MS`(2400ms)を待てば必ず画面が開く。
23 が「止まったまま抜けられない画面を作らない」ためにリセットを1つ穴として残したのと
同じ発想だが、こちらは**逃げ道すら要らない形**にできた。

★**閉じるほうは保留しない。**「儀式のあいだ閉じられない画面」を作らないためである。
`syncMulliganOverlay(start, holding)` は `holding` のとき自席のマリガンを空とみなす ——
開く側だけが空振りし、閉じる側は素通りする。

★保留が明けたら**配信を待たずに**画面を開く。儀式のあとに配信が来る保証はどこにも無い。

### 4-4. ★★★演出を切っている人は待たせない

```js
if (effects && fxAllowed()) {
    riteHold(fxRiteHoldMs(effects));
}
```

`fxDiffNeeded()`(見た目 or 音)ではなく **`fxAllowed()`(見た目だけ)**である。

★理由: `prefers-reduced-motion` の人には儀式が**見えていない**。
見えていないものの終わりを待たせるのは、ただ操作が遅れるだけである。
37 の裁定69「音は動きではない」の裏側にあたる —— **待つ理由は音ではなく絵にある。**
**機械判定あり**(ゲートを `fxDiffNeeded()` にすると落ちる)。

## 5. 効果音 —— 表に3行足しただけである

### 5-1. ★★★発火点は1つも増えていない(裁定68 の継続)

儀式を `fxEffects` が作る**同じ列**に並べたので、`fxSpawn` の
`sfxPlayForEffects(pending.effects)` が**1行も変えずに**拾っている。
`SFX_FOR_KIND` に3行足しただけで音が鳴る。

```js
dice: 'dice',
deal: 'deal',
mulligan: 'shuffle',
```

★★これは 37 の配当が2度目に効いた形である。37 は「決着も同じ列に並んでいるので
`fxBuildDeclare` に個別の呼び出しが要らなかった」と書いた。同じことが儀式でも起きた。
**列を1本に保つと、次に足すものが自動的に載る。**

★裁定72 の番人(`fxEffects` が作る kind をソースから拾って音の表と照合する)も
**何も直さずに** 3種を検出した。番人が番人として働いた実例である。

### 5-2. ★マリガンの音は `shuffle` である(語彙は粗くてよい)

演出の種類は `mulligan`、音の名前は `shuffle`。名前がずれているのは、
**音の語彙は演出の語彙より粗くてよい**(裁定72)からである。
耳から見れば、マリガンで起きているのは「束を混ぜた」である。

### 5-3. ★1配信1音は儀式でも守る(裁定70)

ソロのランダムは**ダイスと配りが同じ配信**で起きる。演出は2つ出るが、音は1つである。

```js
const SFX_PRIORITY = ['decisive', 'dice', 'deal', 'shuffle',
    'lpDown', 'lpUp', 'draw', 'flip', 'tap', 'place'];
```

★★**順序の理由は「珍しさ」1本である**(裁定71)。決着1回 > ダイス1回 > 配り1回 >
マリガン最大2回 > LP数回 > ドロー毎ターン > … の順。
「儀式は大事だから上」と書きたくなるが、**理由を2本にすると次に足す音の位置が決まらなくなる。**
★配りの音がソロで鳴らないのは取りこぼしではなく、この決まりの帰結である。

### 5-4. ★`rattle` 型を1つ足した

ダイスは「転がって止まる」音である。既存の `tone` / `noise` / `chord` では作れない。

```js
dice: { type: 'rattle', ms: 620, hits: 5, from: 2600, to: 1100, q: 9, gain: 0.55 },
```

`sfxRattle` は短い雑音の粒を**間隔を詰めながら**並べ、最後の1粒だけ低く強くする。
★足したのは音の「作り」であって「性格」ではない —— 調整はこれまでどおり
`SFX_SPECS` の表だけで行える(裁定 37 の運用)。

★★**粒が複数でも「1つの音」である。** 裁定70 が数えているのは**出来事**であって
音源ノードではない。したがって検証も、儀式については
「どれを鳴らすか」(純関数)と「鳴ったか」(ノードが0でないこと)の2つで見ている ——
37 の「1配信1音」をノード数 `=== 1` で測っている項目とは測り方を変えてある。

## 6. 実装時に踏んだ / 避けた罠

- **★★「差分の抑制が原因」という前提が違っていた**(1-1)。レビューも裁定81 も
  「差分8件超で抑制されている」と書いているが、実際は `fxStartLocking` で
  **数えられてすらいなかった**。★**指摘の文言ではなくコードを読んでから直す**、が結論である。
  上限を緩める修正をしていたら、何も変わらないまま「直した」ことになっていた。
- **★★保留を入れずに作ったら、儀式が1枚も見えなかった。** fx層(1030)と

  実機で気づくまで分からなかった。
- **★ゴーストを飛ばす時刻に作ると、遷移が発火しない。** 最初 `setTimeout` の中で
  `fxGhost` を作っていたところ、ずらしたぶんのカードが**瞬間移動**した。
  32a の `offsetHeight` による確定は、その時点でDOMに在るものにしか効かない。
  → 全部先に作り、**当てるタイミングだけ**をずらす形に直した。
- **★`at: 0` を `setTimeout(…, 0)` に落とすと、配信直後の観測から消える。**
  0ms のものは同期で当てている。「待ち時間に依存する検証にしない」(31)の実装側の作法である。
- **★検証で音が鳴らなかった。** 直前の項目(37 の設定の永続化)がミュートしたまま
  ページを再読込しているため、`snd` は**ミュート + unlock 前**の状態だった。
  → 鳴る状態へ戻してから測る形にした。★**検証の項目は状態を引き継ぐ**。
  新しい項目を末尾に足すときは、そこまでで何が起きているかを読むこと。
- **★`fxRunning` は `window` に載っていない。** `const` 宣言はグローバルオブジェクトの
  プロパティにならない。`page.evaluate(() => window.fxRunning.size)` は
  `undefined.size` で落ちる(裸の `fxRunning` なら通る)。
