## 0. ★★★59 までの見立ては間違っていた(裁定301)

59・60・63 の設計解説と引き継ぎ書は、同じ文をくり返し書いてきた。

> 割り込み選択(a9)は「効果の解決を**中断**し、再開点(`ResumePoint`)から続きを走らせる」
> 仕組みであり、**中断できるのは登録された再開点だけ**である。
> ドローはこのエンジンのあらゆる場所から呼ばれる —— ターン開始処理・スペルの解決の途中・
> 【知識】の共通処理・破壊時の誘発……。そのどこで中断しても、
> **中断された側の続き**を再開する術が無い。

64 の最初の仕事は、この文が正しいかを実装で確かめることだった。**正しくなかった。**

```java
public void requestChoice(GameRoom room, PlayerState owner, PendingChoice choice) {
    owner.setPendingChoice(choice);          // ← 積んで
    room.addLog(...);
}                                            // ← そのまま戻る
```

`requestChoice` は**呼び出し元を止めない**。呼んだ効果はその場で `return` するだけで、
外側の解決(全体破壊のループ、ターン開始処理、スペルの残り)は**そのまま走り続ける**。
止まるのは「答えで動く部分」だけであり、それは `CardEffectRegistry.resolveChoice` に
別途書いてある。つまりこれは**中断ではなく後回し**である。

> **中断しないのだから、深いところから問い合わせても困らない。**

実際に詰まっていたのは、次の3つだった。

| # | 詰まり | 64 の外し方 |
|---|---|---|
| 1 | **はい/いいえの器が無い** | `PendingChoice.Kind.CONFIRM` |
| 2 | **1人につき1件しか積めない** | `PlayerState` の待ち行列(裁定300) |
| 3 | **再開に要る値を運べない** | `PendingChoice.payload` |

★**裁定194 の3度目の適用である**(「先送りの見積もりは、実際に着手するまで当てにならない」)。
51 の「思っていたより浅かった」、60 の「壊しても落ちないのは試験不足とは限らない」に続く。
★**代償は1つある。**後回しなので、「してもよい」の結果は元の効果の残りより**後**に起きる。
《冥界神ハデス》が全体を破壊し、自分の蘇生まで終えたあとに《執念の暗殺者》のドローが乗る。

## 2. ★はい/いいえは「候補1件の選択」である(裁定299)

新しい型を作らなかった。

```java
public static PendingChoice confirm(ResumePoint resumeAt, String prompt) {
    return new PendingChoice(Kind.CONFIRM, List.of(CONFIRM_YES), 0, 1, resumeAt, prompt, ...);
}
```

- 候補は「はい」1件だけ。**選べば「はい」、選ばなければ「いいえ」**である。
- したがって **WebSocket のリクエスト型もビューの型も1つも増えていない。**
  クライアントは `kind === 'CONFIRM'` を見て2つのボタンに描き替えるだけで、
  [はい] は index 0 を送り、[いいえ] は空を送る。

★**「いいえ」を2つ目の候補にしなかった理由**は、そうすると「何も選ばない」と
「いいえを選ぶ」の2つが同じ意味を持ち、`min`/`max` の検証がどちらを正とするかを
決められなくなるからである。

★**verify がこれを実物で測る。**期待値を verify に書き写すのではなく、
harness の battle.js で実際にボタンを押し、`window.__sent` に届いた中身を見る(裁定296)。

## 3. ★★待ち行列(裁定300)

`PlayerState.pendingChoice`(1件)を `Deque<PendingChoice>` にした。

- `getPendingChoice()` は**先頭を覗くだけ**にした。おかげで
  63 までの呼び出し元(ブロック判定・ビュー・試験40箇所以上)が**1行も変わっていない**。
- 積む口は `GameActions.requestChoice` の1つだけ、取り出す口は
  `GameService.resolveChoice` の1つだけである。
- 上限32。**構築ルールではなく防波堤**である(設計判断27) ——
  ここに引っかかったらカード側の誘発が閉路になっている。

★**63 までのガード(2件目は例外)は「問い合わせが必ず1つずつ起きる」ことを前提にしていた。**
《執念の暗殺者》を問い合わせに移した瞬間にその前提が崩れる。
**器の制限は、たいてい「まだそういうカードが無い」という事実の裏返しである。**

### 3-1. ★★★キュー化が生んだ新しい危険 —— 位置がずれる

`PendingChoice` の javadoc は 12a からこう書いていた。

> 盤面上の識別子(手札の位置・instanceId 等)を直接送らせないのは、
> **中断中に盤面が変化しても位置の解釈がずれないようにするため**である。

**これは半分しか正しくない。**候補の中身が「墓地の位置」なら、位置そのものがずれる。
63 まではずれなかった —— 選択待ちの間は誰も盤面を動かせないからである(裁定214 の対)。
だがキューになると、**手前の選択の解決**が同じゾーンを動かす。

```
[A: 墓地から1体出す]  [B: 墓地から1体出す]     ← 2件並ぶ
A を解決 → 墓地から1枚減る → B の候補「墓地の0番目」は別のカードを指す
```

**解いた形**は控えと照合である。

- `GameActions.requestChoice` が、**積む瞬間に**候補の位置にあるカードIDを控える。
- `GameService.resolveChoice` が、**解決の直前に**同じ読み方で照らし合わせる。
- 1件でもずれていたら、**その問い合わせは何も起こさずに終える。**

★**控えるのも読むのも `GameActions.cardIdAtZonePosition` の1本である。**
控えるときと照合するときでゾーンの読み方が違ったら、番人が番人でなくなる(裁定110)。
★**控えを取る場所を1箇所にしたのが肝である。**候補を作る場所は20以上あるが、
積む口は `requestChoice` 1つしかないので、**新しい問い合わせを足しても控え忘れが起きない**
(裁定68「発火点を増やさない」と同じ形)。
★**ずれた候補だけを落とす形にはしなかった。**そうすると再開先ごとに「空で来たとき」の
分岐が要り、25個ある再開先すべてに同じ但し書きを書くことになる(裁定163 が戒めた形)。

## 6. ★裁定279 の表し方が変わった

59 は「誘発によるドローは数えない」を **`GameActions` の再入フラグ**で表していた ——
「相手ドローの誘発を焚いている最中は、入れ子で焚かない」。

## 8. ★`AutoChoice` の退役(裁定299)

10b から 63 まで、解決中の選択は `AutoChoice` という1つのクラスに集めてあった。
そのクラス説明にはこう書いてあった。

> **このクラスに閉じ込めることが目的である。**将来、割り込み選択システムを実装するときは、
> 各カードの効果ではなく**ここのメソッドの呼び出し元だけを差し替えればよい**形にしてある。

★**その約束はそのとおりに効いた。**64 が触ったのは呼び出し元だけで、
「自動で決めていた」ことがカードの効果本体に染み出していた箇所は1つも無かった。

残った1件(《ホーリー・シグナル》の「最も体力の低いミニオン」)は
`CardEffectRegistry` の private メソッドへ移し、クラスは削除した。
**方針の集約ではなくカード固有の都合になったなら、方針の入れ物は要らない。**

★**退役の番人**は `Class.forName("com.example.qte.effect.AutoChoice")` が
`ClassNotFoundException` になることである。63 の教訓(退役は経路・ファイル・案内を
同時に消す)の適用先がクラスになった形である。

## 9. 壊し検証(`tools/batch64_break_check.py`・16件)

**16件すべて OK。** 軸は12(はい/いいえの器 / 待ち行列に積む / 待ち行列から取り出す /
位置ズレの照合 / 山札が空 / 再誘発を止める / 自動決定へ戻さない / 多重度 /
再開に要る値 / 選択待ち中は動かさない / 画面 / 作り直し)。
照合先は 63 と同じく JUnit と verify の2つである。

### 9-1. ★「条件を落とす」改変が EMPTY になった(裁定304)

`if (cond) { … return; }` を素の `{ … return; }` に置き換えたら、その先が**到達不能**になり
Java がコンパイルを拒んだ。試験が1件も走らず EMPTY である ——
「壊したのに落ちない」ではなく**「壊しすぎて測れない」**。
**常に真になる条件へ書き換える**のが正しい壊し方だった。

裁定196(b)「改変が当たっているか」の3つ目の顔である。

| # | 形 | 初出 |
|---|---|---|
| 1 | 改変が当たっていない(置換が0箇所/2箇所) | 57・59・60 |
| 2 | 試験が実装から値を読むので、定数の改変が当たらない | 63(裁定298) |
| 3 | **改変でコンパイルが通らなくなり、試験が走らない** | **64(裁定304)** |

### 9-2. 壊しどころが無くて外した項目

- **`AutoChoice` の復活** …… クラスを書き戻すのは改変ではなく**新設**である(63 の
  「退役したファイルの復活」と同じ性質)。
- **待ち行列の上限の値を変えること** …… 裁定298 と同じ形で当たらない。
  試験のほうも `PlayerState.MAX_PENDING_CHOICES` を読んで「上限+1件」を作りに行く。

## 12. 理解確認 Q&A

**Q1. 「割り込みは後回しだった」なら、なぜ 59 は中断だと思い込んだのか。**
A. **名前と、書いてあった説明のせいである。**`ResumePoint` の javadoc は
「Java には効果の途中で処理を中断し、後から同じ場所へ戻る仕組み(継続)がない」と書いており、
これは正しい。だが**そこから「だから深いところからは問い合わせられない」は出てこない** ——
継続が無いから続きを再開できないのであって、**続きが無ければ何も要らない**。
「してもよい」のドローは、それ自体が続きの全部である。
★教訓は「先送りの理由は、書いた本人の見立てにすぎない」(裁定194)。

**Q2. なぜ「いいえ」を候補の2つ目にしなかったのか。**
A. 「何も選ばない」と「いいえを選ぶ」が同じ意味になり、`min`/`max` の検証が
どちらを正とするかを決められなくなるからである。候補1件・min=0 なら、
**選択数そのものが答え**になる。送受信の形も1つも増えない。

**Q3. 位置ズレの照合で、ずれた候補だけを落とさないのはなぜか。**
A. 落とすと `chosen` が空になりうるので、**25個ある再開先すべて**に
「空で来たときは何もしない」を書くことになる(裁定163 が戒めた形)。
1件でもずれたら何も起こさない、なら判定は1箇所で済む。
★これは「安全側に倒す」ではなく「**規則を1箇所に置く**」ための選択である。

**Q4. 《不滅のネクロマンサー》の抜けは、どうすれば早く見つかったのか。**
A. **`report_effects.py` では見つからない。**あれは登録の有無しか見ない。
本文と実装の照合は人が読むしかなく、Ver0.4 由来169枚のうち
**作り直しの対象外とされた分は誰も突き合わせていない**。
★候補 D(新カード66枚の目視校正)を「据え置き分の照合」まで広げるのが、いまの最短距離である。

**Q5. 待ち行列の上限32 に根拠はあるか。**
A. **無い。**場のミニオンは両者で最大12体、1回の解決で誘発しうる回数はその程度である、
という見積もりに余裕を掛けた値でしかない。これは構築ルールではなく
**外から来るデータ・暴走した誘発への防波堤**(設計判断27)であり、
「正しい値」ではなく「明らかに異常な値」を捕まえるためのものである。
★だから試験も「32であること」ではなく「上限があること」を測っている(裁定298)。
