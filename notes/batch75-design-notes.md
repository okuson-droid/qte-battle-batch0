## 1. このバッチがやったこと(要点)

### 1-1. 裁定342〜345 を着手時に採番した

| 番号 | 確定した内容 |
|---|---|
| **342** | 通常モードの無人判定は**1段**である。**席を空ける段は作らない** |
| **343** | 対戦中の部屋も、全員切断のまま猶予が過ぎれば消す |
| **344** | 部屋消失は `WsMessage.type = "ROOM_LOST"` で伝える |
| **345** | 部屋が消えたと知ったら、通常モードはロビー(`/auto`)へ戻す |

★詳細と、伺わずに実装で決めたことは `notes/batch75-ruling-requests.md` にある。

### 1-2. ★★★M と N が「同じ工事の裏表」である理由

**片方だけでは成り立たない。**

- **N には M が要る。**部屋を消すようになると、戻ってきた人が
  「接続済みなのに盤面が来ない」状態に落ちる ——
  <b>掃除が、71 が残した穴を踏む人を自分で作り出す</b>。
- **M には N が要る。**サーバの再起動でしか部屋が消えないうちは、
  部屋消失の経路は**滅多に通らない**。掃除ができて初めて、
  <b>日常的に起きる出来事</b>になる。
- ★さらに **N の土台(切断の検知)が M の引き金でもある** ——
  「誰も繋がっていない」を数えられるようになったことと、
  「戻ってきた人が `ready` を撃つ」ことは同じ仕組みの表と裏である。

> ★★番人でもこれを測っている: `掃除の後に戻ると部屋消失を受け取る` ——
> <b>掃除が作った状態を、部屋消失の検出が受け取る</b>。

## 2. N —— 無人部屋の掃除(裁定342・343)

### 2-1. ★★★1段にした(手動モードとの決定的な違い)

```
手動: 切断から5分 → 席を空ける → 在室者0が5分 → 部屋を消す
通常: 誰も繋がっていない状態が5分 → 部屋を消す
```

★理由は `notes/batch75-ruling-requests.md` 1-1 に書いた3つである。
★★**猶予も1つしかない。**手動モードの2つを足して10分にはしない ——
<b>値を写すのではなく、理由から決める</b>(71 の教訓)。

> ★★★**同じ穴を塞ぐことと、同じ形で塞ぐことは別である。**
> 手動モードの2段は<b>あちらの席が「盤面の入れ物」の席だから</b>成り立っている。

### 2-2. ★★★接続の記録は `GameRoom` が持つ(席にも観戦者にも置かない)

```java
private final Map<String, String> sessions = new HashMap<>();   // occupantId → sessionId
private Instant emptySince = Instant.now();                     // 1人でも繋がっていれば null
```

66 が `PlayerSlot` と `Spectator` を**別の型**にしたのは、
席を見るのを忘れた分岐が観戦者をプレイヤーとして扱うのをコンパイルで止めるためであり、
**その理由は今も生きている**。

★しかし**「繋がっているか」はどちらでもまったく同じ性質**であり、
両方の型に同じフィールドを足すと**同じ規則が2箇所に書かれる**(設計判断38)。

> ★★`Spectator` が record で状態を持てないのは、**理由ではなく結果**である ——
> 状態を持たない型でよかったのは、観戦者の性質が「id と名前」だけだったからである。

★★★**72 の不変条件がそのまま効く**: 1つの id は席と観戦者のどちらか一方にしか居ない。
だから鍵が id であることに曖昧さが無く、**席を立って観戦に降りても接続の記録は持ち越される**。

### 2-3. ★★猶予の起点を書く場所は2つ、判定は1つ

接続が減る経路は **切断**(`markDisconnected`)と **退室**(`leave`)の2つある。
判定そのものは `noteSessionsChanged()` **1本**に閉じてある(裁定130)。

★★★**退室でも記録を外すのは、切断イベントが来ない経路があるから**である ——
退室してそのまま同じタブで別の部屋へ入ると、切断は起きない。
外さないと**誰も居ない部屋が永久に「1人繋がっている」と答える**。

### 2-4. ★★★掃除は「今」を受け取る版を持つ

```java
@Scheduled(fixedRate = 60_000)
public void sweep() { sweep(Instant.now()); }

public void sweep(Instant now) { ... }
```

★**時計を差し替えるためだけの引数ではない。**`Instant.now()` を走査の途中で何度も読むと、
部屋ごとに違う「今」で判定することになる —— **1周のあいだ同じ時刻で全部屋を見る**ほうが、
そもそも正しい。
★★設定を足して時計を注入する形は**採らなかった**(器を1つ増やす価値が無い)。

### 2-5. ★★掃除の番人は台帳を自前で持つ

`GameRoomManager` は singleton であり、**他の試験が作った部屋も入っている** ——
`@Autowired` のものを掃除すると、<b>同じ文脈で走る他の試験の部屋まで消す</b>。
★掃除そのものを測る節だけは `new GameRoomManager()` を使う。
依存を持たない `@Component` なので、これで**本物の** `GameCleanupScheduler` が回る。

## 3. M —— 部屋消失の検出(裁定344・345)

### 3-1. ★★★71 の判断は誤りではなかった。前提が消えた

71 は `connectionFatal` を**作らなかった**。理由は
「`showRoomLostFatal` が無く、**その旗を立てる人が1人も居ない**」である(裁定178)。

★★**75 で立てる人ができた** —— サーバが `ROOM_LOST` を送る。
★これは 62 が裁定74(音声ファイルを同梱しない)を失効させたのと**同じ形**である:
<b>旧裁定が誤っていたのではなく、前提が変わったので結論が変わった</b>。

### 3-2. ★★★型で運ぶ(ERROR で代用しない)

`WsMessage` の4つ目の型として `ROOM_LOST` を足した。

★72 が `LEFT` について書いたのと同じ理由である ——
ERROR は「**その操作が拒否された理由**」であって、画面はそれを出して**その場に留まる**。
部屋消失は**留まれない**(次のどの操作も同じ結末になる)。

★★**手動モードは本文の文字列で判定している**
(`msg.message === 'この部屋に入室していません'`)。
あれは**サーバの文言を1文字直しただけで黙って効かなくなる** ——
しかも効かなくなっても画面は「エラーが出た」ように見えるので、**誰も気づかない**。

> ★★★これは 74 の教訓(効きすぎている実装は、別の規則の陰に隠れる)の**裏返し**である。
> あちらは<b>効きすぎているものが見えない</b>、こちらは<b>効かなくなったものが見えない</b>。

★75 は**手動モードを1文字も触っていない**(片肺として書き残した。71 の教訓)。
★★通常モードが**本文で判定していないこと**は壊し検証の軸15 が見張る。

### 3-3. ★roomId は「間違えようがない」

通常モードの roomId は**ページに埋め込まれた値**である
(`/rooms/{roomId}/play` が Thymeleaf で埋める)。
「間違った部屋IDを送る」経路が無いので、**`execute` が部屋を引けなかったら
部屋が本当に消えたということである**。

★手動モードの `showRoomLostFatal` が「猶予切れで席が空いた」も同じ扱いにしているのは、
<b>あちらは席が空くから</b>である。通常モードは席を空けない(裁定342)ので、
`ROOM_LOST` は常に「部屋が本当に無い」を意味する —— だからロビーへ戻す(裁定345)。

### 3-4. ★★★[ロビーへ戻る] は伝播を止める

`#seat-gate-buttons` には**席選択の委譲リスナーが付いている**。
`e.target.closest('button')` で拾われ、しかも `data-seat` が無いので
**「観戦する」として扱われる**。

★手動モードの `showRoomLostFatal` も同じ罠を `e.stopPropagation()` で避けている。
★★**番人の書き方に注意が要った** —— 下の 5-2 を参照。
