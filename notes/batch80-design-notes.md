# Batch 80 設計解説 —— 通常モードの演出(候補 B)

対象: `battle.js` の差分採取層に fx 層を乗せる。
**サーバ(Java)・カード定義・効果には1文字も触れていない。**

発端はマスターの指示である ——
「カードの効果でドローやミニオンの破壊が一瞬で行われ、
どのゾーンからどのゾーンに動いたのかもわかりにくいので動きを作りたい。動きは手動モードを参考に」。

Batch 62 は差分の採取層をここへ作り、
「fx 層(ゴースト・遷移)は作らない。演出を乗せる土台は次のバッチに残る」と書き残した。
★**その「次のバッチ」が 18 バッチ遅れて来たのが 80 である。**

★**「ドローと破壊が見えない」を母集団にしない。**それは症状であって構造ではない(79 の教訓)。
数えるのは「通常モードのビューで**観測できるゾーン間の出入り**の全体」である。

★★母集団を **3段**で取った ——
**A: 何が観測できるか** / **B: 何を演出に置けるか** / **C: 演出がどこへ着地できるか**。
★<b>C を先に確かめたのは 70〜78 の教訓による</b> ——
番人(と演出)を置く場所を選ぶ前に、そこまで届くかを確かめる。

読む側と試験側は `getHand()` を読み取り専用の窓として残せば守れるので、
本当の工事は **77箇所**である。★★<b>ところが、そこにこの一族がそのまま在る</b>:

> ★★★**77箇所のうち1箇所で同一性を落としても、既存の951件は1件も赤くならない。**
> 試験が見ているのは<b>カードIDだけ</b>であり、同一性はどこでも測られていない。

| **ミニオンの破壊** | 場から `instanceId` が消える(出発点が確定)かつ 墓地に同じ名前が積まれる(着地点が確定) | **要らない** |

★<b>場のミニオンはもともと `instanceId` を持っている</b>(母集団A の Z4)。

### 0-7. ★★手動モードを「参考にする」と「写す」は別である

マスターの指示は「動きは手動モードを参考に」であった。
★<b>写さなかった</b> —— 通常モードのビューは手動モードと**材料が違う**(0-1)。
`manual-battle.js` の `fxIndex` / `diffViews` は<b>全ゾーンに `instanceId` が在ること</b>を
前提に書かれており、そのまま持ってきても1件も動かない。

★★<b>写したのは「形」だけである</b>:
- 差分は<b>純オブジェクトの比較</b>で採り、DOM に触らない(検証が直接叩ける)
- 旧位置は<b>描き直す前</b>に読む(read と write の相分離)
- 動く要素は<b>盤面 DOM の外</b>(`position: fixed` の層)に置く
- 強制同期レイアウトは<b>1回だけ</b>
- 上限を超えた配信は<b>黙って何も出さない</b>(演出は1手を語る道具である)

★★★<b>語彙(kind の名前)と時間定数の意味は揃えた</b> ——
片方を読んだ人がもう片方を読めるようにするためである。
★<b>ただし値は揃えていない</b>(裁定358・5章)。

## 1. ★★★何を作ったか(1本の道)

配信が届いてから演出が走るまでは、**1本の道**である。取り付け点は `onMessage` の1箇所だけである。

```
onMessage(配信)
  ├ fxCaptureDelivery(前のビュー, 新しいビュー)   ← ★render の「前」
  │    ├ fxDiff        …… 出口と入口を採る(純オブジェクト・DOM に触らない)
  │    ├ fxEffects     …… 出口と入口を突き合わせて演出の列にする
  │    ├ sfxPlayForEffects …… ★62 の音(順序も取り付け点も1文字も変えていない)
  │    └ fxCaptureOrigins  …… ★旧位置を読む(描き直す前のきれいな DOM)
  ├ render(view)                                  ← 盤面を全消し再描画
  └ fxSpawn()                                      ← ★render の「後」。新位置を読んで走らせる
```

★★**読む相と書く相を分けている**(手動モード 29 の相分離と同じ形)。
描き直したあとでは、出発点の要素はもう存在しない。

★★★**`render()` の中では呼ばない。**`render(latestView)` は
**画面の操作のたびにも走る**(15箇所)——
あそこに置くと**クリックのたびに演出が出る**。
★62 が音でまったく同じ判断をしている(裁定287)。

## 2. ★★★出口と入口(このバッチの語彙)

### 2-1. なぜ「出口と入口」なのか

手動モードは全ゾーンのカードが `instanceId` を持つので、
**前後のビューを突き合わせて「この1枚がここからここへ動いた」と言える**。

★通常モードにそれは無い(母集団A)。だから語彙を1段落とした:

> **1回の配信で、席ごとに「何が減って(出口)、何が増えたか(入口)」を並べる。**

★★これは**観測そのもの**である。「破壊された」「使われた」という解釈は1つも入らない
(手動モード 32 の「判断を実装しない原則」を、材料の違うところで守っている)。

### 2-2. ★★中身が届いているゾーンは名前で、届いていないゾーンは枚数で

| ゾーン | 自席 | 相手席 |
|---|---|---|
| 手札 | 中身の**多重集合** | 枚数だけ |
| 禁忌 | 中身の多重集合 | 枚数だけ |
| マナ | 中身の多重集合(★裏向きも名前つき・裁定351) | 表向きだけ(裏向きは匿名) |
| 墓地・消滅 | 中身の多重集合(公開) | 中身の多重集合(公開) |
| 場 | ★**`instanceId` で一意** | ★**`instanceId` で一意** |
| 山札 | **枚数だけ** | **枚数だけ** |

★★★**見分け方は「枚数 &gt; 届いた配列の長さ」である。**
これは手動モードの `fxWindowedZones` と**まったく同じ規則**である。

★★**最初は `hand` が null かどうかで見分けていた。**サーバは相手の手札に null を入れるので、
それで合っていると思った ——
★<b>置いた番人が、その日のうちに赤くなった</b>(verify 80-6)。
検証のフィクスチャは相手席にも `hand: []` を入れており、**null では来ない**。

> ★★★<b>サーバが null を入れるのは実装の都合であって、規則ではない。</b>
> 空配列で来ても、一部だけ来ても、
> <b>枚数と合わなければ名前では語れない</b>のは同じである。

★<b>75 の教訓(測っているものが生きている番人は、実装が変わるとちゃんと赤くなる)の、
置いた当日の実例である</b> —— しかも**壊し検証より先に**出た。

### 2-3. ★★★突き合わせは3段である(裁定355・356)

```
① カード名で結ぶ    …… 同じ席を先に見る
② 匿名で結ぶ        …… 残りが全体で「出口1・入口1」のときだけ
③ 結ばない          …… 出口は消滅、入口は出現として語る(裁定356)
```

★**①が効く例**: スペルを使って(手札 → 墓地)、その効果でミニオンが1体壊れた(場 → 墓地)。
出口2・入口2 なので**匿名では解けない**が、名前が両端で照らせるので**2本とも正しく結ばれる**。

★★**②が効く例**: ドローである。**山札は名前を持たない**ので①では結べない ——
「残りが1対1だから」結ばれる。★<b>これが匿名で結ぶ段の唯一の出番である。</b>

★★★**③は「何も出さない」ではない。**
「1枚が場から消えた」は**観測できている** —— 観測できていないのは**行き先だけ**である。
> ★<b>観測できたところまでを語り、その先は黙る。</b>

★★**同じ席を先に見る理由**: 同名のカードが両席に在るときに、
「相手の場から自分の墓地へ」という**起きていない移動**を作らないためである。

★★★**「多いほうに合わせて総当たりする」ことはしない。**
総当たりは**当たることも外すこともある推測**であり、外したときに嘘を描く。
<b>一意に決まるときだけ結ぶ</b>のが、観測の範囲を越えない唯一の書き方である。

### 2-4. ★★山札は「窓」である(裁定356 の例外)

山札は**中身が1枚も届かない**。そこで出現・消滅を描いても、
**裏面が1枚点滅するだけで何も語らない**。

★<b>移動の端にはなれる</b>(ドローがそうである)—— 語れなくなるのは**端が片方だけ**のときである。

★★同じ扱いが**相手の手札**と**相手の禁忌**にも掛かる(どちらも枚数しか届かない)。
★★★<b>相手の裏向きマナは「窓」ではない</b> ——
タイルは見えていて居場所が分かるので、裏面のゴーストに意味がある。

## 3. ★★状態系(その場で変わるもの)

| 何 | どう採るか | なぜ |
|---|---|---|
| タップ(場) | 同じ `instanceId` で `tapped` が変わった | ★**居場所が変わっていないミニオンだけ**を見る(手動 32b と同じ切り分け) |
| タップ(マナ) | 同じ**位置**で `tapped` が変わった | マナは識別子を持たない |
| 裏返り(マナ) | 同じ**位置**で `faceUp` が変わった | 同上 |
| 進化(場) | `underCardIds` が**増えた** | ★増加だけを見る(解体は素材が場へ出るので、出入りの側が語る) |

★★★**マナは、枚数が変わった配信では1件も採らない。**
位置で追うしかないので、枚数が変われば位置がずれ ——
<b>裏返っていないマナを「裏返った」と描いてしまう</b>。
★<b>枚数が変わった配信で起きたことは、出入りの側が語る</b>(置いた・墓地へ送った)。

★★**動いたカードに状態の演出は重ねない。**ゴーストが既に語っているので、
同じ1枚に2つの演出を重ねると**かえって読めなくなる**。

## 4. ★★見た目(ゴーストと実要素)

| 演出 | 何に当てるか | なぜ |
|---|---|---|
| `move` / `draw` / `vanish` | **ゴースト**(fx層) | 出発点の要素はもう無い |
| `appear`(場) | **実要素**のフェードイン | 次の配信で再構築されても「最終状態で即時表示」に落ちるだけ |
| `appear`(場以外) | ゴースト | 実要素が無いゾーンだから |
| `tap` / `flip` / `sink` | **実要素** | その場で変わるものだから |

★★**ゴーストの見た目は通常モードの `cardFace()` が作る。**
手動モードのフェイスを持ち込むと**カードフェイスの実装が3つ**になる ——
★<b>裁定111 により通常モードの `cardFace` も `.mcard` を出すので、候補 C は2つのままである</b>。

★★★**名前が届かなかったカードは裏面である。**
裏面は名前を1文字も運ばないので、
<b>非公開情報が漏れることは構造的に無い</b>(サーバのフィルタが唯一の正である・設計判断9)。

### 4-1. ★アンカー(演出の着地点)

★**描画関数が自分の作った要素をその場で登録する**(手動モードの `registerZoneAnchor` と同じ)。
★★<b>添字で引かない</b> —— パイルは4枚とも同じクラス(`.auto-pile`)なので、
並び順を変えた日に**黙ってずれる**。

★★★**9ゾーン × 2席 = 18本**である(母集団C)。
一時公開ゾーンだけは**画面に描かれていない**ので、アンカーが無い ——
