## 2. K: ホバーの取りこぼし(指摘1)

### 2-1. 3箇所に呼び出しを足しただけである

69 が `attachHover` を呼んだのは**場のミニオンと手札の2箇所**だけだった。
70 が足したのは次の3箇所である。

| 場所 | 関数 | 足したもの |
|---|---|---|

★★**禁忌の帯は 69 の教訓「途中」の再演である。**

## 3. 払い方の規則を1本にする(裁定315・316・317)

### 3-1. 69 までの `payCost` には「どれを払うか」が無かった

```java
for (ManaCard mana : player.getManaZone()) {
    if (remaining == 0) break;
    if (!mana.isTapped()) { mana.tap(); remaining--; }
}
```

**マナゾーンの先頭から、未タップのものを順にタップする** —— 表裏も一時マナも1つも見ていない。
裁定315・316 はここに順序を持ち込む。

| 何を払うか | 順 | 理由 |
|---|---|---|
| 通常のコスト | **一時マナ → 裏向き → 表向き** | 一時マナは期限付き(316)。表向きは**禁忌の弾**として温存する(315) |
| 禁忌のコスト | **表向き → 裏向き** | 裏向きを使うとマナが**永久に減る**(317)。減らずに済む側から使う |

★**通常と禁忌で順が逆になるのは、同じ理由の裏返しである。**
表向きマナは禁忌の支払いで「裏返すだけ」で済むが、裏向きしか無ければ「墓地へ送る」ことになる。
つまり**表向きマナは禁忌の弾でもある**ので、通常のプレイでは温存し、禁忌では先に使う。

### 3-2. 順序は `ManaPayment` 1本が正である(裁定130)

`ManaPayment.normalOrder(player)` / `tabooOrder(player)` が、
**払う順に並べたマナゾーンの位置**を返す。呼ぶのは3箇所である。

- `GameService.payCost`(実際に払う)
- `GameService.resolveTabooPayment`(禁忌を自動で払う)
- `GameViewBuilder`(**ビューに載せる**)

### 3-3. ★★★クライアントには「規則」ではなく「順序そのもの」を送る

裁定318・321 により、**カードをドラッグしている最中に「これから払われるマナ」を光らせる**。
つまり**クライアントも同じ順序を知る必要がある**。

★ここで払い方の規則をクライアントへ書き写すと、
**サーバの払い方が変わった日に、強調表示だけが黙って嘘になる**(67 の教訓・**写し**)。

→ **順序そのもの**をビューに載せ(`you.manaPayOrder` / `you.tabooPayOrder`)、
クライアントは「**先頭から n 件**」を取るだけにした。
★**クライアントは払い方の規則を1つも持たない**(裁定234 の筋)。

```js
function plannedManaIndexes() {
    const order = dragging.from === 'TABOO' ? you.tabooPayOrder : you.manaPayOrder;
    return order.slice(0, draggingCost());
}
```

★**相手のビューには入れない。**どのマナから払うつもりかは操作の手の内であり、
盤面の公開情報ではない(設計判断9)。

### 3-4. ★★★順序を入れ替えても、既存の758件は1件も落ちなかった

これは 67 で7枚のカードに起きたのと**同じ形**である ——
「落ちなかった = 変えていない」ではなく、**そもそも測られていなかった**。
**払い方の順序を測る試験は、69 まで1件も無かった。**

→ `Batch70ManaPaymentTest` を置いた。★測り方は2つに分けてある。

| 何を守るか | 測り方 |
|---|---|
| **払いが順のとおりであること** | 払う直前に `ManaPayment` を読んでおき、払ったあとタップされていたのがその先頭 n 枚か。★**期待する位置を1つも書かない**(裁定41) |
| **順序そのものが裁定のとおりであること** | 「一時マナは裏向きより先」「裏向きは表向きより先」など、**並びの前後関係**で測る |

★★**この2つを1つの試験に混ぜてはいけない。**
前者は**実装から期待値を読む**ので、順序を変えても落ちない(裁定298)——
それは番人の失敗ではなく、**そういう性質の試験**だからである。
★壊し検証のケース2 が、その形を**わざと NG として置いてある**。

## 4. 入口を2つにする(裁定318〜323)

### 4-1. 何がどう分かれたか

| 入口 | 操作 | マナ | 確認 |
|---|---|---|---|
| **ドラッグ&ドロップ** | 手札・禁忌から落とす | **自動**(3-1 の順)。ドラッグ中に光る | **挟まない**(裁定321) |
| **クリック** | カードを押す | **手で選ぶ** | **必ず挟む**(裁定319) |

★**違うのは払い方だけである。**落としたあと・確定したあとの道
(進化素材 → 対象選択 → 送信)は**まったく同じ**である。

### 4-2. 確定待ちの器を1つにした

69 まで、確定待ちの状態は**禁忌専用の `tabooPay`** 1つだけだった。
裁定319(クリックからのプレイ)と裁定323(マナチャージ)で、確定待ちが**3種類**になる。

★★**3つを別々の変数にしなかった。**確定・キャンセルの導線が3組に増えると、
「今何を待っているのか」の判定が3箇所に散る(裁定130)。

```js
let manaPay = null;   // { kind: 'PLAY' | 'TABOO' | 'CHARGE', cost, picked, warn, ... }
```

- 種類ごとの違いは **`payCandidate(mana)` 1箇所**だけが持つ
  (`TABOO` は一時マナ以外 / `PLAY` は未タップ / `CHARGE` は候補なし)。
- 案内文は **`manaPayPrompt()` 1本**が作る。
- 確定は **`confirmManaPayment()` 1本**であり、そこから3つの行き先へ分かれる。

★★**禁忌の自動確定をやめた。**43 の禁忌は「必要枚数に達した瞬間に自動で確定」していたが、
指摘5 は明示的に「確定ボタンを押したらプレイされる」と言っている。
★**選んだマナを外せるようにもした**(同じタイルをもう一度押す)——
選び直せない確定を作らない。

### 4-3. ★★★マナが1通りでも自動確定しない(裁定319)

69 の見立ては「マナが1通りにしか払えないなら自動で確定してよい」だった。**外れた。**

★理由は 69 が自分で書いている ——
**あれは効果の解決中の選択についての流儀**(68: 選ぶ余地が無いときだけ自動で決める)であって、
**プレイそのものを始めてよいかという層には効かない**。
★**誤操作の防止は「選ぶ余地の有無」とは別の軸である。**選ぶ余地が無くても、押すつもりが無かったことはある。

→ 実装には**自動確定の分岐そのものを書いていない**。
★壊し検証に「その分岐を消す」ケースが無いのはそのためである(消す対象が無い)。
代わりに軸17 の2件目が「**確定を押すまで飛ばない**」を名指しで測っている。

### 4-4. 落とし先は種別で決まる(裁定318・320)

| 種別 | 落とし先 | 器 |
|---|---|---|
| ミニオン・進化 | 自分のミニオン行 | `#my-minions` |
| ウェポン | 自分のリーダー | `#my-leader` |
| スペル・【賢魂】 | **常設のスペル枠** | `#spell-drop` |
| (マナチャージフェイズ)手札の1枚 | 自分のマナゾーン | `#my-mana-row` |

★対応表は **`dropZoneOfType` 1本**である。種別に合わない落とし先は**光らせない** ——
裁定318 が種別で決めている以上、合わない落とし先は**存在しないのと同じ**である。

★★**スペル枠は「あいている場所」ではなく「決まった場所」にした**(裁定320)。
可変にすると盤面の状態でドロップ先が動き、落とし損ねが増えるうえ、
**検証で位置を固定できない**(65 の「実装の定数を書かずに測る」が測る相手を失う)。
実測: 中央列 966px のうちミニオン6体が使うのは 602px。120px の枠を常設しても足りる。

★**【賢魂】は落とし先で決まる**(裁定318)。同じミニオンカードでも、
盤面へ落とせば召喚、スペル枠へ落とせば賢魂である。**ドラッグ1回で両方を表せる。**

★**進化は素材の上に落とす**(裁定318)。2体目以降は**今までどおり問い合わせる**(裁定322)——
52 が作った素材選択の器(`beginEvolutionSelection` / `pickEvolutionMaterial`)を
**そのまま呼ぶ**ので、足した物は無い。

### 4-5. ★★★確認と「どちらの姿で使うか」は別物である

裁定321 は「ドラッグに**確認**を挟まない」と決めた。
★しかし**【賢魂】か召喚か・特殊召喚か通常か・強化使用か**は確認ではなく、
「**どの規則で使うか**」という宣言である。

- 【賢魂】…… 落とし先で決まる(裁定318)。**問いは消えた。**
- 特殊召喚・強化使用 …… 落としたあとに尋ねる。**落とし先で分けられない**(どちらも盤面である)。

★これは裁定を仰がずに実装で決めた。裁定184 は「2通りに読める本文」の話であり、
裁定321 の「確認」が誤操作の防止を指していることは文脈から1つに定まる。

### 4-6. 裁定317 の警告 —— 器を新しく作らなかった

裏向きのマナが墓地送りになる禁忌のドラッグは、**確認で止まる**(裁定321 の唯一の例外)。

★★**警告専用の器を作らなかった。**
自動の払い方(`tabooPayOrder` の先頭 n 件)を**あらかじめ選んだ状態**で確定待ちへ入れる。

- 人はそのまま[確定]を押してもよい。
- **選び直してもよい**(表向きのマナを手で選べば墓地送りを避けられる)。

★確認と手動選択を別の器にしないのは、どちらも「**確定を待っている**」からである。
★`confirm()` ではなく画面内の確認にしたのは、裁定113(取り消せない操作にだけ確認を置く)と
64 の割り込みの器に合わせるためである。

### 4-7. ★★★ドラッグ中に `render()` を呼ばない

`render()` は `#my-hand` を作り直す。**掴んでいる要素そのものが DOM から消える**ので、
ブラウザがドラッグを中断する。

★これは手動モードの 19b hotfix2 が踏んだのと**同じ性質**の事故である
(あちらは「dragstart の処理中に祖先の `pointer-events` を変えると、
dragstart の直後に dragend が来て dragover も drop も発火しない」)。

→ ドラッグ中の見た目の更新は**クラスの付け外しだけ**で行う。

- `markDropZones()` …… 落とせる場所に `.auto-drop-ready` を付ける
- `refreshPlannedMana()` …… 払われる予定のマナに `.auto-pay-planned` を付ける
- `endDrag()` …… 全部外す(`dragend` は `drop` のあとにも必ず来るので、消去はここ1箇所に集約する)

★**「落とせる場所」と「今その上に居る場所」を分けた**(`.auto-drop-ready` / `.auto-drop-over`)。
1つの印にすると、複数のドロップ先が同時に光っているのか、指がどこに居るのか読めなくなる。

### 4-8. 落ちた場所は座標から取る(20a の A4)

`dragstart` の `e.target` は「指を置いた要素」ではなく、
ブラウザが祖先方向へ探して見つけた `draggable=true` の要素である。
**進化の素材のように「どのカードの上に落ちたか」が要る場面はこれでは取れない。**

```js
const under = document.elementFromPoint(e.clientX, e.clientY);
const card = under && under.closest ? under.closest('#my-minions .auto-card') : null;
```

★そのために `createMinionEl` が `el.dataset.instanceId` を持つようになった。

### 4-9. 光る条件と落とし先の判定を1本にした(裁定130)

44 以来、手札の `playable`(光り)の判定は `createHandCardEl` の中に直書きされていた。
ドロップ先の判定が**同じことを別の場所で計算する**と、
「**光っているのに落とせない**」が黙って生まれる。

→ `handCardPlayability(card, view)` 1本に寄せ、両方がそこを読む。
★同じ理由で、マナチャージができるかの判定も `canChargeMana(view)` 1本にした
(自動進行の `hasAvailableActions` も同じここを読む)。

## 5. 「今プレイしているカード」(指摘2)

### 5-1. 器はホバーと分けた

69 は「対象を選んでいる最中はホバープレビューを出さない」と決めた。
指摘2 が求めているのは**その裏側**である ——
出さないのは「**手を乗せた先**」の面であって、
「**今プレイしているカードそのもの**」は出しっぱなしにしてほしい。

| 何を出すか | いつ | 動き |
|---|---|---|
| ホバープレビュー(44・69) | 手を乗せている間 | 乗せた先で**入れ替わる** |
| **プレイ中の表示**(70) | 解決が終わるまで | **固定**。手を動かしても変わらない |

★★**同じ器を使い回すと、「乗せた先で入れ替わる」性質を引き継ぐ** ——
プレイ中のカードが**手の動きで消える**。だから `#auto-playing` を別に持った。

★**座標は `#auto-hover` と同じでよい。**問い合わせが出ている間はホバーそのものが止まっている
(`hoverBlocked` に `hasPendingChoice()` が入っている)ので、2つが同時に出ることはない。
★★**盤面のカードを覆わないことは実測で確かめてある** ——
この面は x:748 から始まり、ミニオンは6体並んでも x:614 で終わる。
verify 70-10 が「盤面のカードとの重なりが0件であること」を実測で見張る。

### 5-2. ★★★出どころは「積む口」で写し取る

面を描くには**カードID**が要る。64 が作った問い合わせ(`PendingChoice`)は
候補と案内文しか運んでいなかった。

★**クライアントに覚えさせるのは誤りである。**
「直前に自分が送ったカード」を覚えておく手もあるが、

### 5-3. ★★★置く側も1箇所にした —— `runEffect`

「いま解決しているカード」を書き込むのは `CardEffectRegistry.runEffect` **だけ**である。

```java
public void runEffect(String cardId, EffectContext ctx, Consumer<EffectContext> effect) {

}
```

★**戻すのに前の値を使う(null で潰さない)。**効果の解決は入れ子になりうる ——

★★★**直呼びを1つ足すと、そのカードのときだけ表示が黙って出なくなる**(69 の教訓・**途中**)。
症状はそのカードでしか出ないので、気づかれずに残る。
→ `Batch70PlayingCardTest#効果を呼ぶ口はrunEffectだけである` が、
`CardEffectRegistry` と `GameService` に直呼びが1つも無いことを見張る。
★測り方は「唯一の口を挟んでいる**合図のコメント**の間だけを取り除き、残りに `.accept(` が無いこと」である。

### 5-4. ★★【召喚時】の対象の問い合わせは、効果を呼ぶ「手前」で立つ

68 が足した `needsTargetChoice` は、効果を走らせる**手前**で問い合わせを積んで戻る。

## 10. マスターへの実機確認の依頼

- **手札をつまんで運べるか。**落とせる先が**黄色い破線**で光り、
  指が乗っている先だけ**塗りつぶし**になるか。

- **カードをクリックすると、右列に「払うマナを選んでください」が出るか。**
  マナを押して選び、[確定]で出るか。★もう一度押すと選択が外れるか。
- **マナチャージ**が、マナゾーンへのドラッグ**と**クリック(確認つき)の両方でできるか。
- **禁忌を運んだとき**、裏向きのマナしか無ければ**⚠の警告が出て止まる**か。
  表向きが在れば止まらずに出るか。
- **スペル枠**(自分のミニオン行の右の破線の箱)の大きさと位置は使いやすいか。

- **効果の解決中に「プレイ中」の面が出るか**(スペルでもミニオンの【召喚時】でも)。
- **禁忌の帯・墓地のパイル・墓地の一覧**にホバープレビューが出るか。
  ★一覧(モーダル)のときだけ**左に出る**のは読みやすいか。
