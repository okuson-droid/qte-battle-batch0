## 1. ★★★効果から進化を出す —— 「入口を4つ目にしない」

52 の設計解説 9-1 はこう書いていた ——

> `GameActions.putIntoFieldByEffect` は素材を取れない。効果から進化召喚を起こす経路は 53 が作る。
> 53 は「効果側から素材を選ばせる」割り込みを1つ足すことになる**見込み**である。

見込みは当たっていたが、**足したのは割り込みだけではなかった**。

### 1-1. 52 は「着地は1箇所」だったが、それは<b>召喚の</b>着地だった

52 は入口を3つ(通常・特殊召喚・禁忌)通し、着地を `GameService.summonToField` 1箇所に集めた。
ところが効果による「出す」は<b>召喚ではない</b> —— 【召喚時】を焚かないので、
`summonToField` には合流できない。あちらは `GameActions.putIntoFieldByEffect` である。

つまり**束を作る処理が2つの場所に要る**ことになった。素直に書き写すと、
裁定224(引き継ぐのは他のカードによって付与された効果だけ)を実装した長い for 文が2箇所に並ぶ。

**採った形:** 束を作る処理そのものを `GameActions.attachEvolutionMaterials` に切り出し、
**召喚側(`GameService.summonToField`)からもそれを呼ぶ**ようにした。
52 が「着地は1箇所」と書いたものを、53 が**もう1段深く**した形である。

★**壊し検証1番と2番が対になっている** ——
1番は共通化した処理を壊して<b>召喚側</b>の試験(52 が書いたもの)が落ちることを、
2番は同じ処理を壊して<b>効果側</b>の試験(53 が書いたもの)が落ちることを見ている。
1箇所にまとめたなら、まとめた先が両方から生きていることを確かめないと意味がない。

### 1-2. ★「場に出た後」も1本にした(登場の数え上げのため)

52 まで、`summonToField` と `putIntoFieldByEffect` の末尾には**同じ3行の発火**が並んでいた
(ON_ENTER / ON_ALLY_MINION_ENTER / fireAnyMinionEntered)。
52 の時点では「同じことを2箇所に書いている」だけで実害は無かった。

53 で実害が出た ——《英霊・コレキ》が「このターンに何体場に出たか」を要求したからである。
**数える場所が2つあると、片方だけを直した日に制限がすり抜ける。**
そこで `GameActions.fireEntryTriggers` にまとめ、数え上げをその先頭に置いた。
召喚だけが持つのは、その直前の **ON_SUMMON 1つだけ**になった。

★**「同じものが2箇所にある」は、使い手が現れるまで害を出さない。**
現れたときに初めてまとめられるので、52 でまとめなかったことは間違いではない
(裁定178・194 の系譜: 使い手を読んでから形を決める)。

### 1-3. 割り込みは2段(進化カード → 素材)

《英術・スケアロック》は「光のコスト3以下を1体出す。**その後**進化を1体出す」である。
1体目は使用宣言時に選べるが(条件が盤面に依存しない)、2体目は選べない ——
**直前に出した1体目を素材にできる**(裁定243)ので、候補が確定するのは1体目が着地した後である。

```
使用宣言(TargetSpec: 光・コスト3以下・ミニオン を最大1体)
  → 1体目を場に出す
  → 割り込み1: 手札の【進化】光ミニオンのうち、今の場で素材を確保できるものだけ  (SCARELOCK_EVOLUTION)
  → 割り込み2: その進化の素材条件を満たす自分の場のミニオン                     (SCARELOCK_MATERIAL)
  → 素材つきで putIntoFieldByEffect
```

★**進化カードは割り込みのあいだ手札に残したままである。**
先に抜くと、素材が足りなくなったときに<b>どのゾーンにも居ないカード</b>が生まれる
(51 の「先に場から取り除くと行き先の無いカードが生まれる」と同じ形)。
実際に場へ出すことが決まってから抜いている。

★**どの進化を出そうとしているかは `PlayerState.pendingEvolutionCardId` が運ぶ。**
`PendingChoice` は候補の一覧しか持てないので、それ以外の文脈は
`pendingSacrificeCount`(死者蘇生)と同じくプレイヤーの状態に置く既存の形に従った。

### 1-4. ★JavaScript を1行も足さずに済んだ(裁定234 の配当)

割り込みの UI は既にある(`PendingChoice.Kind.HAND` と `Kind.MINION`)。
候補はサーバが絞り込んで送るので、**クライアントは「【進化】とは何か」も
「素材条件」も知らないまま**この2段を通せる。
52 が `TargetSpec.Filter` を増やさない道を選んでいたことが、そのまま効いている。

★**53 が `Filter` を1つも足していない**のはこのためである。
「光文明の【進化】カード」というフィルタを足す案もあったが、
それは <b>battle.js に同じ判定を置く</b> ことを意味する(裁定195)。
候補を送るなら、置かなくてよい。

## 2. ★★墓地からの【特殊召喚】(《サモナーポップ・エンラ》)

「自分の手札**または墓地から**コスト1支払って場に出せる」——
【特殊召喚】は 52 まで「手札からの代替召喚」だけを表していた。

**採った形:** `SpecialSummonSpec` に真偽値 `fromGrave` を1つ足し、
`GameService.specialSummonFromGrave` を作った。
★**新しい規則をどこにも増やしていない** —— 条件・代替コスト・素材・着地は
手札からの特殊召喚とまったく同じ道具を使い、最後は `summonToField` に合流する。
このメソッドが独自に書いているのは<b>墓地から取り除くこと</b>と
<b>そのカードが墓地からも出せると宣言しているか</b>の2つだけである。

★**判定の正はカードの宣言1箇所である。**`GameViewBuilder`(墓地の面に導線を出す側)も
`GameService`(実際に出す側)も同じ `fromGrave` を読む。

★**墓地に居るエンラ自身も「6体」に数える**(裁定240)。
条件の評価は墓地から取り除く前に行われるので、素直に書けばそうなる ——
裁定190(「今の手札の枚数」に自身を含む)と同じ形である。

### 2-1. UI は「墓地を開く」導線に相乗りした

盤面は 1280×800 の1画面に収める決まりがある(裁定146)ので、
新しい常設ボタンは作れない。墓地パイルのクリックで開くフェイス一覧
(`showZoneFaces`)に、**サーバが可と言ったカードにだけ**[★特殊召喚]を添える形にした。

★**「今それができるか」を知っているのはサーバだけである。**
条件(墓地のミニオンが6体以上)もコストも、クライアントは1つも持たない ——
Batch 47 の「印」・52 の素材候補と同じ考え方である(裁定234)。

★**相手の墓地には導線を出さない。**`showZoneFaces` の第3引数が `isSelf` である。
verify 53-1 が「自分の墓地には出て、相手の墓地には出ない」を並べて測っている
(片方だけでは「常に出す」実装でも通る。裁定181)。

## 3. ★★「場に出られるか」を問う場所を1つにした

《英霊・コレキ》は「相手は自身のターン中1度しかミニオンを場に出せない」である。
マスター裁定により、これは<b>あらゆる登場</b>を数える(裁定237)。

この制限を素直に `putIntoFieldByEffect` の中だけに置くと、**3種類の事故**が起きる。

| 呼び出し側 | 何が起きるか |
|---|---|
| ギガマウス・バイト・神の福音 | 満杯でなければ手札から抜いたまま `null` を捨てる → **カードが消える** |
| 黄泉還る水龍・ゾンストライカーの `while` ループ | 墓地から消えないのに出られない → **無限ループ** |
| マナから場に出す(51) | マナを先に取り除く → **マナカードが消える** |

どれも「`isMinionZoneFull()` を先に自分で見る」という<b>既存の形</b>に乗っていたためである。
そこで **`GameActions.isFieldEntryBlocked(room, owner)`** を作り、
満杯を見ていた8箇所をこれに置き換えた。

★**呼び出し側は理由を区別しない。** 満杯でもコレキでも、やることは同じ ——
「出せなかったぶんは手札に戻す」「ループを抜ける」「マナを動かさない」である。
裁定163(同じ規則を2箇所に置かない)の適用先が、
「同じ値を2箇所に書いた」から**「同じ問いを別々の形で聞いている」**へ広がった。

★**召喚の側は例外を投げる。**`GameService.requireCanEnterField` を
5つの入口(通常・進化・特殊召喚・禁忌・墓地からの召喚)が呼ぶ。
<b>召喚は宣言そのものを弾き、効果は出せたぶんだけ出す</b>、という違いである
(マスター裁定237: 3体出す効果でも1体だけ出て残りは手札に戻る)。

★**数え上げはターン番号の刻印である**(`PlayerState.minionEntryTurn` / `minionEntryCount`)。
真偽値にできないのは、この数が<b>相手のターン中の登場も数える</b>からである ——
自分のターン開始時のリセット(`startTurnReset`)では戻し切れない。
裁定156(3) 以来4つ目・5つ目の「ターン番号を刻む」形である。

## 5. ★このバッチで見つかった、自分の作りかけた欠陥

### 5-1. 余計な宣言は、外しても何も落ちない(壊し検証28番)

《リボーンライヴ・ノア》を `CardEffectRegistry.IMPLEMENTED_CARDS` に入れていた。
【常在】をこのクラスのコードに直接書いたからである。だが**このカードは
【召喚時】のほうで表にも載っている**ので、`isRegistered()` は既に真を返す。
つまりその宣言は<b>外しても印が付かない</b> —— 番人を置けない記述だった。

★あの集合は「**表に1行も載らないカード**」の一覧であって、
「このクラスが面倒を見ているカード」の一覧ではない。**壊し検証がそれを教えた。**
(裁定116 の値打ちがいちばん素直に出た例である。)

### 5-2. ★注釈が番人を騙した(裁定114 の3度目)

`tools/report_effects.py` は登録の**左辺の書式**を走査して「登録あり」を数える。
そのことを説明するコメントに<b>走査の対象になる書式を例として書いた</b>ため、
ツールが「未知の登録先がある」と誤検出して止まった。

★裁定114 が言っているのはまさにこれである ——
**注釈は仕様の説明であって、判定に食わせる材料ではない。**
書き方を変えて解消し、コメント自身に「ここに書式を例示しないこと」と書き残した。

### 5-3. ★比べる相手が甘い試験が3つあった(壊し検証9・27番、および目視1件)

- 「墓地から出せないカードは通れない」を、**【特殊召喚】を1つも持たないカード**で測っていた。
  `spec == null` の側で弾かれるので、`fromGrave` の判定を外しても落ちない。
  → 《飛翔鉄人走太》(手札からのみ)に差し替えた。
- 「ニュウキロは自分のスペルを重くしない」を、**相手の手札が0枚**の盤面で測っていた。
  数え違いをしても増加量が 1×0 = 0 になる。→ 相手にも手札を持たせた。
- 「効果で出した進化は【召喚時】を発動しない」は、**光文明の進化3枚に
  【召喚時】を持つものが1枚も無い**ため測れなかった(空振り)。
  → その試験は置かず、同じ経路を通る《灰ノ霊呼者》の側で測った(裁定186)。

★**3件とも「壊してみる」まで気づけなかった。**裁定181 は知っていても、
自分が書いた試験がその形になっていることは、壊さないと見えない。

## 6. ★このバッチが答えていないこと

### 6-1. 効果で出した進化の【召喚時】は、現行のカードプールでは観測できない

《英術・スケアロック》が出せるのは<b>光文明の進化</b>だけで、
その3枚(ニュウキロ・コレキ・タイガラム)に【召喚時】を持つものが1枚も無い。
発動しないこと自体は `putIntoFieldByEffect` が ON_SUMMON を1度も焚かないという
構造で決まっており、その経路は《灰ノ霊呼者》の試験が測っている。
★50 の《演舞の墓守》の2本目・51 の防御的な分岐2つと同じ性質である ——
**カードが増えれば自動的に観測できるようになる。**

### 6-2. 《英霊・コレキ》の制限を「相手のターン中の登場」で観測する経路が無い

「自身のターン中」の限定は、相手の手番中に自分の場へミニオンが出る経路
(【破壊時】の蘇生・カムバックキーパーの自力復帰)でしか観測できず、
どれも8手ぶんの段取りを要する。★この1件だけは<b>判定層に直接問う</b>形にした
(`RuleGuards.minionEntryDenial`)。裁定187 が守りたいのは「発火する場所が正しいか」であり、
ここで測っているのは<b>判定そのものの向き</b>である。

### 6-3. 進化を「効果で出す」経路は、まだスケアロック専用の候補作りを持っている

`requestScarelockEvolution` は「光文明の進化」に絞った候補を作る。
2枚目の「効果で進化を出すカード」が来たら、絞り込みの述語だけを引数に取る形へ
一般化することになる。★<b>今それをやらない</b> —— 使い手が1枚しかない器の形は決められない
(裁定178・194)。

### 6-4. 引き継ぎからの継続

- **作り直し(Ver1.1 で本文が変わった実装済みカード)は手つかず。**48〜53 で範囲外。
- **裏向きマナと `fireManaPlaced` の非対称**(51 設計解説 6-2)。★裁定を仰いでいない。P5。
- **`unlimitedCopies` の死んだ分岐3箇所**(49 設計解説 6-2)。無害。P5。
- **攻撃の経路の到達しない分岐2つ**(51 設計解説 6-1)。★53 でも到達しないままである。
- **プリセットデッキは Ver1.1 版にしていない**(P5)。実機確認用に2つ添えた。
