## 1. ★★発火点を1つも増やしていない

裁定67 は「取り付け点は既に1箇所ずつある(`fxBuildDeclare` / `askConfirm` /
`fxBuild` のディスパッチ)。**新しい発火点を作らずに済むかを最初に確かめること**」と

**足りている。しかも3箇所ではなく2箇所で済んだ。**

| 音 | 取り付け点 | 備考 |
|---|---|---|
| ドロー / 配置 / タップ / めくり / LP増減 / 決着 | `fxSpawn`(1箇所) | |
| 確認の [実行] | 確認モーダルの [実行] ハンドラ(1箇所) | |

## 2. ★★音は動きではない

### 2-1. ゲートを2本に分けた

32a は `fxAllowed()` に2つの条件を入れていた ── `fxEnabled` と
`prefers-reduced-motion` である。音をこのゲートにぶら下げると、
**演出を切っている人には音も鳴らない**ことになる。

`prefers-reduced-motion` が言っているのは「画面を動かすな」であって
「静かにしろ」ではない。むしろ**演出を止めている人にこそ**、音は状態変化を伝える
数少ない手段である。そこでゲートを2本に分けた。

| ゲート | 見るもの |
|---|---|
| `fxAllowed()` | `fxEnabled` / `prefers-reduced-motion` |
| `sfxReady()` | unlock 済みか / ミュートでないか / 音量が0でないか |

★分けたことの帰結として、**差分を採る条件も直す必要がある**。
`applyView` が `fxAllowed()` だけで差分の計算を飛ばしていたので、
そのままだと**音が見た目の道連れで消える**。共通の材料を採るかどうかは
`fxDiffNeeded()`(= どちらかが要るなら採る)に切り出した。

```js
function fxDiffNeeded() { return fxAllowed() || sfxReady(); }
```

★旧位置の採取(`fxCaptureOrigins`)は**見た目のためだけ**のものなので、
音しか出さないときは読まない。29 の「読む相は1回だけ」の規律を無駄に消費しない。

### 2-2. ★共通の制約はそのまま音にも効かせた

分けたのは reduced-motion だけである。次の2つは**音にもそのまま効く**。

- **差分が8件を超えたら鳴らさない**(裁定8)。総入れ替え(リセット・配り直し・
  全アンタップ)は1手ではないので、音でも語らない。
- **開始シーケンス中(`fxStartLocking`)は鳴らさない。** 同じ理由である。

★ここで「リセットしたのに完全に無音」が残るが、それは
**確認モーダルの [実行] の音**(`commit`)が埋めている(1章の表)。
破壊的操作は差分が8件を超えるので演出が出ない ── 押した手応えが画面に何も残らない
場所であり、そこだけは音が単独で1手を語る。取り付け点が2つ要ったのはこのためである。

### 2-3. ★★音源はコードで合成する(ファイルを同梱しない)

`SFX_SPECS` に波形・周波数・長さ・音量を書き、WebAudio の
オシレータ / バンドパスを通したノイズで組み立てている。音声ファイルは1つも足していない。

理由は**失敗の広さ**である(裁定27 の一般形)。

| | 音声ファイル | コードで合成 |
|---|---|---|
| 読み込み失敗 | ある(404・CDN・遅延) | **無い** |
| キャッシュ版数の管理 | **4系統目**が増える | 増えない(js に同居) |
| ライセンス | 要確認 | 不要 |
| 調整 | 素材を作り直す | **数値の表を1行直す** |

★静的ファイルの版数は既に3系統あり(`manual-battle.js` / `battle.js` / `battle.css`)、
36 で「揃っていること」を機械判定にしたばかりである。4系統目を増やす判断は、
そのバッチの次に置くものではない。

★★**合成の音色は機械で測れない。** そこで**マスターが実機で聞いて直せる形**にした ──
調整するのは `SFX_SPECS` の表だけであり、コードには触らない(8-3)。
「機械で測れないものを機械で測ろうとせず、測れる決めごとのほうを測る」の音版である。

## 3. 何を鳴らすか

### 3-1. 音の語彙は演出の語彙より粗い

`fx.kind` は9種類ある(move / draw / vanish / appear / lp / tap / flip / sink / declare)。
音は7つに畳んだ。移動・出現・消滅・スタックへの吸収は、耳から見ればどれも
「カードが動いた」である。

| 音 | 何から鳴るか |
|---|---|
| `draw` | ドロー |
| `place` | 移動・出現・消滅・進化スタックへの吸収 |
| `tap` | タップ / アンタップ |
| `flip` | 表裏の反転 |
| `lpDown` / `lpUp` | LP の減少 / 増加 |
| `decisive` | 決着の宣言 |
| `commit` | 確認モーダルの [実行](★差分から来ない唯一の音) |

★`lp` だけは表に無い。増と減で意味が逆であり、**表では決まらない**からである
(`sfxNameFor` が符号を見る)。

★★**この表の取りこぼしには番人を置いた**(5章)。`fxEffects` が作る `kind` を
**ソースから拾って**、全部に音が付いているかを確かめる。演出を1つ足したとき、
音の表への追加を忘れると落ちる。テスト側に一覧を書き写すと、
写した一覧のほうが古くなるだけで番人にならない。

### 3-2. ★★1回の配信で鳴らす音は1つである

手動モードの**1配信は1操作**である。1操作に対応する手応えは1つである。
差分の件数だけ鳴らすと、音が語るのは「何をしたか」ではなく
**「何件変わったか」**になる ── これは裁定8(総入れ替えでは演出を出さない)や
「演出は1手を語る道具である」と同じ考え方の音側である。

種類が複数あるときは優先順位で1つを選ぶ。

```js
const SFX_PRIORITY = ['decisive', 'lpDown', 'lpUp', 'draw', 'flip', 'tap', 'place'];
```

★★**珍しい出来事ほど優先する。** 決着は1試合に1回、LPの増減は数回、
ドローは毎ターン、タップと移動は毎手である。頻度の高い音は
「何が起きたか」を語らない ── 常に鳴っているものは情報を持たない。

★優先順位は**1箇所にある**。「LPと移動が同時ならどちらか」を
呼び出し側で判断させない(設計判断28 と同じ形である)。

## 4. ★★自動再生ポリシー: unlock は「最初のユーザー操作」である

ブラウザは、ユーザーの操作を経ていない音の再生を止める。
`AudioContext` の生成と `resume()` は**操作のハンドラの中**で行う必要がある。

ハンドオフは「どの操作で行うかは1箇所に決める。**席選択ゲートの決定が素直だが、
復帰はゲートを通らない**」と申し送っていた。答えは次のとおりである。

**★★★どの操作か、を決めない。決めた瞬間に「決めていない経路」ができる。**

```js
const SFX_UNLOCK_EVENTS = ['pointerdown', 'keydown'];
for (const type of SFX_UNLOCK_EVENTS) {
    document.addEventListener(type, sfxUnlockFromGesture, true);   // 一度きり
}
```

- 席選択ゲートの決定を入口にすると、**復帰した人には二度と鳴らない**。
- 「ゲート**または**復帰」と2つ書くと、次に増える経路(直リンク・別タブ)で同じ問題が起きる。
- **操作を名指ししないのが、1箇所に決めるということの中身である。**
  これは裁定27(「失敗の広さで選ぶ」)と同じ形の判断である。

★`capture` で受けているのは、盤面のハンドラが `stopPropagation` しても
unlock を通すためである。
★これは**優先順位11(Pointer Events 移行)ではない。** `pointerdown` を
1つ使っているだけであり、盤面の操作は HTML5 D&D と `contextmenu` のままである。

**★受け入れた制限**: 復帰した直後、まだ何も触っていない間に相手の操作が届いても
音は鳴らない。ブラウザの制約であり、回避策は無い(あるとすればそれは
自動再生ポリシーの回避であって、やるべきことではない)。実害は、
その1手ぶんが無音になることだけである。

## 5. 設定パネル(★裁定16 のもとでは必須である)

BGM を作らないので、パネルにあるのは**ミュートと音量の2つだけ**である。

- **★★初期音量は 30 である。** Discord の通話と同時に鳴るため、既定で大きいと
  「まず音を切る」から始まることになる。裁定67 の「控えめ」を数値にしたものである。
- **保存は localStorage(`qte-manual-sound`)。★裁定31 と同じく部屋ごとにしない。**
  音量は人の性質であって部屋の性質ではない。
  ★読み書きは握りつぶす(0-1章の初回ヘルプと同じ理由。音の設定は対戦より優先されない)。
- **★状態行(`#sound-modal-status`)は「なぜ鳴らないのか」を出す唯一の場所である。**
  ミュート / 音量0 / ブラウザ非対応 / unlock 前を書き分ける。
  ★**色が意味を持つのは、鳴らない理由があるときだけ**である。正常時まで警告色にすると、
  色は何も言わなくなる(`sound-status-warn` の付け外し)。
- **★試聴は `change`(つまみを離したとき)で鳴らす。** `input` で鳴らすと、
  動かしている間じゅう音が連射される。値の反映だけを `input` で行う。
- **★ミュート中は音量のつまみを触らせない**(disabled)。
  「切ってあるのに音量を動かせる」は、鳴らない理由を2つに見せる。

パネルは 36 の規約にそのまま載せてある。

- `.info-modal` + `.info-modal-head` + `#sound-modal-x` + `#sound-modal-close`
- 開閉は `openInfoModal` / `closeInfoModal` を通る(裁定51・機械判定あり)
- したがって **× と Esc とフォーカスのトラップは、何も書かずに効いている**(裁定48)
- 「[閉じる] を持つものには必ず ×」の機械判定(34 hotfix)も自動的に新しい1枚を見ている

★入口は `[?]` の隣の `[♪]` である。どちらも「盤面の操作ではないもの」であり、
盤面の操作ボタン群(席・元に戻す・リセット…)と混ぜない。

## 6. 検証(373 → 397項目)

### 6-1. ★★音そのものは測れない。測ったのは2つに分かれる

| 何を測るか | どう測るか |
|---|---|
| **どの音を選ぶか** | 純関数(`sfxChoose` / `sfxNameFor`)を直接呼ぶ |
| **実際に鳴ったか** | **WebAudio の境界に張り込み**、音源ノードの生成を数える |

★後者を「`sfxPlay` が呼ばれたか」で測らない。呼ばれてもミュートや unlock 前で
**鳴っていない**ことがある。34 hotfix の教訓(「測るのは式ではなく結果である」)の
音版であり、36 の重ね順を `elementFromPoint` で測ったのと同じ形である。

張り込みは `page.addInitScript` で `window.AudioContext` を**包む**
(差し替えない ── 差し替えると「鳴らせない環境」の経路を測ることになる)。
