## 1. ★★★何を揃え、何を揃えなかったか

マスターの指定は「手動モードに合わせる」だが、**合わせてはいけないものが1つある**。

### 1-1. 揃えたもの

| # | 揃えたもの | 手動モードの出どころ |
|---|---|---|
| 1 | 部屋一覧(部屋名・席の埋まり・観戦・鍵) | 21a・21b |
| 2 | 部屋の属性(部屋名・観戦の可否・鍵つき) | 21a `ManualRoomOptions` |
| 3 | 席(A / B)と席選択のゲート | 21a・21b |
| 4 | 観戦 | 21a |
| 5 | 暗色(盤面と同じ #212529 / #f8f9fa) | 34 レビュー B-2 |
| 6 | デッキを**盤面で**読む | 24 |
| 7 | 誰であるかは localStorage が決める | 19a(設計書 6-3) |

### 1-2. ★★揃えなかったもの ——「全公開(一人回し)部屋」

マスターの指定に明記があった。**理由を書き残しておく**(次に読む人が「揃え忘れ」と誤解しないため)。

手動モードの全公開部屋は「1人で両席を操作する」モードである。あれが成り立つのは、
手動モードが**盤面の入れ物**でしかなく、伏せる仕組みが**人の目にしか無い**からである。

通常モードはサーバがルールを執行し、手札・裏向きマナ・禁忌デッキを
プレイヤーごとに伏せる —— そのフィルタは `GameViewBuilder` **1本だけ**である(設計判断9)。
「1人で両席を操作する」は、そのフィルタを1人ぶん解くことと同義であり、
**情報の非対称そのものを壊す**。

★その帰結として、通常モードでは**部屋名も名前も必ず要る**
(手動モードで省略できたのは全公開部屋だけだった)。
`GameRoomOptions` に「種類」という欄が**存在しない**のはそのためである。

### 1-3. ★揃えなかったもの(小)

- **席を立つ / 観戦者から席への昇格**(手動モードの 2-2)。
  通常モードの席は `GameState` の2人と1対1であり、試合が始まったあとに動かすと
  **盤面の持ち主が消える**。
- **切断の猶予と席の保持**(手動モードの 33)。通常モードには切断の追跡が無い。
  ★積み残しに書いた。

## 2. ★★★サンプルデッキ(おまかせ)の排除

### 2-1. 何が消えたか

`DeckFactory` の本体は、65 まで**6文明ぶんのスターターデッキ(各40枚)と禁忌デッキ2本**を
コードに書き並べたもの(約430行)だった。ロビーで
「デッキファイルを選ばずに [部屋を作成して入室] を押した人」に配るためのデッキである。

66 でその入口が無くなったので、**表ごと撤去した**(裁定178)。
残ったのはデッキファイルを並べ替える2つのメソッドだけであり、
このクラスは**依存を1つも持たなくなった**(カードマスタを引かなくなった)。

### 2-2. ★★一緒に消えた番人を書き残す(裁定196)

プリセットには**番人が付いていた**。消すときは、何を測らなくなったかを書く。

| 消した番人 | 測っていたこと | どうしたか |
|---|---|---|
| `Batch60Test` ×3 | プリセットが新カード10種・進化3種を積み、進化の素材が同じデッキに居る | **削除**(測る相手が消えた) |
| `EffectImplementationTest` ×1 | プリセットに載っていることは実装済みの根拠にならない | ★**対象を広げて残した**(下記) |
| `check_all.py` 6章 | プリセットの合計40枚・同名4枚以内 | ★**「消し残りが無い」を測る番人に作り替えた** |
| `DeckValidatorTest` の足場 | プリセットを検証層に通す | ★`support.SampleDecks` に置き換え(下記) |

★**`EffectImplementationTest` は対象が広がった。**
65 までは6文明ぶんのプリセット(各40枚)を走査していたが、66 からは
**その文明のデッキに入れられる全カード**を走査する。プリセットに載っていなかったカードも通る。
**測っていた性質は消えていない —— むしろ強くなった。**

### 2-3. ★試験用のデッキはカードマスタから組む

`src/test/java/com/example/qte/support/SampleDecks.java`(新設)が、
リーダー1枚から「検証を通るデッキ」を組む。

★**IDを書き並べていない。**書き並べた瞬間、それは「本番から消したプリセットの写し」になり、
カードデータが変わったときに**試験だけが古い世界を測り続ける**。
やっているのは3つだけである ——
その文明のデッキに入れられるカードを並べ、同名4枚以内で40枚になるまで詰め、
禁忌8枚を別の文明から採る。★40 も 8 も 4 も**この足場には書かれていない**
(`DeckValidator` の定数を読む。裁定298)。

## 3. ★★★観戦をどう作ったか —— フィルタを増やさない

観戦は 66 で新しく作った経路であり、**情報の非対称を破る道が1本増えた**。
ここをどう作るかが、このバッチでいちばん危ないところだった。

### 3-1. 観戦専用の「見せてよい範囲」を1行も書いていない

`GameViewBuilder.buildSpectatorView` がやっているのは、
`buildPlayerView(state, seat, isSelf = false, viewerTurn = false)` を**両席に当てる**ことだけである。

- `isSelf = false` …… 手札の中身・裏向きマナの中身・禁忌デッキの中身・割り込みの問い合わせが**入らない**
- `viewerTurn = false` …… 攻撃可否・使用可否のハイライトが**全部消える**
  (`attackerSide = isSelf && viewerTurn` から生えているため)

★**観戦専用の分岐を書かなかったのが肝である。**書いた瞬間フィルタが2本になり、
片方に項目を足したときにもう片方が遅れる。設計判断9 が守ろうとしているのはそこである。

### 3-2. ★守っているのは画面ではなくサーバである

観戦者は `playerId` を持たない。画面を書き換えて操作を送っても、
`GameState.playerOf` が**知らない id として弾く**。
画面から導線が消えるのは**見た目の親切**であって、守りではない(設計判断27)。

### 3-3. ★下段が席A、上段が席B(決めの固定)

観戦者に「自分」は無いので、どちらを下に置くかは決めの問題になる。
決めを毎回変えると、観戦者が2人いるときに違う盤面を見る。
席は不変(座り直しが無い)なので、**席で固定すれば必ず同じ絵になる**。

### 3-4. ★手札は裏面の列で出す

観戦者の下段(席A)は手札の中身が届かないので、そのままだと**空の行**になる ——
「手札0枚」に見える。相手の帯と同じ裏面の列を `handCount` から作って出す。
★**中身が無いことと、枚数が分からないことは別である。**

## 4. ★★「誰であるか」の出どころを変えた

### 4-1. 65 までの形とその害

65 までの盤面は `/rooms/{roomId}/play?playerId=<UUID>` だった。
つまり**誰であるかを URL が運んでいた**。害は2つある。

1. **URL を共有すると、相手が自分の席として入れる。**部屋を誘うつもりで URL を送ると、
   相手はこちらの手札を見ることになる。
2. **URL を失うと戻れない。**再読み込みは効くが、タブを閉じたら席が失われる。

66 は手動モードの 19a と同じ形にした ——
**localStorage(`qte-auto-occupant-{roomId}`)と入室APIがクライアント側で決める。**

### 4-2. ★ゲートは盤面ページの「中」に置く

独立ページにしない。盤面ページ内のゲートにしておくと、
`/rooms/{roomId}/play` の直リンクで来た人も**構造的に必ずそこを通る**。
「盤面の前に必ず通る」を**分岐ではなく構造で**保証する ——
分岐で守ると、経路が増えるたびに漏れる。

### 4-3. ★★★踏んだ穴: 一時的死角(TDZ)と、それを飲み込んだ catch

接続の開始(`resolveViewer().then(...)`)を、最初は**1章(接続)にそのまま**置いた。
`resolveViewer` は関数宣言なので**巻き上がって呼べる**。
ところがその中で使う `OCCUPANT_STORAGE_KEY` は `const` であり、
**宣言より前では触れない**(一時的死角)。結果、呼べるのに中身が死ぬ。

**そして自分で書いた `catch` がそれを飲み込んだ。**
画面には「入れませんでした」と出るので、**部屋が無いときと区別が付かない**。
実際に教えてくれたのは verify であり、しかも
**盤面の全項目が一斉に落ちる**という形でしか出なかった
(ゲートが盤面を覆ってクリックを吸うため)。

> **受け止める catch は、書いた本人の間違いも受け止める。**

直したのは2つ ——
接続の開始を「0) 在席」の末尾へ移し(`startViewerSession`)、
catch は `console.error` に**原因を残してから**画面に出す。

## 5. ★★★壊し検証が見つけたもの —— 効いていない CSS が1行

`tools/batch66_break_check.py` の軸7に「通常モードのロビーを白背景に戻す」という改変がある。
最初に当てたとき、**落ちなかった**(NG)。

原因は番人の弱さではない。**壊した行がそもそも効いていなかった。**

```html
<body class="bg-dark text-light">
```
```css
body { background-color: #212529; color: #f8f9fa; }   /* 詳細度 (0,0,1) */
```

`.bg-dark` / `.text-light` は Bootstrap(実ページ)にもハーネスのスタブ(検証)にもある。
**クラスセレクタ(0,1,0)は要素セレクタ(0,0,1)に勝つ**ので、
テンプレートに書いた `body { ... }` は**一度も効いていなかった**。
値が同じだったので、誰も気づかなかった。

> **同じ性質の値を2箇所に置くと、挙動を決めるのは「意図」ではなく「詳細度」になる。**

★これは **65 のマナ行とまったく同じ形**である(設計判断28)。
65 は「重なりの CSS と JS」、66 は「地色の class とテンプレートの style」——
場所が違うだけで、罠は同じである。

★★**手動モードのロビー(34 で暗色にしたほう)にも同じ行があった。**
つまりこの死んだ1行は **34 から 65 まで生きていた**。
両方とも `body.bg-dark`(0,1,1)に直した。**色の値は1文字も変えていない**ので、
見た目は 65 と同じである。

> **壊し検証は、番人の弱さだけでなく「実装の死んだ行」も見つける。**

## 7. ★★verify に何を足したか(+25件)

### 7-1. 通常モードのロビーのハーネス(新設)

`verify/harness-auto-lobby.html` を `build_harness.py` が作る。
**手動モードのロビーと同じスタブを当てる** —— 65 までの通常モードのロビーは
白背景の HTML フォーム2枚であり、比べる相手が無かった。66 で形を揃えたので、
**同じ下地に載せて突き合わせられる**ようになった。

測っているのは10件ほどで、要点は3つである。

- **一覧の中身**(部屋名・席・観戦・鍵・状態)と、**鍵つき部屋のIDが1つも出ないこと**
- **[入る] は遷移しない**(マスター指示) —— 下の欄へ部屋IDを差し込み、焦点を移すところまで
- ★★**2つのロビーの地色と文字色が一致すること**(裁定130 の番人)

★最後の1つが 65 の続きである。**複製は許すが、一致は機械が見張る。**

### 7-2. 盤面の席選択ゲート(新設)

ハーネスに `?seatgate` を付けると、スタブが localStorage を**消す**。
これで「在席が無い」と「在席がある」の両方を作れる。
★**両方測る** —— 片方だけだと「常に開く」「常に開かない」を見分けられない(裁定186)。

★★**踏んだ穴がもう1つある。**最初、ハーネスの部屋ID(`TESTRM`)を
一覧の作り物に入れ忘れていた。すると席選択のゲートは
**「入れませんでした」の顔**で開く —— **開いてはいるので、
「ゲートが開く」だけを見る検証は通ってしまう。**
席のボタンを1つも測らないまま合格になっていた。
`TESTRM` を足し、**埋まっている席は押せず在席者名が出る / 空席は押せる**の
両方を測るようにした。

### 7-3. ★63 の2件は「測る先」ごと書き直した

63 は `lobby.html` の `deckSummary`(main/taboo を数える関数)を**取り出して実行し**、
デッキメーカーの実際の書き出しに当てていた。
66 でデッキの受け取りが盤面へ移り、**画面は中身を1枚も数えなくなった** ——
ファイルをそのままサーバへ渡し、返ってきた枚数を出すだけである。

だから測る先を変えた。

- **画面が数えていないこと**(`lobby.html` / `battle.js` に `deckSummary` が無い)
- **ファイルを丸ごと送っていること**(`fetch` を捕まえて本文を照合する)
- **画面に出る枚数はサーバが答えた値であること**

★枚数が正しいことは JUnit(`LobbyPageTest`)が**本物のサーバ**で測っている。
ここでブラウザに数えさせたら、それは**2つ目の数え方**を作ることになる(裁定130)。

### 7-4. ★ハーネスから Thymeleaf のパーサ水準コメントを落とすようにした

`<!--/* ... */-->` は Thymeleaf が**配信前に消す**。
落とさないハーネスは**実ページより多くの文字を持つ**ことになる。

66 で実際に踏んだ —— 「退役した言葉(おまかせ・プリセット)がページに残っていない」を
ハーネスで測ったら、**テンプレートのコメントに書いた言葉を拾って落ちた**。
`build_harness.py` に `_strip_parser_comments` を足し、4つのハーネス全部に当てている。

★**ハーネスは「実ページと同じ物」でなければ、測った結果が実ページの保証にならない**(31 の教訓)。

## 8. 壊し検証(`tools/batch66_break_check.py`・9件)

**9件すべて OK。**軸は7(開始条件 / 観戦者の視界 / 受付の門 / 鍵つき部屋のID /
一覧の導線 / 席選択のゲート / 見え方)。
照合先は **JUnit と verify の両方**である —— このバッチは Java と静的ファイルの両方を触っている。

### 8-1. ★裁定304 の罠を避ける書き方(64・65 から継続)

改変は**文を消して後続を宙に浮かせる形を1つも使っていない**。
条件を `false &&` で包むか、式ごと置き換えるかのどちらかである。
Java なら到達不能でコンパイルが止まり(64)、JS なら黙って別物が動く(65) ——
どちらも「壊しすぎて測れない」形である。

### 8-2. ★★★壊しどころが無い項目(裁定196 の正直な扱い)

- **席の並びが席順であること** …… 守っているのは**コードではなくデータ構造**である。
  `seats` は `EnumMap<SeatId, PlayerSlot>` であり、反復順は必ず宣言順になる。
  さらに `getSlots()` は `SeatId.values()` を回している。
  **1箇所の改変では崩せない** —— 崩すにはフィールドの型と反復の両方を同時に変えることになり、
  それは「軸ごとに1件」(57 の教訓)を破る。
  ★これは 65 で見つけた4つ目の形(その分岐に入る盤面が作れない)の隣にある**5つ目の形**である ——
  **盤面は作れるが、壊す場所が1つに絞れない。**
  番人は残してある。将来 `seats` を `LinkedHashMap` に替えた人のための門である。

- **観戦者が操作を送れないこと** …… 壊すには「観戦者に playerId を配る」ことになり、
  それは改変ではなく**設計の変更**である。番人は
  `Batch66LobbyTest` の `myTurn / chooseOrder / mulligan` が false であることに置いた。

- **対戦が始まった部屋に座れないこと** …… 試合は両席が埋まってはじめて始まるので、
  始まった部屋には必ず空席が無い。門が単独で効く盤面は作れない。
  それでも門を先に置いてあるのは**断る理由のほうが正しいから**である ——
  「埋まっています」と言われると次の人は空くのを待ってしまう。
  ★測れているのは**文言**だけであり、そこは試験の Javadoc に正直に書いた。

## 10. 理解確認 Q&A

**Q1. なぜ「一人回し」だけを外したのか。マスターがそう言ったから、以外の理由はあるか。**
A. ある。**通常モードで一人回しを作ると、情報の非対称を伏せる仕組みを1人ぶん解くことになる。**
手札・裏向きマナ・禁忌デッキを伏せているのは `GameViewBuilder` ただ1本であり、
「1人で両席を操作する」はその1本に**例外を1つ作る**という意味になる。
手動モードの全公開部屋が成り立つのは、あちらに伏せる仕組みがそもそも無いからである。
★マスターの「通常モードの性質上」という一言は、この構造をそのまま指している。

**Q2. 観戦者に手札が漏れていないことを、どうやって確かめたのか。画面を見ても分からないのでは。**
A. **画面では分からない。**だから `Batch66LobbyTest` が
**ビューの中身**(`view.you().hand()` が null であること)を直接測っている。
★そして**空振りでないことの証拠**を隣に置いた ——
同じ盤面をプレイヤーの視点で組むと `hand()` は null ではない。
これが無いと、上の試験は「ビルダーが常に null を返すだけ」でも通る(裁定186)。
★さらに壊し検証の軸2が、`isSelf = true` を渡す改変でこの試験が落ちることを確かめている。

**Q3. プリセットを消したことで、失われた保証は何か。**
A. 3つある。(1)「新カードが実際にデッキへ入る形になっているか」を数える場所、
(2)「40枚・同名4枚以内」をコードのデータに対して数える場所、
(3)「デッキが1本も無い状態でも対戦を始められる」という遊び方そのもの。
★(1) と (2) は**同じ規則を持つ別の門**が残っている ——
`DeckValidator` は**実際に持ち込まれるデッキファイル全部**にその規則を当てており、
そちらが本番の門である。(3) はマスターの指示で意図的に無くしたものである。
★消した番人は 2-2 の表に書き残した。**何を測らなくなったかを書かずに消すのがいちばん悪い。**

**Q4. `body { ... }` が効いていなかったことに、なぜ 34 から 65 まで誰も気づかなかったのか。**
A. **値が同じだったからである。**`.bg-dark` も `body {}` も #212529 を指しており、
どちらが勝っても見た目は変わらない。**壊してみて初めて、片方が死んでいることが分かる。**
★65 のマナ行も同じ構造だった(あちらは値が違ったので、症状として「ずれ」が出ていた)。
違いは**症状の有無**だけであり、罠は同じである。
★だから壊し検証は「番人が仕事をしているか」を測る道具であると同時に、
**「実装のその行が仕事をしているか」を測る道具**でもある。

**Q5. 席選択のゲートを盤面ページの中に置いたのはなぜか。独立ページのほうが素直では。**
A. **直リンクを塞ぐためである。**独立ページにすると、`/rooms/{id}/play` を直接開いた人は
ゲートを通らない。「通らせる」を分岐で書くと、経路が増えるたびに漏れる ——
盤面ページの中に置けば、**構造として必ず通る**。
★手動モードが 21b で同じ判断をしており、こちらはその踏襲である。
★★ついでに言うと、この形にしたおかげで `playerId` を URL から外せた。
外せたのは副産物ではなく、**同じ判断の別の顔**である ——
誰であるかを画面が決めるなら、URL が運ぶ必要はない。

**Q6. 66 は「1バッチ = 1チャット」の分量として大きすぎないか。**
A. 大きい。★正直に書くと、これは**候補 G(通常モードの UI の続き)よりも広い**。
Java の受付を作り直し、観戦という新しい経路を1本足し、
プリセットという古い経路を1本抜き、画面を2枚書き直している。
★それでも1バッチに収めたのは、**この4つが互いの前提だから**である ——
プリセットを抜くとデッキの受け取り場所が要り、受け取り場所を盤面にすると席選択が要り、
席選択を作ると席が要り、席を作ると一覧に出せるものが増える。
分けると「片方だけ入った中途半端な状態」が1バッチぶん存在することになる。
