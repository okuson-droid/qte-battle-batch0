## 1. ★★★何が壊れていたか(実測)

45 は通常モードのマナ行を「はみ出したら固定の -26px で重ねる」という**簡易版**で作った。
そのコメントにはこう書いてある。

> ★並びきらないときだけ重ねる(手動モードの `applyManaOverlap` と同じ思想の簡易版)

実装を読む前に、**まず測った。**15枚(マナゾーンの上限)を並べ、
タップの有無を変えながら各タイルの矩形を採った。

| 盤面 | はみ出し | 最小の露出 |
|---|---|---|
| 15枚・タップなし | 0px | 41px |
| 15枚・3枚に1枚タップ | 0px | **33px** |
| 15枚・すべてタップ | **+50px** | 65px |

壊れ方は3つあった。

### 1-1. ★回転したタイルの外接を勘定に入れていない

タップの表現は**回転**である(30・マスター指示)。要素の幅は 64px のままだが、
90度回した**見た目の外接は縦の 80px** になり、左右に 8px ずつはみ出す。
45 の計算(`scrollWidth > clientWidth`)は**レイアウト上の幅**しか見ないので、
回転で増えたぶんが最初から数に入っていない。**15枚すべてタップ済で 50px はみ出した。**
その 50px の行き先は右列(リーダー・パイル)である。

### 1-2. ★重なりの量が枚数に依らない

`-26px` は固定値である。12枚では過剰に重なり、15枚では足りない。
**「足りるかどうか」を測っているのに、「どれだけ足りないか」は使っていなかった。**

### 1-3. ★★★下駄が詳細度で負けていた(いちばん質が悪い)

CSS には、回転のはみ出しを吸うための下駄が**ちゃんと書いてあった**。

```css
.auto-mana-row .mana-tile + .mana-tile            { margin-left: 4px; }    /* クラス3つ */
.auto-mana-row.auto-mana-overlap .mana-tile + .mana-tile { margin-left: -26px; }  /* クラス4つ */
.auto-mana-row .mana-tile.tapped { margin-left: 14px; margin-right: 24px; } /* クラス3つ */
```

**重なり側(クラス4つ)がタップ側(クラス3つ)に詳細度で勝つ。**
つまり `margin-left: 14px` は、重なっている間**一度も効いていなかった**。
残るのは `margin-right: 24px` だけなので、タップ済のタイルは
**左隣に食い込み、右隣とは離れる**という非対称な置かれ方になり、
表向きの露出 33px / タップ済の露出 65px という**逆立ちした結果**を生んだ ——
読みたいのは表向きの名前のほうである。

> **同じ性質の値を CSS と JS の両方に置くと、挙動を決めるのは「意図」ではなく「詳細度」になる。**

## 2. ★★★同じ症状は手動モードが 34 で直していた

`applyManaOverlap`(手動モード)の Batch 34 hotfix のコメントにこう書いてある。

> 重なりの上限を**そのタイル自身の占有幅**から引く。従来は常に `MANA_TILE_WIDTH`(64)基準で
> 上限 36px としていた。ところがタップ済のタイルは占有幅が 88px なので、
> 36px しか重ねられないと1枚あたり 52px も食う。15枚すべてタップ済だと 816px 必要になり、
> 裏ストリップ(実測 323px)を**約 480px はみ出して**右列を覆っていた。

**65 が見つけたのと同じ根である。**手動モードは 34 で直り、通常モードのマナ行は 43〜45 で
**新しく作られた**ので、直された知見を継承しなかった。

> **「簡易版」と書いた実装は、本家が直っても自分では直らない。**

★これは 64 の教訓(「暫定でこうしておく」と書いた実装は、前提が消えても自分では戻らない)の
**別の顔**である。64 は**時間**の話だった —— 制約が消えても実装は戻らない。
65 は**空間**の話である —— 隣の実装が直っても、こちらの簡易版は直らない。
どちらも「**自分では戻らない**」という同じ性質を指している。

## 3. ★どう直したか

### 3-1. margin を書く場所を1つにした

CSS から `.auto-mana-row` 系の margin を**全部**外し、
`battle.js` の `applyAutoManaOverlap` が `style` で直接書く形にした
(設計判断28: 同じ役割のものを2つの形で持たない)。
`.auto-mana-overlap` クラスは使い手を失ったので撤去した(裁定178)。

★`.mana-row` の `gap: 3px` も `.auto-mana-row` 側で 0 にした。
**間隔と重なりは同じ軸の値である。**片方を CSS、片方を JS が持つと 1-3 が再発する。
間隔の正は `AUTO_MANA_GAP`(4px)1箇所である。

### 3-2. 規則は手動モードと同じ3つ

| 規則 | 意味 |
|---|---|
| 占有幅はタイルごとに違う | タップ済は 80px(回転の外接)、それ以外は 64px |
| 必要なぶんだけ均等に重ねる | `(自然幅 - 置ける幅) ÷ (枚数 - 1)` |
| 露出の下限を守る | まず 28px で詰め、足りなければ 14px まで譲る |

★定数(28 / 14)は手動モードと同じ値にした。**寸法だけが違う**(手動は 64×88、通常は 64×80)。

### 3-3. ★覆われるのは左のタイルである(手動モードとの1点の違い)

`z-index` を左から昇順に振るので、**タイル i の見える幅は「i 自身の占有幅 + 間隔 - 重なり」**である。
したがって重なりの上限を取るべき対象は **0 〜 n-2**(覆われる側)である。

**手動モードの実装は 1 〜 n-1(覆う側)で取っている。**
均一な行では同じ値になるが、タップ済と非タップが混ざる行では**1枚ぶんずれる**。
通常モードは覆われる側で書いた。

★**手動モードは 65 では触っていない。**このバッチは通常モードの UI が題であり、
7305行の `manual-battle.js` と手動モードの verify を巻き込むのは題を広げすぎる。
**ずれは `notes/qte-pitfalls.md` と積み残しに記録した。**

### 3-4. ★なぜ共有の JS ファイルにしなかったか

同じ規則が2箇所にある。裁定130 の出番である。

選択肢は3つあった。

| 案 | 代償 |
|---|---|
| (a) 通常モードにも同じ規則を書き、**一致を番人が見張る** | 規則が2箇所に在り続ける |
| (b) 共有 JS を新設して両方が読む | 版数の系統が5つ目になる / 手動モードを巻き込む |
| (c) CSS だけで解く | **不可能。**枚数に依存する計算は CSS に書けない |

**(a) を採った。**理由は2つである。

1. 裁定130 が求めているのは「1箇所に置くこと」ではなく
   **「同じ語彙を使い、一致を機械が見張ること」**である。
   verify は既にこの形を使っている ——
   「対象指定のフィルタは Java と `battle.js` の両方に居る(49・裁定130)」は、
   期待値を書かずに**両側を突き合わせる**番人である。
2. (b) は手動モードのファイルを触ることになる。
   ★62 が音のモーダルで**複製を選んだ**のと同じ判断である(版数の系統を増やさない)。
   あちらは複製に番人が付いていない(落とし穴に「片方だけ直さないこと」と書いてある)が、
   **65 の複製には番人が付く。**そのぶんこちらのほうが強い。

★★**ただし完全な一致は測っていない。**3-3 のとおり、通常モードは意図的に1点だけ違う。
測っているのは「通常モードのマナ行が不変量を満たすこと」であり、
「両者が同じコードであること」ではない。**そこは正直に書いておく。**

## 4. ★★verify の書き方 —— 期待値を書き写さない(裁定298)

新しい6件は、**実装の定数を1つも書いていない。**
露出の下限(28px)もタイルの寸法(64 / 80px)も、この節には現れない。
測っているのはブラウザが実際に置いた矩形から出てくる**2つの不変量**である。

### 4-1. はみ出さない

一番右のタイルの `right` が、行の内容box の右端を超えないこと。
★45 の実測は +50px であった。

### 4-2. ★★重なりが均等である

```
slack(i) = (次のタイルの左端 - このタイルの左端) - このタイルの実測幅
```

これは「間隔 - 重なり」に等しく、**均等に重ねているなら全ての隣接対で同じ値になる。**

★**実測幅を使うのが肝である。**回転したタイルの幅を
`getBoundingClientRect()` は 80px と答えてくれるので、
検証の側で「回転しているから 80」と**書かなくてよい** ——
書いた瞬間、それは実装の定数を写した番人になる(裁定298)。

45 の値を当てはめると `slack` は -23 / -31 / … とばらつく。**均等ではなかった。**

### 4-3. ★重なりの前後は `elementFromPoint` で測る

`z-index` を読むのではなく、**重なった点を指したときに右のタイルが返ること**を測る(裁定296)。
名前は左寄せなので、右のタイルが上にいなければ**名前の先頭が隠れる**。
★重なっている対が0件なら測れていないので、**対の数が0でないこと**を条件に含めた(裁定186)。

## 5. 壊し検証(`tools/batch65_break_check.py`・7件)

**7件すべて OK。**軸は6(回転の外接 / 必要量の計算 / 回転の下駄 /

2ファイルであり、Java は1行も変えていない。

### 5-1. ★★裁定304 の JS 版

64 は「条件を落とす」改変が**到達不能でコンパイルを拒まれ** EMPTY になった。
JavaScript には同じ壁が無い ——**黙って別物が動く。**
これは「壊しすぎて測れない」よりも見えにくい失敗である。
だから 65 の改変は、文を消して後続を宙に浮かせる形を1つも使っていない。

- ケース2 は `perTileOverlap` を求める**式ごと** 0 に置き換える(分岐の形は残す)
- ケース4 は呼び出しを消さず、**常に偽になる条件**で包む

### 5-2. ★★★壊しどころが無い項目(裁定196 の正直な扱い)

- **露出の下限**(28px / 14px)…… 1280×800 では 15枚すべてタップ済でも
  必要な重なりが 18px 程度にしかならず、上限(52px)に**一度も触れない**。
  定数をどう変えても盤面が動かないので、改変が当たったかどうかを測れない。
  ★これは裁定298(試験が実装から値を読む)とは**別の形**である ——
  「試験が読んでいる」のではなく「**その分岐に入る盤面が作れない**」。
  59・60 の教訓(その盤面が構造的に作れるかを疑う)の3度目の適用である。
  ★下限が効くのは幅の狭い窓である(実測: 960px 幅で露出 39px)。
  verify のビューポートは 43 から 1280×800 固定であり、
  あそこを動かすと 43-1(1画面に収まる)が意味を失う。
- **枚数の端(0枚・1枚)の守り** …… `tiles.length <= 1` を落としても、
  候補が空のときの `Math.min()` は Infinity を返し、`Math.min(0, Infinity)` は 0 のままである。
  ★番人(65-5)は残してある —— **将来この式を触る人**のための門である。

## 8. 理解確認 Q&A

**Q1. なぜ 45 の実装は「壊れている」と分かったのか。読んで分かったのか。**
A. **測って分かった。**先に 15枚(マナゾーンの上限)の盤面を作り、矩形を採った。
読んでから測ると、読んだときの見立てが測り方を歪める ——
「-26px は小さすぎるかもしれない」と思って測れば、はみ出しの 50px は見えても
**露出の非対称(33 対 65)は見落とす**。
★45 のコメントは「同じ思想の簡易版」と書いてあり、**それ自体は嘘ではない**。
思想は同じで、**勘定に入れる項が足りなかった**だけである。

**Q2. CSS の詳細度の食い違いは、なぜ1年近く誰も気づかなかったのか。**
A. **症状が「少しずれて見える」だったからである。**マナが6枚ある通常の盤面では
そもそも重ならず、CSS の3本目(`.tapped` の下駄)がちゃんと効く。
効かなくなるのは**重なりが始まってから**であり、それはマナが12枚を超えてからである。
★ゲームが長引かないと再現しない。**盤面の端を作って測る**以外に見つける道が無い。

**Q3. なぜ手動モードの `applyManaOverlap` を直さなかったのか。**
A. **題が違う。**65 は「通常モードの UI の修正」であり、
手動モードのマナ行は今のところ**誰も困っていない**(ずれるのは
タップ済と非タップが混ざる行で1枚ぶんであり、あちらのトラックは 323px と狭いので
そもそも常に下限まで詰まっている)。
★直すこと自体は正しいが、**7305行のファイルと手動モードの verify を巻き込む**。
落とし穴と積み残しに書いて次のバッチへ渡した ——
**「気づいたが今回はやらない」を書き残すのが、64 の教訓の実行である。**

**Q4. `slack` で均等さを測るのは、実装をなぞっているだけではないか。**
A. **なぞってはいない。**`slack` は実装に出てこない量である。
実装が持っているのは「重なり(`perTileOverlap`)」で、検証が測るのは
「隣までの距離 - 実測幅」である。両者が一致するのは**そうなるように置いたから**であり、
置き方が壊れれば一致しなくなる。
★決定的なのは**実測幅を使っていること**である。もし検証が
「タップ済なら 80」と書いたら、それは実装の定数を写したことになる(裁定298)。
ブラウザに聞けば書かずに済む。

**Q5. 15枚すべてタップ済という盤面は、実際に起こるのか。**
A. **起こる。**マナがアンタップに戻るのは**自分のターンのアンタップフェイズ**である
(総合ルール 2-6)。したがって自分のターンに使い切ったマナは、
**相手のターンのあいだずっとタップされたまま**である。
マナが 15枚まで伸びた終盤で MP を使い切れば、それがそのまま「15枚すべてタップ済」になる。
★つまりこれは端の盤面ではなく、**長い試合なら毎ターン通る姿**である。

★はみ出しの行き先について、測れたことと測れていないことを分けて書く。
**測れたのは「行の内容box を右へ 50px 超えた」までである。**
行の右端は中央列の端から 10px 内側(`.auto-strip` の padding)にあり、
中央列と右列の間隔も 10px なので、超えた 50px のうち**およそ 30px は右列に届く**計算になる ——
ただし**その重なりの写真は撮っていない**(直したあとに気づいたため)。
実害の大きさは計算であり、実測ではない。
