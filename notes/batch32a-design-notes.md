## 1. 何を作ったか

配信のたびに、前回ビューと今回ビューを instanceId で突合し、
起きたことを**観測の語彙**(移動・出現・消滅・ドロー・LP増減)に落として、
盤面DOMの外にあるオーバーレイ層(fx層)で描く仕組みを入れた。

- カードが動くと、旧位置から新位置へゴーストが飛ぶ。
- カードが増えると、その場でフェードインする。減ると旧位置でフェードアウトする。
- ドローは山札から手札へ滑り込む。**相手のドローは裏面1枚**が飛ぶ。
- LPが動くと、リーダーの上に `+n` / `−n` が浮かんで消える。

タップ/表裏の状態系・ターンの節目・カードフェイスの質感は 32b / 32c である。

## 2. 中心にある設計判断

### 2-1. 「全消し再描画とアニメーションは噛み合わない」は、条件付きの命題だった

`renderAll` は毎回すべてのDOMを捨てて作り直す。だからアニメーションは無理だ、
というのが 26 以来の暗黙の前提であり、そのために「盤面DOMの差分更新」が
低優先の宿題としてずっと残っていた。

しかしこの制約が効くのは、**動く要素が盤面DOMの中にいる場合だけ**である。
動く要素を `position: fixed` の独立層に持てば、下で盤面が全消し再構築されても
演出は生き続ける。**この形は既にアプリの中にあった**——21c のドラッグ軌跡
(`#manual-cue-layer`)がまさにそれで、`renderAll` のあとに `renderDragCues()` で
引き直している。

つまり今回やったのは新技法の導入ではなく、**既にある形の第2の適用**である。
差分更新という大きな改修は、演出のためには要らなかった。

```
   z-index の並び(32 で確定)
   fx層 1030  <  ドラッグ軌跡 1035  <  帯 1040  <  全面表示 1050
   └ 装飾              └ 操作の道具
```

操作の道具(矢印)が装飾(ゴースト)より常に上、という順序にしてある。

### 2-2. ★★イベントの検出をビューの差分に置いた(サーバ変更ゼロ)

演出を作るとき素直に思いつくのは「サーバがイベントを送る」だが、それは選ばなかった。
配信は完全なスナップショットなので、**前後を突合すれば何が起きたかは全部読める**。
この選択には、楽ができる以上の意味が4つある。

1. **Java を1行も触っていない。** `mvn test` 未検証の山(21c・23・24・27・28・29)を
   これ以上増やさずに済む。揮発メッセージも新DTOも要らない。
2. **★視点フィルタが構造的に効く。** 差分は「自分に届いたビュー」にしか基づかない。
   見えないカードはそもそも差分に現れないので、
   **「相手の手札の中身が演出で漏れる」は原理的に起こらない**。
   21a 3-3 の判定をクライアントで再実装しなくてよい。
3. **相手にも観戦者にも同じ演出が出る。** 各クライアントが自分のビューの差分から
   独立に描くので、矢印(21c)のような揮発メッセージの配信経路が要らない。
4. **★「判断を実装しない」原則を破りようがない。** 差分が語れるのは
   「どこからどこへ動いたか」「いくつ増減したか」という事実だけである。
   「破壊されたから墓地へ」という解釈はどこにも入り込む場所が無い。

★ログを材料にしないのは 32 設計時の裁定どおりである。配信されるログは
**描画済みのテキスト**(`ManualLogView`)でありイベント種別を持たない。
書式に依存した検出は、書式を直した瞬間に黙って壊れる。

### 2-3. ★★「窓」のゾーンでは出現・消滅を演出しない(実装で見つかった穴)

設計書には無かったが、実装して初めて表に出た問題である。

Batch 29 以降、**山札は最上段の1枚しか配られない**。相手のマナも表向きだけが届く。
このようなゾーンでは、**届く配列の出入りが実際の出入りと一致しない**。

```
1枚ドローする → 山札の「新しい最上段」が初めて届く
                → 素朴に差分を取ると「山札の上にカードが出現した」に見える
シャッフルする → それまで届いていた最上段が届かなくなる
                → 「山札の上のカードが消滅した」に見える
```

どちらも実際には何も出現しておらず、何も消えていない。**観測の窓が動いただけ**である。

そこで、`counts` が届いた配列の長さより大きいゾーンを「窓」と判定し、
**そこでは出現・消滅を出さない**ことにした(移動は両端が分かるので出してよい)。

```js
function fxWindowedZones(view) { /* counts > zones[z].length のゾーンを集める */ }
```

これは 1-1 の「観測できないことは演出にしない」を、そのまま条件式にしたものである。
★この穴は「山札の演出が変だ」という形でしか表面化しないので、
検証項目(46番)として固定した。

### 2-4. ドローは「裁定」ではなく「観測」として定義した

`drew` の定義は次のとおりで、ルール上のドローかどうかは判定していない。

> 同じ席で **山札の枚数が減り、手札の枚数が増えた**

自席のドローは山札の最上段が届いているので、**識別された移動**として拾える。
相手のドローは手札が非公開なので**枚数しか分からない**——そのときは識別子を持たない
演出になり、飛ぶのは `cardBackFace()` の**裏面1枚**である。

★裏面は imageId を持たない(26)。したがって「非公開情報を運ばない」性質は
**気をつけて守るもの**ではなく、**構造的にそうなっている**。
検証項目45はこれを固定している(fx層に名前も imageId も現れないこと)。

### 2-5. 進化スタックの素材は「束の持ち主と同じ場所に居る」ものとして畳む

`ManualCardView.materials` は入れ子である。素直に走査すると、進化するたびに
素材が索引から消えて「**消滅**」に見える。実際には束の中に在る。

27 の教訓は「状態にはあるが画面のどこからも触れないのは消失と同じ」だった。
今回はその裏返しで、「**在るのに消えたと描く**」誤りである。
索引を作るとき素材を持ち主と同じ (席, ゾーン) に畳むことで解消した。

### 2-6. 読む相と書く相を混ぜない(29 の規約をそのまま守る)

```
msg.view 受信
  → (1) diff      prevView と突合(純オブジェクト比較。DOMに触らない)
  → (2) capture   差分に該当するカードだけ旧位置を採る(read・renderAll の前)
  → (3) renderAll 従来どおり全消し再描画(write)
  → (4) fxSpawn   新位置を読んでゴーストを出す(read・measurePhase の末尾)
```

(4) を `measurePhase` の末尾——`renderDragCues()` と同格の位置——に置いた。
29 で「実測は1箇所」に集めた読み取り相にそのまま同居させている。

★**強制同期レイアウトは1回だけ**である。全部の開始状態をDOMへ載せてから
`void layer.offsetWidth` で確定させ、そのあとまとめて終了状態を当てる。
`flashDenied`(21c)と同じ idiom であり、**rAF を待たないので検証が配信直後に
そのまま観測できる**。「待ち時間に依存する検証」を作らずに済んだ。

### 2-7. 配信の反映を `applyView` 1本にした

差分は**再描画の前**に採らなければならない。「`latestView` に入れて `renderAll` を呼ぶ」を
2箇所に書けてしまうと、いつか片方だけが順序を間違える。
そこで入口を `applyView(view)` 1本に閉じ、`onMessage` はそれを呼ぶだけにした。

★リサイズやカード定義の取得後に呼ばれる `renderAll` は `pendingFx` が空なので
演出を起こさない。**「再描画」と「配信の反映」が別物である**ことが型として表れている。

### 2-8. 出す/出さないの境界

| 条件 | 扱い | 理由 |
|---|---|---|
| `prevView` が無い(初回) | 出さない | 比較対象が無い |
| 差分が 8 件を超える | **全部出さない** | それは1手ではなく**盤面の総入れ替え**(リセット・配り直し・すべてアンタップ)である |
| 走行中の演出が 8 件 | 超過分は出さない | 追いつけない演出は捨ててよい。盤面の正は下のDOMである |
| `start.locking` が真 | 出さない | 開始シーケンス中は盤面が総入れ替えされる |
| `prefers-reduced-motion` | 出さない | CSS と JS の両方で止める |
| `fxEnabled === false` | 出さない | 検証の「わざと壊す」入口・将来の設定UIの取り付け点 |

★**Undo は抑制しない**(設計書 1-2)。墓地へ送ったカードが場へ飛んで戻るのは、
実際に起きた状態変化の正確な描画であり、何が取り消されたかが見えるのは利益である。

★`prefers-reduced-motion` を CSS だけで止めないのは、DOM が作られ続けるからである。
JS だけで止めないのは、将来 CSS 側に足した演出が漏れるからである。

### 2-9. 見た目の正を増やさない

ゴーストの中身は `cardFace()` / `cardBackFace()` がそのまま作る。
**ゴースト専用の見た目を作っていない。**25 以来の「見た目の正は1箇所」の延長である。

出現(appeared)だけは**実要素**にクラスを当てる方式にした。ゴーストを作らないので、
途中で次の配信が来て再構築されても「最終状態で即時表示」に落ちるだけで、壊れ方が無い。

★このとき CSS は `transition` ではなく `animation` を使った。
`transition` で書くには「盤面のカード全部に `transition-property` を生やす」ことになり、
**マナのタップ回転(transform)まで巻き込む**。32b でタップの回転にトランジションを
足すときの設計を、いま先に潰してしまわないためである。

## 3. 色の決め方(31 の手順を踏襲)

LPポップの色は**黒背景(#212529)の上で**選んだ。

| | 色 | コントラスト比 |
|---|---|---|
| 増加 | `#6ee7a0` | 9.99:1 |
| 減少 | `#ff9b9b` | 7.65:1 |

★そして**機械判定の対象セレクタに fx層を追加した**。

(検証項目48)。

| 48 | fx層のラベルも黒背景で 4.5:1 以上 | 判定の網から漏らさない |

| 50 | 開始シーケンス中は演出しない | 配り直しの総入れ替え |
| 51a | **★`fxEnabled` を切ると項目41が検出できなくなる** | 自己確認(31の手順) |
| 51b | **★`moveDetected` は「動いていない/旧位置から出ていない」ゴーストを認めない** | 判定の中身が飾りでないこと |
| 52 | `prefers-reduced-motion` ではゴーストを作らない | 演出を切る経路 |

★**51a と 41 は同じシナリオ関数・同じ判定関数を通る。**
別々に書くと「片方だけ直して両方通る」が起きる。31 で
「判定を入れたら、判定が落ちることを1回確かめる」を手順として固定したが、
今回はさらに一歩進めて、**判定関数そのものに反例を食わせる**項目(51b)を足した。
30 のコントラスト判定が「常に通る飾り」だったのは、
判定が**何も検出できない状態でも通る**形だったからである。

検証は実マウス(`page.mouse`)である。合成 DragEvent は使っていない。
`prefers-reduced-motion` は Playwright の `reducedMotion: 'reduce'` で実際にエミュレートしている。

## 5. マスターへの依頼・確認事項

1. **★★`mvn test` を手元で実行してほしい(最優先の積み残し)。**
   21c・23・24・27・28・29 の Java 変更が未検証のまま積まれている。
   **32a は Java を1行も触っていない**ので、32a のせいで落ちることは無いはずだが、
   積み残しの解消はこのバッチとは独立に必要である。
2. **演出の速さ・強さを実機で見てほしい。** 移動 220ms / ドロー 260ms /
   フェード 180ms / LPポップ 700ms で入れてある。
   「速すぎて見えない」「遅くて操作の邪魔」があれば数値を調整する(定数1箇所である)。
3. **LPポップの位置**はリーダータイルの中央上寄り(高さの35%)から28px浮かせている。
   自席のリーダーは右列にあるため、大きく動かすと右列の外へ出る。
   もっと目立たせたい場合は盤面中央に出す案もあるが、
   「どちらの席のLPか」が読みにくくなるためリーダー付近を採った。
4. **同時演出の上限8**は、超えると**演出が丸ごと消える**(中途半端に出さない)。
   すべてアンタップやリセットのときに何も出ないのは意図した挙動である。

## 6. 32b への申し送り

- 状態系(タップの回転トランジション・減光・flip)と節目系(ターン合図・進化パルス)。
  **`diffViews` に `tapChanged` / `flipped` / `stackGrew` / `turnAdvanced` を足す**のが
  最初の作業になる。基盤(fx層・捕捉・スポーン・上限・抑制)はそのまま使える。
- ★タップ表現の非対称(場のタイル=減光+バッジ / マナ=回転)は維持すること。
  32a で `[data-instance-id]` への一律 transition を**入れなかった**のは、
  ここを潰さないためである(2-9)。
- ★ターン合図は `turnNumber` が**増加したときだけ**出す(巻き戻しでは出さない)。
  差分の語彙としては既に `turnNumber` が読める位置にある。
- 版数は js v=23 / css v=30 へ。
