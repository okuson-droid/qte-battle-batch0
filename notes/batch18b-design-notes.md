## ⚡ 結論チートシート

- **既存ファイルの変更は `battle.css` のみ**(v10 → v11 で新規参照)。それ以外は
  すべて新規ファイルである(コントローラ1・テンプレート1・JS1)。
- **18cとの境界を4箇所で空振りにした。** 山札の右クリック全面表示、進化スタックの
  `+n` バッジクリック(帯表示)、自席以外のゾーンパイル(墓地等)を開く操作、
  相手席の小型ゾーンバーを開く操作。押すとログ欄に「Batch 18c で実装予定」と出るだけで、

- **進化かどうかの判定は「ドロップ先が埋まっているFIELDタイルかどうか」で一本化した。**

  定めているとおりである。

  選択が無ければドロップ先のタイル1枚だけを素材にする。並び順は送らない

- **MPを直接編集する操作は作っていない。** マナのアンタップ枚数からの派生値であり、
  引き継ぎ書の既知の限界にも明記されている制約である。
- **デッキ読み込みUIを含めた。** 17b がすでに持つ `POST /manual/api/rooms/{roomId}/deck`
  を呼ぶだけであり、新しい判断ロジックではない(0章で確認した方針)。
  「リセットして引き直す」は19a送りなので入れていない。
- **盤面への入口を暫定で新設した。** `GET /manual/battle/{roomId}` で、occupantId が
  無ければその場で入室してリダイレクトする。19a の正式なロビーに置き換わるまでの
  繋ぎであり、`LobbyController` には一切触れていない。

## 2. 設計判断

### 2-1. 進化とドロップ判定を1つの条件に閉じた

設計書 4-5 の表を読むと「ミニオンゾーンの空き枠」「既存のミニオンタイルの上」で
挙動が変わる。クライアントはこれを次の1条件で判定している。

```javascript
if (zoneName === 'FIELD' && targetCard) {
    // 既存タイルの上 → 進化
} else {
    // 空き枠・他ゾーン → move
}
```

`targetCard` はドロップ先に描画されている `ManualCardView` であり、空き枠
(`tile-slot-empty`)には紐付けていない。これにより「空き枠かどうか」を
別途フラグで持ち回る必要が無く、DOM要素の生成元だけで判定が閉じる。

WEAPON も同じ関数を通るが、`zoneName === 'WEAPON' && targetCard` の場合は
常に拒否(`flashReject`)する。進化の素材になれるのはFIELD上のカードのみ
(設計書 4-5-1 の4)であり、WEAPONを埋まった状態で上書きする操作は
「古いウェポンの行き先をアプリが決める」ことになり 5-1 の原則に反するためである
(4-5「ウェポンの入れ替えは自動で行わない」)。

### 2-2. 進化の素材はセレクション経由でしか渡さない

4-5-1 の複数素材の操作は「Ctrl/Cmd選択 → 選択中のタイルへドラッグ」である。
クライアント側では、ドロップ時に `selected` 集合を見て、次の条件を満たすものだけを
素材候補として拾う。

```javascript
const sameFieldSelection = [...selected].filter((id) => {
    const loc = cardLocation.get(id);
    return loc && loc.seatId === seatId && loc.zone === 'FIELD' && id !== evolutionCardId;
});
```

「ドラッグしているカード自身」を選択から除外しているのは、進化ミニオンを
手札から選択せずにそのままドラッグしたときに自分自身を素材と誤認しないためである
(通常は起きないが、進化前のミニオンをFIELD上で選択したまま別の進化ドラッグを
行うような操作順序を防ぐ安全策)。

選択が空、または選択が別の席・別のゾーンにしか無い場合は、ドロップ先のタイル1枚だけを
素材にする(4-5-1「素材が1体の場合」)。

並び順はクライアントで組み立てない。18a 2-2 が「クライアントが選択した順ではなく
盤面上の並び順に並べ替えてから適用する」とサーバ側の責務として定めているためである。

### 2-3. 場のタイルは3つの独立したクリック領域を持つ

4-4 は同じ「場のタイル」の中でクリック対象によって挙動が変わる(タップ / 数値編集 /
札の着脱)。DOMでは、数値表示(`manual-tile-stats`)と札チップ・`+`ボタンに
それぞれ個別の `click` リスナーを付け、`e.stopPropagation()` で外側のタイル本体の
クリック(タップ⇔アンタップ)に伝播させない形にした。

Shift+クリック(表裏)とCtrl/Cmd+クリック(複数選択)は、タイル本体のクリック
ハンドラの先頭で分岐させ、他の領域より優先する。数値・札の編集中にShiftやCtrlを
併用するケースは設計書に無いため、この優先順位で問題ない。

### 2-4. 文明色の文字色は毎回計算する(直書きしない)

```javascript
function textColorFor(hex) {
    const rgb = [1, 3, 5].map(i => parseInt(hex.slice(i, i + 2), 16) / 255);
    const lin = rgb.map(c => (c <= 0.03928 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4)));
    const luminance = 0.2126 * lin[0] + 0.7152 * lin[1] + 0.0722 * lin[2];
    const contrastWithBlack = (luminance + 0.05) / 0.05;
    return contrastWithBlack < 4.5 ? '#ffffff' : '#000000';
}
```

WCAGの相対輝度からコントラスト比を算出し、黒文字とのコントラスト比が4.5未満なら
白文字にする。設計書 4-2 の実値7色をそのまま `CIV_COLORS` に置き、この関数を通して
初めて文字色が決まる。将来色を調整しても、この関数を経由する限り追従する。

### 2-5. デッキ読み込みは17bのエンドポイントをそのまま叩く

`ManualLobbyController.importDeck`(`POST /manual/api/rooms/{roomId}/deck`)は
17bで既に完成しているため、盤面のヘッダから `fetch` で直接呼んでいる。
zipは `arrayBuffer()` で読み、`Content-Type: application/octet-stream` のまま
本文に流し込む(コントローラのJavadocにあるとおり、multipart上限を避けるための
素のバイト列受け取りである)。読み込み結果(枚数・警告)はヘッダの
`#deck-import-status` に表示するだけで、盤面の再描画はWebSocket配信
(`ManualBroadcaster.broadcast`)が別途届けてくれるため、クライアント側で
明示的な再取得は行っていない。

### 2-6. 18cへの空振りは「押せるが何も起きない」ではなく案内を出す

`notYetImplemented(label)` は、ログ欄と同じ位置(`#deck-import-status`)に
「◯◯ は Batch 18c で実装予定」を4秒だけ表示する関数である。ボタン自体を
disabledにしなかったのは、押しても壊れないことを保証しつつ、
「機能が無い」のではなく「次のバッチで来る」ことを伝えるためである。
対象は次の4箇所。

1. 山札の右クリック(全面表示)
2. 進化スタックの `+n` バッジクリック(帯表示)
3. 自席ゾーンバーの墓地・消滅・禁忌・一時公開(中身が0枚のときのクリック/右クリック)
4. 相手席の小型ゾーンバーのクリック(枚数表示のみで、開けない)

## 4. 既知の限界(要確認・未対応)

- **★undo/redoの粒度はサーバ任せ。** 画面は `canUndo` / `canRedo` の真偽値をそのまま
  ボタンのdisabledに反映するだけで、何が戻るかは表示しない。
- **★ドラッグ中のビジュアルフィードバックは最小限。** `dragover` で対象に緑の輪郭
  (受理)/赤の輪郭(拒否)を付けるのみで、ドラッグ元のカードを半透明にする等の
  演出は無い。
- **相手席の手札・マナ・リーダーは無い。** 設計書 4-1 が定める相手席の構成
  (LP + ミニオンゾーン + 小型ゾーンバー)のとおりであり、欠落ではない。
- **LPの編集は `prompt()`。** 数値編集モーダル(ATK/HP用)と統一していない。
  頻度が低く、値の範囲チェックも無い(4-4に「上限20は強制しない」とあるとおり)ため、
  簡易な実装で済ませた。18cや19aで統一するなら候補にあげておく。
- **在室者リスト・接続状態の表示が無い。** 設計書 6-3・11-2 はフェイズ2およびQ3の
  回答で19a送りとした範囲であり、本バッチでは扱っていない。
- **`check_undeclared.py` の `BUILTINS` に `OCCUPANT_ID` / `DEFAULT_LABELS` が無い**
  (3章参照)。実害は無いが、`tools/` 改修時に追加すること。

## 6. 次バッチ予告 — Batch 18c(b系・Sonnet 5)

**ゾーンを開く画面(帯・全面表示・検索・スタック帯)。** 設計書に明記された範囲に加え、
本バッチが空振りにした4箇所(3章・5章)を実装で埋める。既存ファイルの変更は無し
(18bで新設した `manual-battle.js` / `manual-battle.html` への追記が中心になる見込み)。

| 作るもの | 要点 |
|---|---|
| 山札の全面表示 | 右クリックで開く。任意位置への挿入(ドラッグ)を含む |
| 進化スタックの帯 | `+n` バッジクリックで開き、素材1枚ずつを任意ゾーンへドラッグ可能に(4-5-2) |
| ゾーンの帯・全面 | 墓地・消滅・禁忌・一時公開・相手席の各ゾーンを開く共通部品 |
| 検索 | 帯・全面表示内でのカード名検索(設計書のスコープに含まれる) |

18b が作った `cardLocation` 索引は最上段のみを対象にしている。18cでは帯を開いた際に
表示される下段のカードも同じ索引に含める必要があり、`renderStackRow` 系の関数を
拡張する形になる見込みである。
