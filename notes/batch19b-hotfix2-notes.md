# Batch 19b hotfix2 — 帯からドラッグできない不具合の真因と修正

対象: `manual-battle.js`(`onDragStart`)+ `manual-battle.html`(v=4→v=5)。
本ノートは、19b・hotfix1 の納品後も「墓地・禁忌などの一覧表示(帯)からカードを
ドラッグできない」状態が続いていたことへの対応記録である。

---

## ⚡ 結論

- **真因は、19b で入れた修正そのものであった。** バックドロップの遮断を解除するために
  `dragstart` ハンドラ内で `<body>` に `manual-drag-active` を**同期的に**付与していたが、
  このクラスは `.manual-band` の `pointer-events` を変える。`.manual-band` は
  ドラッグ元カードの**祖先**であるため、Chromium は「ドラッグ開始処理中にドラッグ元の
  ヒットテスト条件が変わった」と扱い、**ドラッグ操作自体を即座に中断する。**
- 中断の症状は特徴的で、`dragstart` の直後に `dragend` が来て、`dragover` も `drop` も
  一度も発火しない。つまり「どこにも落とせない」という報告どおりの挙動になる。
- **修正は `setTimeout(..., 0)` によるクラス付与の非同期化1点。** ドラッグが確立した後に
  `pointer-events` を変えれば中断は起きず、設計書2-5が要求する「帯の背後(B席行)へも
  落とせる」という要件も満たしたまま解決する。
- 変更ファイルは `manual-battle.js` と、キャッシュバスティング更新のための
  `manual-battle.html`(v=4→v=5)の2つのみ。`battle.css` は無変更(19bのCSSルールは正しかった)。

---

## 1. なぜ hotfix1 までの検証で見抜けなかったか

hotfix1 までの検証は、Playwright 上で **合成 `DragEvent`**(`new DragEvent(...)` を
`dispatchEvent` する方式)を使っていた。合成イベントはブラウザ本来のドラッグ機構を
一切通らないため、**「ブラウザがドラッグを中断する」という事象そのものが再現しない。**
その結果、修正前のコードでも `drop` が成功したように見えていた。

さらに、19b の作業中に実マウス操作(`page.mouse`)で試した際のログには

```
PAGE LOG: dragstart target=card1
PAGE LOG: dragend, class removed
```

と、`dragstart` の直後に `dragend` が来る**中断の証拠がすでに出ていた**。しかし当時は
これを「ヘッドレス環境では実ドラッグが再現できないのだろう」と誤って解釈し、合成イベントに
切り替えてしまった。**手元の証拠を環境の制約と決めつけたことが、2回の見落としの原因である。**

---

## 2. 原因の特定(A/B/C 比較)

同一構造の最小ページを3通り用意し、実マウス操作でドラッグして比較した。
ドロップ先は「帯の外」と「帯に完全に覆われた領域」の2箇所を用意した。

| 案 | CSS | クラス付与 | 帯の外へ | 帯の背後へ |
|---|---|---|---|---|
| **A(19b現行)** | backdrop + `.manual-band` を透過 | 同期 | **落とせない** | **落とせない** |
| B | backdrop のみ透過 | 同期 | 落とせる | 落とせない |
| **C(採用)** | backdrop + `.manual-band` を透過 | **`setTimeout(0)` で非同期** | **落とせる** | **落とせる** |

A のイベント列は両方とも `dragstart -> dragend` であり、`dragover`・`drop` が一切
発火していない。これが中断の直接の証拠である。

B は中断こそ起きないが、`.manual-band` が遮断側に残るため、帯に覆われた盤面上部
(B席行)へは落とせない。設計書2-5が明示的に要求している要件を満たさないため不採用とした。

C は両方を満たす。ドラッグが確立した後に `pointer-events` を変えるため、ドラッグ元の
ヒットテスト条件は開始処理中には変化せず、中断が起きない。

## 3. 修正内容

`manual-battle.js` の `onDragStart` を次のように変更した。

```js
    const timer = setTimeout(() => {
        document.body.classList.add('manual-drag-active');
    }, 0);
    document.addEventListener('dragend', () => {
        clearTimeout(timer);
        document.body.classList.remove('manual-drag-active');
    }, { once: true });
```

19b からの差分は3点である。

1. **クラス付与を `setTimeout(..., 0)` で遅らせた**(本修正の本体)。
2. **`dragend` の受け口を `e.target` から `document` へ移した。** 帯のカードは
   `<div class="manual-band-card">` の中に `<img>` を持ち、画像は既定で
   `draggable` であるため、ブラウザが実際のドラッグ元として内側の `<img>` を選ぶ場合がある。
   `dragend` は元要素から `document` まで確実にバブリングするので、こちらで受けるほうが堅い。
3. **`clearTimeout(timer)` を追加した。** 付与前に `dragend` が来た場合(ごく短いドラッグや
   即キャンセル)に、クラスが付いたまま取り残されるのを防ぐ。

`battle.css` は変更していない。19bで追加したCSSルール自体は正しく、問題は**適用の
タイミング**だけだった。`manual-battle.html` はJS変更に伴うキャッシュバスティングのみ
(`v=4` → `v=5`)。

## 4. 検証

**実ファイル**(`battle.css` / `manual-battle.js`)を読み込んだ検証用ページに対し、
**実マウス操作**(`page.mouse.down` → `move` → `up`)でドラッグして確認した。
合成イベントは今回の不具合を再現できないため使っていない。

墓地(TRASH)・禁忌(TABOO)の両方について、パイルを実際にクリックして帯を開き、
帯のカードを2種類のドロップ先へドラッグした。

| 経路 | 修正前 | 修正後 |
|---|---|---|
| 墓地の帯 → 自軍ミニオン空き枠 | moveが飛ばない | **成功**(`toZone:"FIELD"`) |
| 墓地の帯 → 手札 | moveが飛ばない | **成功**(`toZone:"HAND"`) |
| 禁忌の帯 → 自軍ミニオン空き枠 | moveが飛ばない | **成功**(`toZone:"FIELD"`) |
| 禁忌の帯 → 手札 | moveが飛ばない | **成功**(`toZone:"HAND"`) |

同一のテスト・同一のファイル構成で、`onDragStart` の実装だけを19b版に戻すと4経路すべてが
再び失敗することも確認した(因果関係の確認)。

機械チェックも再実行し、すべて通過している。

- `node --check src/main/resources/static/js/manual-battle.js` → 構文エラー無し
- `tools/check_undeclared.py` → 未宣言の識別子無し
- `tools/check_structure.py` → 異常無し(Javaは無変更)

## 5. 教訓

- **ドラッグ&ドロップの検証に合成 `DragEvent` を使ってはならない。** 合成イベントは
  ブラウザのドラッグ機構を通らないため、「ブラウザがドラッグを中断する」種類の不具合を
  原理的に再現できない。必ず `page.mouse` による実操作で検証する。
- **`dragstart` ハンドラの中で、ドラッグ元やその祖先の見え方・ヒットテスト条件を
  同期的に変更しないこと。** `pointer-events`・`display` などの変更はドラッグを
  中断させる。変更が必要なら `setTimeout(..., 0)` でドラッグ確立後まで遅らせる。
- **自分が直前に入れた修正を、不具合の容疑者から外さないこと。** 今回の真因は
  19bで加えた修正そのものであった。「修正したはずの箇所」は最初に疑うべき対象である。
- **手元に出ている観測結果を、環境の制約だと決めつけないこと。** 19bの時点で
  `dragstart -> dragend` という中断の証拠は出ていたが、ヘッドレス環境の限界と
  解釈してしまい、2回の納品を無駄にした。
