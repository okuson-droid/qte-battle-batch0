## 1. ★★★寄せる先は「ファイル」であって「値の書き写し」ではない

### 1-1. 34 は書き写した。39 は読み込んだ

34 でロビーを黒くしたとき、`battle.css` は**読み込ませなかった**。設計解説にはこう書いてある。

> battle.css には書かない。あれは盤面と通常モードの共有ファイルであり、
> ロビーは読み込んでいない。**読み込ませると共有範囲が理由なく広がる。**

39 は逆の判断をした。矛盾ではない。**34 の「理由なく」が効いている。**

- ロビーが `battle.css` から欲しいものは**1つも無かった**。あの画面にはモーダルも
  トーストもカードも無く、必要なのは背景と文字の色だけである。色を6つ書き写すほうが安い。
- デッキメーカーが欲しいものは**4つある** ——
  確認モーダルの器(`.info-modal` 一式)、トースト(`.manual-toast`)、
  フォーカスの枠(`:focus-visible`)、そして文明色(`:root` の `--civ-*`)。
  これを書き写すと、**寄せた直後から2つに割れる**。

★一般形: **共有ファイルを読ませるかどうかは「共有範囲」ではなく
「読む側が実際に使う項目があるか」で決まる。** 使う物が1つも無いのに読ませるのが
「理由なく広がる」であり、4つ使うのに書き写すのは単に複製である。

★この判断は既存の番人にそのまま乗った。裁定59 の
「`battle.css` を読み込むテンプレートはすべて黒背景である」と
「版数はすべてのテンプレートで揃っている」は、**デッキメーカーが仲間に入った瞬間に
この画面も見張り始める**。番人を1つも増やさずに範囲が広がっている。

### 1-2. ★★Bootstrap は入れなかった

確認モーダルの markup は盤面では Bootstrap のクラス(`btn` / `d-none` / `d-flex` …)で
出来ている。同じ markup にするなら Bootstrap を読み込むのがいちばん素直に見える。**やめた。**

- この画面は Bootstrap のクラスを**1つも使っていない**。3ペインもカードタイルも自前である。
  数個のユーティリティのために CDN を1本増やすと、既存の40近い規則が
  Reboot と当たるかどうかを**実サーバでしか確認できない**変更になる。
  ★裁定23(実サーバで確認できない間はやらない)と同じ性質の話である。
- ハーネスは Bootstrap を落とす(裁定39)。入れれば、**この画面も
  「ハーネスでだけ違う画面」になる**。今はそうではない ——
  **このハーネスには落とす CDN が1つも無く、スタブが1行も要らない**(6-1)。

代わりに:

- ボタンは自前の `.io-btn` / `.io-btn.primary` を当てた(見た目は盤面の
  `btn-outline-light` / `btn-warning` と同じ色である)。
- 閉じるのは **`hidden` 属性**である。`.d-none` は Bootstrap のクラスであり、
  **落ちてもいない CDN の代わりを自分の CSS に書くのは筋が悪い**(裁定39 の考え方)。
  `battle.css` に `.info-modal[hidden] { display: none; }` を1行足した ——
  `.info-modal` は `display: flex` なので、UA スタイルの `[hidden]` はそのままでは負ける。

★**閉じ方が2つあること自体は害ではない。** 盤面は `.d-none`、デッキメーカーは `hidden`。
どちらも `openInfoModal` / `closeInfoModal` の**中に閉じており**、呼ぶ側には出てこない。
裁定51(開閉は関数を通す)が守っているのは、まさにこの境界である。

### 1-3. `bg-dark` は印であって実装ではない

`<body class="bg-dark text-light">` を付けたが、Bootstrap を読み込まないので
**このクラスは何もしない**。色は同じテンプレートの `<style>` が持つ。

これはロビーと同じ形である ——
ロビーも Bootstrap を読み込みながら `body { background-color: #212529 }` を自分で書いている
(ハーネスが Bootstrap を落とすため)。**クラスは印、`<style>` が実装**、という関係は変わらない。

★印だけになると番人が空回りするので、**計算値でも測っている**
(「背景が `rgb(33, 37, 41)` である」)。実際、`<style>` の背景だけ消す壊し方を試すと
印の項目は通り、計算値の項目が落ちる(7章の15)。**印と実物の両方に番人が要る。**

## 2. パレットとブランドマーク

### 2-1. 捨てたのは値と、値が嘘をついていた名前

38 まで、この画面には紫と金の16色があった(`--bg:#0c0b12` / `--gold:#c9a15a` …)。
ロビー・カード一覧・盤面のどれとも違い、レビューが「第3のデザイン系統」と呼んだ実体である。

変数そのものは残した。差し替えたのは**値**と、値が合わなくなった**名前**である。

| 38 まで | 39 | 由来 |
|---|---|---|
| `--bg: #0c0b12` + 放射グラデーション | `--bg: #212529`(平ら) | 盤面・ロビー・カード一覧 |
| `--surface: #181624` | `#2b3035` | ロビーの `.card` |
| `--surface-2` / `--surface-3` | `#343a40`(1つに畳んだ) | ロビーの `.card-header` |
| `--line: #3c3656` | `#495057` | 盤面・ロビー |
| `--gold: #c9a15a` / `--gold-soft` | **`--accent: #ffca28`** | 盤面の `.manual-tile-selected` / 軌跡 |
| `--emerald` / `--crimson` | **`--ok: #6ee7a0` / `--bad: #ff9b9b`** | 盤面の LP 増減(9.99:1 / 7.65:1) |
| `--text: #ece8f7` | `#f8f9fa` | 盤面・ロビー |
| `--text-dim: #9d97b8` | `#adb5bd` | 34 でロビーが選んだ値 |
| `--text-faint: #6a6484` | **削除** | 黒地で 2.6:1。34 が `#6c757d` を捨てたのと同じ理由 |

★`--gold` を `--accent` に改名したのは飾りではない。**金色でないものを `--gold` と呼び続けると、
次に色を足す人が「金の系統に合う色」を探してしまう。**

★`--text-faint` の削除で、この画面のコントラスト不足が3種類まとめて消えた
(フィルタの行ラベル・プールの操作ヒント・詳細ペインの空表示)。
**寄せた副産物ではなく、寄せたから見えた欠陥である** ——
独自パレットのままなら「その系統ではそういう色」で通っていた。

### 2-2. ★★カードの面は寄せない。**もう寄っている**

この画面には**2つのパレット**がある。画面のクローム(バー・ペイン・ボタン)と、
カードの面(`.tile` / `.bigcard`)である。**寄せたのは前者だけである。**

カードの面は 25b / 32c で作った盤面のフェイス(`.mcard-*`)と同じ設計で描かれており、
文字色(`#ece8f7` / `#cfc9e4` / `#e2ddf2`)も攻守の色(`#f0c869` / `#e88a9a`)も
**元から `battle.css` と同じ値**だった。39 で直したのは2箇所だけである。

- `.tile-inner` / `.bc-inner` の地を `#16141f,#1c1929` → **`#17151f,#1b1827`**
  (`.mcard-inner` の値)。1〜2 の差の「近い色」が2つあった。
- カード名が `--text` を継承していた。クロームの `--text` が `#f8f9fa` になった瞬間、
  **盤面のカード名(`#ece8f7`)と別の白になる**。`.t-name` / `.bc-name` に明示した。

★2つ目は、**寄せる作業そのものが作りかけた壊れ方**である。
「画面の文字色」と「カードに印刷された文字色」は別の概念であり、
片方を動かすときにもう片方が継承でついてくると気づかない。

★カードの面はコントラストの機械判定の対象外である(32c の裁定)。**目視が要る**(8-2)。

### 2-3. ★セリフ体の [TABOO] は消したのではなく、置き場所を直した

このマークが悪かったわけではない。**同じ意匠は手動モードにちゃんと在る** ——
`battle.css` の `.mcard-back-mark`、つまり**カードの裏面**である。

あれは「カードに印刷されているもの」であって、アプリの看板ではない。
同じ記号を画面の看板にも使うと、**「裏向きのカード」と「このアプリ」が同じ記号になる**。

代わりに、ロビー・カード一覧と同じ「見出し + 薄い補助文」にした。

```
← ロビー   デッキメーカー   クイン・タブーエレメント
```

★製品名の書き方も `<title>`(`デッキメーカー — クイン・タブーエレメント`)と揃っている。
レビュー B-2 が挙げた「製品名が3種類」のうち、この画面のぶんは元から正しかった。

## 3. ★★★文明色の正を1箇所にする(レビュー B-2)

### 3-1. 3箇所どころか、コメントで運用されていた

同じ7色が3箇所にあった。

1. `manual-battle.js` の `FACE_CIV_COLORS`(キーは文明コード)
2. `manual-deck-maker.html` の `CIV_COLOR`(キーは**日本語**)
3. `tools/make_brand_assets.js` の `CIV`(**配列**。順序だけが意味を持つ)

3つ目にはこう書いてあった。

> ★文明色は FACE_CIV_COLORS(manual-battle.js)と同一である。
> **ここを直すときは向こうも直すこと**——という状態を作らないため、…

★**「直すときは向こうも直すこと」は、覚えごとであって仕組みではない。**
そう書いた本人ですら、書いた時点で不安だったことがこの文からわかる。

### 3-2. ★なぜ CSS に置いたのか

正の置き場所の候補は3つあった。

| 案 | 却下・採用の理由 |
|---|---|
| `manual-cards.json` の `meta` に足す | 両方の画面が読む口はある。だが**色は表示の都合**であって台帳の持ち物ではない。盤面は最初の描画で色が要るのに、台帳は非同期で届く |
| どちらかの JS を正にする | ブラウザは別ページのスクリプトを読めない。共有の JS ファイルを作ると版数の系統が4つ目になる(裁定74) |
| **`battle.css` の `:root`** | **採用** |

採用の理由は、**3者のうち2者が既に CSS を読むから**である。
盤面はタイルとフェイスに `--mc` を立て、デッキメーカーは `--c` を立てる。
どちらも**最終的な使い道は CSS のカスタムプロパティ**であり、
JS は「どの色か」を選ぶだけで「何色か」を知る必要が無い。

```css
:root {
    --civ-water: #2f6fb5;  --civ-fire:  #b53a3a;  --civ-wind:  #3a8f57;
    --civ-light: #b8952f;  --civ-dark:  #6b42a8;  --civ-earth: #c05a8e;
    --civ-none:  #6f6f7c;
}
```

3つ目(OGP の帯を描く Node スクリプト)は、**ブラウザではないので CSS をファイルとして読める**。
正規表現で7行を拾うだけで正に届く。

```js
const CIV = (() => {
    const root = (fs.readFileSync(BATTLE_CSS, 'utf8').match(/:root\s*\{[^}]*\}/) || [''])[0];
    return Array.from(root.matchAll(/--civ-(?!none\b)[a-z]+:\s*(#[0-9a-f]{6})/gi)).map((m) => m[1]);
})();
```

★生成物が1バイトも変わらないことを確認済みである(`git status` にPNGが出ない)。

### 3-3. ★★対応表を持たない

両側とも、名前は「`--civ-` + 文明コードの小文字」で**機械的に**決まる。

```js
function civColor(civ) {                     // manual-battle.js(文明コードで引く)
    const key = String(civ || 'NONE').toLowerCase();
    …getPropertyValue('--civ-' + key)…       // ★1度読んだら覚える
}
```

★**表を持てば、それが色の複製と同じだけ壊れる。** 文明が1つ増えたときに直す場所が2つになる。
デッキメーカーが持っている `CIV_CODE`(日本語 → 文明コード)は**名前**の対応であり、
`CIV_JA` の逆引きとして元から必要だったものである。色の表ではない。

★**既定の色を書かない。** `|| '#6f6f7c'` を1つ書いた瞬間、それが8つ目の複製になる
(初版で実際に書いてしまい、番人が検出した。7章の1件目)。
読めなかったときは空文字が返り、枠の色が付かないだけである。

★**描画のたびに `getComputedStyle` を呼ばない。** 1度読んだら `Map` に覚える。
29 の「描画関数の中で幅を実測しない」と同じ理由である。

### 3-4. ★★番人の対象は「コード」である

「この7色が `battle.css` 以外に現れないこと」を機械判定にした。走査するのは
`static/js/*.js` / `templates/*.html` / `tools/*.js` の**コード**だけである。

★**焼き込んだ画像は複製ではなく出力である。** `favicon.svg` には3色が入っており、
カードの PNG 235枚には全部の色が入っている。あれらを「正から読め」と言うことはできない。

★検証側も期待値を書かない。盤面のリーダーの色を見る項目(9-3)は
`#2f6fb5` を書くのをやめ、**`:root` から読んだ値と突き合わせる**形に直した。
確かめたいのは「水のタイルに水の色が乗ること」=**結線**であって、色そのものではない。
値を書くと、正を1文字直すたびに検証も直すことになり、
「正が1箇所」を機械で守っている意味が薄れる。

## 4. ★★★確認モーダル —— 規約は共有し、コードは複製した

### 4-1. 共有できなかった

裁定53 は「破壊的操作に素の `confirm()` を書かない」であり、
その実装(`modalStack` / `openInfoModal` / `askConfirm`)は `manual-battle.js` の 0-3 / 0-4 にある。
デッキメーカーからは**呼べない**。

- 盤面のスクリプトを読み込ませることはできない。あれは 7,100行あり、
  読み込んだ瞬間に STOMP クライアントを作り、盤面のDOMを前提に走り出す。
- 共有の JS ファイルを1本作ると、**静的ファイルの版数の系統が4つ目になる**(裁定74)。
  版数の手動管理は既に破綻の実例が出ている(`battle.html` が v=10 のまま取り残されていた)。

したがって **39 のこの部分は複製である。**約110行の同じ形のコードが2箇所にある。

### 4-2. ★★複製を許す代わりに、同じ問いで測っている

複製が危険なのは、**黙って離れていける**からである。そこを塞いだ。

デッキメーカーの検証は、**36 の 5-1 と同じ項目立て**にしてある。

| 36 が盤面に立てた問い | 39 がデッキメーカーに立てた問い |
|---|---|
| Esc でモーダルが閉じる | ★★Esc で確認モーダルが閉じる |
| 確認の初期フォーカスは [キャンセル] | ★確認の初期フォーカスは [キャンセル] |
| Tab を繰り返しても裏へ抜けない | ★★Tab を繰り返してもモーダルの外へ出ない |
| 裏の要素へフォーカスが移っても引き戻す | ★裏の要素へフォーカスが移っても引き戻す |
| 閉じるとフォーカスは開く前の位置へ戻る | ★閉じるとフォーカスは文明ボタンへ戻る |
| 確認を出している間はまだ何も送らない | ★確認を出している間はまだ何も壊れていない |
| 取り消した確認は何も送らない | ★取り消した確認は何も壊さない |
| 破壊的操作で素の `confirm()` を呼ばない | ★★破壊的操作で素の `confirm()` を呼ばない |
| ソースに `confirm(` が残っていない | ★★テンプレートに `confirm(` の呼び出しが残っていない |

★**同じ問いで測っていなければ、複製は必ず離れていく。**
これが 39 で複製を許している唯一の根拠である。
共有のファイルを作るときは、この表がそのまま「1本になったこと」の確認項目になる(9章)。

### 4-3. 実装は盤面と同じ形にした

覆うものは今**1つしか無い**が、`modalStack` で持った(裁定47)。
優先順位9(マナカーブ・検証一覧)で2つ目が来たときに、
**規約より先に実装が崩れる**のを防ぐためである。

- Esc は × と同じ資格しか持たない(裁定48)。どちらも [キャンセル] を `click()` する。
- Esc は下の層へ落とさない(裁定49)。出口が無ければそこで止まる。
- 開閉は `openInfoModal` / `closeInfoModal` を通す(裁定51)。
- 初期フォーカスの既定は「× を除いた最初の焦点可能要素」、
  確認だけ `data-initial-focus="#confirm-modal-close"` で名指しする(裁定52)。
  **破壊的操作の [実行] に初期フォーカスを載せてはいけない。**
- Tab の折り返しと `focusin` の網の**2枚**を張る(入口が2つあるため)。
- 確認はコールバックで受ける(裁定54)。ボタンには動詞を書く(裁定55)。

### 4-4. ★確認が非同期になると「続き」に名前が要る

38 まではこう書けていた。

```js
function selectCiv(civ, silent){
  if(!silent && …){ if(!confirm('…')) return; }
  mainCiv = civ; …                      // ★そのまま下へ続く
}
```

素の `confirm()` は JavaScript を止めるので、**続きを同じ関数に書ける**。
止めなくなると書けない。実行する中身を `applyCiv(civ)` として切り出した。

```js
function selectCiv(civ, silent){
  if(!silent && (deck.leaderId||deck.counts.size)){
    askConfirm(`メイン文明を ${civ} に変更する。組みかけのデッキは失われる。`,
      '文明を変更する', ()=>applyCiv(civ));
    return;
  }
  applyCiv(civ);                        // ★確認の有無に関係なく同じ1本
}
```
