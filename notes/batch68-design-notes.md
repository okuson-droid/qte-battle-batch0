## 1. ★★★裁定282 —— 対象は「場に出てから」選ぶ

### 1-1. 66 までの姿と、なぜ間違っていたか

66 まで、ミニオンの【召喚時】が要求する対象は
**使用を宣言した時点**({`GameService.playMinion`})で選ばせていた。
`TargetSpec` を1本持ち、それをクライアントへ送り、選択を受け取ってから召喚する形である。

これは総合ルールに反していた。対象は**効果が発動する時点**で選ぶものであり、
【召喚時】が発動するのはミニオンが場に出た後である。マスター裁定282 がそれを確定させた。

★この誤りは**単なる順序の問題ではなかった**。66 までのコードには、
「宣言時に選ぶ」という前提から生まれた**ねじれの手当て**が積み重なっていた ——

| 手当て | 何を塞いでいたか | 68 でどうなったか |
|---|---|---|
| 裁定258 の罠(52) | 進化召喚の検証は**素材を場から外す前**に走る。素材にしたミニオンを対象に選べる | **構造ごと消えた**(選ぶ頃には素材は場に居ない) |
| 裁定282 の門(60) | 墓地から出すカード自身が墓地の候補に混じる | **構造ごと消えた**(候補を数える頃には墓地を離れている) |
| 48 の落とし穴 | 候補ゼロだと**召喚そのものが弾かれる** | 宣言時の検証を通らないので起きない |
| 裁定278(c) の導線(60) | 墓地からの召喚に「対象を運ぶ口」を新設した | **要らなくなった**(引数は互換のため残す) |

★**3つの穴を塞ぐコードを消したのではない。穴が作れなくなった。**
これが 68 でいちばん大きい変化である。

### 1-2. 移したのは15枚

対象を要求するミニオンは235枚中15枚である(【召喚時】14 + 【登場時】1)。

```
DARK-3  生贄を求める邪鬼    DARK-17 腐敗の投擲者      DARK-20 執念の暗殺者
DARK-22 墓場の怨念集合体    DARK-30 リボーンライヴ・ノア DARK-34 サモンズライト
DARK-4  ボーン・コレクター  EARTH-16 大地の巨頭        EARTH-33 分那愚利
FIRE-17 逆境の猛火者        LIGHT-8 天界の守護神 ゾディアック
LIGHT-21 光の召喚士(★【登場時】) LIGHT-32 英霊・タイガラム
WATER-21 海獣バハムート      WATER-4 手札を喰らう大蟹
```

★この15枚という数は**機械が数えている** ——
`Batch68SummonTargetTest#対象を要求するミニオンは要求1件で召喚時と登場時を同時に持たない`
が `isEqualTo(15)` で固定する(裁定186: 空振りでないことの証拠)。

### 1-3. ★★★効果コードを1行も書き換えずに移した

移し方の肝は、**再開先を1つに統一した**ことである。

```java
// fire() の末尾(CardEffectRegistry)
if (effect == null) { return; }
if (needsTargetChoice(ctx, minion, trigger)) { return; }   // ★対象が無ければ問い合わせて戻る
effect.accept(ctx);
```

`needsTargetChoice` は問い合わせを1件積み、`payload` に
`<instanceId>|<TriggerType>` を載せる。答えが返ると `resumeSummonTargets` が
**同じ `fire()` を呼び直す** —— 2度目は `ctx.targets()` が埋まっているので素通りして効果が走る。

★**15枚の効果ラムダは `ctx.targets()` を読むだけであり、それがいつ選ばれたかを知らない。**
だから1行も変わっていない。「選ばせる仕掛け」と「使う効果」を分けたことの利得である(裁定130)。

★**判定を `fire()` の入口に置いた理由**は《悪夢》(裁定265)と同じである ——
ON_SUMMON を焚く場所は通常召喚・進化召喚・特殊召喚・禁忌・墓地からの召喚と複数あり、
呼び出し側で分岐すると**足し忘れた経路だけが素通りする**(裁定163)。

### 1-4. ★★実装で実際に踏んだ穴 —— 誘発の種別を見ていなかった

最初の実装は `needsTargetChoice` で**誘発の種別を見ていなかった**。
`targetSpecs` はカードに1本しか無く、そこに書いてあるのは【召喚時】【登場時】の対象である。
種別を見ないと、**同じカードの【破壊時】まで**「まだ対象を選んでいない」と読まれる。

《サモンズライト》(DARK-34)は【召喚時】(相手1体に1ダメージ)と
【破壊時】(墓地からコスト1を出す)の両方を持つ。
絞りが無いと、**破壊されたときに蘇生の代わりにダメージ対象を問われた**。

★症状は `EvolutionEffectTest` の**ノアと無関係な2件**として出た ——
「墓地から出たミニオンが突進を得るか」を測っていた試験が、
蘇生そのものが起きなくなって落ちた。**穴の在り処と症状の出る場所が離れている**典型である。

```java
// 直したあと
if (trigger != TriggerType.ON_SUMMON && trigger != TriggerType.ON_ENTER) {
    return false;
}
```

★番人: `Batch68SummonTargetTest#破壊時の誘発は召喚時の対象を問わない`(壊し検証の軸3)。

### 1-5. 2つの文を持つ2枚は、本文の順序どおりに問う

1件の `PendingChoice` は**1つの要求しか運べない**。要求を2つ持つ2枚は書き換えた。

| カード | 本文 | 68 の形 |
|---|---|---|
| 《生贄を求める邪鬼》 | 自分のミニオン2体を破壊する。相手のミニオンを1体破壊する。 | 1件目 = `SUMMON_TARGETS`、2件目 = `SACRIFICE_FIEND_OPPONENT` |
| 《手札を喰らう大蟹》 | 自分の手札を1枚捨てる。**そうしたら**ミニオン1体を持ち主の手札に戻す。 | 1件目 = `SUMMON_TARGETS`、2件目 = `CRAB_BOUNCE` |

★**本文に忠実になった**。とくに大蟹は「そうしたら」が入っており、
**捨てが成立したか**は捨てたあとにしか分からない ——
2件をまとめて宣言時に選ばせる形では、そもそも表現できていなかった。

★番人が要る場所が1つ増えた: 「対象を要求するミニオンの要求は**1件**である」。
2件目を足すと、割り込みは1件目しか問わず**2件目が黙って消える**。

## 2. ★★★裁定311 —— 手札から出たなら【召喚時】は発動する

### 2-1. 切り直したのは「経路」ではなく「出どころ」

63 から 67 までの規則は「【召喚時】は**召喚**でのみ発動する」(設計判断19)であった。
裁定311 はこれを**出どころ**で切り直した。

| 出どころ | 【召喚時】 | 【登場時】 |
|---|---|---|
| 召喚(通常・進化・特殊・禁忌・墓地からの召喚) | ○ | ○ |
| 効果で**手札から**出た | ○(**新しい**) | ○ |
| 効果で墓地・マナ・山札から出た | × | ○ |

実装は `GameActions.putIntoFieldByEffect` に
`FieldEntryOrigin`(`HAND` / `OTHER`)を1つ足しただけである。

### 2-2. ★入口を分けなかった理由

「手札から出す専用の入口」を1本足す形も考えたが、採らなかった。
あの入口は既に **`null` を返す理由が2つある**という難所を抱えており
(場が満杯 / 光霊・モアニールの置換。50 の落とし穴)、
3本目の分かれ道を作ると「どちらを呼ぶか」の判断が呼び手に増える。

★**出どころは「値」であって「経路」ではない。**

### 2-3. ★渡し忘れは、組み合わせたときにしか症状が出ない

呼び出し側が `HAND` を渡し忘れると、**【召喚時】が黙って発動しなくなる**。
しかも症状が出るのは「手札から出す効果」と「【召喚時】を持つカード」を
**組み合わせたときだけ**である。人の目には見えない類の壊れ方なので、
`Batch68SummonFromHandTest` が実際に出して実際に焚けたかを測る。

該当は9枚 ——《逆境の猛火者》《天界の守護神 ゾディアック》《光の召喚士》《神の福音》
《聖なる降誕の儀式》《ギガマウス・バイト》《英術・スケアロック》
《スタンディングテント》《英霊・タイガラム》。

### 2-4. ★★★235枚でただ1つの例外 ——《スタンディングテント》

本文: 「【賢魂：2】このミニオンを場に出す。**そのミニオンの【召喚時】は使えない。**」

67 まで、この一文は**既定(裁定245)の言い換え**にすぎなかった ——
効果で出すのだから元から発動しない、と書いてあるだけだった。

★**裁定311 で既定が反転したことにより、この一文は本物の例外になった。**
【賢魂】は手札のカードを使うので、既定に従えば発動してしまう。
総合ルール2-7(カードの本文は総合ルールに優先する)により、
この1枚だけ `FieldEntryOrigin.OTHER` のままにしてある。

★番人:
`Batch68SummonFromHandTest#スタンディングテントの賢魂で出た自身は召喚時を発動しない`。
★**この試験が無いと、次の人はこれを「渡し忘れ」だと思って直してしまう。**

### 2-5. ★★★裁定311 が壊した既存の規則 ——《ガイル・フォックス》

裁定262(59)は「このターン中にカードを3枚以上使用しているなら【潜伏】」を、
**閾値を誘発の種類で分ける**形で実装していた。

```java
// 59 の姿
register(WIND-6, ON_SUMMON, ctx -> { if (used >= 2) grant(); });  // 自身が使用されている
register(WIND-6, ON_ENTER,  ctx -> { if (used >= 3) grant(); });  // 自身は使用されていない
```

使用カウンタは解決中の自分自身をまだ数えていない(裁定1)。
だから「召喚されたなら 2 でよい・効果で出たなら 3 要る」という 1 の差が生まれる。

★**この書き方は「効果で出たなら【召喚時】は発動しない」が成り立つ間だけ正しい。**
裁定311 が手札からの【召喚時】を発動させた瞬間、
《光の召喚士》に出されたフォックスは **ON_SUMMON の閾値 2 を通ってしまう** ——
自身は使用されていないのに、1枚甘くなる。

直し方は、**誘発の種類で代用するのをやめて、そのものを読む**ことである。

```java
private int galeFoxCardsUsed(EffectContext ctx) {
    int used = ctx.owner().getCardsUsedThisTurn();
    boolean summoned = ctx.source() != null && !ctx.source().isEnteredByEffect();
    return summoned ? used + 1 : used;   // ★分けているのは「自身が使用されているか」1つだけ
}
```

`MinionInstance.enteredByEffect` を新設した(★Batch 68)。
「【召喚時】が発動したか」では代用できない —— 311 でその2つが分かれたからである。

★**この一件が 68 のいちばんの学びである**: *誘発の種類を、別の性質の代用として使ってはいけない。*
代用は、代用元の規則が変わった瞬間に**黙って別物になる**。

## 3. ★★★`battle.js` を1行も変えなかった

68 は235枚すべてに掛かる規則を2つ書き換えたのに、クライアントは無変更である。
偶然ではなく、**64 が作った割り込みの器がそのまま使えた**からである。

- 66 までミニオンの【召喚時】の対象は「使用宣言の対象指定」の道(`beginSelection`)を通っていた。
- 68 でそれは丸ごと**割り込み**({`resolve-choice`})へ移った。
- 割り込みの描画は **`Kind` を数えていない** —— `CONFIRM` の1分岐だけが特別で、
  あとは候補のラベルを並べるだけである。

★だから `PendingChoice.Kind` に **`WEAPON`** を足しても、JS は何も知らずに描ける。
★これを**性質として固定した**:
verify の「割り込みの描画は Kind を数えていない(68)」——
マスタに存在しない架空の `Kind` を流し込んでもボタンが出ることを測る。

★サーバ側だけ1つ足した: ウェポンの候補ラベルに**どちらの側か**を添える。
ウェポンは1人1つなので候補は `"SELF"` / `"OPPONENT"` という側の名前であり、
名前だけを出すと**同名を両者が装備しているときに押し間違える**。

## 4. ★★裁定308 —— 進化ミニオンを候補に戻した

### 4-1. 67 が塞ぎ、68 が開け直した

67 は《聖なる降誕の儀式》《神の福音》に `Filter.MINION_CARD` を足して、
**素材なしで進化ミニオンが場に出る**穴を塞いだ(裁定226 に反していた)。
★ただしそれは「そういうルール」ではなく「今はこうするしかない」であり(60 の教訓)、
本文の読みを裁定308 で伺っていた。

マスター裁定308(b): **進化ミニオンも選べる。ただし必要な素材がない場合は選択できない。**

### 4-2. ★「素材を確保できるか」は宣言時には表せない

素材の有無は**属性の一致ではなく盤面に依存する規則**である。
`TargetSpec.Filter` はクライアントへ送られる値であり、
そこへ規則を書くと**クライアントが規則を持つ**ことになる(裁定234 に反する)。

→ **宣言時の対象指定をやめ、割り込みへ移した。**
★Batch 53 が《英術・スケアロック》で下したのとまったく同じ判断である。

### 4-3. ★53 の専用の名前を一般化した(裁定196)

`ResumePoint.SCARELOCK_MATERIAL`(53〜67)は《英術・スケアロック》専用の名前だったが、
やっていることは「手札の進化ミニオンの素材を選ばせ、素材つきで場に出す」だけである。
68 で3枚が同じものを要るようになったので、
**`EVOLUTION_MATERIAL_FROM_HAND` に統合して置き換えた**。

★**消した名前を書き残してある**(`ResumePoint` の Javadoc)。測っていた性質は1つも減っていない。

### 4-4. ★使用条件と候補が同じ関数を呼ぶ形にした

67 は「使用条件と絞り込みの**両方を直す**」で済ませた。
68 は**規則そのものを1箇所にした**(`putFromHandCandidates`)——
2箇所に同じ規則が書かれている限り、片方だけ直る事故はいつでも起きる(裁定130)。

```java
playConditions.put("QTE-M-LIGHT-11", (state, player) -> !putFromHandCandidates(player,
        m -> m.hasKeyword(Keyword.GUARD) && m.cost() != null && m.cost() <= 7).isEmpty());
```

### 4-5. `PutFromHandState` —— 割り込みを跨いで運ぶ4つの値

割り込みを跨いで持ち越せるのは `PendingChoice.payload`(文字列1本)だけである。
《神の福音》は「2体まで出す」「進化なら素材を問う」「出した数だけ引く」を持つので、
**4つの値を1本に畳んで運ぶ**。

```
<起こしたカードID>|<進化カードID>|<まだ出していないID列>|<ここまでに出した数>
```

★`split("\\|", -1)` の `-1` は必須である ——
既定の `split` は末尾の空要素を落とすので、「残り無し・0体」の `A||0` が3要素になって添字が壊れる。

## 10. 理解確認 Q&A

**Q1. 対象を割り込みへ移したのに、なぜ効果コードを書き換えずに済んだのか。**
A. **再開でやることが「選ばれたものを詰めて `fire()` を呼び直す」だけだからである。**
15枚の効果は `ctx.targets()` を読むだけで、それがいつ選ばれたかを知らない。
★もし再開先をカードごとに作っていたら、15本の再開コードを書くことになっていた。
`payload` に `<instanceId>|<TriggerType>` を載せるという1つの工夫で、**再開先は1つで足りた**。

**Q2. 裁定282 で「3つの穴が構造ごと消えた」というが、本当に消えたと言えるのか。**
A. **言える。ただし「消えた」の意味は「守るコードを消した」ではない。**
たとえば墓地の自己参照は、66 までは「検証 → 除去」の順だったから
検証の瞬間にカード自身が墓地に居た。68 は**出してから候補を数える**ので、
カードはもう墓地に居ない —— **穴のある状態を作れない**。
★それでも `Batch60Test` に「候補に現れない」を測る試験を置いてある。
消えたのが順序に依存した事実である以上、**順序が戻れば穴も戻る**からである(壊し検証の軸2)。

**Q3. `battle.js` を1行も変えていないのは、手抜きではないか。**
A. 逆である。**64 が「割り込みの描画は Kind を数えない」形で作ってあったことの配当**である。
★68 はそれを**性質として固定した** —— verify に架空の `Kind` を流し込む検査を足した。
固定しなければ、次に誰かが「HAND なら手札風に描こう」と分岐を書いた瞬間に、
**新しい Kind が空欄になる**。今回はその壊し方を実際に試して、番人が落ちることを確かめている。

**Q4. 《ガイル・フォックス》の直しは、裁定311 と関係ないのに 68 でやる必要があったのか。**
A. **関係がある。裁定311 が壊したのである。**
59 の「閾値が経路で1違う」は「効果で出たなら【召喚時】は発動しない」が成り立つ間だけ正しい書き方だった。
311 でそれが崩れ、**フォックスが1枚甘く【潜伏】を得るようになった**。
★試験が落ちたから気づいたのではない —— 落ちた試験は別の理由(数え方のずれ)で落ちていた。
気づいたのは「ON_SUMMON の閾値 2 は何を代用していたのか」を読み直したときである。
★**誘発の種類を別の性質の代用に使わない**、というのが 68 の教訓である(2-5)。

**Q5. 《スタンディングテント》だけ例外にするのは、裁定311 に穴を開けたことにならないか。**
A. ならない。**本文がそう書いてあるからである**(総合ルール2-7)。
★危ういのは「例外である」と気づかれないことのほうである ——
67 まではこの一文が既定の言い換えだったので、
**コメントも「本文が念を押しているだけで、例外を作ってはいない」と書いてあった**。
68 でその注記を書き換え、番人を1本置いた。

**Q6. 既存試験の書き換えが30件というのは多くないか。もっと少なく済ませられたのでは。**
A. 済ませられない。**召喚が2手になったのだから、召喚を書いた試験はすべて2手になる。**
★むしろ 30件で済んだことのほうが情報である ——
15枚のうち試験を持っていたのは一部だけであり、
**対象を要求するミニオンのうち何枚が測られていなかったか**がここに出ている。
68 の新設29件はその穴も埋めている。

**Q7. 裁定312(245 と 311 の衝突)を待たずに実装を進めてよかったのか。**
A. **よい。裁定184 が求めるのは「仰ぐこと」であって「止まること」ではない。**
番号の大きい裁定を優先するという既存の規則(`qte-rulings.md`)に従って実装し、
依頼文に「(b) になった場合の手当ては1行で済む」まで書いてある。
★止めると、この1点のために他の裁定10件と2つの構造書き換えが全部止まる。

**Q8. `TargetCandidates` を新設したが、`GameService.checkFilter` が111行から24行に減った。
これは「委譲しただけ」ではないのか。**
A. 減ったのは行数だけではない。★**判定と文言が同じ場所に来た。**
`rejectReason` は「通らない理由の文字列」を返す ——
通るなら `null`、通らないなら画面に出す言葉そのものである。
66 までは「宣言時の検証(文言を返す)」と「候補の列挙(真偽を返す)」が別々に書かれており、
**片方だけ直る余地があった**。68 はどちらも同じ1本を呼ぶ(裁定130)。
★おかげで、文言で照合していた既存試験が1件も壊れていない。
