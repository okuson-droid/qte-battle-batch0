# 通常モード × 手動モード — 揃えるものの仕分け

作成: 2026-08-16。マスター指示「実際にプレイしている感覚を持たせるため、手動モードの
見た目・仕様を通常モードへ。まず仕分けを提出。コードはまだ触らない」への回答。

**判断の物差しは1本である: 手動モードは「人間がルールを守る前提の検証の道具」、
通常モードは「サーバがルールを強制する対戦」。見た目は揃えてよいが、
情報の見え方は総合ルールの公開・非公開に従う。** 迷ったらこれで裁く。

ビュー(GameView / PlayerView / ManaView / CardView)を実際に読んで、
Java 変更の要否を確認済み。予想と違った点が2つ:

- ★墓地は**両席とも CardView 全量が既に配信されている**(公開情報として正しい)。
  相手の墓地の最上段表示は Java ゼロで作れる。
- ★マナは **cardId・name が既にビューにある**(表向きは両席へ、裏向きは持ち主のみ。
  サーバが既にフィルタしている)。マナのタイル化も Java ゼロで作れる。

---

## A. 揃える — JS/CSS だけでできる(Java 変更ゼロ)

| # | 項目 | 根拠・備考 |
|---|---|---|
| A1 | **山札・禁忌のパイル表示**(裏面 + 枚数バッジ、両席) | `deckCount` / `tabooCount` は配信済み。裏面は 25 の CSS 紋章(`.mcard-backface`)を流用 |
| A2 | **墓地のパイル表示**(最上段の表面 + 枚数、両席) | ★`trash` の CardView が両席とも配信済み(上記)。クリックで全量一覧もテキスト行 → フェイス表示に格上げできる |
| A3 | **マナのタイル化**(名前・文明色・タップは回転・裏向きは裏面) | `ManaView` に cardId / name あり。文明色は cardId → card-library(42 と同じ結線)。相手の裏向きは null が届く = 裏面で描くだけ |
| A4 | **リーダーの効果がぱっと分かる** | `leaderText` / `leaderCardId` は配信済み。リーダータイルの大型化(手動の自席リーダーフェイス 25/26 相当)+ **ホバープレビュー**(レビュー B-1 の残り)。42 の右クリック拡大は入口として既にある |
| A5 | **相手の手札を裏面カードの列で見せる** | `handCount` から裏面を並べるだけ。枚数の体感が数字と桁違いに変わる |
| A6 | **切断UXの移植**(33 相当) | ★battle.js は今も死んだソケットへ**無言で publish する**(33 が手動側だけ直した)。送信ガード・切断バナー・トースト。見た目ではなく信頼性だが、「プレイしている感覚」の土台 |
| A7 | **勝敗の帯**(35 相当)・**演出 fx 層 / SFX の移植**(32系・37 相当) | 既に Batch 44 候補として計画済み。この仕分けの「揃える」の本丸 |
| A8 | 操作説明モーダル(34 相当)・トーストの形式統一 | 小物。演出の移植と同じバッチに畳める |

## B. 揃える — Java の小変更が要る(ビューに項目を足すだけ)

| # | 項目 | 必要な変更 | 公開情報か |
|---|---|---|---|
| B1 | **消滅ゾーンの最上段表示** | `lostCardNames`(名前のみ)→ CardView のリストに格上げ(`GameViewBuilder` 数行) | ★公開。墓地と同じ扱いでよい |
| B2 | **ウェポンの効果がぱっと分かる** | `weaponName` / `weaponAttack` しか無い → **`weaponCardId` を追加**(テキスト・文明は card-library から引く。42 の結線と同じ) | ★公開。場に見えているもの |
| B3 | (任意)一時公開領域のフェイス化 | `RevealedCardView` に cardId を追加すると、公開の束もフェイスで出せる | 公開(公開中だけ) |

★B1・B2 は合わせても Java 数十行・既存テストへの影響なしの見込み。
名前で card-library を引けば Java ゼロにもできるが、**名前をキーにするのは ID を
リテラルで書くのと本質的に同じ**(qte.manual.pure-element-id の注記と同じ理屈)なので勧めない。

## C. 揃える価値がある — Java の中規模変更(独立バッチとして)

| # | 項目 | 中身 |
|---|---|---|
| C1 | **観戦者** | ★通常モードの部屋には観戦者という**概念そのものが無い**(2人の playerId だけ)。要るのは: 観戦入室の経路 / **公開情報のみのビュー**(`GameViewBuilder` に buildSpectatorView)/ 配信先 / 読み取り専用UI。★ルール強制モードでは「公開のみ」が総合ルールで定義できるから、実は手動より筋がいい。ビルダーのフィルタ機構(設計判断9)がそのまま土台になる |
| C2 | 部屋の属性(部屋名・鍵・一覧)の手動モードとの統一 | C1 とセットで検討するのが自然。単独では急がない |

★切断の「席の猶予」は**通常モードでは不要**と判断した。手動モードの猶予は
「席と人の対応が揺れる」問題への答えだが、通常モードは playerId がそのまま席であり、
同じ URL で戻れば復帰する。必要なのは A6(切断中の見せ方)だけ。

## D. 揃えない — できない・すべきでない

| # | 項目 | 理由 |
|---|---|---|
| D1 | **山札の中身・全面表示**(手動の山札ビューア) | ★★最重要の線引き。手動で許されるのは「人間がルールを守る道具」だから。通常モードで自分の山札の中身と順序が見えたら、サーチもシャッフルも意味を失いゲームが壊れる。**山札は裏面と枚数だけ**(A1) |
| D2 | 相手の手札・裏向きマナ・禁忌の中身 | サーバが送っていない(設計判断9)。できないし、すべきでもない |
| D3 | **Undo / Redo** | 効果は解決済みであり、巻き戻しはルール強制と両立しない |
| D4 | 自由なドラッグ移動・LP/数値の直接編集・札(ラベル)・手動タップ | 「判断はサーバ」の根幹に反する。通常モードの操作は宣言(クリック)であってカードの物理操作ではない |
| D5 | 観戦者の**視点切替**(A視点/B視点。手動 21c) | 手動では全公開の前提があって成立する機能。通常モードで席の視点を許すと手札・裏マナが漏れる。観戦は**公開のみ固定**(C1 の仕様として明記) |
| D6 | 進化スタックの表示 | 通常モードの台帳(qte-cards.json)に進化ミニオンが**存在しない**。Ver1.1 追随(+効果実装)が前提。今はできない |

## E. 保留(この仕分けの外)

- デッキ読込・デッキ選択まわりの手動モードとの統一 — 効果未実装カード(34枚 +
  作り直し69枚)の扱いと不可分。台帳 Ver1.1 追随の計画に含めて考える。
- ドラッグでのプレイ(手札 → 場へドラッグして召喚)— 「宣言」の入力方法の話であり、
  禁止ではないが D4 と区別して設計が要る。タブレット対応(優先順位11)と同時に検討が自然。
