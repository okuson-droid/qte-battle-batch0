## 283. ★★読み込みに失敗した音をどう扱うか

**背景**: Batch 37 は「音声ファイルを同梱しない」を選んだ理由に**失敗の広さ**(裁定27)を挙げていた。
ファイル化は、その挙げられていた失敗経路を**こちらから引き受ける**ということである。
404・回線の遅延・キャッシュの取りこぼしで、**今まで必ず鳴っていた音が鳴らなくなる**場面ができる。

**選択肢**:

- **(a) 合成コードを全部消す。**失敗したら無音。
  `sfxTone` / `sfxNoiseSweep` / `sfxEnvelope` / `sfxRattle` を撤去する。
  ★コードがいちばん減る。★★機械検証11件は**全部作り替え**になる。
- **(a+c) (a) に加えて、起動時に11種を先読みし、1つでも失敗したら設定の状態行
  (`#sound-modal-status`)に理由を出す。**鳴らない理由を出す場所は既にある(裁定76)。
- **(b) 合成を保険として残す。**ファイルが無ければ今の合成音で鳴らす。
  ★無音にはならないが、**同じ操作なのに人によって違う音が鳴る**状態を許すことになる。

★**わたし(クロエ)の見立て: (a+c)。**

(b) は裁定70・71 と同じ理由で筋が悪いと思う ——
**「どちらが鳴るか」の分岐を1つ増やすと、音が語るものが1つ減る。**
「この音は、置いたという意味である」が「置いたか、あるいは合成側にフォールバックしたか」になる。
音は情報を持つ、という筋がそこで折れる。

ただし**「なぜ鳴らないか」を黙らせる理由は無い。**状態行は 37 が
「鳴らない理由を出す唯一の場所」として作ったものであり、
**読み込み失敗はまさにその「理由」の新しい1件である。**
(c) は新しい仕組みではなく、**既にある場所に1行足すだけ**である。

## 284. ★★音声ファイルの版数をどう持つか

**背景**: 静的ファイルの版数は現在3系統ある(`manual-battle.js` v=33 / `battle.js` v=26 /
`battle.css` v=47)。裁定74 は「4系統目を増やさない」と書いており、
落とし穴にも2箇所写っている。**ファイル化はこれを4系統目にする。**

★**実測**: このプロジェクトは `Cache-Control` を1つも設定していない。
Spring Boot の静的配信は既定でキャッシュ指示を付けないので、
**ブラウザは `Last-Modified` から勝手に有効期限を推定する**(ヒューリスティックキャッシュ)。
既存の js / css が `?v=` を付けているのは、まさにこれを避けるためである。
★したがって**「版数を持たない」は、既存3系統と同じ穴に落ちる。**

**選択肢**:

- **(a) ファイル名に版数を入れる**(`place-v1.mp3`)。差し替えたら名前が変わるので確実。
  ★ただし **`CREDITS.md` の記録と実ファイル名の対応が版ごとにずれる**。
  散らし(286)を採ると、名前の数がさらに増える。
- **(b) `?v=` を JS 側の定数1つで付ける**(`const SFX_VERSION = 1;`)。
  ★★**JS の版数と同じ数字を使い回さない。**「音だけ差し替えたのに `manual-battle.js` の版数を
  上げる」ことになり、1つの数字に意味が2つ載る。
- **(c) 版数を持たない。**`Cache-Control` に任せる。★上の実測から、このままでは危ない。

★**わたしの見立て: (b)。**

理由は **`SFX_SPECS` の表1つを見れば全部わかる、という 37 の規律を保てるのが (b) だけ**だからである。
定数は表のすぐ隣に置ける。(a) はファイル名という**表の外**に版数が出るので、
「音の性格をコードの各所に散らさない」の裏返しで、**音の版数がファイル名に散る。**

★(a) が優れている点も書いておく: **取りこぼしが構造的に起きない**(名前が違えば別ファイルである)。
(b) は「差し替えたのに定数を上げ忘れる」経路が残る。
★そこで **(b) を採るなら番人を1つ置く**つもりでいる ——
「`static/sounds/` のファイルの更新日時が `SFX_VERSION` の更新より新しくないか」までは測れないが、
**`CREDITS.md` との突き合わせ**(下記 286・3-6)は測れる。

## 285. ★★★素材はどれを使うか(★これが答えないと実装が止まる)

**前提の再確認**: `okuson-droid/qte-battle-batch0` は**公開リポジトリ**である。
`static/` に置いたファイルは **GitHub 上で誰でも単体でダウンロードできる**。
したがって「アプリに組み込んでよい」だけでは足りず、**「再配布してよい」素材でなければならない。**
マスターの裁定により、**素材は CC0(パブリックドメイン相当)に限る**と決まっている。

★**調査は済んでいる。**掘り直しはしない。**Kenney(`kenney.nl`)の3パックだけで11種が全部埋まる。**
CC0 1.0 であり、作者本人が「Attribution: No requirement / Commercial use: Yes / edit・remix: Yes」
と明言している。

| 音 | 候補ファイル | パック |
|---|---|---|
| `draw` | `cardSlide1〜8` | Casino Audio |
| `place` | `cardPlace1〜4` | Casino Audio |
| `tap` | `click_00x` / `tick_00x` / `select_00x` | Interface Sounds |
| `flip` | `cardShove1〜4` | Casino Audio |
| `lpDown` | ★`minimize_001〜009`(下降スイープ) | Interface Sounds |
| `lpUp` | ★`maximize_001〜009`(上昇スイープ) | Interface Sounds |
| `decisive` | `jingles-<楽器>_00〜16` | Music Jingles |
| `commit` | `confirmation_00x` / `switch_00x` / `toggle_00x` | Interface Sounds |
| `dice` | `diceThrow1〜4` / `dieShuffle1〜3` | Casino Audio |
| `deal` | `cardFan1〜2` | Casino Audio |
| `shuffle` | ★`cardShuffle`(1つしかなく、名前がそのものである) | Casino Audio |

★**`lpDown` に `error_00x` は当てない。LPが減るのは失敗ではない。**
相手のLPが減るのは**自分の成功**であり、自分のLPが減るのも**盤面の出来事**であって
操作のエラーではない。`error_` を当てると音が「しくじった」という意味を勝手に足す。
**`maximize_` / `minimize_` の対を当てるのが正しい** —— 裁定80 が
「増と減は意味が逆だから2種に分けた」と決めているのだから、
**同じ作者が上下の対として作ったスイープ**を当てれば、その関係が音の側でも保たれる。

★**形式**: Kenney の配布は `.ogg` である。**iOS Safari は 17.3 以前で Ogg Vorbis を再生できない。**
CC0 は改変を無条件に許すので、**`ffmpeg` で `.mp3` に変換して同梱する**のが素直である
(サンドボックスに `ffmpeg` は入っている)。変換した事実も `CREDITS.md` に記録する。

**質問**:

- **(a) この候補でよい。**マスターが Kenney の3パックをダウンロードして接続フォルダに置く。
  ★**置いた場所を教えていただければ `device_stage_files` で取り込める。**
- **(b) 既に別の素材をダウンロード済みである。**★その場合、**接続フォルダのどこにあるかを教えてほしい。**
  ★★取り込んだら、**それが本当に CC0 かを1件ずつ確かめる。**
  効果音ラボ等(再配布禁止)であれば**公開リポジトリには置けない**ので、その場で報告する。
- **(c) 別の出所から探してほしい**(freesound.org / OpenGameArt.org の CC0 フィルタ)。
  ★★これらは**素材ごとにライセンスが違う**。CC BY を1つ混ぜた時点で表記の義務が発生するので、
  1件ずつの確認になる。★出所がばらけると**11種ぶんの音量を全部手で合わせ直す**ことになる。

★**わたしの見立て: (a)。**同じ作者が同じ時期に作った素材は**音量・残響・帯域が揃っている。**
37 が「調整は数値の表を1行直すだけ」と書いていた利点は、
**出所をばらした瞬間にいちばん失われやすい。**

## 286. ★★1つの音に複数のファイルを当てて、鳴るたびに散らすか

**背景**: 候補の素材は1音につき複数ある(`cardSlide` は8種、`cardPlace` は4種、
`maximize` は9種)。ゲーム音響では**同じ音の連打による耳の疲労**を防ぐために散らすのが定石である。

★**これは裁定70(1配信1音)とは別の軸である。**「何個鳴らすか」ではなく
**「同じ意味に何通りの音を許すか」**の話である。

**選択肢**:

- **(a) 1音1ファイル。**今の形をそのまま保つ。★`SFX_SPECS` が1行1音のままである。
- **(b) 全部散らす。**候補のあるものは全部複数ファイルを持たせ、鳴るたびに選ぶ。
- **(c) 回数の多い `tap` と `place` だけ散らす。**

★**わたしの見立て: (c)。**

裁定71 の筋(音は情報を持つ)は、散らしても**折れない**と思う ——
`tap` が8通りあっても**8通りとも `tap` である**。意味は1つのままである。
むしろ**頻度の高い音ほど、意味がすでに摩耗している** ——
毎手鳴る `tap` は「タップした」を語る前に、まず**耳に残り続ける**。散らす価値はそこにある。

逆に **`decisive`(1試合1回)や `dice`(1試合1回)を散らすのは害のほうが大きい。**
滅多に鳴らない音が毎回違うと、**「これは前と同じ出来事か?」という迷いが生まれる。**
珍しい音は、珍しいからこそ**同一であることが情報**である。

★**実装上の含意**: (c) なら `SFX_SPECS` の値が「1ファイル名」か「ファイル名の配列」かの
2通りになる。★**表の形が2通りになるのは規律の観点で少し苦しい**ので、
**採るなら全部を配列に統一する**つもりである(1つしかない音は要素1の配列にする)。
そうすれば表は1行1音のままで、**「何通りあるか」が表の上で読める。**

## 287. ★★通常モードの音の取り付け点

**背景**: 通常モードには**手動モードの fx 層が無い**。実測した構造の違いは次のとおりである。

| | 手動モード(`manual-battle.js`) | 通常モード(`battle.js`) |
|---|---|---|
| 描画 | 差分を採ってから描く(`diffViews` / `applyView`) | ★**`render(view)` で毎回まるごと描き直す** |
| fx 層 | ある(32a・32b・35・38) | ★★**無い。**`fx` / `prevView` / `diff` は**0件** |
| 音の材料 | `fx.kind` の列 | ★**存在しない** |

つまり **`SFX_FOR_KIND` に相当する入口が通常モードには無い。**

**選択肢**:

- **(A) 通常モードにも差分層を作る。**手動モードと同じ形になる。
  ★**規模が大きい** —— 32a・32b・35・38 の4バッチぶんの設計が向こうにはある。
  ★★**ただし、これは音のためだけの投資ではない** ——
  通常モードに**演出**を入れるなら、いずれ必要になるものである。
- **(B) 通常モードの構造に合った取り付け点を新しく探す。**★**2本立てにする**:
  - **自分の操作の手応え** …… `battle.js:134` の **`send()` の1箇所**で足りる
    (`action` の名前で音を選べる)。★ユーザーの操作は**全部ここを通る**。
  - **サーバから来た出来事**(LPの増減・決着) …… `render(view)` の入口で
    **前回の view と数個の値だけ**を比べる。差分層まるごとは要らない。

★**わたしの見立て: (B)。**

理由は **(B) が裁定68(発火点を増やさない)の通常モード版だから**である。
`send()` は既に**1箇所に集まっている** —— 手動モードで `fxSpawn` が
「盤面で起きたことは全部1つの列に集まっている」を利用したのと、**同じ形の利用**である。
新しい集約点を作るのではなく、**既にある集約点を読む。**

★**(A) を採るべき理由も正直に書いておく。**「通常モードにも演出を入れる」が
将来の予定にあるなら、**(B) は捨てることになる投資**である。
★★**この判断は音だけの話ではなく「通常モードの今後の演出」に効く**ので、
実装で決めずにお伺いしている(裁定184)。

## 288. ★★通常モードで鳴らす出来事の一覧

**背景**: 通常モードには**手動モードに無い概念**がある。実測した操作(`action`)は15種である。

`ready` / `choose-order` / `next-phase` / `end-turn` / `charge-mana` / `mulligan` /
`play-card` / `special-summon` / `special-summon-from-grave` / `play-taboo` /
`play-taboo-soul` / `minion-ability` / `attack` / `leader-attack` / `resolve-choice`

★**畳み方の案**(287 で (B) を採った場合):

| 出来事 | 音の案 | 備考 |
|---|---|---|
| `play-card` / `special-summon` / `special-summon-from-grave` / `play-taboo` / `play-taboo-soul` | `place` | 「場に出た」で1つに畳む |
| `charge-mana` | `place` | 置く動作である |
| `minion-ability` / `resolve-choice` / `next-phase` | `tap` | 軽い操作の手応え |
| `end-turn` / `ready` / `choose-order` | `commit` | 「押した」の手応え |
| `mulligan` | `shuffle` | 手動モードと同じ |
| **`attack` / `leader-attack`** | ★★**新しい音?** | **手動モードに無い概念である** |
| LPの増減(view から) | `lpDown` / `lpUp` | 手動と同じ |
| 決着(`status === 'FINISHED'`) | `decisive` | 手動と同じ |
| 手札が増えた(view から) | `draw` | 手動と同じ |

**質問: `attack` に新しい音を足すか。**

- **(a) 足す。**★12種目になる。**通常モードの主役の操作**であり、
  「置く」と同じ音にすると盤面でいちばん起きることが語られない。
- **(b) 足さない。**既存11種のどれかに畳む(`commit` か `place`)。
  ★裁定72「音の語彙は演出の語彙より粗くてよい」の筋である。

★**わたしの見立て: (a)。**ただし**足すのは `attack` の1種だけ**にしたい。
通常モードは**攻撃で勝敗が決まるゲーム**であり、攻撃が「置く」と同じ音なのは、
手動モードで言えば**ドローとタップを同じ音にする**のに近い。
★逆に `leader-attack` を別の音にはしない —— **攻撃は攻撃である**(裁定72 の粗さで足りる)。

★★**もう1つ確認したいこと**: **相手の操作で音を鳴らすか。**
通常モードは**サーバから相手の手も配信されてくる**。
LPの増減と決着は相手の手でも鳴るが、**相手が「置いた」ことまで鳴らすか**は別の判断である。
- (i) 鳴らさない(自分の操作 + LP・決着だけ)★わたしの推し。★**通話が前提である**(裁定16) ——
  相手の手は声で伝わる。全部鳴らすと**耳が忙しくなるだけ**である
- (ii) 鳴らす(手動モードは差分由来なので、そもそも相手の手でも鳴っている)

## 289. ★設定 UI と `localStorage` キーを手動モードと共有するか

**背景**: 通常モードの音の設定 UI は、手動モードの `#sound-modal` の**複製になる**。
そのとき裁定111(「確認モーダルは `manual-battle.js` の複製である。片方だけ直さないこと」)と
同じ落とし穴が1つ増える。

**質問は2つある。**

**(1) `localStorage` のキーを共有するか。**

- **(a) 共有する。**★裁定31 の筋(「音量は人の性質である」)ならこちらである。
  同じ人が同じ端末で両モードを使うのに、音量を2回合わせるのは不自然である。
  ★★ただし現在のキー名は **`qte-manual-sound`** であり、**手動モード専用の名前に見える。**
  - (a-1) 名前はそのままで共有する(★**移行が要らない。**既に合わせた人の設定が消えない)
  - (a-2) `qte-sound` へ改名し、旧キーがあれば読んで引き継ぐ(★1回だけの移行コードが要る)
- **(b) 分ける。**通常モードは `qte-battle-sound` にする。
  ★手動モードは通話併用の対面プレイ、通常モードは一人回しも多い、と用途が違うという理屈は立つ。

★**わたしの見立て: (a-1)。**裁定31 が「部屋ごとにしない」と決めた理由(音量は人の性質)は、
**モードごとにしない理由でもある。**改名(a-2)は筋は通るが、
**既に音量を合わせたマスターの設定が1回消える**ことのほうが実害が大きいと思う。
★キー名が古く見える件は、**コメントに「手動モード専用ではない」と書けば足りる。**

**(2) UI のコードをどうするか。**

- **(a) 複製する。**★裁定111 と同じ形になる。**複製である旨をコメントと落とし穴に必ず書く。**
- **(b) 共有の JS ファイルを作る。**★★**版数の系統が5つ目になる**
  (音声ファイルで4つ目、共有 JS で5つ目)。★裁定111 が共有 JS を退けた理由がまさにこれである。

★**わたしの見立て: (a)。**裁定111 と同じ判断になる。
