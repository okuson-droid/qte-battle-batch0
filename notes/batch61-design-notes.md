## 1. ★いちばん大事な発見 —— カードフェイスの実装がすでに2つあった

デッキメーカーの `.tile` / `.t-*` と、盤面の `.mcard` / `.mcard-*` は
**同じ見た目を2回書いたもの**だった。値まで一致している。

| | デッキメーカー | 盤面(battle.css) |
|---|---|---|
| 本文 | `.t-text` 9.5px / 1.5 / #cfc9e4 | `.mcard-text` **同値** |
| 拡大 | `.bc-text` 13px / 1.7 / #e2ddf2 | `.mcard-large .mcard-text` **同値** |
| コスト | `.t-cost` 六角形の宝石 | `.mcard-cost` **同形** |

デッキメーカー側のコメントにも「盤面 `.mcard-cost` と同じ」と書いてある。
つまり**デッキメーカーの形式 = 盤面の形式**であり、正が2箇所に散っているだけだった。

### 1-1. ★だから3つ目のコピーを作らなかった

新しい2つのカード一覧は、**`battle.css` の `.mcard` 系をそのまま使う**。
見た目はデッキメーカーと同じで、CSS は1行も足していない。

★`battle.css` の光沢の宣言セレクタ一覧には**もともと `.tile` も `.bigcard` も並んでいる** ——
あのファイル自身が「面の見た目の正は battle.css 1つ」と書いており、
今回はその約束の上に乗っただけである。

### 1-2. ★デッキメーカー側を `.mcard` に寄せて1本化するのは、別の作業にした

本筋はそちらである。だが**機械検証545件のうち28件が `.tile` / `.t-*` を名指しで見ている**。
今クラス名を変えると、直したい対象より先に検証のほうが壊れる。
引き継ぎ書に積んで、検証の作り替えと一緒にやるほうが安全である。

★**「正しい形が分かっている」ことと「今それをやってよい」ことは別である。**
分かったことは記録に残し、着手の可否は別に判断する。

## 2. 改行が全画面で潰れていた

カード定義の `text` は改行を持っている(235枚中**28枚**)。

```
【守護】
このミニオンの攻撃力は、自分の手札の枚数と同じになる。
```

HTML は既定で改行を空白1つに畳むため、60 まではこれが1行につながって出ていた。
★**カード画像では2行に分かれている**ので、実物と見比べると形が違って見える。

`white-space: pre-wrap` を当てて直した。当てた先は2箇所である。

- `battle.css` の `.mcard-text`(盤面 + 新しいカード一覧2画面)
- デッキメーカーの `.t-text` / `.bc-text`

★**`pre` ではなく `pre-wrap` である。**`pre` にすると行内の折り返しまで止まり、
長い1行がカードの外へはみ出す。生かしたいのは「データが持つ改行」だけである。

★**番人を2件置いた**(verify)。宣言が2箇所にあるのだから、番人も2箇所に要る ——
片方だけ直された日を捕まえられない番人は、番人ではない(裁定130)。
測るのは CSS に文字列があることではなく、**computed style が `pre-wrap` であること**である。

## 3. 本文の表記を76枚ぶん揃えた

### 3-1. 揃えた規則(新カードの書き方に寄せる)

| 規則 | 直した枚数の目安 |
|---|---|
| 丸括弧は**全角**（） | 2枚(残り32枚は既に全角だった) |
| 数字は**半角** | 4枚 |
| 各行は**句点か閉じ記号**で終わる | 70枚 |
| 【】の内側・直後の空白を削る | 17枚 |
| 全角スペース・連続空白・半角カンマを直す | 3枚 |

合計 **76枚**が変わった。★**語も数値も意味も1文字も変えていない。**

### 3-2. ★なぜ安全だと言えるのか

カード本文は、このエンジンで**いちばん多くのものがぶら下がっている値**である ——
キーワードはここから作られ(裁定158)、効果の「印」も、【賢魂：n】のコストもここから読む。
表記を触るのは、見た目より先に**挙動を壊しうる作業**である。

安全だと言えるのは、既に番人が3つあるからである。

1. `CardTextKeywordsTest` の **169枚のキーワード照合**(Batch 60 で凍結した物差し)
2. `EffectImplementationTest` の**効果の印**(未実装0枚)
3. **626件の JUnit 全部**

★76枚を書き換えても3つとも緑のままだった。
**「壊れていないこと」を人が読んで判断していないのがこの作業の肝である。**

### 3-3. ★揃えたことより、揃ったままでいることのほうが難しい

カードを1枚足すたびに、書き方は元のばらつきへ戻ろうとする。
そこで `CardTextKeywordsTest` に**書き方の番人を4件**足した ——
丸括弧・数字・行末・空白のそれぞれについて、違反したカードを
**「ID 名前」の一覧で返す**形にしてある(落ちたとき、その一覧がそのまま直す対象になる)。

★これは「読み方」の規則ではなく「**書き方**」の規則である。
エンジンの挙動には影響しない —— どちらの書き方でも抽出は同じ結果を出す。
**だからこそ、試験が無ければ誰も気づかないままばらついていく。**

### 3-4. 触らなかったもの

- **カード名**。「愚乱怒土地(グランドランド)」の半角括弧などは名前の一部であり、
  ログ・試験・デッキファイルが名前で照合している。表記の統一とは別の判断が要る。
- **【常在】：のコロン**(3枚)。句読点の統一ではなく**語の削除**に近いので見送った。

## 4. カード一覧2画面の作り替え

### 4-1. 部品を1つ作った

`templates/fragments/card-face.html` に markup の正を置き、2画面がそれを呼ぶ。
このプロジェクトで**Thymeleaf のフラグメントを使うのは初めて**である。

### 4-2. ★2つの型を同じ部品で描けた理由

通常モードは `CardMaster`、手動モードは `ManualCardMaster` を渡す。
型は別系統だが(設計書 2-1)、部品が触る名前 —— `id` / `name` / `type` /
`civilization` / `cost` / `attack` / `hp` / `text` —— は両方が同じ名前で持っている。
列挙体の定数名(`LEADER`…`WEAPON` / `WATER`…`NONE`)も一致しているので、
`type.name()` と `civilization.name()` で分岐できる。

★**型を共有しない**という 2-1 の判断はそのままである。
共有したのは型ではなく**名前**であり、そこが揃っていれば部品は1つで足りる。

### 4-3. ★`ManualCardMaster` が本文を持つようになった

手動モードのカード一覧が本文を1文字も出せなかったのは、
`ManualCardMaster` が `text` を持っていなかったからである。設計書 3-1 の理由はこうだった。

> 新カード66枚にはテキストデータが存在せず、既存168枚ぶんも Ver.0.4 以降の変更で
> 信用できない。半分だけ値があるフィールドは「値がある方だけ使ってしまう」不具合を生む。

★**その理由はもう成り立たない。**Ver1.1 移行で `manual-cards.json` は
**全235枚に本文を持ち**、しかもそれが全モード共通の正である。
「半分だけ値がある」状態ではない。

★**`keywords` は今も持たせていない。**こちらの理由は生きている ——
キーワードはテキストから作るのであって、データが持つものではない(裁定158)。

### 4-4. ★文明色の値を画面に書かない(裁定60)

`--mc` に入れるのは `var(--civ-<文明の小文字>)` であり、値の正は `battle.css` の `:root` である。
`battle.js` の `civColor` が同じ変数を読んでいる。
壊し検証のケース2がこの軸で、値を直書きすると試験が落ちる。

### 4-5. `/manual/cards` から画像を外した(マスター判断)

もともとこの画面は「235枚の画像に欠けが無いか」を目で見るために作られた(Batch 17a)。
その役目は `missingImageIds`(サーバがファイルの実在を確かめて名指しする)が引き継いでいる。
裏面だけは「表の面」を持たないので画像のまま残してある。

## 5. ★このプロジェクトで初めて、画面が描けることを試験した

`CardListPageTest`(7件)を新設した。**60 までこの2画面には試験が1件も無かった。**

- 機械検証(verify)はテンプレートから作った**ハーネス**を見るだけで、
  **Spring がテンプレートを解決できるか**は誰も測っていない。
- Thymeleaf のフラグメントは**書き間違えても Java のコンパイルが通る**。
  壊れていることが分かるのは、誰かがブラウザで開いて 500 を見たときである。

★**実際に1回落ちた。**`th:each` と `th:replace` を同じタグに書いていて、
Thymeleaf の優先順位(replace 100 が each 200 より**先**)により
まだ存在しない `card` を渡していた。試験が無ければ、マスターがページを開くまで分からなかった。

★MockMvc は手で組み立てている。Spring Boot 4 の `@AutoConfigureMockMvc` を提供する
モジュールがこのプロジェクトの依存に入っていないためである
(`spring-test` の `MockMvcBuilders` は使える)。
