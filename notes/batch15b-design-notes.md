# Batch 15b 設計解説 — Ver.0.4 の火5枚・水12枚の効果反映

対象: Ver.0.4 バランス調整のうち、火文明5枚と水文明12枚の計17枚。
変更したファイルは Java 4ファイルのみであり、JavaScript・HTML・CSS・カード台帳は無変更である。

**17枚のうち1枚(剛火の将 L004)は基盤の新設が必要と判明したため、実装せず 15e(仮)へ送った。**
理由と必要な改修は6章に記す。

---

## ⚡ 結論チートシート

- **「スタッツだけの変更」に見えて実際にコード修正が要ったのは3枚。** イグニッション・バースト(0064)の
  自傷1、背水の炎壁(0057)の【召喚時】回復1、溢れ出る英知(0024)のドロー3が、いずれも
  `CardEffectRegistry` に数値として埋まっていた。**台帳を直しても効果は古いままだった。**
- **逆に、コード作業が不要だったのは6枚。** 0029 / 0042 / 0021 / 0035 / 0032 / 0031 である。
  キーワードの追加は台帳から読まれるため、登録側に手を入れる必要がない。
  とくに氷結の杖(0031)の【知識】は `GameService.equipWeapon` が
  `master.hasKeyword(KNOWLEDGE)` で汎用処理しており、カード固有の登録は要らなかった。
- **アクア・サーチ(0028)は割り込み選択(a9)を1つ増やした。** 「2枚引いてから捨てる」は
  使用宣言時に選び終える `TargetSpec` では表現できない。`ResumePoint` に
  `AQUA_SEARCH_DISCARD` を足し、`resolveChoice` に分岐を1つ追加した。ビューは無変更である。
- **静寂の瞑想(0033)の「メインフェーズの最初にしか使えない」は `playConditions` で足りた。**
  新しい判定点を作らず、海皇ポセイドンと同じ近似(このターンまだ1枚も使っていない)を使った。
- **手札を喰らう大蟹(0034)の「そうしたら」は、要求を optional にして空判定で止める形にした。**
  再起の炎陣(0052)・血の対価(0065)で確立済みのパターンである。
- **★剛火の将(L004)は実装していない。** 「場にある【速攻】を持つカードのHP+2」は
  盤面を参照する常在の体力修正であり、現行の体力評価(`MinionInstance.getMaxHp`)は
  盤面もリーダーも見えない。a系の横断改修が要る。

## ★★★★ 1. 数値がコードに埋まっていた3枚

Ver.0.4 の一覧は「ダメージ1→2」「召喚時回復1→2」「3ドロー→2」といった、
一見すると台帳の数値を直せば済むように読める書き方をしている。しかし
**これらはいずれもカードテキストの中の数値であり、台帳の cost/attack/hp 欄ではない。**
テキストの中の数値は効果の実装に直接書かれているため、コードを直さなければ挙動は変わらない。

| カード | 台帳が持つもの | コードが持っていたもの |
|---|---|---|
| イグニッション・バースト(0064) | cost 1(変更なし) | `damageLeader(..., 1, ...)` ← **1のまま** |
| 背水の炎壁(0057) | cost 6→7 | `healLeader(..., 1, ...)` ← **1のまま** |
| 溢れ出る英知(0024) | cost 5(変更なし) | `drawCards(..., 3)` ← **3のまま** |

> **★設計根拠。** 台帳(`qte-cards.json`)が持つのは「カードの識別と、ルールが一律に扱える属性」
> (コスト・攻撃力・体力・キーワード)だけである。効果テキストは表示用の文字列として
> 台帳に入っているが、**その中の数値はルール側が解釈しない。**
> したがって「台帳を直したから効果も直った」は成立しない。b系バッチで
> `grep -rn "QTE-XXXX" --include=*.java` を1枚ずつ回す運用は、この非対称性への対策である。

### 1-1. 背水の炎壁(0057)の合計回復量

このカードは【召喚時】と【特殊召喚の追加効果】の2つを持つ。Ver.0.4 で変わったのは前者だけである。

| 出し方 | 【召喚時】 | 特殊召喚の追加 | 合計 |
|---|---|---|---|
| 通常召喚 | 2(旧1) | — | **2**(旧1) |
| 【特殊召喚】 | 2(旧1) | 1(据え置き) | **3**(旧2) |

【特殊召喚】も召喚であるため ON_SUMMON を通る(設計判断17・キーワード表)。
`SpecialSummonSpec` の第5引数(特殊召喚時のみの追加効果)は 15a で `healLeader` に
発生源を配線済みであり、今回は数値を触っていない。

なお、この2つの回復はどちらも火文明のカードによるものとして
`healedAmountByCivilizationThisTurn` に計上される(15aの4章)。
**通常召喚でも2、特殊召喚なら3が貯まるため、鳳凰神ヴォルカニクスレヴォ(0058)の
「火文明で累計5以上」の到達がやや速くなった。** 意図された連動と解釈している。

## ★★★★ 2. アクア・サーチ(0028) — 引いた後に選ばせる

### 2-1. なぜ TargetSpec では書けないか

新テキストは「カードを2枚引く。その後手札のカードを1枚捨てる。」である。

`TargetSpec` による対象選択は**カードを使う瞬間にすべての選択を終える**前提であり、
検証 → 支払い → 解決 が一直線に進む(`PendingChoice` の Javadoc に明記されている)。
アクア・サーチが捨てる対象は**引いた後の手札**であり、使用宣言の時点では
候補そのものが存在しない。したがってこの経路では表現できない。

### 2-2. 採った形

12b で用意された割り込み選択(a9)をそのまま使った。増やしたのは次の2点だけである。

```java
// ResumePoint(列挙体に1つ追加)
AQUA_SEARCH_DISCARD

// spellEffects(引いた後に問い合わせる)
ctx.actions().drawCards(ctx.room(), ctx.owner(), 2);
if (ctx.owner().getHand().isEmpty()) return;
ctx.actions().requestChoice(ctx.room(), ctx.owner(), PendingChoice.one(
        PendingChoice.Kind.HAND, handPositions, ResumePoint.AQUA_SEARCH_DISCARD, "..."));

// resolveChoice(分岐に1つ追加)
case AQUA_SEARCH_DISCARD -> {
    int idx = Integer.parseInt(chosen.get(0));
    String cardId = ctx.owner().getHand().remove(idx);
    ctx.owner().getTrash().add(cardId);
    ...
}
```

**ビュー(`GameViewBuilder.buildPendingChoice`)は無変更である。**
`PendingChoice.Kind.HAND` のラベル生成は既に実装されており、
フロントエンドも候補を汎用的に描画するためである。引き継ぎ書は割り込み選択の追加に
「4点(Kind・ResumePoint・resolveChoice の分岐・ラベル生成)」を挙げていたが、
既存の Kind を使う限りラベル生成は再利用できる。

### 2-3. ☆ 選択の追い風(0126)との違い

同じ「引いた後に捨てる」でも、必須か任意かが違う。

| カード | 生成 | min | 選ばなかった場合 |
|---|---|---|---|
| 選択の追い風(0126) | `PendingChoice.upTo` | 0 | 何も起きない(「捨ててもよい」) |
| **アクア・サーチ(0028)** | `PendingChoice.one` | **1** | **選ばない選択肢が出ない** |

`one` を使うためクライアントにスキップボタンは出ず、`chosen` が空で戻ることもない。

### 2-4. ☆ 既知の限界(a9共通)

**スペル本体が墓地へ行くのは、捨てる手札を選ぶより前である。**
`GameService.playSpell` は `resolveSpell` から戻った直後に `disposeUsedSpell` を呼ぶが、
このとき選択はまだ保留されている。厳密な順序ではないが、
アクア・サーチには【還元】も墓地参照もないため、盤面の結果は変わらない。
風のマナ変換(0127)・風護の杖(0123)と同じ既知の限界であり、本バッチで新たに生じたものではない。

## ★★★ 3. 静寂の瞑想(0033) — 判定点を増やさずに済ませる

新テキストの追加分は「このカードはメインフェーズの最初にしか使えない。」である。

「最初」をルールとして厳密に扱うなら、フェイズ開始時点のスナップショットが要る。
しかし**同じ意味の近似が既にプロジェクト内にある。** 海皇ポセイドン(0038)の【特殊召喚】条件
「メインフェーズ開始時」は、Batch 3 から `!player.isPlayedCardThisTurn()` で表現されている。

```java
playConditions.put("QTE-0033",
        (state, player) -> state.getPhase() == TurnPhase.MAIN && !player.isPlayedCardThisTurn());
```

> **★設計根拠。** `RuleGuards` に新しい判定メソッドを足す案もあったが、採らなかった。
> `RuleGuards` は「複数のカードが共有する判定点」を集める場所であり(設計判断34)、
> 1枚しか使わない条件を置くと判定層が台帳の代用品になる。
> `playConditions` は「そのカード固有の使用条件」を置く既存の入れ物であり、こちらが正しい。

`playedCardThisTurn` が立つのは `playCard` の**末尾**(効果の解決後)であるため、
このカード自身の使用によって自分の条件が壊れることはない。

**☆ 既知の限界。** `requirePlayable` は `GameService.playCard`(手札からの使用)からのみ呼ばれ、
`playTabooCard` からは呼ばれない。したがって**禁忌デッキに入れた静寂の瞑想はこの制限を受けない。**
これは 0006・0069・0075 など既存の `playConditions` カード全般に共通する構造であり、
本バッチで新たに生じたものではない。修正するなら `playTabooCard` にも
`requirePlayable` を1行足すだけで済むが、既存カードの挙動を一斉に変えるため独立バッチとした。

## ★★★ 4. 手札を喰らう大蟹(0034) — 「そうしたら」と対象範囲

変更は2点である。

1. バウンス対象が「相手のミニオン」から側の限定なしになった(記法規約により両者参照)
2. 「そうしたら」が入り、手札を捨てられた場合にのみバウンスが発動する

### 4-1. 対象範囲

`Requirement` の `Side.OPPONENT` を `Side.ANY` に変えた。これだけで、
`findOnSide` が両者の場から探すようになる。

なお【潜伏】の扱いは自動的に正しくなる。`validateTargets` の潜伏チェックは
`tm.owner() != player` を条件にしており、**自分の潜伏ミニオンは自分で対象にできる**
(キーワード定義どおり)。側を広げても専用の分岐は要らない。

### 4-2. 「そうしたら」をどう表現するか

このエンジンには「手札が0枚なら捨てをスキップして次へ進む」という中間状態がない。
`Requirement` が持つのは `optional`(0個でもよい)だけである。

既に確立しているパターンがある。再起の炎陣(0052)・血の対価(0065)がまったく同じ
「1枚捨てる。そうしたら〜」という文型で、次の形をとっている。

```java
new Requirement(Kind.HAND, Side.SELF, 1, true, ...)   // optional にする
...
if (selection.isEmpty()) { return; }                   // 捨てが成立しなければ後続を実行しない
```

同じ形に揃えた。バウンス側の要求も optional にしてある。場にミニオンが1体もいない
(大蟹自身は選択時点でまだ場に出ていない)状況で召喚そのものが弾かれるのを避けるためである。

> **☆ この近似の代償。** optional にすると、**手札があるのに「捨てない」を選ぶこともできる。**
> カードテキストは捨てを強制しているため、厳密には忠実でない。
> 捨てを拒否した場合はバウンスも起きないため、プレイヤーが得をすることはなく、
> 既存2枚と挙動が揃うことを優先した。厳密化するには `Requirement` に
> 「候補があるなら必須、無いなら0でよい」という第3の状態を足す必要があり、
> `requireCount` と `battle.js` のスキップボタン表示の両方に影響するためa系の作業になる。

## ★★★ 5. 双流の幻術師(0041)・溢れ出る英知(0024) — 参照範囲を狭める/広げる

### 5-1. 双流の幻術師: コスト参照の拡大

```java
// 変更前: 【知識】を持つミニオンの数
// 変更後: ミニオンの数(キーワードを問わない)
long minionsOnBoard = Stream.of(state.getPlayer1(), state.getPlayer2())
        .mapToLong(p -> p.getMinionZone().size()).sum();
cost -= (int) minionsOnBoard;
```

数える対象が両者の場である点は変わっていない(記法規約)。
バウンス対象は2体から3体へ増やした(`Requirement` の count)。

**☆ 注意。** バウンスの要求は必須のままである(変更前も必須だった)。
したがって**場のミニオンが合計3体未満のときは召喚できない。** テキストが
「ミニオンを3体選び」と数を指定しているためだが、コスト軽減もミニオン数に連動するため、
「軽くなるほど出しにくくなる」ことはない(3体並んでいれば cost 7−3 = 4 で出せる)。

### 5-2. 溢れ出る英知: バフ対象を水文明に限定

判定を**評価側(`StatCalculator.effectiveAttack`)に置いた。**

```java
for (String aura : owner.getThisTurnAuras()) {
    if ("QTE-0024".equals(aura)
            && minion.getMaster().civilization() == Civilization.WATER) {
        attack += owner.getHand().size();
    }
}
```

> **★設計根拠。** 「唱えた時点で場にいる水文明ミニオンにだけ修正を積む」形(付与側で絞る)も
> 書けるが、採らなかった。このオーラは `thisTurnAuras` に文字列を1つ置くだけの
> **場を持たない効果**であり、評価のたびに現在の場を見る。したがって
> **唱えた後に出てきた水文明ミニオンにも効く。** 付与側で絞ると、この「後から出たものにも効く」
> 性質が失われる。手札枚数への連動(既存)と同じく、参照は常に現在の盤面である。

禁忌デッキ経由で水以外の文明のリーダーがこのスペルを使うことは成立するため、
「自分のミニオン=全部水文明」とは仮定できない。文明の判定は実際に必要である。

## ★★★★ 6. ★実装せず送った1枚 — 剛火の将(QTE-L004)

新テキストの追加分: **「場にある【速攻】を持つカードのHPを+2する。」**(常在効果・両者参照)

### 6-1. なぜ b系で実装しないのか

体力の評価は現在 `MinionInstance.getMaxHp()` にある。このメソッドは
**そのインスタンスに積まれた `StatModifier` しか見えない。** 盤面もプレイヤーもリーダーも参照できない。

`MinionInstance` の Javadoc は、この日が来ることを先に書いている。

> 攻撃力・コストと違って StatCalculator に出していないのは、現行の体力修正がすべて固定値であり、
> 盤面の参照を必要としないためである。**盤面参照型の体力修正が出た時点で StatCalculator へ移す。**

剛火の将がその1枚目である。必要な改修は次のとおりで、b系の範囲を超える。

| やること | 影響範囲 |
|---|---|
| `StatCalculator.effectiveHp(state, owner, minion)` を新設 | 新規メソッド |
| `getMaxHp()` / `getCurrentHp()` の呼び出しを差し替え | **8箇所**(破壊判定・ビュー・HP_5_OR_LESSフィルタ・ポセイドン・コアの合計体力・他) |
| 呼び出し側に `state` と `owner` を持ち回る | `GameActions` / `GameService` / `GameViewBuilder` / `CardEffectRegistry` |

これは攻撃力が `effectiveAttack` に移されたときと同じ形の横断改修であり、
**a系(Opus・拡張思考)で行うべき作業**である。

### 6-2. インスタンスに修正を積む「逃げ方」を採らなかった理由

召喚時に「リーダーが剛火の将なら HP+2 の `StatModifier` を積む」形なら b系でも書ける。採らなかった。

1. **後から【速攻】を得たミニオンに乗らない。** 捨て身の猛進(0053)は【突進】、
   ポセイドン・コア(0035)も【突進】だが、キーワードを後付けする効果は既に複数ある。
   【速攻】を付与するカードが今後出た時点で静かに壊れる。
2. **15a の判断と逆行する。** ミニオンゾーン上限で「常在能力は保持せず、参照のたびに算出する」
   (設計判断4に揃える)と決めたばかりである。同じ常在効果を、体力だけ保持方式にすると扱いが割れる。
3. **両者参照である。** 相手の場のミニオンにも +2 が乗る。積む方式だと、
   相手のミニオンが場に出るたびに自分のリーダーを見に行く発火口が別途要る。

### 6-3. 15a で削除した起動能力との関係

**剛火の将の起動能力(ライフ2減・次の火ミニオンのコスト-1)は削除しない。**
Ver.0.4 の変更は「常在効果の追加」であって、大地の巨頭(L011)のような
「起動能力の廃止」ではない(転記ノート4章の裁定2: 「起動能力とは別枠」)。
`leaderAbilities.put("QTE-L004", ...)` はそのまま残してある。

## ✅ 理解確認

<details>
<summary>Q1. 「ダメージ1→2」のような変更が、台帳(qte-cards.json)を直しただけでは反映されないのはなぜか。</summary>

台帳が持つのは「カードの識別と、ルールが一律に扱える属性」(コスト・攻撃力・体力・キーワード)
だけだからである。効果テキストは表示用の文字列として台帳に入っているが、
**その中の数値をルール側は解釈しない。**

「リーダーに2ダメージ」の 2 は `CardEffectRegistry` の
`damageLeader(..., 2, ...)` に書かれた値であり、台帳とは別の場所にある。
一方 cost / attack / hp / keywords は `CardMaster` としてルールが直接読むため、
台帳を直せばそれだけで反映される。この非対称性が
「1枚ずつ grep して要否を判断する」運用の理由である。
</details>

<details>
<summary>Q2. アクア・サーチの「2枚引いてから1枚捨てる」を TargetSpec で書けないのはなぜか。</summary>

`TargetSpec` は「カードを使う瞬間に必要な選択をすべて終える」前提であり、
検証 → 支払い → 解決 が一直線に進むからである。

アクア・サーチが捨てる対象は**引いた後の手札**であり、使用宣言の時点では
候補そのものがまだ存在しない。したがって解決を中断して問い合わせる
割り込み選択(a9: `PendingChoice` / `ResumePoint`)を使うしかない。
</details>

<details>
<summary>Q3. 溢れ出る英知の「水文明限定」を、唱えた時点の場のミニオンに修正を積む形ではなく、評価側(StatCalculator)の条件として書いたのはなぜか。</summary>

このオーラは `thisTurnAuras` に文字列を1つ置くだけの効果であり、
**評価のたびに現在の場を見る**性質を持つ。だからこそ
「唱えた後に召喚した水文明ミニオンにも効く」「手札枚数の増減に連動する」が成立している。

付与側で絞る(唱えた瞬間に場にいる水文明ミニオンにだけ修正を積む)形にすると、
後から出たミニオンに乗らなくなり、この性質が失われる。
</details>

<details>
<summary>Q4. 氷結の杖に【知識】が付いた変更で、カード固有の登録が1行も要らなかったのはなぜか。</summary>

`GameService.equipWeapon` が `master.hasKeyword(Keyword.KNOWLEDGE)` を見て
装備時に1枚引く汎用処理を持っているためである。ウェポンの【知識】は装備時に発動する
という裁定が、既にカードに依存しない形で実装されていた。

ただし「キーワードを足しただけだから作業不要」と一般化してはいけない。
そのキーワードを実行する共通処理が存在するかどうかを毎回確かめる必要がある。
</details>

<details>
<summary>Q5. 剛火の将のHP+2を、召喚時に StatModifier を積む形で実装しなかった理由を3つ挙げよ。</summary>

1. **後から【速攻】を得たミニオンに乗らない。** キーワードを後付けする効果は既に複数あり、
   【速攻】を付与するカードが出た時点で静かに壊れる。
2. **15a の判断と逆行する。** ミニオンゾーン上限で「常在能力は保持せず参照のたびに算出する」
   と決めたばかりであり、体力だけ保持方式にすると扱いが割れる。
3. **両者参照である。** 相手の場のミニオンにも乗るため、積む方式では
   相手のミニオン登場時に自分のリーダーを見に行く発火口が別途必要になる。
</details>

<details>
<summary>Q6. 静寂の瞑想の「メインフェーズの最初にしか使えない」を RuleGuards ではなく playConditions に置いたのはなぜか。</summary>

`RuleGuards` は「複数のカードが共有する判定点」を集める場所(設計判断34)であり、
1枚しか使わない条件を置くと判定層が台帳の代用品になってしまうからである。

`playConditions` は「そのカード固有の使用条件」を置く既存の入れ物であり、
禁忌の代償・冥府への道・死者蘇生などが同じ形で使っている。
</details>
