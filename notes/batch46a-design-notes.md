## 0. なぜ 46 を 46a と 46b に割ったか(マスター裁定)

移行(46b)は次の2つを同時に行う。

1. `CardMasterRepository` が読むファイルを `qte-cards.json` から `manual-cards.json` へ差し替える
2. Java にベタ書きされた台帳ID **169種** を `QTE-M-<文明>-<番号>` へ機械的に書き換える

このとき、**キーワードは「テキストから読む」ことになる**。Ver1.1 のカード定義には
`keywords` フィールドが無いためである(Batch 24 hotfix2 で廃止した。テキストが正)。
つまり移行の瞬間、全169枚のキーワードの出どころが人手の表から機械の抽出に変わる。

もし抽出規則に穴があれば、**全カードの挙動が静かに変わる**。しかもそれは
「IDの書き換えを間違えた」のか「抽出が間違っている」のか、落ちたコンパイルエラーや
おかしな挙動からは区別がつかない。

**わたし(クロエ)は Java をコンパイルもテストもできない**(サンドボックスから
Maven Central へ到達できない。403)。したがって1バッチ = マスターの `mvn test` 1回である。
2つの原因が混ざった状態でその1回を使うのは高すぎる。

**46a は抽出規則だけを、台帳という「答え合わせの相手」がまだ生きているうちに固める。**
台帳が退役したあと(46b 以降)は、この突き合わせは二度とできない。

## 1. キーワード抽出層(`master/CardTextKeywords.java`)

### 1-1. 規則

テキスト中の `【…】` のうち `Keyword` の表示名と一致するものを候補にし、次の2つを外す。

| 外すもの | 判定 | 例 |
|---|---|---|
| **参照** | 直後が `を持` `を与` `を付` `付与` `を行` `を得` `を失` | 相手の【守護】**を持つ**ミニオンを破壊 |
| **条件付きの付与** | 直前が `なら` `たら` `とき` `時` `場合`(末尾の空白・読点は無視) | 3枚以上使用している**なら**【潜伏】。 |

残ったものが、そのカード自身が常時持つキーワードである。

状態を持たない `static` メソッド1つで、入力はテキストだけ。**抽出結果を表に焼き付けない。**
表を作った瞬間に「テキスト」と「表」という2つの正ができる(設計判断28)。

### 1-2. ★素朴に拾うと22枚が狂う

最初に「`【】` の中がキーワード名なら拾う」という素朴な規則で台帳169枚と突き合わせたところ、
**22枚が食い違った。** 内訳を見ると、そのほとんどが**他のカードを指しているだけ**の記述だった。

- `フレイム・スナイプ`(スペル): 「相手の【守護】を持つHP5以下のミニオンを1体選び破壊」
  → このスペル自身が守護を持つわけではない
- `捨て身の猛進`(スペル): 「自分のミニオンすべての攻撃力+1、および【突進】付与」
- `秩序の執行官`: 「相手はメインフェーズに【特殊召喚】を行えない」

参照を外すと12枚まで減り、さらに**条件付きの付与**を外すと**9枚**になった。

- `赫灼の重戦士`: 「体力が10以下ならこれは【速攻】**を得る**」 ← 常に速攻ではない
- `ガイル・フォックス`: 「3枚以上使用しているなら【潜伏】。」 ← 常に潜伏ではない

**★条件付きの付与をキーワードにしないのは意味論の判断である。**
キーワードは「そのカードが常に持つ性質」であり、条件付きで得るものは効果として
`CardEffectRegistry` 側で表現する。台帳の人手の `keywords` もそう扱っていた
(赫灼の重戦士もガイル・フォックスも台帳では keywords が空である)ので、
移行の前後で解釈がぶれない。

### 1-3. ★残る9枚はすべて Ver1.1 の実変更である

規則を通したあと台帳と食い違うのは9枚で、**1枚ずつ両方の本文を読んで確認した。
どれも抽出の誤りではなく、Ver1.1 でカードそのものが変わったものだった。**

| カード | 台帳 | Ver1.1 | 変わった内容 |
|---|---|---|---|
| 知識の守り手 (WATER-17) | 守護・知識・還元 | +**突進** | 本文が `【知識】【還元】【守護】【突進】` に |
| 波濤の突撃兵 (WATER-18) | 突進 | +**潜伏** | 本文が `【潜伏】【突進】攻撃時1枚引く。` に |
| **英知の継承者 (WATER-19)** | 守護・知識 | **なし** | ★裁定155。消失は Ver1.1 の意図どおり |
| カース・ボーン (DARK-2) | なし | +**還元** | 効果文が丸ごと差し替え |
| 裏切りの魔女 (DARK-4) | なし | +**知識** | 発動条件が2枚以上→1枚以上に緩和、知識が付いた |
| 聖域の案内人 (LIGHT-3) | 知識 | +**守護** | 末尾に【守護】が付いた |
| 煌めきの盾 (LIGHT-16) | 守護 | +**知識** | 本文が `【守護】【知識】` + 「攻撃できない」に |
| ストーム・カイザー (WIND-8) | 速攻 | +**特殊召喚** | 条件が括弧内に明記された |
| 神風の大号令 (WIND-12) | なし | +**還元** | 効果文が丸ごと差し替え(スペルの還元は台帳にも8枚ある) |

**★この9枚は 46b 以降で挙動が変わる。**遊び味に関わるので、表は
`CardTextKeywordsTest.VER11_KEYWORD_CHANGES` に理由つきで持たせてある(コードが正)。

### 1-4. 扱わない語彙

`【常在】` `【進化】` `【賢魂：n】` `【起動：n】` `【召喚時】` `【破壊時】` は
キーワード能力ではない。`vocabulary()` が語彙として数え上げるだけで、`Keyword` には変換しない。
常在・進化・賢魂はエンジンにまだ無く、47 以降で作る。

## 2. JUnit の土台

### 2-1. ★期待値を書き並べていない(裁定110)

`CardTextKeywordsTest` の本体が突き合わせているのは、

- **台帳 `qte-cards.json` から読んだ `keywords`**(人手で付けた値)
- **Ver1.1 のテキストから規則が読んだ値**

であり、どちらもファイルから来る。テストが自分で持っているのは**食い違う9枚の表だけ**である。
169枚ぶんのキーワードをテストに書き写していたら、それはただの写経になる。

さらに `既知の差分表に載っているカードは実際に差分である` という判定を足した。
Ver1.1 側が台帳に寄せられたのに表だけ残る、という取り残しを検出する
(裁定116・135 の系。**表が飾りになっていないことを測る**)。

### 2-2. 語彙の番人

`全235枚の語彙が既知のものだけである` は、カードデータに**知らない `【】` が黙って増えないこと**を守る。
Ver1.1 の235枚に現れる語彙はちょうど **15種**で、一覧と過不足なく一致する
(`既知の語彙はすべて実際に使われている` が逆向きも見る。使われなくなった語彙が
一覧に残り続けると、一覧が現状を語らなくなる)。

★この一覧は「エンジンが意味を知っている語彙」ではない。守っているのは
「知らない語彙が増えたらその場で気づく」ことだけである。

### 2-3. 移行の前提を測る(`CardIdMappingTest`)

46b の機械変換が成り立つ条件を、**移行前に**機械で確かめる。

- Ver1.1 は235枚で、種別の内訳が リーダー18 / ミニオン119 / **進化18** / スペル61 / ウェポン19
- 6文明が各39枚 + 文明なし1枚
- **台帳169枚と Ver1.1 の169枚が全単射**(重複なし・欠けなし・余りなし)
- 新カードは66枚で、**進化18枚はすべて新カード**
- **エンジンの列挙体で表せない type は `EVOLUTION` だけ** ← 46b で `CardType` に足す根拠
- 文明はすべて `Civilization` で表せる
- 画像IDが235枚そろっていて重複しない
- カードIDが `QTE-M-<文明>-<番号>` の形である ← 機械変換はこの形を前提にする
- リーダー18枚は cost=0 / attack=null / hp=null

★**台帳のリーダーは `cost=null`、Ver1.1 のリーダーは `cost=0`** である。46b で
`CardMaster.cost()` が null から 0 に変わる。現在リーダーのコストを見ている場所は無いが、
できたときにこの差が効くので書き留めてある。

### 2-4. ★ずっと赤だったテストを直した

`CardMasterLoadTest.台帳の全カードが読み込まれる` が **`hasSize(72)`** のままだった。
台帳は Batch 0 の時点で72枚だったが、以後カードが増えても**ここが更新されていない**。
現在は169枚なので、このテストは長いあいだ落ち続けていたことになる。

**落ちているテストは番人ではない。**「どうせ赤だから」と見なされた瞬間に、
本物の異常も同じ扱いになる。169 に直した(46b で 235 になる)。

★枚数は人が決めた数を意図して置いている(裁定110 の例外)。ファイルから読んだ値と
突き合わせる形にすると、**ファイルが途中で切れていても通ってしまう**。

## 3. ツール

### 3-1. `tools/build_id_map.py` — 台帳ID ↔ Ver1.1 ID の対応表

対応の出どころは `manual-cards.json` の `ledgerCardId` **1つだけ**である
(対応表を別ファイルに保存しない。正はカード定義ファイル)。

出力の前に前提を4つ確かめ、1つでも崩れていれば**終了コード1で止まる**。
黙って一部だけ変換された状態がいちばん危ない。

```
$ python3 tools/build_id_map.py --check
# 台帳 169 枚 / Ver1.1 235 枚 / 対応 169 組 / 新カード 66 枚
# Java にベタ書きされた台帳ID: 169 種
OK: 対応は全単射で、Java の全IDに変換先がある
```

`--sed` を付けると `s/QTE-0001/QTE-M-FIRE-6/g` の形で出る。46b の機械変換はこれを使う。

### 3-2. `tools/report_effects.py` — 実装状況レポート

2026-08-18 時点の数字(スクリプトが生成)。

| 区分 | 枚数 |
|---|---|
| Ver1.1 全カード | 235 |
| うちキーワードのみ(効果の登録は不要) | 16 |
| うち効果の文がある(登録が要る) | **219** |
| ├ 登録あり(`CardEffectRegistry` の9つの表) | 112 |
| ├ 参照あり(表ではなくルール側に実装) | 44 |
| └ **未実装** | **63** |

未実装63枚は**すべて新カード**である(台帳と対応づく169枚は、少なくともどこかに実装がある)。
種別で見ると **進化18枚は1枚も実装が無い**(エンジンに概念が無いため当然である)。

| 種別 | 要実装 | 登録あり | 参照あり | 未実装 |
|---|---|---|---|---|
| LEADER | 18 | 8 | 4 | 6 |
| MINION | 104 | 53 | 26 | 25 |
| EVOLUTION | 18 | 0 | 0 | **18** |
| SPELL | 61 | 47 | 1 | 13 |
| WEAPON | 18 | 4 | 13 | 1 |

**★「登録あり」と「参照あり」を分けている理由。** `RuleGuards` `StatCalculator`
`GameService` には、表ではなくルール側に直接書かれた挙動がある(平和の結界・大天使ミカエル
など)。これらも実装ではあるが、登録の表には現れない。素朴に「表に無い = 未実装」と
数えると44枚を作り直す羽目になる。

作り直しの候補も出す。字面の比較では **169枚中121枚**の本文が異なり、そのうち
**80枚は効果が登録済み**である。★ただしこれは表記を整えただけのものを含む
機械的な数であり、2026-08-16 の読み合わせでは実質変更86・うち実装済み69だった
(`notes/ver11-migration-plan.md` 0-2)。**スクリプトは測れることしか言わない。**

### 3-3. ★同じ規則を2つの言語に置いていない(裁定130)

レポートは「効果の文があるか」を **`【…】` を取り除いて文が残るか**だけで判定する。
どの `【】` がそのカード自身のキーワードかという難しい判定は **Java 側にしか無い**。
Python にも書くと、必ず片方だけが直される日が来る。

またレポートは、`CardEffectRegistry` の**知らない表への `put` を見つけたら止まる**。
表が増えたのに数え漏れる、という静かな事故を防ぐ(裁定114 の系)。

### 4-2. ★Java を実行できない中で、抽出規則をどう裏取りしたか

`mvn test` が使えないので、**Java のソースから正規表現の文字列そのものを取り出して**
Python で回し、実データ169枚に当てた。手で写した規則ではなく、
**マスターの手元でコンパイルされるのと同じ式**を測っている。

結果は「169枚を比較 / 食い違い 0 枚」「差分表の9行はすべて実際に差分」
「語彙 実データ15種 = 一覧15種」「単体ケース13件すべて期待どおり」。

### 4-3. ★判定が落ちることを確かめた(裁定116)

10通りの壊し方を試した。

| 壊し方 | 結果 |
|---|---|
| REFERENCE から `を持` を外す | 食い違い **7枚** |
| REFERENCE から `を付\|付与` を外す | 食い違い **2枚** |
| REFERENCE から `を得` を外す | 食い違い **1枚** |
| CONDITION を無効化 | 食い違い **1枚** |
| **CONDITION から読点の許容を外す** | **食い違い 0枚** ← ★下記 |
| 差分表から1行消す | 食い違い **1枚** |
| 差分表の1行を台帳と同じ内容にする | 食い違い **1枚**(実効性の判定が落ちる) |
| カードに未知の語彙 `【超越】` を混ぜる | 未知 **1種**を検出 |
| 一覧に使われていない語彙を足す | 未使用 **1種**を検出 |

### 4-4. ★★実データが1枚も通らない枝が1つある

上表のとおり、**CONDITION の `[\s、,]*`(条件の直後の読点・空白を読み飛ばす部分)を
外しても、台帳との突き合わせは1枚も落ちない。** Ver1.1 の235枚に
「〜なら、【…】」という書き方が存在しないためである。

これは**裁定135 と同じ形の穴**である —— 測っている状態のほうが甘く、漏れる余地が無い。
枝そのものは将来のカードのために残す判断をしたので、
**単体テストの1行(「手札が5枚以上なら、【守護】。」)をその枝の唯一の番人として明示した。**
コード上のコメントにも「実データが1枚も通っていない唯一の枝」と書いてある。

★なお改行(`\s`)のほうは、正規表現の `$` が末尾の改行の手前にも一致するため、
1個だけの改行では枝を通らない。連続した空白や複数改行のためだけに残っている。
