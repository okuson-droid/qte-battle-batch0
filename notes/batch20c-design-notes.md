## 2. 設計根拠★

### 2-1. ★カードの大きさの上限は「幅」ではなく「画面の高さ」から決める

これが本バッチで最も重要な判断である。

横幅いっぱいに使う構成にすると、ミニオン枠(7枠)や手札は幅に応じていくらでも大きくできる。
しかし**カードは縦長であり、幅を広げるとそのぶん確実に縦を食う。**
1920×1080 のような「横に広いが縦は短い」画面では、幅を基準に大きくした瞬間に
手札が画面外へ落ちる。制約は縦のほうにある。

そこで上限を次のようにした。

```css
.manual-minion-row > .manual-tile { flex: 1 1 0; max-width: min(180px, 16vh); }
```

```js
function handCardMaxWidth() {
    return Math.max(60, Math.min(120, Math.round(window.innerHeight * 0.105)));
}
```

`flex: 1 1 0` が「入るなら広げる」を、`max-width` が「縦に入る範囲で」を担う。
実測は次のとおりで、どちらの画面でも縦は収まっている。

| 画面 | ミニオンタイル | 手札カード | 盤面の高さ |
|---|---|---|---|
| 1280×950 | 136px(従来110) | 100px(従来90) | 約842px |
| 1920×1080 | 173px | 113px | 約1000px |

★固定pxの上限(最初は124pxで実装した)では、1920幅で中央列に約690pxの死に幅が出た。
「余白がもったいない」という指摘への答えになっていないため作り直している。

### 2-2. ★余りは中央寄せにする

上限で頭打ちになると、超ワイド画面では中央列に余りが出る(1920で約240px)。
`justify-content: center` でミニオン行を中央寄せにし、余りを左右へ均等に散らした。
左詰めのまま右に大きな空きを作ると「レイアウトが崩れている」ように見えるが、
中央寄せなら意図した配置として読める。

### 2-3. ★共有クラスの定義は変えない(19bからの約束)

`battle.css` は通常モードと手動モードの共有ファイルである。
伸縮の指定は `.minion-row` にではなく、手動モード専用の `.manual-minion-row` の内側だけに
書いた(`.manual-minion-row > .manual-tile { ... }`)。
`.manual-tile` の `width:110px; height:120px` は通常モード側が使うため、
ここで上書きするのは手動モードの子孫セレクタに限る。

### 2-4. ★ミニオン行は折り返さない

`.minion-row` は `flex-wrap: wrap` を持つ。幅追従にすると、狭い画面でタイルが
折り返して2段になり、**ミニオン枠が何枠あるのか読めなくなる**。
`.manual-minion-row { flex-wrap: nowrap; }` と `min-width: 0` の組み合わせで、
狭いときは折り返さずに縮む挙動にした。

### 2-5. ★カード幅はDOMに載せてから実測して決める

`fitCardWidths(row, maxWidth, gap)` は、行を DOM に挿入した後に `row.clientWidth` を
測ってから各カードの幅を決める。マナの重ね表示(`applyManaOverlap`)と同じ手順である。
幅がウィンドウに追従する以上、レイアウト前の固定値では決められない。

下限を45pxに置いてあるのは、それ以下だと画像が何のカードか判別できなくなるためである。
下限に張り付いた場合は行が溢れるが、**溢れは人間が気づける。判別不能は気づけない。**

### 2-6. ★リサイズで描き直す

ミニオンのタイルはCSSのflexで自動追従するが、手札とセンターラインのカード幅は
JSが実測して決めているため、ウィンドウのリサイズでは追従しない。
120msのデバウンスを挟んで `renderAll(latestView)` をやり直す。
デバウンスは、ドラッグでのウィンドウ変形中に毎フレーム全描画が走るのを避けるためである。

### 2-7. ログの折りたたみは残した(ただし既定値を変えた)

20bの「既定は直近2行だけ」は、右列が224pxと細かった頃の折衷である。
拡大画像の右横に置ける今は、既定でひととおり読めるほうがよい。
既定232px(拡大画像と合計286pxで高さが揃う)、クリックで460pxへ拡張する。

★実装時の落とし穴: ログを包む列に `height:286px` を固定したところ、`log-box` が
flex で押し縮められ、**クリック拡張が一切効かなくなった**(高さが常に218px)。
包む側の高さは固定せず、中身の既定値の合計で286pxに揃うようにしてある。

### 2-8. マナ行は「行見出しを消す」ことで詰めた

タイルの大きさは据え置き(マスター確認済み)。削ったのは次の3つである。

1. `マナ MP n` の行見出し(約20px)を廃止し、MPを「表 (MP n)」というストリップの
   ラベルへ寄せた
2. `.mana-strip-track` の padding を 4px → 1px/3px へ
3. 行そのものの padding を 8px → 4px へ

リーダータイル(120px)が抜けたことと合わせて、135px → 約100px になった。

## 4. 理解確認 Q&A

**Q1. なぜタイルの上限に `vh` を混ぜたのか。`max-width: 180px` ではいけないのか。**

A. カードが縦長だからである。幅の上限だけを決めると、縦が短い画面(例: 1920×1080 の
ノートPCや、ブラウザのブックマークバーで縦が削れた状態)で盤面が画面外へ落ちる。
`min(180px, 16vh)` は「180pxを超えない、かつ画面の高さの16%を超えない」という2条件であり、
効いてほしいのは後者である。前者は超縦長ウィンドウでの暴走を止める保険にすぎない。

**Q2. `flex: 1 1 0` の `0` は何か。`flex: 1` との違いは。**

A. flex-basis である。`flex: 1` は `flex: 1 1 0%` と同じなので実質同じだが、
明示的に0にしているのは「内容の幅を基準にしない」ことをはっきりさせるためである。
`flex-basis: auto` だと、タイルの中身(カード名の長さ)によって枠の幅が変わってしまい、
6枠が等分にならない。

**Q3. 中央列に `min-width: 0` を書いたのはなぜか。**

A. flex アイテムの既定は `min-width: auto` であり、**内容の最小幅より縮まない**。
中央列に幅の広い子(ミニオン行など)があると、中央列がその幅を保とうとして
右列(400px固定)を画面外へ押し出す。`min-width: 0` はこれを解除する定型句である。

**Q4. 自分のリーダーだけ右列へ移したのに、相手のリーダーは中央に残っている。ちぐはぐでは。**

A. マスターの選択である(20cの確定事項2)。相手側は「盤面の上にある」という位置関係の
ほうが自然であり、また相手上段の行はミニチップ列だけになると薄すぎる、という判断による。
なお超ワイド画面では相手リーダーが中央列の右端まで離れる。気になるようであれば
チップ列の隣へ寄せる調整余地がある(次バッチの候補)。

## 5. 追補 — パイル配置の確定とリーダーの文明色(マスター指示・UI確定)

20c の直後、マスターの指示で次の2点を入れた。**これをもって手動モードのUIは確定である。**
キャッシュバスティングは `manual-battle.js` v=8→**v=9**、`battle.css` v=16→**v=17**。

### 5-1. パイルの配置

```
  [リーダー][禁忌][山札][確認]
            [消滅][墓地]
```

★**CSS Grid で行と列を直接指定する**(`PILE_PLACEMENT` + `grid-area`)。
flex で「行を2本並べる」方式だと、リーダー枠だけ幅が違う(108px)ぶん下段が左へずれ、
「禁忌の真下が消滅」「山札の真下が墓地」という縦の対応関係が崩れる。
位置そのものに意味がある配置なので、位置を直接書ける Grid が正しい道具である。

列幅は `108px 90px 90px 90px`、gap 6px。合計 396px で右列(400px)にちょうど収まる。

★`align-items: start` を置いてある。山札だけシャッフル・上へ/下への枠ぶん背が高いため、
これが無いと同じ行の禁忌・確認・リーダーが引き伸ばされる。
**その結果、禁忌と確認の下には空きが出る**(山札の操作ボタンが占める高さぶん)。
消滅・墓地の上端が揃うことを優先した判断であり、右列は縦に余裕があるため
盤面全体の高さには影響しない。列ごとに縦積みして空きを潰す案もあるが、
そちらは消滅と墓地の上端が揃わなくなる。

### 5-2. リーダーの文明色

リーダータイルの背景を文明の色で塗る。場のタイル(`createFieldTile`)と同じ
`civColor` / `textColorFor` を使い、**色と文字色の決め方を1箇所に揃える**。
文字色を直書きせず計算で出しているのは、光文明(#FFDE59)のように明るい色で
黒文字が要る場合と、水文明(#5E17EB)のように白文字が要る場合を、
色を足すたびに人が判断しなくて済むようにするためである(19b以来の方針)。

自席・相手席の両方に効く(同じ `createLeaderTile` を通るため)。
突合できていないリーダー(`civilization` が無い)は既定の灰色のままにする。

### 5-3. 検証

実マウス検証を **36 → 42項目**へ拡張し、すべてパス。追加分は次のとおり。

- 上段が左から [リーダー][禁忌][山札][確認] の順に並ぶこと
- 消滅が禁忌の真下、墓地が山札の真下にあること(x座標の一致)
- 消滅と墓地の上端が揃っていること
- パイル群が右列(400px)に収まること
- 自分のリーダーが文明の色(水 = `rgb(94,23,235)`)で塗られること
- 相手のリーダーも文明の色で塗られること
