## 1. 裁定278(c) —— 墓地からの召喚に対象選択の導線を付けた

### 1-1. 何が起きていたか

Batch 57 から 59 まで、《黄泉の召喚主》の墓地からの召喚には次のガードがあった。

```java
if (!effects.targetSpecOf(master.id()).requirements().isEmpty()) {
    throw new IllegalStateException("【%s】は召喚時に対象を選ぶため、墓地からは召喚できません"...);
}
```

これは Ver.0.4 から潜っていた穴(対象を読む【召喚時】が `null` を触って
NullPointerException で 500 になる)を、**理由を返して止める形に変えたもの**である。

裁定275 が「手札にあるかのように」を**狭く読んだ**結果、59 の時点ではこのガードが
恒久のルールになる見込みだった。

### 1-2. ★止めていた理由は「ルール」ではなく「実装の都合」だった

裁定278 の依頼文で3つの道を並べたところ、マスターは **(c) 導線を新設する** を採った。

★ここが今回いちばん大事な区別である ——
**裁定275(狭い読み)は今も変わっていない。**変わったのは、
「対象を運ぶ口が無いから止めていた」という**実装の都合**のほうである。
2つを混ぜて「裁定が覆った」と読むと、次の人は裁定275 まで疑い始める。

闇のスターターは《黄泉の召喚主》と《執念の暗殺者》を同時に積んでいる。
ガードを残すと「墓地に暗殺者が居るのに拾えない」場面が実際に起き、
しかも**その制限はカードテキストのどこにも書かれていない**。

### 1-3. ★工事は思ったより小さかった —— 道具が既にあった

依頼文では「Java 3ファイル + JS 2本」と見積もっていた。実際に触ったのは:

| 層 | 変更 |
|---|---|
| `GameService` | `summonFromGrave` が `List<TargetChoice>` を受け取る。ガードを削除し、検証を足す |
| `GameWsController` | 受ける型を `TrashActionRequest` → `GraveSummonRequest` に変えた(**既存の型**) |
| `battle.js` | `beginGraveSummon` を新設。中身は `beginSelection` を呼ぶ**2行** |

★**新しい仕組みは1つも作っていない。**
Batch 53 が墓地からの【特殊召喚】のために作った「墓地の位置 + 対象」の形が、
そのまま使えたからである。`GraveSummonRequest` も `beginSelection` も共用している。

★**見積もりを外したのではなく、既存の道具を数え忘れていた。**
「新しい導線が要る」と読んだ時点で、53 が同じ導線を敷いていたことを確かめていなかった。
次に同じ形の見積もりをするときは、**先に「似た経路が既にあるか」を grep する**。

### 1-4. ★順序を通常召喚に揃えた

ガードを外すついでに、`summonFromGrave` の順序を `playMinion` と同じにした。

```
検証(状態を変えない) → 支払い → 墓地から取り除く → 場に出す → 効果
```

59 までは「支払い → 墓地から取り除く → 場に出す」で、検証が無かった。
検証を足すなら**支払いより前**に置かなければならない ——
そうしないと、対象が不正だったときにマナだけタップされて墓地が減る。

★壊し検証のケース2がこの軸である。順序を入れ替えると
「対象の検証で弾かれたとき盤面を1つも変えない」が落ちる。

### 1-5. ★ついでに塞いだ穴 —— 墓地の自己対象

検証を墓地から取り除く**前**に行うので、その瞬間は**出すカード自身がまだ墓地に居る**。
`Kind.TRASH` の要求はそれを普通の候補として見てしまう ——
「墓地から出るのに、出た後の効果でもう一度墓地から拾われる」1枚が作れる。

今の235枚では実害が出ない。`Kind.TRASH` の【召喚時】を持つ唯一のミニオンは
《墓場の怨念集合体》で、その要求は `SPELL_CARD` で絞られており、
ミニオンである自分自身は絞り込みで落ちるからである。

★**だからこそ塞いだ。**絞り込みが偶然守っているだけの穴は、
次に「墓地のミニオンを拾う【召喚時】」が1枚増えた瞬間に開く。
`requireTrashSourceNotTargeted` を新設し、**墓地からの【特殊召喚】にも同じ門を当てた**
(同じ順序で同じ穴を持っていた)。裁定282 で確認を依頼している。

## 2. 裏向きマナと `fireManaPlaced` の非対称(51 設計解説 6-2)

### 2-1. 何が非対称だったか

《豊穣の地霊主》の本文はこうである。

> 【常在】:マナにカードが置かれたときそのターン中それが2回目ならカードを1枚引く

54 から 59 までの実装は、**表向きの配置しか数えていなかった**。
`placeCardInManaFaceUp` だけが `recordManaPlacement` と `fireManaPlaced` を呼び、
裏向きの経路(6つある)はどれも呼んでいなかった。

### 2-2. ★本文どおりの読みが1つに定まる

本文は「マナにカードが置かれたとき」であって「表向きで置かれたとき」ではない。
**向きを条件にしていない。**したがって裁定184(2通りに読めるなら仰ぐ)の対象ではなく、
引き継ぎ書2章の但し書き(本文どおりの読みが1つに定まるなら実装して確認を依頼する)に当たる。

裏向きも数えるようにし、**裁定280 で確認を依頼した**。

### 2-3. 入口を1本にした

裏向きでマナに置く経路は6つに散らばっていて、どれもこう書いていた。

```java
ManaCard mana = new ManaCard(cardId, false);
mana.turnFaceDown();
owner.getManaZone().add(mana);
```

これを `addFaceDownMana(room, owner, cardId)` 1本に集約し、その中で
`manaPlaced(room, owner)` を呼ぶ形にした。

★**上限(15枚)の判定までは集約していない。**
上限に達したときの振る舞いが経路ごとに違うからである ——
【還元】は墓地に落とし、山札からの配置は山札の上に戻し、手札からの配置は false を返す。
そこまで1つにまとめると**嘘の共通化**になる。

★対になるのは `manaLeft` である(51 で作った「マナが離れた」の発火口)。
名前を揃えたので、次の人は対称に読める。

### 2-4. ★一時マナ(ピュア・エレメント)も数える

《ピュア・エレメント》はターンの終わりに消える一時マナだが、
本文は「このターンの間マナゾーンに置く」であり、**置いてはいる**。
《豊穣の地霊主》が見ているのは**置かれたこと**であって、
置かれたものが残るかどうかではない、と読んだ。

★これは `GameActions` の共通入口には合流させていない ——
一時マナを作るのはこの1枚だけであり、共通処理に「一時かどうか」の引数を足すと、
**1枚のために全経路が分岐を持つ**ことになる。置いたあとで通知だけを送っている。

### 2-5. ★遊びにどう効くか

いちばん分かりやすいのは《ガイア・リソース》である。

1. 効果で山札の上を**表向き**に1枚マナへ(1回目)
2. 【還元】で自分自身を**裏向き**に1枚マナへ(2回目)

土のリーダーが《豊穣の地霊主》なら、**この1枚だけで1ドローが付く**。
59 までは付かなかった。土のプリセットには【還元】持ちが3枚入っている。

## 3. Ver0.4 台帳(`qte-cards.json`)を削除した

### 3-1. 何を消したか

| 消したもの | 大きさ | 理由 |
|---|---|---|
| `src/main/resources/cards/qte-cards.json` | 101KB | 46b で読まれなくなり、59 で戻り道も要らなくなった |
| リポジトリのルートの同名ファイル | 101KB | 上と中身が同一(md5 一致)の重複 |
| `src/test/java/.../support/LedgerCards.java` | — | 台帳を読むテスト専用の口 |
| `tools/build_id_map.py` | — | 台帳と Ver1.1 の対応表を作るツール |
| `tools/rework_triage.py` | — | 作り直し121枚の進捗を数えるツール(P5 完了で役目終了) |
| `report_effects.py` の「作り直しの候補」の節 | — | 数えるのに台帳が要る。P5 完了で相手が居ない |
| `CardIdMappingTest` の台帳照合1件 | — | 相手のファイルが存在しない |

### 3-2. ★番人だけを凍結して残した(マスター判断)

台帳を消すと、`CardTextKeywordsTest` の**169枚のキーワード照合**という番人も死ぬ。
これは `CardTextKeywords`(テキストからキーワードを読む規則)を触ったときの
**唯一の検出手段**であり、裁定159 のとおり**素朴な規則では22枚が狂う**。

3つの道をマスターに伺い、**「番人だけ凍結して残す」**が選ばれた。

- 台帳から**人手が付けていたキーワード169件だけ**を抜き出し、
  Ver1.1 のカードIDに写し替えて `src/test/resources/keyword-baseline.json`(7KB)に凍結した。
- 読み口は `support/KeywordBaseline` に置き換えた。
- ★**`ledgerCardId` を経由しない。**Ver1.1 のIDで直に引くので、
  このテストから「台帳」という概念が完全に消えた。

★**なぜ台帳を丸ごと残さなかったか。**
番人に必要なのは169行のキーワードだけである。101KB のカード台帳を
「番人のために」置いておくと、**次に読む人はそれを台帳として読む** ——
コスト・攻撃力・本文が全部入っているのだから、そう読むほうが自然である。
`LedgerCards` の Javadoc が「片方だけ残すと、次の人は『まだ台帳が生きている』と読む」と
書いていたのは、まさにこの危険のことだった。

★**この物差しは原則として更新しない。**凍結した過去の断面であることが値打ちである。
抽出規則を意図して変えた結果ここが赤くなったら、直すのは物差しではなく
テスト側の「既知の差分表」(`VER11_KEYWORD_CHANGES`)のほうである。

### 3-3. ★消したツールの代わりに何を残したか

`build_id_map.py` が持っていた検査のうち、台帳が無くても成り立つ分を
`tools/check_legacy_ids.py` に移した。

1. **Ver0.4 形式のID(`QTE-0001` / `QTE-L001` / `QTE-X001`)が本番のコードに書かれていない**
2. `ledgerCardId` が重複せず、ちょうど169枚に付いている

★1 は「変換し忘れ」ではなく**新しく書き足された**ことを捕まえる番人である。
次に誰かが古いドキュメントを見て `QTE-0002` と書いたら、ここで止まる。

★**探す先を `src/main/java` と `static/js` に絞った。**最初に `src/test` も含めたところ、
`CardMasterLoadTest` の「`findById("QTE-0027")` は例外になる」という試験が引っかかった ——
**問題そのものではなく、問題を捕まえる番人**である。ここで数えると符号が逆になる。

### 3-4. `convert_manual_cards.py` は「退役」にした(消していない)

CSV から `manual-cards.json` を作るツールである。読んでいた台帳が消えたので動かないが、
★**消さずに、実行すると理由を出して止まる形にした。**

理由は2つある。

1. `manual-cards.json` が「CSV 6文明 + 画像ディレクトリ」からどう組み上がったかを
   書き残しているのは、このファイルだけである。
2. ★**そのまま再実行すると本文が消える。**このツールは `text` を持たない JSON を出すが、
   今の `manual-cards.json` は全235枚に本文を持っている ——
   キーワード抽出もカード効果も、全部そこにぶら下がっている。

「動かないから消す」と「動かないことを伝えて残す」の分かれ目は、
**そのファイルが持っている知識が他に無いかどうか**である。

## 4. `unlimitedCopies` の掃除

裁定267 で《ゾンストライカー》の構築特例(同名4枚超え)が廃止され、
Ver1.1 の235枚に「4枚以上入れられる」を持つカードは**1枚も無くなった**。
`manual-cards.json` にはこの項目自体が存在しない ——
つまり読む側の分岐は**必ず偽になる道**だった。

消したのは4箇所である。

| 場所 | 中身 |
|---|---|
| `ManualCardMaster` | レコードの `boolean unlimitedCopies` |
| `ManualCardRepository` | JSON を受ける DTO の項目 |
| `ManualDeckImporter.checkNameLimit` | 同名上限の免除リスト |
| `manual-deck-maker.html` | `isUnlimited()` と、それを見る2箇所 |

★`DeckValidator` は 46b の時点で既に例外表を捨てていた。
**同じ規則が2箇所にあり、片方だけが直された状態が14バッチ続いていた**ことになる(裁定130)。

★消したことの番人は `ManualDeckJsonImportTest`「規定枚数違反と文明違反は警告に留まる」である
(同名5枚で警告が出ることを測っている)。壊し検証のケース10がこの軸に当たる。

## 5. プリセットデッキの Ver1.1 化

### 5-1. 何が古かったか

46b で Ver1.1(235枚)へ移行したあとも、`DeckFactory` の中身は Ver0.4 の169枚のままだった ——
**新カード66枚が1枚も入っていなかった。**効果の実装が追いついていなかったからである
(進化は Batch 52 で解禁、最後の16枚は Batch 59 で完了)。

### 5-2. 入れ方

6文明とも、**その文明の新カード10種を全部**入れた(3進化 + 7枚)。

- 合計40枚・同名4枚以内は不変。入れたぶんは**既存カードの枚数を削って**作った。
- 削り方は「厚く積んでいたものを1枚ずつ薄くする」を基本にし、
  枠が足りない分だけ 1枚積みのカードを落とした。
- 闇には新カード10種に加えて《墓場の怨念集合体》と《悪夢》も入れた ——
  どちらも Ver0.4 から在るのにプリセットに居らず、しかも**60 と 59 の変更が実際に効くカード**である
  (前者は裁定278 の道具、後者は裁定265 で遊び味が大きく変わった)。

★**これは「強いデッキ」ではなく「全カードに触れるデッキ」である。**
プリセットの役目は、遊びはじめた人がその文明の道具を一通り見られることであり、
勝率を詰めることではない。バランスの調整は別の作業である。

### 5-3. ★試験が見つけたこと —— 進化には素材が要る

「進化を入れただけでは足りない。素材条件を満たすミニオンが同じデッキに居なければ、
その進化は手札で死ぬ」という番人を置いたところ、**1枚落ちた**。

> 《海淵獣ゾクシム》…… 素材は「**水文明ではない**ミニオン1体」

水のメインデッキはリーダーと同じ文明しか入らない(総合ルール1-2)。
つまりこのカードの素材は、**禁忌デッキ(1-3: リーダーと異なる文明8枚)から来るしかない。**

★**カードのほうを疑いかけた**が、疑うべきは試験の見ている範囲だった。
禁忌デッキも数えるように直したら通った。
この1枚は、禁忌デッキを前提に設計されている証拠である。

### 5-4. ★試験の道具が壊れた

`DeckValidatorTest.replaceOneMainCard`(デッキの1枚を差し替える道具)が落ちた。
「デッキに無いカードを1枚足す」前提だったが、
**Ver1.1 化でその文明のカードはほぼ全種類がプリセットに入った**ので、
足そうとしたカードが既に居て行が重複した。

既にある行なら枚数を1増やす形に直した。
★**プリセットを厚くすると、プリセットを土台にした試験の前提が変わる。**
次にプリセットを触るときも、まずこの手の道具を疑うこと。

## 6. 副産物 —— 版数を上げたら機械検証が落ちた

`battle.js` を触ったので版数を v=25 → v=26 に上げたところ、
`verify/verify.js` が `render is not defined` で落ちた。

原因は `verify/build_harness.py` にあった。

```python
battle = battle.replace(
    '<script th:src="@{/js/battle.js(v=25)}"></script>',   # ← 版数まで含めた文字列一致
    '<script src="/js/battle.js"></script>',
)
```

**版数まで含めた文字列一致**だったので、版を上げると一致しなくなり、
Thymeleaf の記法のまま残ったスクリプトタグが読み込まれず、関数が1つも定義されなかった。

★**黙って一致しなくなるのがいちばん悪い。**正規表現で版数を吸う形に直したうえで、
**置換が0件ならその場で止める** `_sub_once` を通すようにした。
次に版を上げても落ちないし、テンプレートの書き方が変わったら理由が出る。

★これは「壊し検証」ではなく**「壊れていたことに気づけた」**例である ——
JS を触るバッチが久しぶりだったので、59 までは誰も踏まなかった。

## 7. 壊し検証(`tools/batch60_break_check.py`)

10ケース。**OK 10 / NG 0。**

| # | 壊した軸 | 落ちるべき試験 |
|---|---|---|
| 1 | 墓地からの召喚が対象を場に運ばない | 対象を選ぶミニオンを墓地から召喚できる |
| 2 | 順序が逆(検証より先に支払う) | 弾かれたとき盤面を1つも変えない |
| 3 | 墓地の自己対象の門が効かない | 墓地から出すカード自身は対象に選べない |
| 4 | 裏向きの配置が「置かれた」を知らせない | 還元による裏向きの配置も2回目として数える |
| 5 | 一時マナが知らせない | ピュアエレメントの一時マナも1回として数える |
| 6 | 「2回目」の条件が緩い | 表向き1回だけでは引かない |
| 7 | キーワード抽出の条件付き付与の判定が緩い | 物差しと対応づく169枚の照合 |
| 8 | 対象要求が固定2体(少なく選べない) | 2体いても1体だけ選べる |
| 9 | プリセットから新カードが1枚抜ける | 6文明とも新カード10種をすべて積んでいる |
| 10 | 同名上限の警告が1枚ぶん甘い | 規定枚数違反と文明違反は警告に留まる |
