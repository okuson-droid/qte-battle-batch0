## Batch 84(確定・2026-09-09)

**通常モードの段階的解決(方式B)** である。正は `notes/batch84-auto-staging-design.md` 1本。
調査時の HEAD は `c886123`(batch82&83)である。

解いている問題は「カードをプレイしてからの処理が一瞬で終わり、何が起きたか分からない」。
原因は3つ重なっている —— 1操作の解決が1回の配信に畳まれている / 差分が順序を持たない /
`FX_LIMIT`(8)を超えると演出が丸ごと消える。★**派手なカードほど何も起きない**のが最も悪い。

| 決めたこと | 中身 |
|---|---|
| 対象 | 通常モードのみ。**手動モードは1文字も触らない** |
| Java 変更 | **許容する。**32〜80 の「通常モードは Java 変更ゼロ」を意図的に破る |
| 裁定 | **362〜369 の8件**。84a の着手時に台帳へ写すこと |
| 分割 | 84a(サーバ・a系) / 84b(クライアント・b系) / 84c(調整・b系) |
| 飛ばし | 出口を作らない。そのぶん総再生時間の上限を設計で保証する |

★84a は画面が何も変わらない納品でよい。サーバだけ先に入れても壊れない形にしてある。

## 効いている教訓

- 症状を母集団にしない(79)。前のバッチが書いた症状にも当てはまる(83)
- 非同期の向こうを時間で待たない(79)。待つべき事実を取り違えると、正しく待っているのに揃わない(83)
- 壊せない待ちは残さない。偽の番人を1本置くのと同じである(83)
- 根拠にしたものには、その日に番人を置く(83)
- 壊し検証で NG が出たら、まず実装ではなく番人を疑う(75)。NG は「番人が足りない」ことも教える(83)
- 実寸は「その工事は今やることではない」も教える(83 の候補 V)
- 「反映済み」はドキュメントを信じず、実ファイルを読んで確かめる
